title: Migrations and Backups
description: The template's optional database step before a deploy rolls out - a read-only plan of production's pending migrations, a backup to a private bucket, migrating in a Job before the new pods start, and a maintenance window for breaking changes.
---

A deploy normally migrates the database when the new php pod starts. That's fine for most releases, but for a migration that rewrites a large table, or one the running release can't work with, you want to see the SQL first, keep a backup, and maybe close the site while it runs.

The template can do each of these before the rollout. They're all off by default except the read-only plan, and they come from the template's deploy scripts, not the bundle ([#180](https://github.com/components-web-app/components-web-app/issues/180), [`ebbb6ed`](https://github.com/components-web-app/components-web-app/commit/ebbb6ed5cc9a1fe3d1194725a75663d61501c2b4), [`03cc5f5`](https://github.com/components-web-app/components-web-app/commit/03cc5f580fa79121fc25b3acdf206b8e3520e110), [`d8a2384`](https://github.com/components-web-app/components-web-app/commit/d8a2384f5f4b2b883bdeb42b980f8573e8db1367), [`6bc3ac7`](https://github.com/components-web-app/components-web-app/commit/6bc3ac7a4810764154b74e4a24e380abb3c461cb)). *On `main` after template 2.0.0-alpha.42.*

| Step | Switch | Default |
|------|--------|---------|
| [The migrations plan](#the-migrations-plan) | `CWA_CI_MIGRATIONS_PLAN_PRODUCTION` | On, production only |
| [A backup before migrating](#a-backup-before-migrating) | `CWA_CI_DATABASE_BACKUP_<TRACK>` | Off |
| [Migrating in a Job before the rollout](#migrating-in-a-job-before-the-rollout) | `CWA_CI_MIGRATIONS_JOB_<TRACK>` | Off |
| [The maintenance window](#the-maintenance-window) | `CWA_CI_MAINTENANCE_DURING_MIGRATIONS` | Off, and set for one pipeline only |

You can also back the database up without a deploy (see [A backup on demand](#a-backup-on-demand)).

`<TRACK>` is `PRODUCTION`, `STAGING`, `CANARY` or `REVIEW`. The switches are named per track because on GitLab staging runs under the `production` environment, so an environment scope can't tell the two apart. Each one is on only when it's exactly `"true"`. All the variables are listed in [CI/CD Variables › Migrations and backups](/deployment/variables#migrations-and-backups).

::callout{icon="i-heroicons-information-circle"}
**These steps need PostgreSQL.** The plan makes its database session read-only with PostgreSQL's own commands, and the backup runs `pg_dump`, which refuses any other `DATABASE_URL` with `DATABASE_URL is not a PostgreSQL URL, so there is no backup.`
::

## How the steps run

Every step runs in a one-off Kubernetes Job made from the chart's `templates/database-job.yaml`. Helm never installs that template. The deploy renders it on its own from the live release's values, with the **new** php image, so the Job connects to the release's database with the release's settings but runs the code you're about to deploy.

The Jobs set `SKIP_MIGRATIONS=true`, so the php entrypoint doesn't migrate on start the way a pod does. The plan and the backup also run in read-only database sessions, so neither can change the database. `SKIP_MIGRATIONS` is a reserved name (see [CI/CD Variables › Reserved names](/deployment/variables#reserved-names)): `CWA_API_SKIP_MIGRATIONS` can't turn off the API's own migrations.

Inside a deploy, the database step runs after the checks that stop a bad deploy cold, and before Helm runs. So a deploy it stops leaves the live site as it was. The track's image tag only moves once the migrations and both rollouts have succeeded, so a failed deploy never moves it (see [CI/CD › Which build a deploy runs](/deployment/ci-cd#which-build-a-deploy-runs)). It does nothing unless a switch is on, and it stops after the plan when nothing is pending.

`CWA_CI_DATABASE_JOB_TIMEOUT` (1800 seconds) is each Job's deadline. A Job that's never scheduled, or runs past it, stops the deploy with `Job <name> did not finish (not scheduled, or past its deadline): kubectl describe job <name> -n <namespace>`.

## The migrations plan

The plan lists production's pending migrations and the SQL they'll run, without changing anything. Read it before you start the production deploy: starting the deploy after reading it is the approval.

- **GitLab:** the **migrations plan production** job, in the production stage of every `main` pipeline, after `build api` and staging. It runs by itself and may fail without blocking the deploy. `CWA_CI_MIGRATIONS_PLAN_PRODUCTION="false"` removes it.
- **GitHub:** run the **Production** workflow with the action **migrations-plan**.

It uses the php image this pipeline built. On GitHub, where `production.yml` builds nothing, it's whatever `:main` holds when it runs, as for the deploy (see [CI/CD › Which build a deploy runs](/deployment/ci-cd#which-build-a-deploy-runs)), so run it again if `main` moves on before you deploy.

The Job runs `app:database:migrations-plan`, the template's own command. It lists the migrations with `doctrine:migrations:up-to-date --list-migrations`, then prints their SQL from a dry run of `doctrine:migrations:migrate --write-sql`. Doctrine prints "Successfully migrated" for the dry run too, but nothing ran. The job's log ends with one of:

```
Migrations plan: the database of '<release>' is up to date; this deploy migrates nothing.
Migrations plan: 2 migration(s) pending for '<release>' (PostgreSQL 16.4); their SQL is above.
Migrations plan: release '<release>' isn't deployed yet, so its first deploy creates the schema.
```

A database with no migrations table yet counts every migration as pending and shows no SQL.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**A migration that writes data from `up()` or `postUp()` fails the plan.** The session is read-only, so a write made through the connection, rather than with `addSql()`, fails instead of running. While any of the switches below is on, the deploy runs the same plan first, and **a failed plan stops the deploy** with `MIGRATIONS PLAN FAILED (exit <code>): see the log above. Nothing was changed.` Write data changes with `addSql()`.
::

## A backup before migrating

`CWA_CI_DATABASE_BACKUP_PRODUCTION="true"` dumps production's database to Cloud Storage before a deploy that has migrations pending. A deploy with nothing pending takes no backup, so this is a backup before each migration, not a schedule.

The backup Job runs `pg_dump --format=custom` in a `postgres:<major>-alpine` container, using the server's major version from the plan (16 if the plan didn't report one), and checks the dump with `pg_restore --list`. It honours `sslmode` and the `DATABASE_*_CERT` settings. The php container then uploads it with the template's `app:database:backup-upload` command to:

```
gs://<CWA_CI_DATABASE_BACKUP_BUCKET>/<project folder>/<track>/<release>/<YYYYMMDD-HHMMSS>Z-<commit>.dump
```

`<project folder>` is the project's own folder in the bucket (see [The backup bucket](#the-backup-bucket)), and `<track>` is `production`, `staging`, `canary` or `review`. `GCLOUD_PATH_PREFIX` plays no part: it's for the media bucket. *On `main` after template 2.0.0-alpha.42 ([`724f51d`](https://github.com/components-web-app/components-web-app/commit/724f51de3c16a079d4b548887699a8cf9fe1455f)).*

It keeps the newest `CWA_CI_DATABASE_BACKUP_KEEP` (5) in that directory and deletes older ones. Only names in exactly that form are ever deleted, so nothing else in the bucket is touched. The log prints `Database backup: gs://…`.

**A failed backup stops the deploy** before anything migrates: `DATABASE BACKUP FAILED (exit <code>): the deploy stopped before migrating; the live site is unchanged.`

### The backup bucket

A backup needs two variables. Without either, a deploy with a backup switch on fails before it starts any Job.

- `CWA_CI_DATABASE_BACKUP_BUCKET`: a private bucket of its own. Several projects can share it, each in its own folder, so set it once on a GitLab group or as a GitHub organisation variable.
- `CWA_CI_DATABASE_BACKUP_GCLOUD_JSON`: the key of a service account that can only reach this project's folder. Set it on the project, masked (on GitHub, a repository secret). It can be the key JSON base64-encoded on one line, which GitLab can mask, or the JSON itself.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**Never use the media bucket (`GCLOUD_BUCKET`), and keep the backup bucket private.** A dump holds every user's email address and password hash. The media bucket is public, and the [Kubernetes & Helm › Daily Orphan Scan](/deployment/kubernetes#daily-orphan-scan) lists everything under the media storage's root, so deleting all orphaned files would delete the dumps too. The deploy refuses `GCLOUD_BUCKET`. After each upload, the command also asks Cloud Storage for the dump **without credentials**: if that works, it deletes the dump and fails with `Anyone can read objects in the bucket <bucket>, so the backup was deleted again. Use a private bucket (no allUsers or allAuthenticatedUsers access).` If it gets no clear answer, it only warns.
::

**Backups never use `GCLOUD_JSON`**, the key the API uses for media. The deploy refuses a backup key that belongs to the same service account, and the backup Job gets its key in a Secret of its own, deleted as soon as the Job finishes. The API pods never have it. The service account needs **create, get, list and delete** on objects in its folder, and nothing else. *On `main` after template 2.0.0-alpha.42 ([`724f51d`](https://github.com/components-web-app/components-web-app/commit/724f51de3c16a079d4b548887699a8cf9fe1455f)).* Before, the upload used the release's `GCLOUD_JSON` and wrote under `<GCLOUD_PATH_PREFIX>database/<release>/`.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**On GitLab, don't make the key variable Protected unless the branch that deploys is protected.** A Protected variable only reaches pipelines on protected branches, so on any other branch the job never gets it and fails with `A database backup needs CWA_CI_DATABASE_BACKUP_GCLOUD_JSON, … A Protected variable only reaches protected branches.` ([`0921e60`](https://github.com/components-web-app/components-web-app/commit/0921e60972524b5127437e38cf6019995925825a))
::

#### Setting up the bucket with `backup-bucket.sh`

The template's `bin/devops/backup-bucket.sh` sets up a shared bucket on Google Cloud, with one folder and one service account for each project. Run it yourself, with the Google Cloud CLI signed in as someone who can manage the Google Cloud project, never from CI. Every command can be run again safely.

Set `CWA_BACKUP_GCP_PROJECT` and `CWA_BACKUP_BUCKET` to your Google Cloud project and bucket name first, and `CWA_BACKUP_LOCATION` for the bucket's region. The script's built-in defaults aren't yours.

```bash
export CWA_BACKUP_GCP_PROJECT=<gcp project> CWA_BACKUP_BUCKET=<backup bucket> CWA_BACKUP_LOCATION=<region>

# Once: the bucket, and a custom role that can only create, get, list and delete objects
bin/devops/backup-bucket.sh init

# Once per project: its folder, its service account and a new key, printed as one base64 line
bin/devops/backup-bucket.sh project <project slug> --output backup-key.txt

# Check the key works in its folder, and only there
bin/devops/backup-bucket.sh verify <project slug> backup-key.txt
```

- **`init`** creates the bucket with uniform bucket-level access and public access prevention enforced, sets a lifecycle rule that **deletes objects after 90 days**, and creates the role. Run again, it puts those settings back.
- **`project <project slug>`** creates a managed folder named after the slug, a service account with the role on that folder only, and a new key. It prints the key as one base64 line, or writes it to the file `--output` names: that's the project's `CWA_CI_DATABASE_BACKUP_GCLOUD_JSON`. Delete the file once the key is in CI. `--no-key` skips the key. If the service account already has a key, it says so: delete the old one once CI uses the new one.
- **`verify <project slug> <key file>`** uses the key to write, list and delete a test object in the folder, and checks that it can't reach the rest of the bucket and that an anonymous read is refused.

The slug is the folder the deploy writes to: GitLab's `CI_PROJECT_PATH_SLUG`, or on GitHub `owner/repo` lower-cased with every other character a dash. If you named the folder something else, set `CWA_CI_DATABASE_BACKUP_FOLDER` to it.

::callout{icon="i-heroicons-information-circle"}
**The 90-day rule applies on top of `CWA_CI_DATABASE_BACKUP_KEEP`.** A production site that hasn't migrated for 90 days has no backup left from a deploy. Before risky work, take one by hand (see [A backup on demand](#a-backup-on-demand)).
::

`CWA_CI_DATABASE_BACKUP_IMAGE` replaces the `pg_dump` image, for example to use a mirror.

### Restoring a backup

A failed migration rarely needs one: the migrations run with `--all-or-nothing`, in one transaction, so PostgreSQL rolls the whole set back. Restore when a migration succeeded but did the wrong thing.

**Restoring replaces the database**, so it loses anything written since the backup. Download the dump first. You need the Google Cloud CLI signed in with access to the backup bucket:

```bash
gcloud storage cp gs://<bucket>/<path>.dump database.dump
```

With the **in-cluster PostgreSQL**, restore it inside the PostgreSQL pod:

```bash
kubectl exec -i -n <namespace> <release>-postgresql-0 -- sh -c 'PGPASSWORD="$POSTGRES_PASSWORD" pg_restore --clean --if-exists --no-owner -h 127.0.0.1 -U "$POSTGRES_USER" -d "$POSTGRES_DATABASE"' < database.dump
```

With an **external database** (`CWA_CI_POSTGRES_ENABLED="false"`), restore it from anywhere that can reach it:

```bash
pg_restore --clean --if-exists --no-owner --dbname='postgresql://<user>:<password>@<host>/<database>' database.dump
```

A failed maintenance window prints these commands with the namespace, release and backup path filled in (see [When the window fails](#when-the-window-fails)).

### A backup on demand

To back production up without a deploy, for example before risky manual work, run:

- **GitLab:** the manual **database backup production** job, in the production stage of `main` pipelines. It's there only while `CWA_CI_DATABASE_BACKUP_BUCKET` is set, and may fail without blocking anything.
- **GitHub:** the **Production** workflow with the action **database-backup**.

It runs the read-only plan first, to learn the server's PostgreSQL version, then the same backup Job as a deploy, to the same directory, with the same bucket, key and `CWA_CI_DATABASE_BACKUP_KEEP`. It backs up whether or not migrations are pending, and doesn't need `CWA_CI_DATABASE_BACKUP_PRODUCTION`. *On `main` after template 2.0.0-alpha.42 ([`c0a0545`](https://github.com/components-web-app/components-web-app/commit/c0a05455556e170236dcb8a529c8a24cf0546e15)).*

## Migrating in a Job before the rollout

`CWA_CI_MIGRATIONS_JOB_PRODUCTION="true"` runs the pending migrations in a Job before Helm, instead of in the new pod's entrypoint. If they fail, the deploy stops before the rollout and the old pods keep serving:

```
!!!! MIGRATIONS FAILED (exit <code>): the deploy stopped before the rollout; the old pods still serve. !!!!
```

Without it, a failed migration fails the new pod's start, and the rollout waits on a pod that never becomes ready.

The Job runs `app:database:migrate`, the same command the entrypoint runs (see [Kubernetes & Helm › Running Migrations](/deployment/kubernetes#running-migrations)). The new pods still run it when they start, and find nothing left to do.

::callout{icon="i-heroicons-information-circle"}
**The old release still serves while the migration runs, and until the rollout finishes.** For an additive migration (a new table or column) that's fine. For one the running release can't work with, such as a renamed or dropped column, use the maintenance window.
::

## The maintenance window

For a large or breaking migration, run that one production pipeline with `CWA_CI_MAINTENANCE_DURING_MIGRATIONS="true"`. Visitors get the maintenance page from before the migration until the new release is warmed. Admins bypass maintenance mode, so you can check the release before it ends.

- **GitLab:** set it as a variable when you run a new pipeline on `main`, or on the manual **production** job when you start it.
- **GitHub:** tick **maintenance_during_migrations** when you run the **Production** workflow. The job sets the variable from the input itself, so a repository variable of that name is never used.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**Never set it as a project variable.** Every production deploy with a pending migration would close the site. GitLab can't stop you, so it's up to you to set it for one pipeline only.
::

It applies to production only: staging, canary and review deploys print that it's ignored. It only opens a window when the plan finds migrations pending; with nothing pending, the deploy runs as usual.

With migrations pending, the production deploy:

1. Checks the live API can run `silverback:api-components:maintenance` (see [Console Commands › maintenance](/api/console-commands#maintenance)), and stops if it can't.
2. Turns maintenance on.
3. Backs the database up, if `CWA_CI_DATABASE_BACKUP_PRODUCTION` is `"true"`.
4. Migrates in a Job. A window always does, whatever `CWA_CI_MIGRATIONS_JOB_PRODUCTION` says.
5. Rolls out the new release with Helm, and clears the cached pages.
6. Flushes the whole HTTP cache and warms `/_api`.
7. Turns maintenance off.

The commands run in a ready API pod, never one that's shutting down.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**The live site's API image needs the maintenance command**, from api-components-bundle 2.0.0-alpha.33 ([api-components-bundle#549](https://github.com/components-web-app/api-components-bundle/issues/549)). The check runs in the pod that's serving now, not the new image, so the first deploy that brings the bundle in can't use the window. Otherwise it stops before changing anything:

```
❌ The live API can't run silverback:api-components:maintenance, so the window can't start: <error>
   Deploy once without CWA_CI_MAINTENANCE_DURING_MIGRATIONS (or with an API image that has the command).
```
::

A window without a backup still runs, but warns: `WARNING: this maintenance window takes no database backup (CWA_CI_DATABASE_BACKUP_PRODUCTION isn't "true"): a failed migration can only be fixed forward.` On GitHub it's also a **No backup** warning on the run.

### When the window fails

**Anything that fails after maintenance is on leaves it on**, so visitors never see a half-migrated site. The job's log then ends with what to do: GitLab's `after_script` prints it, and on GitHub the step **Maintenance mode is still on** does, with an error on the run.

```
!!!! MAINTENANCE MODE IS ON for '<release>': visitors see the maintenance page (CWA_CI_MAINTENANCE_DURING_MIGRATIONS). !!!!
The backup taken before migrating: gs://<bucket>/<path>.dump
A failed migration is rolled back (one transaction), so restoring is rarely needed. To restore it (replaces the database):
  gcloud storage cp gs://<bucket>/<path>.dump database.dump
  kubectl exec -i -n <namespace> <release>-postgresql-0 -- sh -c '…pg_restore …' < database.dump
Fix forward and deploy again (the window resumes and ends), or turn it off by hand:
  kubectl exec -n <namespace> deploy/<deployment> -- php bin/console silverback:api-components:maintenance off
```

The backup and restore lines appear only when a backup was taken, and an external database gets the `pg_restore --dbname=…` line from [Restoring a backup](#restoring-a-backup) instead.

To finish the window, deploy again **with `CWA_CI_MAINTENANCE_DURING_MIGRATIONS` still set**. If nothing is pending by then and maintenance is still on, the deploy says `Maintenance mode is still on from an earlier attempt: this deploy turns it off after the rollout.`, then rolls out, flushes, warms and turns it off. A deploy without the variable never turns maintenance off, so then turn it off by hand. GitLab doesn't retry a failed deploy by itself: the production job is retried only when CI itself failed, such as a lost runner or the job's timeout (see [CI/CD › Production](/deployment/ci-cd#production)).

## Staging and other tracks

The backup and migrate switches work on every track (`CWA_CI_DATABASE_BACKUP_STAGING`, `CWA_CI_MIGRATIONS_JOB_REVIEW` and so on), each with its own backup directory named after the track and release. The plan job and the maintenance window are production only.

### A track on production's database

Staging and canary deploy into production's namespace, and on GitLab they get production's variables, so with an external `DATABASE_URL` (`CWA_CI_POSTGRES_ENABLED="false"`) they can share production's database (see [CI/CD › Staging](/deployment/ci-cd#staging)). **A staging or canary deploy never migrates production's database.** The deploy compares its `DATABASE_URL` with the one in production's live release: when the host, port and database name match, whatever the credentials, then:

- Its pods and CronJobs get `SKIP_MIGRATIONS=true`, so none of them migrates.
- The deploy runs production's read-only migrations plan with the new image, instead of the track's own backup and migrate steps.
- With migrations pending, **staging isn't deployed**: the job succeeds with a warning, the old staging keeps running, and its cached pages aren't purged. A **canary fails** with `CANARY NOT DEPLOYED: <N> migration(s) pending on production's database, which a canary must not run. Deploy production instead.`

So the production deploy runs the migrations, with its own plan, backup and window. Deploy staging again after it. *On `main` after template 2.0.0-alpha.42 ([`724f51d`](https://github.com/components-web-app/components-web-app/commit/724f51de3c16a079d4b548887699a8cf9fe1455f)).* Before, staging's deploy migrated production's database first, without production's backup or window.

::callout{icon="i-heroicons-information-circle"}
**The check reads production's release in the deploy's own namespace.** Staging and canary deploy into production's namespace, so they're covered. A review app has a namespace of its own, so give review apps their own database.
::
