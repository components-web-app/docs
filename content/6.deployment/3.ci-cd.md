The template ships complete CI/CD for **both GitLab CI and GitHub Actions**. Every step delegates to shell functions in `bin/devops/` — readable, modifiable scripts you own.

Choose your CI/CD provider when you run `pnpm create cwa` — the CLI wires up the correct pipeline files automatically. You can switch later by copying the relevant files from the template.

## GitHub Actions

Three workflows drive your app, in `.github/workflows/`:

| Workflow | Trigger | What it does |
|----------|---------|-------------|
| `ci.yml` | Every push | Build + test; deploy a review environment for non-`main` branches, or staging on `main` |
| `production.yml` | Manual | Deploy canary or full production |
| `cleanup.yml` | PR closed | Tear down the review environment |

The template repo also has `publish-create-cwa.yml`, which publishes the scaffolding CLI. `create-cwa` leaves it out of new projects, and a project that has it can delete it.

Images push to GHCR (`ghcr.io/${{ github.repository }}`). The workflows call the same `bin/devops/` shell functions as GitLab CI. Required secrets and variables are declared in the workflow files themselves, and listed under [Required CI/CD Variables](#required-cicd-variables) below.

On its own, GitHub Actions only gives a job the variables its `env:` block names. The template closes that gap: every job that checks out the repository runs `bin/devops/github-export-vars.sh` straight after the checkout, which exports every GitHub **variable** (repository, organisation and environment) to the job's later steps, as GitLab does. To set a variable from the [lists below](#required-cicd-variables), add it under **Settings → Secrets and variables → Actions → Variables**. You don't need to change a workflow.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**Secrets still need an `env:` mapping, except `NUXT_*` and `CWA_API_*` ones.** Secrets aren't in `vars`, so the script can't export them, and mapping them explicitly keeps them masked in logs. A name the job already sets in `env:` is left alone, so the workflow's mapping wins over a variable of the same name. The template's deploy jobs map `KUBE_CONTEXT`, `DATABASE_URL`, `MAILER_DSN`, `GCLOUD_JSON`, `APP_SECRET`, the JWT and Mercure keys and `ADMIN_PASSWORD` from secrets, so set those as secrets: a variable with one of those names is ignored. `KUBECONFIG` and `KUBE_NAMESPACE_PRODUCTION` are secrets too. Secrets named `NUXT_*` or `CWA_API_*` need no mapping: the deploy jobs export them for you (see [Site settings](#site-settings)).
::

::callout{icon="i-heroicons-information-circle"}
The workflows run on every push by default. Set the GitHub Actions **variable** `CWA_CI_DISABLED=true` (under Settings → Secrets and variables → Actions → Variables) to suppress them. This is used on the template repo itself, which deploys via GitLab CI and only mirrors to GitHub.
::

## GitLab CI

The `.gitlab-ci.yml` has seven stages: build, test, review, staging, canary, production and cleanup. There is no GitLab Auto DevOps magic here.

GitLab runs branch pipelines only. The workflow creates no merge request pipelines, because every job is limited to branches. A merge request shows its branch pipeline's result, so **Pipelines must succeed** works as expected.

## Pipeline Overview

::DiagramCiPipeline
::

On every branch: **build** then **test** then spin up a **review app** on Kubernetes. When a branch merges to `main`: build and test run again, then the pipeline auto-deploys to **staging**, from where you manually promote through **canary** to **production**.

## Stages

### Build

Two parallel jobs — `build api` and `build app` — each run `docker buildx` and push to the GitLab Container Registry. Layer caching is handled with `--cache-to` / `--cache-from` against a dedicated cache image tag, so incremental builds are fast.

```
$CI_REGISTRY_IMAGE/php:$CI_COMMIT_REF_SLUG    ← FrankenPHP image (--target frankenphp_prod)
$CI_REGISTRY_IMAGE/app:$CI_COMMIT_REF_SLUG    ← Nuxt image       (--target prod)
```

The PHP image build uses `api/Dockerfile`; the Nuxt image uses `app/Dockerfile`. Build logic lives in `build_api()` and `build_app()` in `bin/devops/k8s.sh`.

Composer downloads about 180 packages from github.com per install. Anonymously, GitHub allows 60 requests an hour per IP, so on a shared runner an install can fail part way through with a `429`. Set the optional [`GITHUB_TOKEN`](#composer) variable to authenticate them. `build_api` passes it to the image build as the `composer_auth` build secret, never a build arg, so the token stays out of the image history. The build log's `github rate limit for this build:` line prints `60` when the token didn't reach the build and `5000` when it did ([!12](https://gitlab.com/silverback-web-apps/cwa/components-web-app/-/merge_requests/12), [`a3c6ef6`](https://github.com/components-web-app/components-web-app/commit/a3c6ef67c79f4c5c43c081a601ebae8c8f806cea)).

### Test

Two parallel jobs against the image built in the previous stage:

| Job | What runs |
|-----|-----------|
| `unit tests` | `vendor/bin/phpunit tests/Unit` — fast, no database. It also runs the template's Souin and Caddy checks: `bin/test/souin-purge-isolation.sh`, `bin/test/souin-flush-storage.sh` (which checks that otter, badger and nuts still cache after a full flush), `bin/test/souin-coalesced-5xx.sh` (which checks that requests Souin coalesces onto an upstream `5xx` all get that `5xx`, not an empty `200`), `bin/test/caddy-validate.sh` (which checks that the Caddyfile loads for both Helm's and compose's `SERVER_NAME`) and `bin/test/cache-encoding.sh` (which runs the real Caddyfile and checks that pages are cached compressed, one entry for each normalised `Accept-Encoding`). See [Docker gotchas](/deployment/docker#common-gotchas) |
| `functional tests` | `vendor/bin/phpunit tests/Functional` with a live PostgreSQL service. The tests use API Platform's `ApiTestCase`, and the schema is rebuilt from the entity mapping (Doctrine `SchemaTool`, not migrations) before each test. For a large suite, see [Faster Functional Tests](/deployment/faster-functional-tests) |

Both export JUnit XML for GitLab's test report UI. On GitHub the jobs are `unit-tests` and `functional-tests`.

**Functional tests never send real email.** Every CI variable reaches the test job, and a real environment variable beats `api/.env.test`, so a project's live `MAILER_DSN` would deliver any email a test sends, such as a contact form or a password reset. `run_test_functional` unsets `MAILER_DSN` and `MAILER_EMAIL`, and `api/.env.test` sets `MAILER_DSN=null://null`. Mail is still built, and Symfony's mailer assertions still see it, but nothing is delivered. Keep both: without the `.env.test` line, tests fall back to `api/.env`'s `smtp-relay` host, which CI doesn't have, so a test that sends email errors. The job also generates a test JWT keypair (`lexik:jwt:generate-keypair --skip-if-exists`), so tests that sign in work in CI ([!12](https://gitlab.com/silverback-web-apps/cwa/components-web-app/-/merge_requests/12), [`a3c6ef6`](https://github.com/components-web-app/components-web-app/commit/a3c6ef67c79f4c5c43c081a601ebae8c8f806cea), [`3a6c366`](https://github.com/components-web-app/components-web-app/commit/3a6c3663d4107800631f6ce50ac7755645cac651)).

**The CI JWT keys never reach the tests.** `run_test_functional` also unsets `JWT_SECRET_KEY`, `JWT_PUBLIC_KEY` and `JWT_PASSPHRASE`. In CI these hold the keys' contents for the deploy, while the tests read `api/.env`'s file paths and the keypair the job generates. With the CI values in place, the functional tests failed, and the job log printed the encrypted key ([#130](https://github.com/components-web-app/components-web-app/issues/130), [`c1d2581`](https://github.com/components-web-app/components-web-app/commit/c1d2581a2c1478d618765474b5d5808857b98868)).

Functional tests extend `App\Tests\Functional\FunctionalTestCase`. Its `setUp()` **refuses to run unless the database name contains `test`**, because it drops the schema. Entities a test persists directly need `createdAt` and `modifiedAt` set by hand, since the bundle sets them only on its own write path (see `RoutesTest`).

### Review Apps

A branch (other than `main`) gets a review app, with its own Helm release, **only once someone creates its Kubernetes namespace**. The pipeline never creates namespaces. The URL follows the pattern `https://$CI_COMMIT_REF_SLUG-review.$KUBE_INGRESS_BASE_DOMAIN`.

::callout{icon="i-heroicons-information-circle"}
Namespaces must be **created by hand**, with role bindings for the CI's identity. Letting one project create namespaces and role bindings would give it rights across the whole cluster, so the pipeline's permissions stop at the namespace. See the comment in `ensure_namespace()`.
::

The review job checks for the namespace first (`skip_review_without_namespace`):

| Namespace | GitLab | GitHub Actions |
|-----------|--------|----------------|
| Exists, and the CI can read it | Deploys | Deploys |
| Not found, or the CI is forbidden to read it | The job exits with code `3`, which the job allows, so the pipeline is **orange** ("passed with warnings") | A *No review environment* warning annotation. The deploy, fixtures and cache warm steps are skipped |
| Any other `kubectl` error, such as an unreachable cluster or a bad context | **Red** | **Red** |

The jobs that follow a review (the review fixture load, cache warm, performance audit and stop jobs) start with `skip_unless_review_deployed`. When the review job didn't deploy, they exit with code `3` and say why, instead of running against an environment that doesn't exist. Projects created before the template's `2.0.0-alpha.2` release don't have this guard.

An orange pipeline on a branch just means that branch has no review app. A deploy that really fails is still red. Staging, canary and production don't make this check: a missing namespace there fails the job.

#### Creating a namespace for a branch

1. Find the name. The job log prints it: `No namespace '<name>', so this branch has no review environment to deploy to.` It is `KUBE_NAMESPACE`, which defaults to `<project name>-<environment slug>`. On GitHub that is `<repository name>-review-<branch slug>`. On GitLab the slug is GitLab's `CI_ENVIRONMENT_SLUG` for `review/<branch>`, which GitLab shortens and may give a random suffix, so copy the name from the log.
2. Create the namespace, and bind the identity your CI deploys with to a role in it. For example, with the built-in `edit` role:

   ```sh
   kubectl create namespace <name>
   kubectl create rolebinding ci-deploy --namespace <name> \
     --clusterrole=edit --serviceaccount=<ci-namespace>:<ci-service-account>
   ```

   Which identity and role you need depends on your cluster and on how the CI connects (the GitLab agent, or the `KUBECONFIG` secret on GitHub). Give it the same access as your other environments.
3. Run the review job again.

A namespace that exists without the role bindings still shows orange, because the CI is forbidden to read it.

Review apps are torn down manually via the **stop review** job (triggered from the GitLab environment list), or automatically when the branch is deleted. Stopping one uninstalls its Helm release but leaves the namespace, so delete the namespace by hand once the branch is gone.

### Staging

Runs automatically on every merge to `main` (controlled by `$CWA_CI_STAGING_ENABLED`, default `"true"`). Calls `deploy staging` which runs `helm upgrade --install` for a separate `-staging` release. Staging runs under the production environment, so it deploys into production's namespace and gets production's variables.

### Canary

A manual job that runs `deploy canary`. Useful for routing a portion of production traffic to the new image before full rollout. Enable/disable via `$CWA_CI_CANARY_ENABLED`.

Like production, it waits for the builds and tests (see Production below).

### Production

A manual job requiring explicit trigger from GitLab. Calls `deploy` (stable track), then `delete canary` and `delete staging` to clean up the intermediate environments.

Production and canary can't start until `build api`, `build app`, `unit tests` and `functional tests` have passed, and staging too when it is enabled. Each of these `needs` is optional, so `CWA_CI_BUILD_DISABLED` and `CWA_CI_TEST_DISABLED` still work.

## The Devops Scripts

All CI logic lives in two scripts sourced at the top of every job:

### `bin/devops/setup.sh`

Sets shared environment variables:
- `CI_APPLICATION_REPOSITORY` / `CI_APPLICATION_TAG` — image repo and SHA tag
- `PHP_REPOSITORY` / `APP_REPOSITORY` — full image paths
- `PHP_REPOSITORY_CACHE` / `APP_REPOSITORY_CACHE` — layer cache image paths
- `DOMAIN` — the host of `CI_ENVIRONMENT_URL`, unless it's already set by [`bin/devops/project.sh`](#project-hooks) or a CI variable. With neither, it's empty, and `check_kube_domain` fails the job. There's no fallback host
- `CWA_CI_DEPLOYMENT_BRANCH` — defaults to `main`
- `COMPOSER_AUTH` — built from [`GITHUB_TOKEN`](#composer) when it's set, and left unset otherwise
- `COMPOSER_MAX_PARALLEL_HTTP=6` — half composer's default of 12, which is a big enough burst to be throttled even when authenticated
- `KUBERNETES_VERSION` / `HELM_VERSION` — the kubectl and Helm versions `install_dependencies` installs, `1.31.0` and `3.19.0` unless a CI variable sets them (see [Kubernetes](#kubernetes))

### `bin/devops/k8s.sh`

Contains all the functions the pipeline calls:

| Function | What it does |
|----------|-------------|
| `install_dependencies` | Installs Helm, kubectl, curl, and other tools on the Alpine CI runner |
| `setup_docker_environment` | Handles Docker-in-Docker host config for Kubernetes runners |
| `build_api` / `build_app` | `docker buildx build --push` with registry layer caching. `build_api` passes `COMPOSER_AUTH` as the `composer_auth` build secret |
| `run_test_phpunit` | Runs PHPUnit unit tests; outputs JUnit XML |
| `run_test_functional` | Runs `phpunit tests/Functional` against the job's own database (set up by `setup_test_db_environment`); outputs JUnit XML to `api/build/logs/phpunit/functional.xml`. Unsets `MAILER_DSN`, `MAILER_EMAIL` and the `JWT_*` keys first and generates a test JWT keypair (see [Test](#test)). See [Faster Functional Tests](/deployment/faster-functional-tests) once the suite is slow |
| `helm_init` | Updates and builds Helm chart dependencies |
| `review_namespace_state` | Prints `present`, `missing` (the namespace is not found, or the CI is forbidden to read it) or `error` (any other `kubectl` failure) for `$KUBE_NAMESPACE`. The GitHub review job calls it directly |
| `skip_review_without_namespace` | Runs first in the GitLab review job. Exits with code `3` when the namespace is missing, which the job allows, so the pipeline shows orange. See [Review Apps](#review-apps) |
| `skip_unless_review_deployed` | Runs first in the jobs that follow a review. Exits with code `3` when the review job uploaded no `environment_url.txt`, meaning it didn't deploy |
| `ensure_namespace` | Verifies the K8s namespace exists and fails the job if not. Staging, canary and production rely on it |
| `create_docker_pull_secret` | Creates or updates the `imagePullSecret` for the GitLab registry with `kubectl apply`, so releases sharing a namespace don't race with "already exists". The first deploy over a secret that an older template created with `kubectl replace --force` prints a one-off warning about a missing `last-applied-configuration` annotation. It's harmless, and the secret is updated |
| `check_kube_domain` | Fails the job when there is no `DOMAIN` to deploy to, or when it starts or ends with a dot. A dot there means the variable in the environment url was empty, as in `https://staging.` with no `KUBE_INGRESS_BASE_DOMAIN` |
| `deploy [track]` | Generates `values.tmp.yaml` from CI variables and runs `helm upgrade --install`, with a project's [`project_values`](#project-hooks) applied last. It runs `check_php_memory_budget` before anything changes in the cluster, and `deploy_secrets` before Helm |
| `check_php_memory_budget` | Runs inside `deploy`. Fails the deploy when the [php memory budget](#php-memory-budget) doesn't fit the API's memory limit |
| `deploy_secrets [release]` | Runs inside `deploy`. Takes `APP_SECRET`, `MERCURE_JWT_SECRET` and the JWT key pair from a CI variable, else from the release's live Secret, else generates them. See [Secrets](#secrets) |
| `ensure_jwt_keys` | Called by `deploy_secrets`. Generates a JWT key pair when there's none, or derives `JWT_PUBLIC_KEY` from a supplied key, and fails on a key without its passphrase |
| `ensure_tls_certificate` | Runs inside `deploy` before Helm. When production's hostnames change, it issues the new certificate first. See [Changing a live site's hostnames](#changing-a-live-sites-hostnames) |
| `purge_rendered_html [track]` | Waits for the Nuxt and php rollouts to finish, then clears every cached page, or the whole HTTP cache when Cloudflare is configured. Runs after every `deploy` |
| `warm_cache [base_url]` | Refills the page cache after `purge_rendered_html`, and reports each page's status and time to first byte. `base_url` defaults to `https://$DOMAIN`. Runs as its own job or step after every deploy |
| `performance_audit [base_url]` | Runs a Lighthouse audit of a few pages. `base_url` defaults to `https://$DOMAIN`. Only runs when you start it. See [Auditing performance after a deploy](#auditing-performance-after-a-deploy) |
| `load_fixtures [track]` | Loads fixtures into the php pod with `--append`, so existing content is kept, unless `CWA_CI_FIXTURES_PURGE` asks for a purge. Then flushes the whole HTTP cache. Only runs when `CWA_CI_FIXTURES_ENABLED` is `"true"`. See [Pipeline Flags](#pipeline-flags) |
| `persist_environment_url` | Writes `https://$DOMAIN` to `environment_url.txt`, the artifact the later jobs check, and `SITE_ENVIRONMENT_URL=https://$DOMAIN` to `environment_url.env` |
| `delete [track]` | Runs `helm uninstall` for review/canary/staging cleanup |

### Project hooks

Keep `setup.sh`, `k8s.sh` and the chart exactly as the template ships them, so each release is a plain file copy. A project's own deploy logic goes in an optional **`bin/devops/project.sh`** ([!14](https://gitlab.com/silverback-web-apps/cwa/components-web-app/-/merge_requests/14), [`1a7c30b`](https://github.com/components-web-app/components-web-app/commit/1a7c30b2793f9ad17d1fe4979905e842cd85dec8), [`ed4c725`](https://github.com/components-web-app/components-web-app/commit/ed4c725417aa64318bebbe7054fba5bfa29e61cd)). A project without one deploys exactly as before.

`setup.sh` sources `project.sh` in every job, on GitLab and GitHub, after its own defaults and before it sets `DOMAIN` and the image paths. `k8s.sh` isn't loaded yet, so `project.sh` can't call its functions. In it you can:

- **Set `DOMAIN`**, the host the deploy serves, for example to choose which of several sites a job deploys. `setup.sh` keeps a `DOMAIN` that's already set, and otherwise takes the host of the job's environment url. A `DOMAIN` CI variable works the same way. `check_kube_domain`, `persist_environment_url`, the ingress hosts, `NUXT_SITE_URL`, the [host-based defaults](#required-cicd-variables), and the cache warm and performance audit jobs all follow it ([#132](https://github.com/components-web-app/components-web-app/issues/132), [`7b26140`](https://github.com/components-web-app/components-web-app/commit/7b26140895c524ad5083e48470883bffd99d3410)).
- **Export site settings** and other variables, such as `KUBE_INGRESS_ALIAS_DOMAINS`, or `NUXT_*` and `CWA_API_*` values for the [site settings passthrough](#site-settings), such as each site's `CWA_API_WEBSITE_NAME`. Use `export`: the passthrough only sees exported variables.
- **Reserve more names** with `SITE_ENV_RESERVED_API_EXTRA` and `SITE_ENV_RESERVED_PWA_EXTRA`, space-separated. Add the names your own chart values set on a container, so a site setting of the same name fails the deploy instead of being ignored. See [Reserved names](#reserved-names). They can be CI variables too.
- **Define `project_values`**. `deploy` calls it with the track (`stable` for production, `staging`, `canary` or `review`) and passes what it prints to `helm upgrade` as the last `-f` values file, after the template's own. Use it for the values of a template you add to `helm/cwa/templates`, or to change one of the chart's values. If it exits non-zero, the deploy stops before helm. The five `--set` values (`APP_SECRET`, the JWT keys and the Mercure JWT keys) still win over it, as `--set` always does in helm.

```sh [bin/devops/project.sh]
# Sourced by bin/devops/setup.sh in every job. POSIX sh only.

# One repository, two sites: SITE is a CI variable scoped to each environment.
if [ "$SITE" = "shop" ]; then
  export DOMAIN="shop.example.com"
  export NUXT_PUBLIC_SITE_NAME="Example Shop"
  export CWA_API_WEBSITE_NAME="Example Shop"
fi

# Chart values, applied after the template's.
project_values() {
  if [ "$1" = "stable" ]; then replicas=2; else replicas=1; fi
  cat <<EOF
redirects:
  replicaCount: $replicas
EOF
}
```

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**Write the hooks in POSIX sh.** GitLab's jobs run on `alpine`, where the shell is busybox ash: no arrays and no `declare`. A hook that only works in bash passes on GitHub and fails on GitLab.
::

`environment_url.env` is for a job whose url is worked out in the job, such as a multi-site deploy. The template's own jobs don't read it, and their environment urls stay as they are. If your `project.sh` sets `DOMAIN`, you can point your GitLab deploy job's environment url at it: add the file as a `dotenv` report and use the variable as the url:

```yaml
  environment:
    url: $SITE_ENVIRONMENT_URL
  artifacts:
    paths: [ environment_url.txt ]
    reports:
      dotenv: environment_url.env
```

The cache warm and performance audit jobs pass no url, so `warm_cache` and `performance_audit` use `https://$DOMAIN`, and a `DOMAIN` set here reaches them. The GitHub **Performance audit** workflow sources `setup.sh` too.

### Why every deploy clears the page cache

Cached pages link to the JavaScript and CSS files of the build that rendered them. A new front-end build gives those files new names and deletes the old ones. Without a purge, the cache keeps serving pages that point at files that no longer exist, so visitors see an unstyled page that does not work until the cached copy expires, which can take up to an hour.

`purge_rendered_html` prevents this. It waits until the new Nuxt pods have fully replaced the old ones, because an old pod could otherwise put an old page back into the cache. Then it runs `php bin/console silverback:api-components:purge-rendered-html` in the php pod. That command clears only the rendered pages, which share the `cwa-html` cache tag, and leaves cached API responses alone. It uses the pipeline's existing `kubectl` access, so it needs no extra credentials. If a site has no HTTP cache configured, the command does nothing and still succeeds.

If Cloudflare or another CDN caches your pages, this purge reaches it only when Souin's `CADDY_CACHE_CDN_CONFIG` is set to purge it. See [Purges must reach Cloudflare](/deployment/cloudflare#purges-must-reach-cloudflare).

When `CADDY_CACHE_CDN_CONFIG` contains `provider cloudflare`, `purge_rendered_html` runs `silverback:api-components:purge-http-cache` instead. Cloudflare can also hold API responses, through the optional [API rule](/deployment/cloudflare#api-responses-optional), and the `cwa-html` tag doesn't cover them. A full flush reaches Cloudflare as a purge of everything in the zone, so a release that changes API output doesn't leave stale responses at the edge. It costs nothing at the origin, because the restarted php pod's cache is already empty. Staging uses the same variable, so a staging deploy also empties the edge for production; the warm job and normal traffic refill it.

### Warming the cache after a deploy

A purge leaves the cache empty, so the first visitor to each page would wait for a server render. `warm_cache` fills it again, as its own job after a deploy: `warm cache review`, `warm cache staging`, `warm cache canary` and `warm cache production` on GitLab, and a *Warm the page cache* step on GitHub, after the fixtures step so a new environment is warmed once its content exists. **Only production is warmed by default**; the other tracks opt in (see the table below). The production deploy never waits for a warm job. It reads `/sitemap.xml` from `https://$DOMAIN`, or the url passed to `warm_cache` (following one level of sitemap index), then requests every page anonymously, three at a time by default, and prints each page's status and time to first byte.

Any page that doesn't return `200` is listed under a `CACHE WARM FAILED` banner, and on GitHub it also raises an `::error` annotation on the run summary. The warm job fails, but it is allowed to (`allow_failure: true` on GitLab, `continue-on-error: true` on GitHub), so the pipeline shows a warning instead of a failed deploy. By then the new release is already live, and the deploy and its cleanup steps have already run. Read the warm job's log when it warns.

| Variable | Default | Effect |
|----------|---------|--------|
| `CWA_CI_WARM_CACHE_PRODUCTION` | on | Set `"false"` to stop warming production |
| `CWA_CI_WARM_CACHE_STAGING` | off | Set `"true"` to warm staging |
| `CWA_CI_WARM_CACHE_CANARY` | off | Set `"true"` to warm canary |
| `CWA_CI_WARM_CACHE_REVIEW` | off | Set `"true"` to warm review apps |
| `CWA_CI_WARM_CACHE_CONCURRENCY` | `3` | Pages requested at once |
| `CWA_CI_WARM_CACHE_INSECURE` | — | Set `"true"` to skip TLS verification, e.g. for an environment with a self-signed certificate |

Set these as GitLab CI/CD variables or GitHub repository variables. There's one variable per track, not one environment-scoped variable, because the template's staging deploy job uses `environment: production`. An environment scope therefore can't tell staging and production apart.

### Auditing performance after a deploy

`warm_cache` tells you how quickly the server answered. `performance_audit` tells you what a visitor experiences. It runs [Lighthouse CI](https://github.com/GoogleChrome/lighthouse-ci) (`@lhci/cli`) against a few pages and reports LCP, CLS, TBT, FCP, Speed Index and page weight. Run it after the cache warm, so it measures cached pages, which is what visitors get. Each page is loaded anonymously with no query string, so the audit neither bypasses nor splits the cache.

The audit is **manual**. It is available by default, but it never runs by itself.

- **GitLab:** after a deploy, press play on the `performance audit review`, `performance audit staging` or `performance audit production` job. Each one waits for its deploy job, and for its warm job when warming is on. Set `CWA_CI_PERFORMANCE_AUDIT_REVIEW`, `CWA_CI_PERFORMANCE_AUDIT_STAGING` or `CWA_CI_PERFORMANCE_AUDIT_PRODUCTION` to `"false"` to remove that job. `performance audit canary` is opt-in (`CWA_CI_PERFORMANCE_AUDIT_CANARY="true"`), because canary shares production's hostname and would measure whichever pod answers.
- **GitHub Actions:** run the **Performance audit** workflow (`performance-audit.yml`) from the Actions tab. Choose the environment (production, staging or review) and the form factors. For a review app, run the workflow from that branch, because the URL is built from the branch name. Set a repository variable `CWA_CI_PERFORMANCE_AUDIT_PRODUCTION`, `CWA_CI_PERFORMANCE_AUDIT_STAGING` or `CWA_CI_PERFORMANCE_AUDIT_REVIEW` to `"false"` to disable that environment.

By default it audits the first three pages of `/sitemap.xml`, on mobile, five runs each. That is 15 page loads. Five runs stop one slow run on a shared CI runner from changing the median. Pages are audited one after another, never in parallel, because parallel runs share the runner's CPU and network and skew every metric.

The audit uses real throttling (Lighthouse's `devtools` method) by default. Lighthouse's simulated throttling gave very different scores for the same page on shared CI runners, from 0.60 to 0.96. Only the performance category is collected.

|----------|---------|--------|
| `CWA_CI_PERFORMANCE_AUDIT_URLS` | — | Pages to audit instead of the sitemap. Paths or full URLs, comma or space separated. A path such as `/blog` is joined to the environment URL |
| `CWA_CI_PERFORMANCE_AUDIT_MAX_PAGES` | `3` | How many sitemap pages to audit when `CWA_CI_PERFORMANCE_AUDIT_URLS` is unset |
| `CWA_CI_PERFORMANCE_AUDIT_FORM_FACTORS` | `mobile` | `mobile`, `desktop` or `mobile,desktop`. On GitHub you choose this when you start the workflow |

#### Budgets

The budgets are in `bin/devops/lighthouserc.json`. They use Lighthouse's "good" thresholds:

| Metric | Budget | A miss is |
|--------|--------|-----------|
| Performance score | at least `0.8` | an error |
| Largest Contentful Paint | at most 2.5s | an error |
| Cumulative Layout Shift | at most `0.1` | an error |
| Total Blocking Time | at most 200ms | an error |
| Page weight | at most 1.6MB | a warning only |

To change them, edit `bin/devops/lighthouserc.json`, or point `CWA_CI_PERFORMANCE_AUDIT_CONFIG` at your own file.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
Don't put a `collect.settings` block in this file. `performance_audit` passes settings such as `--collect.settings.chromeFlags` on the command line, and any `--collect.settings.*` option replaces the file's whole `settings` block. Projects generated earlier have `onlyCategories` in the file, which never applied, so their audits ran all four categories.
::

A missed error budget fails the audit, but **it never fails a deploy**. On GitLab the job is allowed to fail, so the pipeline shows "passed with warnings". On GitHub the audit run fails with a warning. That run is only the audit, and the deploy has already finished.

#### Reading the results

The reports go in `performance-report/`: Lighthouse's HTML and JSON for each page and form factor, the budget results, and a `summary.md` table.

The end of the job log shows the same results as an aligned text table. It has one row per page and form factor, from the median run. The columns are Page, Device, Score, LCP, FCP, TBT, CLS, Speed Index and Weight. Each value with a budget is marked:

- `✓` within budget
- `✗` over an error budget, which fails the audit
- `⚠` over a warning budget

The marks are read from the budgets in `lighthouserc.json`, so they match what failed the audit.

- **GitLab:** download the job's `performance-report/` artifact, kept for 30 days. The job also writes a `browser_performance` report. GitLab uses it to compare metrics between pipelines in the merge request, but that widget needs GitLab Premium. On Free, you still get the artifact.
- **GitHub Actions:** the table is in the workflow run's summary. The full reports are in the `performance-report-<environment>` artifact, kept for 30 days.

## Required CI/CD Variables

Set these in **Settings → CI/CD → Variables** in GitLab. On GitHub, set them as Actions variables, except the ones the workflows map from secrets (see [GitHub Actions](#github-actions)). The [secrets](#secrets) (`APP_SECRET`, `MERCURE_JWT_SECRET` and the JWT key pair) are optional: a deploy keeps the release's live values, and generates them only for a new release.

The deploy works out the settings that would otherwise be the same on every site: `CWA_CI_INGRESS_ENABLED`, `CORS_ALLOW_ORIGIN`, `TRUSTED_HOSTS`, `MERCURE_CORS_ORIGIN` and `DATABASE_SSL_MODE`. A variable you set still wins. So a new site sets only what is its own: the domain, the secrets, the database, the media bucket and the mailer, plus `CWA_CI_CLUSTER_ISSUER=letsencrypt-prod` for production once its domain points at the cluster. The host-based defaults use the deploy's own hostname, plus `KUBE_INGRESS_ALIAS_DOMAINS` in production, so review apps and staging get their own instead of production's.

The variables follow three naming rules:

- **`CWA_CI_*`** are the template's own pipeline and deploy switches, such as `CWA_CI_STAGING_ENABLED` or `CWA_CI_PWA_AUTOSCALE_MIN`. The sizing of the php pod is `CWA_CI_API_*`.
- **`CWA_API_*`** and **`NUXT_*`** are settings the containers read at runtime, passed through by prefix. See [Site settings](#site-settings).
- Site values, secrets and names set by the platform keep their own names: `DATABASE_URL`, `POSTGRES_*`, `APP_SECRET`, `JWT_*`, `MERCURE_JWT_SECRET`, `MAILER_*`, `GCLOUD_*`, `ADMIN_*`, `CORS_ALLOW_ORIGIN`, `TRUSTED_HOSTS`, `MERCURE_CORS_ORIGIN`, `DATABASE_SSL_MODE`, `CADDY_CACHE_CDN_CONFIG`, `GITHUB_TOKEN`, `KUBERNETES_VERSION`, `HELM_VERSION`, and the `KUBE_*` and `CI_*` variables.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**Template 2.0.0-alpha.16 renamed the switches, and the old names are no longer read.** A project that still sets `POSTGRESQL_ENABLED`, `CLUSTER_ISSUER`, `ENABLE_DATABASE_FIXTURES` or another old name gets the default instead, without a warning. The full list is in [Upgrading the Template → 2.0.0-alpha.16](/deployment/upgrading-the-template#_200-alpha16).
::

::callout{icon="i-heroicons-information-circle"}
**GitLab environment scopes:** the staging job runs under `environment: production`, so a variable scoped to `production` reaches staging too, as well as canary and production.
::

### Secrets

*Since template 2.0.0-alpha.21 · [upgrade notes](/deployment/upgrading-the-template#_200-alpha21)*

| Variable | Notes |
|----------|-------|
| `APP_SECRET` | Symfony's secret, which signs URLs and other tokens |
| `JWT_SECRET_KEY` | The private key's contents |
| `JWT_PASSPHRASE` | The private key's passphrase. If you set `JWT_SECRET_KEY`, set this too, or the deploy fails |
| `JWT_PUBLIC_KEY` | When you supply `JWT_SECRET_KEY` and leave this empty, it's derived from the key with `JWT_PASSPHRASE`, and the deploy fails if the passphrase doesn't decrypt the key |
| `MERCURE_JWT_SECRET` | Signs the Mercure publisher and subscriber tokens |

All of them are optional. For each one that isn't a CI variable, `deploy_secrets` reads the value from the release's live Secret, and generates a new one only when the release doesn't have one yet ([#144](https://github.com/components-web-app/components-web-app/issues/144), [`816997e`](https://github.com/components-web-app/components-web-app/commit/816997eaebb7cfb167172e38065042ee5a42f710)). The JWT key is kept together with its own passphrase, and the public key is derived from them. So logins, signed URLs and Mercure cookies survive a deploy, and pods on either side of a rollout agree.

Setting them as **protected, masked** CI variables (GitHub: secrets) is still worth it for production. A release that is uninstalled, for example with `CWA_CI_HELM_UNINSTALL` or a stopped review app, loses its Secret, and its next deploy generates new values. A CI variable also lets you rotate a value on purpose.

To rotate a value, set a new one as the CI variable and deploy. Removing the variable doesn't rotate it, because the deploy then keeps the live value. For the JWT key pair, set `JWT_SECRET_KEY` and `JWT_PASSPHRASE`, and leave `JWT_PUBLIC_KEY` empty to have it derived. **A new JWT key pair signs every user out** when it's deployed, because tokens signed with the old key no longer verify.

The `JWT_*` values hold the keys' contents, for the deploy. The `functional tests` job unsets them, so they never reach the tests (see [Test](#test)).

With the in-cluster PostgreSQL (`CWA_CI_POSTGRES_ENABLED` not `"false"`), the deploy writes the three `POSTGRES_*` variables that are set to the chart's `postgresql.global.postgresql.auth`. Bitnami's subchart creates the database from those values, and the chart builds the API's `database-url` from them, percent-encoding each part ([`e15f168`](https://github.com/components-web-app/components-web-app/commit/e15f16818a61f9a3f68697808bea5998bf34b0dc)). An unset variable keeps the chart's default.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**By default the in-cluster PostgreSQL has no volume.** Its data lives in the pod and is lost whenever the pod is replaced, for example after a node restart or a credentials change. Use an external database (`DATABASE_URL` with `CWA_CI_POSTGRES_ENABLED="false"`) for a real site, or turn on [persistence](#in-cluster-postgresql-persistence).
::

PostgreSQL creates the user and database only when it starts on an empty data directory. Without persistence, **changing the user or database name on a live site restarts the PostgreSQL pod empty**, so the content has to be loaded again. A new password alone doesn't restart the pod, so the API can't connect until you run `kubectl delete pod <release>-postgresql-0`, which also starts it empty.

With persistence, the volume keeps the user, password and database it was created with, and a deploy doesn't change them. Change them in PostgreSQL first, as the `postgres` superuser, with `ALTER USER` or `ALTER DATABASE` (renaming a user clears its password, so set it again), then set the new values and deploy.

#### In-cluster PostgreSQL persistence

The three `CWA_CI_POSTGRES_*` persistence variables go to the chart's `postgresql.primary.persistence`, and only the ones that are set. Unset, the chart's defaults apply: no volume, and `standard` at `1Gi` once it's turned on ([`7675190`](https://github.com/components-web-app/components-web-app/commit/767519054d9b8473a42eb30144ea6eaeae65d39a)).

Kubernetes can't change a StatefulSet's volume once it exists, so Helm would fail part way through. Before anything changes, the deploy compares the variables with the live PostgreSQL and **stops when they differ**, with the commands to run and what happens to the data. It never deletes anything itself:

| Change on a live release | What the deploy tells you to do |
|--------------------------|---------------------------------|
| Turn persistence on | `pg_dump` the data if you need it, run `kubectl delete statefulset <release>-postgresql -n <namespace> --cascade=orphan`, and deploy again. The new pod starts with an empty volume, so load fixtures or restore the dump |
| Turn persistence off | The same `kubectl delete statefulset … --cascade=orphan`, then deploy. The new pod starts empty. The volume `data-<release>-postgresql-0` keeps its data until you delete it with `kubectl delete pvc` |
| Change the size | Set it back, or delete the StatefulSet with `--cascade=orphan` and deploy: the volume and its data are kept at the old size. To grow it, if the storage class allows expansion, patch the volume with the `kubectl patch pvc` command the log prints |
| Change the storage class | Set it back, or `pg_dump`, delete the StatefulSet with `--cascade=orphan` and the volume with `kubectl delete pvc`, deploy, and restore the dump |

A first deploy, with no PostgreSQL yet, can use any settings. If the CI can't read the StatefulSet, the deploy prints a warning and skips the check.

Helm leaves volumes behind when it uninstalls a release. **Stopping a review app also deletes its PostgreSQL volume**, so a branch deployed again starts with fresh data and credentials. Staging and canary keep theirs: a persistent staging volume outlives `delete staging`, so delete it by hand with `kubectl delete pvc data-<release>-staging-postgresql-0`. On GitLab, a `CWA_CI_POSTGRES_PERSISTENCE` scoped to `production` reaches staging and canary too.

On GitLab, a `POSTGRES_*` variable with the **All** environment scope also reaches the `functional tests` job, where it replaces the job's own `runner`/`password`/`test`, for both the test database and its URL. Scope these variables to your deploy environments. On GitHub, the deploy jobs don't map them from secrets, so set them as Actions variables; the test job sets its own and ignores them.

The php pod and the Nuxt pod scale separately. The `AUTOSCALE_*` variables control php and the `PWA_*` variables control Nuxt.

| `CWA_CI_API_AUTOSCALE_MAX` | `1` |
| `CWA_CI_API_AUTOSCALE_CPU_PERCENT` | `90` |
| `CWA_CI_API_AUTOSCALE_MEMORY_PERCENT` | `90` |

| `CWA_CI_API_MEMORY_REQUEST` | `350Mi` for production and canary, `256Mi` otherwise |

| `CWA_CI_API_GOMEMLIMIT` | empty: what the php memory budget leaves of `CWA_CI_API_MEMORY_LIMIT`, at least `64MiB`, when the limit is in `Mi` or `Gi`. A Go value such as `800MiB` overrides it, and `off` leaves `GOMEMLIMIT` unset. Helm value `php.goMemLimit` |

`CWA_CI_API_AUTOSCALE_MAX` is `1` on purpose. The php pod keeps its cache and its Mercure data in memory, so a second pod would not see purges made by the first. See [Kubernetes → Autoscaling](/deployment/kubernetes#autoscaling).

#### php memory budget

*Since template 2.0.0-alpha.20 · [upgrade notes](/deployment/upgrading-the-template#_200-alpha20)*

These size the php container's memory, as the chart values `php.workers`, `php.memoryLimit`, `php.imagineMemoryLimit` and `php.reservedMemory` ([#136](https://github.com/components-web-app/components-web-app/issues/136), [`1868035`](https://github.com/components-web-app/components-web-app/commit/1868035b41a4edd48d42b84c2de736026c8f5ce6)):

| Variable | Default | Notes |
|----------|---------|-------|
| `CWA_CI_API_WORKERS` | `4` | FrankenPHP's worker threads (`FRANKENPHP_WORKER_NUM`) |
| `CWA_CI_API_PHP_MEMORY_LIMIT` | `128Mi` | Each request's PHP `memory_limit` (`FRANKENPHP_MEMORY_LIMIT`, as `128M`) |
| `CWA_CI_API_IMAGINE_MEMORY_LIMIT` | `320Mi` | The limit the bundle raises a request to while it generates an imagine filter. Keep it equal to the bundle's `imagine.memory_limit`, whose default is `320M` |
| `CWA_CI_API_RESERVED_MEMORY` | `160Mi` | opcache, APCu, the binaries and a console command run in the pod |

The budget is:

```
workers × PHP memory limit + (imagine limit − PHP memory limit) + reserved + Go ≤ CWA_CI_API_MEMORY_LIMIT
```

Go (Caddy, Souin and Mercure) gets what is left, as `GOMEMLIMIT`: with the defaults, 4 × 128 + 192 + 160 = 864Mi, which leaves Go 160Mi of 1Gi. The imagine limit counts once: the budget allows for one request generating a filter at a time.

**The deploy fails before it changes anything in the cluster** when the budget leaves Go under 64Mi, or when a value isn't a whole number or an `Mi`/`Gi` quantity. The log shows the sum and what to change. With a `CWA_CI_API_MEMORY_LIMIT` in another form, such as `1G`, the check is skipped and `GOMEMLIMIT` is left unset unless `CWA_CI_API_GOMEMLIMIT` sets it. So when you raise the workers or the PHP memory limit, raise `CWA_CI_API_MEMORY_LIMIT` too.

Console commands, such as the orphan scan or a `kubectl exec` into the pod, don't use `FRANKENPHP_MEMORY_LIMIT`. They run at the `memory_limit` of `256M` in `api/frankenphp/conf.d/10-app.ini`.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**Set the worker count with `CWA_CI_API_WORKERS`, not `CWA_API_FRANKENPHP_WORKER_NUM`.** `FRANKENPHP_WORKER_NUM` and `FRANKENPHP_MEMORY_LIMIT` are [reserved names](#reserved-names), so the deploy refuses them as site settings.
::

The template's `Image` entity accepts uploads up to 30 megapixels: what the 320M imagine limit can thumbnail with the template's libvips driver. If you switch the driver back to GD, lower it to 20 megapixels. See [Uploadable](/api/components/annotations/uploadable).

| `CWA_CI_PWA_AUTOSCALE_MEMORY_PERCENT` | unset (no memory target) |
| `CWA_CI_PWA_CPU_REQUEST` / `CWA_CI_PWA_CPU_LIMIT` | `100m` on every track / `1000m` |
| `CWA_CI_PWA_MEMORY_REQUEST` / `CWA_CI_PWA_MEMORY_LIMIT` | `160Mi` for production and canary, `128Mi` otherwise / `1Gi` |

**Change `CWA_CI_PWA_CPU_REQUEST` and `CWA_CI_PWA_AUTOSCALE_CPU_PERCENT` together.** The target is a percentage of the request, and request × target should stay near 175m, about one render a second. See [Kubernetes → Nuxt scales out](/deployment/kubernetes#nuxt-scales-out).

The minimums, maximums and memory requests depend on the environment, so review apps and staging don't reserve as much as production. Limits are the same everywhere.

The Nuxt HPA scales on CPU only. Server rendering is CPU-bound, and an extra pod doesn't relieve memory, because each pod keeps its own caches. Node also rarely hands memory back, and an HPA only scales down when every metric is under its target, so a memory target would add pods under normal load and then keep them. Set `CWA_CI_PWA_AUTOSCALE_MEMORY_PERCENT` if you want one anyway. If you set a variable, your value is used in every environment.

### Orphan Scan

The [daily orphan scan](/deployment/kubernetes#daily-orphan-scan) is a CronJob that runs `scan-orphaned` and emails `MAILER_EMAIL` when the orphans change.

| Variable | Default | Notes |
|----------|---------|-------|
| `CWA_CI_ORPHAN_SCAN` | `"true"` for production, `"false"` otherwise | `"true"` or `"false"`. Your value is used on every track |
| `CWA_CI_ORPHAN_SCAN_SCHEDULE` | `0 3 * * *` | Cron schedule |
| `CWA_CI_ORPHAN_SCAN_TIMEZONE` | `Europe/London` | Time zone for the schedule. Needs Kubernetes 1.27+; older clusters use UTC |

Staging and canary are off by default because they can share production's database, so their scans would repeat production's alert. Review apps are short-lived.

The email goes to `MAILER_EMAIL`, the same address the site sends from (`orphaned_resources.notify.recipients` in `api/config/packages/silverback_api_components.yaml`). Both a bare address and the `Name <address>` form work; see [Emailing when orphans change](/api/console-commands#emailing-when-orphans-change).

An empty `MAILER_EMAIL` means no email. An unset `MAILER_DSN` renders as `null://null`, so nothing is sent. The GitHub deploy jobs pass `MAILER_DSN` (a secret), `MAILER_EMAIL` and the `CWA_CI_ORPHAN_SCAN*` variables.

### Origin Protection

These protect php and Nuxt from requests that get past the cache. Every one is optional: leave it unset, or empty, and the default in `api/frankenphp/Caddyfile` or `worker.Caddyfile` applies. On GitHub, set them as Actions variables and they reach the deploy without a workflow change.

The Caddy settings are [site settings](#site-settings): set `CWA_API_<NAME>` in CI and the php container gets `<NAME>`, so `CWA_API_RATE_LIMIT_EVENTS` arrives as `RATE_LIMIT_EVENTS`. The local compose stack uses the bare names. The `CWA_CI_INGRESS_*` ones are deploy switches, which the deploy turns into ingress annotations.

| Variable | Default | Notes |
|----------|---------|-------|
| `CWA_API_CACHE_QUERY_ALLOWLIST` | `page search order` | Query parameters that pages keep, space-separated. A name also keeps `name[...]`. Add your pages' own parameters, but never `cwa_force`. `*` turns it off. See [Query parameters on pages](/nuxt-module/page-caching#query-parameters-on-pages) |
| `CWA_API_RATE_LIMIT_ENABLED` | `true` | `false` turns off the per-visitor limit on cache misses |
| `CWA_API_RATE_LIMIT_EVENTS` | `3000` | Requests per window per visitor. Cache hits, `/_nuxt`, Mercure and private addresses aren't counted |
| `CWA_API_RATE_LIMIT_WINDOW` | `1m` | Window length, as a Go duration such as `10s` |
| `CWA_API_CADDY_TRUSTED_PROXIES` | `private_ranges` | Proxies whose `X-Forwarded-For` is believed. Add a public proxy's ranges, e.g. a Google load balancer: `private_ranges 35.191.0.0/16 130.211.0.0/22` |
| `CWA_API_CLOUDFLARE_IP_RANGES` | Cloudflare's published ranges | Only requests from these addresses are counted by `CF-Connecting-IP`. Update it if Cloudflare changes [its ranges](https://www.cloudflare.com/ips/) before a template release does |
| `CWA_API_FRANKENPHP_MAX_WAIT_TIME` | `5s` | A request that waits this long for a free php worker gets a `503` at once instead of queueing into a `504`. `0` turns it off. See [Kubernetes → Load shedding](/deployment/kubernetes#load-shedding) |
| `CWA_CI_INGRESS_RATE_LIMIT_RPS` | unset (off) | ingress-nginx `limit-rps`. See [Kubernetes → Ingress rate limits](/deployment/kubernetes#ingress-rate-limits) before you set it |
| `CWA_CI_INGRESS_RATE_LIMIT_BURST_MULTIPLIER` | unset (nginx's default, 5) | ingress-nginx `limit-burst-multiplier`. Used only with `CWA_CI_INGRESS_RATE_LIMIT_RPS` |
| `CWA_CI_INGRESS_RATE_LIMIT_CONNECTIONS` | unset | ingress-nginx `limit-connections`. Used only with `CWA_CI_INGRESS_RATE_LIMIT_RPS` |

See [Rate limit on cache misses](/nuxt-module/page-caching#rate-limit-on-cache-misses) for what is counted and how the visitor's address is found.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**The per-visitor rate limit needs the cluster's ingress controller to keep the client address.** Set `externalTrafficPolicy: Local` on the ingress controller's own Service, ideally with 2 replicas and a PodDisruptionBudget, as the template's own cluster runs it. With the default `Cluster`, every request seems to come from a node's private address, so every visitor looks internal and the limit never applies ([#135](https://github.com/components-web-app/components-web-app/issues/135)). Check `visitor_ip` in php's access log. See [Kubernetes → Ingress rate limits](/deployment/kubernetes#ingress-rate-limits).
::

::callout{icon="i-heroicons-information-circle"}
`CADDY_EDGE` isn't a deploy variable. Only `compose.prod.yaml` sets it, and the chart doesn't pass it, so on Kubernetes it stays `false`. That's right there, because Caddy sits behind the ingress.
::

### CDN Purging

Only needed when a CDN caches your pages. See [Cloudflare](/deployment/cloudflare#purges-must-reach-cloudflare).

| Variable | Default | Notes |
|----------|---------|-------|
| `CADDY_CACHE_CDN_CONFIG` | `strategy hard` | Souin's `cdn` block, one setting per line. Leave it unset without a CDN. Setting it replaces the default, so repeat `strategy hard`. For Cloudflare: `strategy hard`, `provider cloudflare`, `zone_id <zone ID>` and `api_key $CLOUDFLARE_API_TOKEN`, with no `email` line. It is stored in the release's Secret |
| `CLOUDFLARE_API_TOKEN` | — | GitLab only, and a name you choose: a masked variable holding a Cloudflare API token scoped to Zone → Cache Purge for the site's zone. `CADDY_CACHE_CDN_CONFIG` refers to it, so turn on **Expand variable reference** for that variable. | `CWA_API_CLOUDFLARE_PURGE_PLAN` | `free` | Cloudflare only. `free`, `pro`, `business` or `enterprise`: paces purges to that plan's limit. See [Queued and paced purges](/deployment/cloudflare#queued-and-paced-purges) |
| `CWA_API_CLOUDFLARE_PURGE_REQUESTS` | from the plan | Purge requests per `CWA_API_CLOUDFLARE_PURGE_WINDOW`. Set it lower when staging and production, or several sites, share a Cloudflare account |
| `CWA_API_CLOUDFLARE_PURGE_WINDOW` | from the plan | A Go duration, such as `1m` or `1s` |

The `CWA_API_CLOUDFLARE_PURGE_*` settings reach php as `CLOUDFLARE_PURGE_*`, like any [site setting](#site-settings). `CADDY_CACHE_CDN_CONFIG` keeps its own name, because the deploy checks it before anything changes.

On GitHub, a variable can't refer to another one. Put the token directly in `CADDY_CACHE_CDN_CONFIG`, store that as a secret, and map it in the deploy jobs' `env:`, because the template's workflows don't map it.

On GitLab, scope both variables to `production`, and protect the token only if the deploy branch is protected: see [Cloudflare → Secrets](/deployment/cloudflare#secrets). A deploy fails before rolling anything out if a `cdn` setting has no value or an unexpanded `$NAME`.

### Pipeline Flags

| Variable | Default | Effect |
|----------|---------|--------|
| `CWA_CI_BUILD_DISABLED` | `false` | Skip the build stage entirely |
| `CWA_CI_TEST_DISABLED` | `false` | Skip the test stage |
| `CWA_CI_STAGING_ENABLED` | `true` | Auto-deploy staging on merge to main |
| `CWA_CI_CANARY_ENABLED` | `true` | Show the canary job |
| `CWA_CI_REVIEW_DISABLED` | — | Set `"true"` to disable review apps on branches |
| `CWA_CI_PRODUCTION_DISABLED` | — | GitLab only. Set `"true"` to remove the production job, with its fixture, cache warm and performance audit jobs |
| `CWA_CI_DISABLED` | — | GitHub only. Set `"true"` to stop the workflows running at all (see [GitHub Actions](#github-actions)) |
| `CWA_CI_FIXTURES_ENABLED` | `false` | Set `"true"` to load fixtures after deploying: a manual job on GitLab, an automatic step on GitHub |
| `CWA_CI_FIXTURES_PURGE` | `false` | Makes the fixture job empty the database before loading. Review apps: `"true"` or `"force"`. Production: only `"force"` |
| `CWA_CI_RESET_DATABASE` | `false` | Set `"true"` to make the php pod drop the whole schema before it runs migrations, every time it starts. Never leave it on |
| `CWA_CI_HELM_UNINSTALL` | — | Any value uninstalls the release before the deploy installs it again |
| `CWA_CI_TRACE` | — | Any value makes `setup.sh` print each command it runs (`set -x`) |

Fixtures seed a new environment: the scaffold pages and the first admin user. They are off unless `CWA_CI_FIXTURES_ENABLED` is `"true"`.

- **GitLab:** a **load fixtures** job appears for review apps and for production, after the deploy job. It never runs automatically; trigger it from the pipeline UI. With `CWA_CI_PRODUCTION_DISABLED="true"`, there is no production fixture job, because the job it waits for doesn't exist.
- **GitHub Actions:** a **Load fixtures** step runs after each review deploy, and after a manual production run, while the variable is `"true"`. GitHub has no manual jobs inside a push-triggered workflow, so set the variable for a new environment's first deploy, then remove it.

Staging has no fixture job on either. It runs under the production environment, so with an external database (`DATABASE_URL`) it uses production's database, and a fixture load there would write to production.

By default `load_fixtures` runs `doctrine:fixtures:load --append`, so it never deletes existing content. The admin user fixture can be run any number of times. On a database that already has content, appending creates only what is missing and keeps existing content. See [Appending to an Existing Site](/api/data-fixtures#appending-to-an-existing-site).

After a successful load, `load_fixtures` flushes the whole HTTP cache (`silverback:api-components:purge-http-cache`), API responses and pages alike. The load changes the database underneath what Souin has cached since the deploy, and nothing else would purge it, so production could otherwise serve the old content for up to a year.

#### Purging before a load

`CWA_CI_FIXTURES_PURGE` is for an early project whose database should be rebuilt from a changed scaffold. It runs `doctrine:fixtures:load` without `--append`, which **empties every table** first.

| Track | Purges with | Otherwise |
|-------|-------------|-----------|
| Review apps | `"true"` or `"force"` | Appends |
| Production | `"force"` only | `"true"` prints a notice and appends, so a project-wide `"true"` meant for review apps can't empty production |

Only the fixture job reads it. A deploy or a pod restart never purges.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
On GitHub the fixture step runs after every deploy while `CWA_CI_FIXTURES_ENABLED` is set. With `CWA_CI_FIXTURES_PURGE` set too, **every** review deploy empties the review database, and every manual production run with `"force"` empties production. Unset `CWA_CI_FIXTURES_PURGE` once the database has been rebuilt. Add `CWA_CI_FIXTURES_PURGE` to repository variables, not secrets: the workflows read `vars.CWA_CI_FIXTURES_PURGE`.
::

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
Before the template fixed this (components-web-app#74), the GitHub workflows loaded fixtures on **every** deploy, including production. `load_fixtures` ran without `--append`, which empties the database first. If your project was generated from an earlier version and deploys with GitHub Actions, check `.github/workflows/*.yml` and `bin/devops/k8s.sh` for this before your next production deploy.
::

On GitHub, staging also only runs when the `CWA_CI_STAGING_ENABLED` variable is set to `true`. `ci.yml` has no default for it.

## Site settings

A site's own settings, such as an analytics ID for Nuxt or an API key for a Symfony service, are CI variables. The Kubernetes deploy passes them to the containers by their prefix, so adding one needs no change to `k8s.sh`, the chart or a workflow ([#125](https://github.com/components-web-app/components-web-app/issues/125), [`497e8ac`](https://github.com/components-web-app/components-web-app/commit/497e8ac74cf3ba8b066982df0192bff238abd906), [`75a416b`](https://github.com/components-web-app/components-web-app/commit/75a416bc14edcdd601918bf44fa291f391abcbcf)).

| CI variable | Reaches | As | Stored in |
|-------------|---------|----|-----------|
| `NUXT_PUBLIC_<NAME>` | The Nuxt pods | `NUXT_PUBLIC_<NAME>`, unchanged | The ConfigMap `<fullname>-pwa-env` |
| Any other `NUXT_<NAME>` | The Nuxt pods | `NUXT_<NAME>`, unchanged | The Secret `<fullname>-pwa-env` |
| `CWA_API_<NAME>` | The php pod and the orphan scan CronJob | `<NAME>`, without the prefix | The Secret `<fullname>-api-env` |

The chart adds them to the containers with `envFrom`. The API's settings need the `CWA_API_` prefix because its own names, such as `DATABASE_URL` or `APP_SECRET`, are too generic to pass through whole.

**An empty `CWA_API_` value is left out**, and the log says so (`api: <NAME> left unset, CWA_API_<NAME> is empty`). An empty variable would replace the Caddyfile's `{$NAME:default}` and Symfony's defaults, so leaving it out keeps them. An empty `NUXT_*` value is still delivered, because Nuxt applies an empty value on purpose.

### The API's optional settings

The template's own optional API settings go through the same passthrough. Set them as `CWA_API_<NAME>` in CI; the local compose stack uses the bare `<NAME>`. Unset, the default in the Caddyfile or in Symfony applies ([`d64c278`](https://github.com/components-web-app/components-web-app/commit/d64c278997770b07fb0c2d04ed2fa7383059ab03)).

| CI variable | What it sets |
|-------------|--------------|
| `CWA_API_CACHE_QUERY_ALLOWLIST`, `CWA_API_RATE_LIMIT_ENABLED`, `CWA_API_RATE_LIMIT_EVENTS`, `CWA_API_RATE_LIMIT_WINDOW`, `CWA_API_CADDY_TRUSTED_PROXIES`, `CWA_API_CLOUDFLARE_IP_RANGES`, `CWA_API_FRANKENPHP_MAX_WAIT_TIME` | Origin protection. See [Origin Protection](#origin-protection) |
| `CWA_API_CLOUDFLARE_PURGE_PLAN`, `_REQUESTS`, `_WINDOW`, `_BURST` | Cloudflare purge pacing. See [CDN Purging](#cdn-purging) |
| `CWA_API_CADDY_GLOBAL_CONFIG` | Extra lines for the Caddyfile's global options block, such as `debug` |
| `CWA_API_JWT_COOKIE_SAMESITE` | The `SameSite` attribute of the session, JWT and refresh token cookies. Default `lax` |
| `CWA_API_MERCURE_JWT_ALGORITHM` | The algorithm Symfony signs Mercure tokens with. Default `hmac.sha256` |
| `CWA_API_WEBSITE_NAME` | The site's name in emails (the bundle's `website_name`). Default `New Website`, from `api/.env`. A multi-site project can export it per site from [`project.sh`](#project-hooks) ([`c1a3201`](https://github.com/components-web-app/components-web-app/commit/c1a3201e24378ef54e7bd64393110bb6b1a0cfce)) |

Their bare CI names, such as `RATE_LIMIT_EVENTS` or `CLOUDFLARE_PURGE_PLAN`, are no longer read by the deploy.

Each side reads them as it reads any environment variable:

- **Nuxt** uses a `NUXT_*` variable only for a key you declare in `runtimeConfig` in `app/nuxt.config.ts`. `NUXT_PUBLIC_ANALYTICS_ID` sets `runtimeConfig.public.analyticsId`, and `NUXT_MAPS_KEY` sets the server-only `runtimeConfig.mapsKey`.
- **Symfony** reads `CWA_API_MAPS_KEY` as `MAPS_KEY`, through `'%env(MAPS_KEY)%'`. Give it a default in `api/.env` so the local stack still boots.

```ts
// app/nuxt.config.ts
export default defineNuxtConfig({
    runtimeConfig: {
        mapsKey: '',          // NUXT_MAPS_KEY, server only
        public: {
            analyticsId: '',  // NUXT_PUBLIC_ANALYTICS_ID, sent to browsers
        },
    },
})
```

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**`NUXT_PUBLIC_*` values aren't secret.** Nuxt sends public runtime config to every browser, in the page HTML. Put keys and tokens in a `NUXT_*` name without `PUBLIC_`, which stays on the server.
::

::callout{icon="i-heroicons-information-circle"}
**Site settings are runtime only, never build args.** The values reach the containers when they start. The image builds get only what `build_api` and `build_app` name, so one image serves every environment. Don't add a `--build-arg` or build secret for a site setting, and don't read one in a Dockerfile: read it at runtime, through `runtimeConfig` in Nuxt or `%env()%` in Symfony.
::

On GitLab, every CI variable already reaches the deploy job. Remember that staging runs under `environment: production`, so a setting scoped to `production` reaches staging too. Use [the environment name](#the-environment-name) where the two must behave differently.

The deploy log prints `Environment name: <name>` and one line for each setting, such as `pwa config NUXT_PUBLIC_ANALYTICS_ID (from NUXT_PUBLIC_ANALYTICS_ID)` or `api secret MAPS_KEY (from CWA_API_MAPS_KEY)`. It never prints a value.

### Reserved names

The deploy fails, before it changes anything in the cluster, when a site setting uses a name the chart or its image already sets on that container. The chart's own `env:` entry would win over `envFrom`, so the value would be ignored without a word. It also fails on a name that isn't usable, such as `CWA_API_` with nothing after it, or a `<NAME>` that starts with a digit. The log lists every problem:

```
❌ Site environment variables (NUXT_*, CWA_API_*) that can't be passed through:
  CWA_API_DATABASE_URL: DATABASE_URL is reserved on the api container: the chart or its image sets it (use its own CI variable, if it has one, or delete this one)
```

Reserved on the Nuxt container (`SITE_ENV_RESERVED_PWA` in `k8s.sh`):

`NUXT_CWA_API_URL`, `NUXT_PUBLIC_CWA_API_URL`, `NUXT_PUBLIC_CWA_API_URL_BROWSER`, `NUXT_SITE_URL` and `NUXT_PUBLIC_CWA_ENVIRONMENT`. The deploy sets `NUXT_SITE_URL` to `https://$DOMAIN`, so cached pages' canonical URL and `og:url` use the site's own host, not whichever host rendered the page. A multi-site project gives each site its host through `DOMAIN` ([#140](https://github.com/components-web-app/components-web-app/issues/140), [`45a3794`](https://github.com/components-web-app/components-web-app/commit/45a379404852fc164b15f706d0aac3479c61b6ab)). The chart sets the API URLs itself (see [Kubernetes → `apiUrl` should stay unset](/deployment/kubernetes#apiurl-should-stay-unset)). `NUXT_PUBLIC_CWA_API_URL` is the deprecated name of `NUXT_CWA_API_URL`, and as public config it would put the internal API URL in every page.

Reserved on the php container (`SITE_ENV_RESERVED_API`), as the `<NAME>` in `CWA_API_<NAME>`:

`ADMIN_EMAIL`, `ADMIN_PASSWORD`, `ADMIN_USERNAME`, `APP_DEBUG`, `APP_ENV`, `APP_SECRET`, `APP_UPSTREAM`, `BROWSER_SERVER_NAME`, `CACHE_URL`, `CADDY_CACHE_CDN_CONFIG`, `CADDY_CACHE_EXTRA_CONFIG`, `CORS_ALLOW_ORIGIN`, `CWA_ENVIRONMENT`, `DATABASE_CA_CERT`, `DATABASE_CLIENT_CERT`, `DATABASE_CLIENT_KEY`, `DATABASE_SSL_MODE`, `DATABASE_URL`, `FRANKENPHP_CONFIG`, `FRANKENPHP_MEMORY_LIMIT`, `FRANKENPHP_WORKER_NUM`, `GCLOUD_BUCKET`, `GCLOUD_JSON`, `GCLOUD_PUBLIC_URL`, `GOMEMLIMIT`, `JWT_PASSPHRASE`, `JWT_PUBLIC_KEY`, `JWT_SECRET_KEY`, `MAILER_DSN`, `MAILER_EMAIL`, `MERCURE_CORS_ORIGIN`, `MERCURE_EXTRA_DIRECTIVES`, `MERCURE_JWT_SECRET`, `MERCURE_PUBLIC_URL`, `MERCURE_PUBLISHER_JWT_ALG`, `MERCURE_PUBLISHER_JWT_KEY`, `MERCURE_SUBSCRIBER_JWT_ALG`, `MERCURE_SUBSCRIBER_JWT_KEY`, `MERCURE_URL`, `RESET_DATABASE`, `SERVER_NAME`, `TRUSTED_HOSTS` and `TRUSTED_PROXIES`.

Most of these have their own CI variable, such as `MAILER_DSN` or `CORS_ALLOW_ORIGIN` (or `CWA_CI_API_GOMEMLIMIT` for `GOMEMLIMIT`, `CWA_CI_API_WORKERS` for `FRANKENPHP_WORKER_NUM`, `CWA_CI_API_PHP_MEMORY_LIMIT` for `FRANKENPHP_MEMORY_LIMIT`, and `CWA_CI_RESET_DATABASE` for `RESET_DATABASE`), so set that one instead.

If your own chart values add `env:` entries to a container, reserve their names too, without editing `k8s.sh`: set `SITE_ENV_RESERVED_API_EXTRA` or `SITE_ENV_RESERVED_PWA_EXTRA` to a space-separated list in [`project.sh`](#project-hooks) or as a CI variable ([#133](https://github.com/components-web-app/components-web-app/issues/133)).

```sh [bin/devops/project.sh]
export SITE_ENV_RESERVED_API_EXTRA="MAPS_REGION"
```

### On GitHub

Variables named `NUXT_*` or `CWA_API_*` reach the deploy through `github-export-vars.sh`, like every other variable. GitHub can't list secrets, so each deploy job (review, staging, canary and production) also runs `bin/devops/github-export-secrets.sh`, in the step *Expose NUXT_\* and CWA_API_\* secrets to the deploy*. It receives every secret and exports only the `NUXT_*` and `CWA_API_*` ones to the later steps, masked, including each line of a multi-line value. It runs after the kubectl and Helm setup actions, so those never see the values, and no build job runs it. So a site secret needs no workflow edit: add it under **Settings → Secrets and variables → Actions → Secrets**.

The step adds a warning to the run in two cases:

- **Public value stored as a secret:** a `NUXT_PUBLIC_*` secret. It is still exported, but browsers receive it, so make it a variable.
- **Secret shadowed:** a variable, or the job's `env:`, already sets the name, so the secret isn't used. Delete one of the two.

### The environment name

The deploy names the environment it serves, from its track, and sets it as `CWA_ENVIRONMENT` on the php pod and the orphan scan, and as `NUXT_PUBLIC_CWA_ENVIRONMENT` on the Nuxt pods:

| Track | Name |
|-------|------|
| Production | `production` |
| Staging | `staging` |
| Canary | `canary` |
| Review apps | `review` |

So staging is told apart from production, although its GitLab job runs as `environment: production`. A `CWA_ENVIRONMENT` CI variable replaces the name on every track it reaches; on GitLab, a value scoped to `production` reaches staging and canary too. It may hold only letters, digits, `.`, `_` and `-`, or the deploy fails with `CWA_ENVIRONMENT must be letters, digits, '.', '_' or '-', not '<value>'.`

Nuxt sees the name only once you declare it, as `runtimeConfig.public.cwaEnvironment`. Symfony reads it with `'%env(CWA_ENVIRONMENT)%'`; give it a default in `api/.env` for the local stack.

## Changing a live site's hostnames

Production's certificate covers its main hostname and every entry in `KUBE_INGRESS_ALIAS_DOMAINS`. You change that list when you launch a site, add `www`, or retire the preview hostname. To do it, edit the variables and deploy:

- **Add a hostname:** add it to `KUBE_INGRESS_ALIAS_DOMAINS`.
- **Retire a hostname**, such as the preview host: remove it from `KUBE_INGRESS_ALIAS_DOMAINS`. It then goes offline. The template has no redirect feature, by design.
- **Change the main hostname at launch**, for example `new.example.org` → `example.org`: the main hostname is the production environment URL, `https://$KUBE_INGRESS_BASE_DOMAIN`, so change `KUBE_INGRESS_BASE_DOMAIN` (or the `DOMAIN` your [`project.sh`](#project-hooks) sets). Staging and review apps are subdomains of it, so they move too. Keep the old host in `KUBE_INGRESS_ALIAS_DOMAINS` if it should still work.

When the list differs from the live certificate's, the deploy creates a new cert-manager `Certificate` for the new list. It waits until the certificate is issued, for up to `CWA_CI_TLS_CERTIFICATE_TIMEOUT` (default `600s`), and only then runs Helm. The ingress moves from one valid certificate to another, with no downtime. When the list is unchanged, which is almost every deploy, the deploy keeps the live certificate and nothing is reissued. The order and case of the hostnames don't matter.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**Point a new hostname's DNS at the cluster's ingress before you deploy.** Let's Encrypt's HTTP-01 challenge must reach it. If it can't, the certificate isn't issued and **the deploy fails before anything changes**. The live site keeps its current certificate, and the log lists the hostnames to check. Fix the DNS and run the deploy again.
::

::callout{icon="i-heroicons-light-bulb"}
**Why the certificate is issued first.** If the names on the live certificate change in place, cert-manager serves a temporary self-signed certificate while it gets the new one. That takes minutes, or up to an hour of back-off if a challenge fails. With HSTS, browsers refuse the connection outright, on every hostname, including the live one. Let's Encrypt also allows only 5 certificates for the same set of names per week, so don't switch the list back and forth.
::

Some details:

- The deploy compares against the certificate on the chart's own ingress, which it finds by the release name. This is why changing the main hostname at launch is still safe.
- Other ingresses in the namespace are ignored, even with the same chart labels. For example, a redirect ingress you added by hand for a retired hostname keeps its own certificate. The deploy doesn't compare against it or remove it.
- New certificates are named `<CWA_CI_TLS_SECRET_NAME>-stable-api-<hash>`, from a hash of the hostname list. After a successful deploy, older ones created this way are deleted, with their secrets. The one just replaced is kept, so a rollback still has a valid certificate. You don't change `CWA_CI_TLS_SECRET_NAME` by hand.
- Only production (the stable track) is covered. Review, staging and canary each serve one hostname that doesn't change. The first deploy of a release issues its certificate directly, because nothing is live yet.

### Permissions

The CI service account needs access to `certificates.cert-manager.io` in the namespace. The deploy creates, patches, gets, watches, lists and deletes Certificates, and deletes the secrets of the ones it removes. It checks only `create` up front. Without it, the deploy prints a warning and falls back to changing the live certificate in place, which causes the downtime described above.

With `CWA_CI_INGRESS_ENABLED` set to `"false"` there is no ingress, so none of this runs. Nor does it with an empty `CWA_CI_CLUSTER_ISSUER`.

### Changing hostnames by hand

Use this if the CI account can't manage Certificates, or your pipeline doesn't have `ensure_tls_certificate`.

1. Choose a new value for `CWA_CI_TLS_SECRET_NAME`, for example `letsencrypt-cert-2`. The production ingress uses the secret `<CWA_CI_TLS_SECRET_NAME>-stable-api`.
2. Apply a `Certificate` that writes that secret and covers the new hostnames:

    ```yaml
    apiVersion: cert-manager.io/v1
    kind: Certificate
    metadata:
      name: letsencrypt-cert-2-stable-api
    spec:
      secretName: letsencrypt-cert-2-stable-api
      issuerRef:
        group: cert-manager.io
        kind: ClusterIssuer
        name: letsencrypt-prod # your CWA_CI_CLUSTER_ISSUER
      dnsNames:
        - example.org
        - www.example.org
    ```

3. Wait until it is ready: `kubectl wait --for=condition=Ready certificate/letsencrypt-cert-2-stable-api -n <namespace> --timeout=600s`.
4. Set `CWA_CI_TLS_SECRET_NAME` to the new value, update the hostname variables, and deploy.
5. Keep the old Certificate and secret until the site works on the new one. Then delete them.

## Rollback

```bash
# List Helm history
helm history cwa --namespace production

# Roll back to a specific revision
helm rollback cwa 3 --namespace production

# Roll back to the previous release
helm rollback cwa --namespace production
```

Helm's rollback restores the previous release's values, image tag included. The template's pipeline tags images with the branch slug (`$CI_COMMIT_REF_SLUG`, so `main` for production), not the commit SHA, and deploys with `pullPolicy: Always`. The previous release therefore points at the same tag, and a rollback pulls whatever image that tag currently holds. To roll the code back as well, tag images with the commit SHA (`CI_APPLICATION_TAG` in `setup.sh`) and deploy that tag.
