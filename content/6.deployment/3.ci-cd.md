The template ships complete CI/CD for **both GitLab CI and GitHub Actions**. Every step delegates to shell functions in `bin/devops/` — readable, modifiable scripts you own.

Choose your CI/CD provider when you run `pnpm create cwa` — the CLI wires up the correct pipeline files automatically. You can switch later by copying the relevant files from the template.

## GitHub Actions

Three workflows drive your app, in `.github/workflows/`:

| Workflow | Trigger | What it does |
|----------|---------|-------------|
| `ci.yml` | Every push | Build + test; deploy a review environment for non-`main` branches, or staging on `main` |
| `production.yml` | Manual | Deploy canary or full production |
| `cleanup.yml` | PR closed | Tear down the review environment |

The template repo also has `publish-create-cwa.yml`, which publishes the scaffolding CLI. `create-cwa` leaves it out of new projects, and a project that has it can delete it.

Images push to GHCR (`ghcr.io/${{ github.repository }}`). The workflows call the same `bin/devops/` shell functions as GitLab CI. Required secrets and variables are declared in the workflow files themselves, and listed on [CI/CD Variables](/deployment/variables).

On its own, GitHub Actions only gives a job the variables its `env:` block names. The template closes that gap: every job that checks out the repository runs `bin/devops/github-export-vars.sh` straight after the checkout, which exports every GitHub **variable** (repository, organisation and environment) to the job's later steps, as GitLab does. To set a variable from [CI/CD Variables](/deployment/variables), add it under **Settings → Secrets and variables → Actions → Variables**. You don't need to change a workflow.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**Secrets still need an `env:` mapping, except `NUXT_*` and `CWA_API_*` ones.** Secrets aren't in `vars`, so the script can't export them, and mapping them explicitly keeps them masked in logs. A name the job already sets in `env:` is left alone, so the workflow's mapping wins over a variable of the same name. The template's deploy jobs map `KUBE_CONTEXT`, `DATABASE_URL`, `MAILER_DSN`, `GCLOUD_JSON`, `APP_SECRET`, the JWT and Mercure keys and `ADMIN_PASSWORD` from secrets, so set those as secrets: a variable with one of those names is ignored. `KUBECONFIG` and `KUBE_NAMESPACE_PRODUCTION` are secrets too. Secrets named `NUXT_*` or `CWA_API_*` need no mapping: the deploy jobs export them for you (see [Site settings](/deployment/variables#site-settings)).
::

::callout{icon="i-heroicons-information-circle"}
The workflows run on every push by default. Set the GitHub Actions **variable** `CWA_CI_DISABLED=true` (under Settings → Secrets and variables → Actions → Variables) to suppress them. This is used on the template repo itself, which deploys via GitLab CI and only mirrors to GitHub.
::

## GitLab CI

The `.gitlab-ci.yml` has seven stages: build, test, review, staging, canary, production and cleanup. There is no GitLab Auto DevOps magic here.

GitLab runs branch pipelines only. The workflow creates no merge request pipelines, because every job is limited to branches. A merge request shows its branch pipeline's result, so **Pipelines must succeed** works as expected.

## Pipeline Overview

::DiagramCiPipeline
::

On every branch: **build** then **test** then spin up a **review app** on Kubernetes. With [browser tests](/deployment/browser-tests) turned on, they run beside the PHPUnit tests, and every deploy waits for both. When a branch merges to `main`: build and test run again, then the pipeline auto-deploys to **staging**, from where you manually promote through **canary** to **production**.

## Stages

### Build

Two parallel jobs — `build api` and `build app` — each run `docker buildx` and push to the GitLab Container Registry. Layer caching is handled with `--cache-to` / `--cache-from` against a dedicated cache image tag, so incremental builds are fast. The cache is written with `mode=max`, so it keeps every stage, including the app's `pnpm fetch` and base setup, not only the final image's layers. A branch's first build also reads the default branch's cache, so it doesn't start cold.

```
$CI_REGISTRY_IMAGE/php:$CI_COMMIT_REF_SLUG    ← FrankenPHP image (--target frankenphp_prod)
$CI_REGISTRY_IMAGE/app:$CI_COMMIT_REF_SLUG    ← Nuxt image       (--target prod)
```

The PHP image build uses `api/Dockerfile`; the Nuxt image uses `app/Dockerfile`. Build logic lives in `build_api()` and `build_app()` in `bin/devops/k8s.sh`.

Each build pushes only its branch tag, and records the digest it pushed: `CWA_CI_PHP_IMAGE_DIGEST` or `CWA_CI_APP_IMAGE_DIGEST`, in the dotenv artifact `image_digest.env` on GitLab and as a job output on GitHub. The deploys run exactly that build. See [Which build a deploy runs](#which-build-a-deploy-runs).

Composer downloads about 180 packages from github.com per install. Anonymously, GitHub allows 60 requests an hour per IP, so on a shared runner an install can fail part way through with a `429`. Set the optional [`GITHUB_TOKEN`](/deployment/variables#composer) variable to authenticate them. `build_api` passes it to the image build as the `composer_auth` build secret, never a build arg, so the token stays out of the image history. The build log's `github rate limit for this build:` line prints `60` when the token didn't reach the build and `5000` when it did ([!12](https://gitlab.com/silverback-web-apps/cwa/components-web-app/-/merge_requests/12), [`a3c6ef6`](https://github.com/components-web-app/components-web-app/commit/a3c6ef67c79f4c5c43c081a601ebae8c8f806cea)).

### Test

Two parallel jobs against the image built in the previous stage:

| Job | What runs |
|-----|-----------|
| `unit tests` | `vendor/bin/phpunit tests/Unit` — fast, no database. It also runs the template's Souin and Caddy checks: `bin/test/souin-purge-isolation.sh`, `bin/test/souin-flush-storage.sh` (which checks that otter, badger and nuts still cache after a full flush), `bin/test/souin-coalesced-5xx.sh` (which checks that requests Souin coalesces onto an upstream `5xx` all get that `5xx`, not an empty `200`), `bin/test/caddy-validate.sh` (which checks that the Caddyfile loads for both Helm's and compose's `SERVER_NAME`) `bin/test/cache-encoding.sh` (which runs the real Caddyfile and checks that pages are cached compressed, one entry for each normalised `Accept-Encoding`), `bin/test/souin-backend-timeout.sh` (which checks that a 12-second render is served and cached once, not turned into a `504`, and that the store is otter) and `bin/test/storage-prefix-parity.sh` (which checks that the deploy and php tidy [`GCLOUD_PATH_PREFIX`](/deployment/variables#storage-path-prefix) the same way). See [Docker → The HTTP cache in Caddy](/deployment/docker#the-http-cache-in-caddy) |
| `functional tests` | `vendor/bin/phpunit tests/Functional` with a live PostgreSQL service. The tests use API Platform's `ApiTestCase`, and the schema is rebuilt from the entity mapping (Doctrine `SchemaTool`, not migrations) before each test. For a large suite, see [Faster Functional Tests](/deployment/faster-functional-tests) |

Both export JUnit XML for GitLab's test report UI. On GitHub the jobs are `unit-tests` and `functional-tests`.

A third job, `browser tests`, is opt-in. It runs this branch's production images in a throwaway stack and drives the site in Chromium with Playwright. Set `CWA_CI_E2E_ENABLED="true"` to turn it on; every deploy then waits for it. See [Browser Tests](/deployment/browser-tests). *Since template 2.0.0-alpha.34 · [release notes](https://github.com/components-web-app/components-web-app/releases/tag/v2.0.0-alpha.34)*

**Functional tests never send real email.** Every CI variable reaches the test job, and a real environment variable beats `api/.env.test`, so a project's live `MAILER_DSN` would deliver any email a test sends, such as a contact form or a password reset. `run_test_functional` unsets `MAILER_DSN` and `MAILER_EMAIL`, and `api/.env.test` sets `MAILER_DSN=null://null`. Mail is still built, and Symfony's mailer assertions still see it, but nothing is delivered. Keep both: without the `.env.test` line, tests fall back to `api/.env`'s `smtp-relay` host, which CI doesn't have, so a test that sends email errors. The job also generates a test JWT keypair (`lexik:jwt:generate-keypair --skip-if-exists`), so tests that sign in work in CI ([!12](https://gitlab.com/silverback-web-apps/cwa/components-web-app/-/merge_requests/12), [`a3c6ef6`](https://github.com/components-web-app/components-web-app/commit/a3c6ef67c79f4c5c43c081a601ebae8c8f806cea), [`3a6c366`](https://github.com/components-web-app/components-web-app/commit/3a6c3663d4107800631f6ce50ac7755645cac651)).

**The CI JWT keys never reach the tests.** `run_test_functional` also unsets `JWT_SECRET_KEY`, `JWT_PUBLIC_KEY` and `JWT_PASSPHRASE`. In CI these hold the keys' contents for the deploy, while the tests read `api/.env`'s file paths and the keypair the job generates. With the CI values in place, the functional tests failed, and the job log printed the encrypted key ([#130](https://github.com/components-web-app/components-web-app/issues/130), [`c1d2581`](https://github.com/components-web-app/components-web-app/commit/c1d2581a2c1478d618765474b5d5808857b98868)).

Functional tests extend `App\Tests\Functional\FunctionalTestCase`. Its `setUp()` **refuses to run unless the database name contains `test`**, because it drops the schema. Entities a test persists directly need `createdAt` and `modifiedAt` set by hand, since the bundle sets them only on its own write path (see `RoutesTest`).

### Review Apps

A branch (other than `main`) gets a review app, with its own Helm release, **only once someone creates its Kubernetes namespace**. The pipeline never creates namespaces. The URL follows the pattern `https://$CI_COMMIT_REF_SLUG-review.$KUBE_INGRESS_BASE_DOMAIN`.

::callout{icon="i-heroicons-information-circle"}
Namespaces must be **created by hand**, with role bindings for the CI's identity. Letting one project create namespaces and role bindings would give it rights across the whole cluster, so the pipeline's permissions stop at the namespace. See the comment in `ensure_namespace()`.
::

The review job checks for the namespace first (`skip_review_without_namespace`):

| Namespace | GitLab | GitHub Actions |
|-----------|--------|----------------|
| Exists, and the CI can read it | Deploys | Deploys |
| Not found, or the CI is forbidden to read it | The job exits with code `3`, which the job allows, so the pipeline is **orange** ("passed with warnings") | A *No review environment* warning annotation. The deploy, fixtures and cache warm steps are skipped |
| Any other `kubectl` error, such as an unreachable cluster or a bad context | **Red** | **Red** |

The jobs that follow a review (the review fixture load, image variants and warm, performance audit and stop jobs) start with `skip_unless_review_deployed`. When the review job didn't deploy, they exit with code `3` and say why, instead of running against an environment that doesn't exist.

An orange pipeline on a branch just means that branch has no review app. A deploy that really fails is still red. Staging, canary and production don't make this check: a missing namespace there fails the job.

#### Creating a namespace for a branch

1. Find the name. The job log prints it: `No namespace '<name>', so this branch has no review environment to deploy to.` It is `KUBE_NAMESPACE`, which defaults to `<project name>-<environment slug>`. On GitHub that is `<repository name>-review-<branch slug>`. On GitLab the slug is GitLab's `CI_ENVIRONMENT_SLUG` for `review/<branch>`, which GitLab shortens and may give a random suffix, so copy the name from the log.
2. Create the namespace, and bind the identity your CI deploys with to a role in it. For example, with the built-in `edit` role:

   ```sh
   kubectl create namespace <name>
   kubectl create rolebinding ci-deploy --namespace <name> \
     --clusterrole=edit --serviceaccount=<ci-namespace>:<ci-service-account>
   ```

   Which identity and role you need depends on your cluster and on how the CI connects (the GitLab agent, or the `KUBECONFIG` secret on GitHub). Give it the same access as your other environments.
3. Run the review job again.

A namespace that exists without the role bindings still shows orange, because the CI is forbidden to read it.

A review app is stopped by GitLab's **stop review** job, which GitLab runs when the branch is deleted (for example on a merge with *Delete source branch*) and which you can also start from the environment list. On GitHub, the **Cleanup Review** workflow stops it when the pull request closes. Stopping one uninstalls its Helm release and deletes its database volume, but leaves the namespace, so delete the namespace by hand once the branch is gone.

GitLab's **stop review** doesn't check out its branch (`GIT_STRATEGY: none`), because the branch may already be deleted. It fetches `bin/devops` from the default branch instead, so a stop runs the **default branch's** `k8s.sh` and [`project.sh`](#project-hooks), not the branch's own ([#165](https://github.com/components-web-app/components-web-app/issues/165), [`e3286b4`](https://github.com/components-web-app/components-web-app/commit/e3286b4a9f8f2c12faa713c7e595506bfdd66c36)). *Since template 2.0.0-alpha.38 · [release notes](https://github.com/components-web-app/components-web-app/releases/tag/v2.0.0-alpha.38)*

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**Older GitLab projects: copy the `stop review` job from the template's `.gitlab-ci.yml`.** Before template 2.0.0-alpha.38 it checked out the deleted branch and failed in `get_sources` (exit code `128`). The review app, its database volume and its stored files stayed behind, and the environment stuck in *stopping*. For an environment that is already stuck, run `helm uninstall -n <namespace> <release>-review`, delete its PostgreSQL PVC (label `app.kubernetes.io/instance=<release>-review`), then force-stop the environment in GitLab. Its stored files are left to the [lifecycle rule](/deployment/variables#review-app-paths).
::

#### Review app storage

*Since template 2.0.0-alpha.37 · [release notes](https://github.com/components-web-app/components-web-app/releases/tag/v2.0.0-alpha.37)*

A review app stores its uploads under its own path of the bucket, `<GCLOUD_PATH_PREFIX>review/<slug>/` ([Storage path prefix](/deployment/variables#storage-path-prefix)). Stopping it deletes them. Before `helm uninstall`, `delete review` runs the bundle's [`delete-stored-files`](/api/console-commands#delete-stored-files) in the review app's API pod. This happens in GitLab's **stop review** job and in GitHub's **Cleanup Review** workflow, which runs when a pull request closes:

```bash
php bin/console silverback:api-components:delete-stored-files gcloud --all \
  --only-if-value="$GCLOUD_PATH_PREFIX" --matching='~(^|/)review/[^/]+/$~'
```

`--all` empties the filesystem, which is only the pod's prefix. The guard checks the prefix the pod really has, so the delete runs only when it ends in `review/<slug>/`. A review app deployed before template 2.0.0-alpha.37 has no prefix, and there `--all` would empty the bucket, so the command refuses and deletes nothing.

A failure doesn't stop the job. When the pod can't be found, the guard refuses or the delete fails, the job prints a warning that names the app's real path and the lifecycle rule's prefix, and uninstalls the release anyway. With `GCLOUD_PATH_PREFIX=site-a/`:

```
WARNING: could not delete <release>'s stored files under site-a/review/feat-x/; a bucket lifecycle rule on site-a/review/ is the backstop.
```

Add the [lifecycle rule](/deployment/variables#review-app-paths) for that prefix so those files are removed later. The warning names the real path from template 2.0.0-alpha.38 ([#169](https://github.com/components-web-app/components-web-app/issues/169)); before, it always said `review/`.

### Staging

Runs automatically on every merge to `main`, while `CWA_CI_STAGING_ENABLED` is `"true"`. GitLab defaults it to `"true"`; on GitHub, `ci.yml` has no default, so set the variable to turn staging on. Calls `deploy staging` which runs `helm upgrade --install` for a separate `-staging` release. Staging runs under the production environment, so it deploys into production's namespace and gets production's variables.

### Canary

A manual job that runs `deploy canary`. Useful for routing a portion of production traffic to the new image before full rollout. Enable/disable via `$CWA_CI_CANARY_ENABLED`.

Like production, it waits for the builds and tests (see Production below).

### Production

A manual job requiring explicit trigger from GitLab. Calls `deploy` (stable track), then `delete canary` and `delete staging` to clean up the intermediate environments. To undo a release, see [Kubernetes → Rollback](/deployment/kubernetes#rollback).

Production and canary can't start until `build api`, `build app`, `unit tests` and `functional tests` have passed, and `browser tests` and staging too when they are enabled. Each of these `needs` is optional, so `CWA_CI_BUILD_DISABLED` and `CWA_CI_TEST_DISABLED` still work.

### Which build a deploy runs

A deploy never runs the moving branch tag. It pins the image by digest, so every pod started later runs the build that was deployed ([#164](https://github.com/components-web-app/components-web-app/issues/164), [`e5b2a29`](https://github.com/components-web-app/components-web-app/commit/e5b2a291f7702d1723e5891026944c0fc9ee080e)). *Since template 2.0.0-alpha.35 · [release notes](https://github.com/components-web-app/components-web-app/releases/tag/v2.0.0-alpha.35)*

- **Staging, canary and production** copy the pipeline's own build to their track's tag, `:staging`, `:canary` or `:production`, through the registry API. Nothing is pulled or pushed again. Helm then gets `<track tag>@<digest>`, such as `production@sha256:…`, with `pullPolicy: IfNotPresent`.
- **Review apps** stay on their branch tag, pinned the same way: `<branch slug>@<digest>`.
- **With no build digest**, the deploy pins the digest the branch tag has when the deploy runs. That's the case when `CWA_CI_BUILD_DISABLED` skipped the build, and always in GitHub's `production.yml`, which builds nothing, so it deploys whatever `:main` holds at that moment. If the registry can't be reached, the deploy fails before Helm.

Before this, pods ran `:main` with `pullPolicy: Always`. A restart, an eviction, a scale-up, or the nightly [orphan scan](/deployment/kubernetes#daily-orphan-scan), which runs migrations when it starts, pulled whatever `:main` held then. It could run a build that was never deployed against the live database. Now the API and Nuxt pods, the orphan scan and the [image variants Jobs](/deployment/kubernetes#image-variants-jobs) all run the deployed build. A new build changes the pod spec, so it always rolls out.

The registry keeps a fixed set of tags: `main`, `staging`, `canary`, `production`, and one for each review branch. There are no tags per commit. A track's tag is created by its first deploy, and only a deploy moves it. It also keeps the deployed build tagged, so a registry that cleans up untagged images doesn't remove it once `:main` moves on.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**On GitHub, the deploy jobs need `packages: write`** to add the track tag in GHCR. The template's review, staging and production jobs ask for it, with `contents: read`. If you copy only part of a workflow, keep their `permissions` blocks.
::

To go back to an earlier build, see [Kubernetes → Rollback](/deployment/kubernetes#rollback).

## The Devops Scripts

All CI logic lives in two scripts sourced at the top of every job:

### `bin/devops/setup.sh`

Sets shared environment variables:
- `CI_APPLICATION_REPOSITORY` / `CI_APPLICATION_TAG` — image repo and SHA tag
- `PHP_REPOSITORY` / `APP_REPOSITORY` — full image paths
- `PHP_REPOSITORY_CACHE` / `APP_REPOSITORY_CACHE` — layer cache image paths
- `DOMAIN` — the host of `CI_ENVIRONMENT_URL`, unless it's already set by [`bin/devops/project.sh`](#project-hooks) or a CI variable. With neither, it's empty, and `check_kube_domain` fails the job. There's no fallback host
- `CWA_CI_DEPLOYMENT_BRANCH` — defaults to `main`
- `COMPOSER_AUTH` — built from [`GITHUB_TOKEN`](/deployment/variables#composer) when it's set, and left unset otherwise
- `COMPOSER_MAX_PARALLEL_HTTP=6` — half composer's default of 12, which is a big enough burst to be throttled even when authenticated
- `KUBERNETES_VERSION` / `HELM_VERSION` — the kubectl and Helm versions `install_dependencies` installs, `1.31.0` and `3.19.0` unless a CI variable sets them (see [CI/CD Variables → Kubernetes and hostnames](/deployment/variables#kubernetes-and-hostnames))

### `bin/devops/k8s.sh`

Contains all the functions the pipeline calls:

| Function | What it does |
|----------|-------------|
| `install_dependencies` | Installs Helm, kubectl, curl, and other tools on the Alpine CI runner |
| `setup_docker_environment` | Handles Docker-in-Docker host config for Kubernetes runners |
| `build_api` / `build_app` | `docker buildx build --push` with registry layer caching. `build_api` passes `COMPOSER_AUTH` as the `composer_auth` build secret. Both then call `save_image_digest`, which records the pushed digest for the deploys |
| `run_test_phpunit` | Runs PHPUnit unit tests; outputs JUnit XML |
| `run_test_functional` | Runs `phpunit tests/Functional` against the job's own database (set up by `setup_test_db_environment`); outputs JUnit XML to `api/build/logs/phpunit/functional.xml`. Unsets `MAILER_DSN`, `MAILER_EMAIL` and the `JWT_*` keys first and generates a test JWT keypair (see [Test](#test)). See [Faster Functional Tests](/deployment/faster-functional-tests) once the suite is slow |
| `run_browser_tests` | Logs in to the registry and runs `e2e/run.sh` against this ref's php and app images. Only runs when `CWA_CI_E2E_ENABLED` is `"true"`. See [Browser Tests](/deployment/browser-tests) |
| `helm_init` | Updates and builds Helm chart dependencies |
| `review_namespace_state` | Prints `present`, `missing` (the namespace is not found, or the CI is forbidden to read it) or `error` (any other `kubectl` failure) for `$KUBE_NAMESPACE`. The GitHub review job calls it directly |
| `skip_review_without_namespace` | Runs first in the GitLab review job. Exits with code `3` when the namespace is missing, which the job allows, so the pipeline shows orange. See [Review Apps](#review-apps) |
| `skip_unless_review_deployed` | Runs first in the jobs that follow a review. Exits with code `3` when the review job uploaded no `environment_url.txt`, meaning it didn't deploy |
| `ensure_namespace` | Verifies the K8s namespace exists and fails the job if not. Staging, canary and production rely on it |
| `create_docker_pull_secret` | Creates or updates the `imagePullSecret` for the GitLab registry with `kubectl apply`, so releases sharing a namespace don't race with "already exists". The first deploy over a secret that an older template created with `kubectl replace --force` prints a one-off warning about a missing `last-applied-configuration` annotation. It's harmless, and the secret is updated |
| `check_kube_domain` | Fails the job when there is no `DOMAIN` to deploy to, or when it starts or ends with a dot. A dot there means the variable in the environment url was empty, as in `https://staging.` with no `KUBE_INGRESS_BASE_DOMAIN` |
| `deploy [track]` | Generates `values.tmp.yaml` from CI variables and runs `helm upgrade --install`, with a project's [`project_values`](#project-hooks) applied last. It runs `check_cdn_config`, `check_cache_config`, `check_php_memory_budget` and `gcloud_path_prefix` before anything changes in the cluster, and `deploy_secrets` and `promote_images` before Helm |
| `promote_images [track]` | Runs inside `deploy`. Copies the build to the track's tag (`:staging`, `:canary` or `:production`) and sets the image tags Helm gets to `<tag>@<digest>`. See [Which build a deploy runs](#which-build-a-deploy-runs) |
| `check_cache_config` | Runs inside `deploy`. Fails the deploy when `CADDY_CACHE_EXTRA_CONFIG` names a store or a `timeout` block, or `CWA_API_CADDY_CACHE_BACKEND_TIMEOUT` isn't a Go duration. See [HTTP cache](/deployment/variables#http-cache) |
| `gcloud_path_prefix [track]` | Runs inside `deploy`. Tidies `GCLOUD_PATH_PREFIX` as php does, fails on a `.`, `..` or `review` segment, and adds `review/<slug>/` for a review app. See [Storage path prefix](/deployment/variables#storage-path-prefix) |
| `check_php_memory_budget` | Runs inside `deploy`. Fails the deploy when the [php memory budget](/deployment/variables#php-memory-budget) doesn't fit the API's memory limit |
| `deploy_secrets [release]` | Runs inside `deploy`. Takes `APP_SECRET`, `MERCURE_JWT_SECRET` and the JWT key pair from a CI variable, else from the release's live Secret, else generates them. See [Secrets](/deployment/variables#secrets) |
| `ensure_jwt_keys` | Called by `deploy_secrets`. Generates a JWT key pair when there's none, or derives `JWT_PUBLIC_KEY` from a supplied key, and fails on a key without its passphrase |
| `ensure_tls_certificate` | Runs inside `deploy` before Helm. When production's hostnames change, it issues the new certificate first. See [Changing a live site's hostnames](#changing-a-live-sites-hostnames) |
| `purge_rendered_html [track]` | Waits for the Nuxt and php rollouts to finish, then clears every cached page, or the whole HTTP cache when Cloudflare is configured, followed by `warm_api_cache`. Runs after every `deploy` |
| `warm_api_cache` | Runs `warm-http-cache` in the API pod, gzip then br, each pass for at most `CWA_CI_API_WARM_HTTP_CACHE_MAX_TIME` seconds, after a full flush. A failure only warns |
| `generate_image_variants [track]` | Waits for the API rollout, then creates every missing image variant in one-off Kubernetes Jobs, and purges the HTTP cache if it made any. See [Generating image variants after a deploy](#generating-image-variants-after-a-deploy) |
| `warm_cache [base_url]` | Refills the page cache after `purge_rendered_html`, and reports each page's status and time to first byte. `base_url` defaults to `https://$DOMAIN` |
| `image_variants_and_warm [track]` | GitLab's post-deploy job: `generate_image_variants`, then `warm_cache`, each only when its switch is on. A failed half doesn't stop the other, and either one fails the job. On GitHub they're two steps of the deploy job |
| `performance_audit [base_url]` | Runs a Lighthouse audit of a few pages. `base_url` defaults to `https://$DOMAIN`. Only runs when you start it. See [Performance Audit](/deployment/performance-audit) |
| `load_fixtures [track]` | Loads fixtures into the php pod with `--append`, so existing content is kept, unless `CWA_CI_FIXTURES_PURGE` asks for a purge. Then flushes the whole HTTP cache. Only runs when `CWA_CI_FIXTURES_ENABLED` is `"true"`. See [Fixtures on a deploy](#fixtures-on-a-deploy) |
| `persist_environment_url` | Writes `https://$DOMAIN` to `environment_url.txt`, the artifact the later jobs check, and `SITE_ENVIRONMENT_URL=https://$DOMAIN` to `environment_url.env` |
| `delete [track]` | Runs `helm uninstall` for review/canary/staging cleanup. For `review`, it first deletes the app's stored files. See [Review app storage](#review-app-storage) |

### Project hooks

Keep `setup.sh`, `k8s.sh` and the chart exactly as the template ships them, so each release is a plain file copy. A project's own deploy logic goes in an optional **`bin/devops/project.sh`** ([!14](https://gitlab.com/silverback-web-apps/cwa/components-web-app/-/merge_requests/14), [`1a7c30b`](https://github.com/components-web-app/components-web-app/commit/1a7c30b2793f9ad17d1fe4979905e842cd85dec8), [`ed4c725`](https://github.com/components-web-app/components-web-app/commit/ed4c725417aa64318bebbe7054fba5bfa29e61cd)). A project without one deploys exactly as before.

`setup.sh` sources `project.sh` in every job, on GitLab and GitHub, after its own defaults and before it sets `DOMAIN` and the image paths. `k8s.sh` isn't loaded yet, so `project.sh` can't call its functions. In it you can:

- **Set `DOMAIN`**, the host the deploy serves, for example to choose which of several sites a job deploys. `setup.sh` keeps a `DOMAIN` that's already set, and otherwise takes the host of the job's environment url. A `DOMAIN` CI variable works the same way. `check_kube_domain`, `persist_environment_url`, the ingress hosts, `NUXT_SITE_URL`, the [host-based defaults](/deployment/variables#minimum-for-a-new-site), and the cache warm and performance audit jobs all follow it ([#132](https://github.com/components-web-app/components-web-app/issues/132), [`7b26140`](https://github.com/components-web-app/components-web-app/commit/7b26140895c524ad5083e48470883bffd99d3410)).
- **Export site settings** and other variables, such as `KUBE_INGRESS_ALIAS_DOMAINS`, or `NUXT_*` and `CWA_API_*` values for the [site settings passthrough](/deployment/variables#site-settings), such as each site's `CWA_API_WEBSITE_NAME`. Use `export`: the passthrough only sees exported variables.
- **Reserve more names** with `SITE_ENV_RESERVED_API_EXTRA` and `SITE_ENV_RESERVED_PWA_EXTRA`, space-separated. Add the names your own chart values set on a container, so a site setting of the same name fails the deploy instead of being ignored. See [Reserved names](/deployment/variables#reserved-names). They can be CI variables too.
- **Define `project_values`**. `deploy` calls it with the track (`stable` for production, `staging`, `canary` or `review`) and passes what it prints to `helm upgrade` as the last `-f` values file, after the template's own. Use it for the values of a template you add to `helm/cwa/templates`, or to change one of the chart's values. If it exits non-zero, the deploy stops before helm. The five `--set` values (`APP_SECRET`, the JWT keys and the Mercure JWT keys) still win over it, as `--set` always does in helm.

```sh [bin/devops/project.sh]
# Sourced by bin/devops/setup.sh in every job. POSIX sh only.

# One repository, two sites: SITE is a CI variable scoped to each environment.
if [ "$SITE" = "shop" ]; then
  export DOMAIN="shop.example.com"
  export NUXT_PUBLIC_SITE_NAME="Example Shop"
  export CWA_API_WEBSITE_NAME="Example Shop"
fi

# Chart values, applied after the template's.
project_values() {
  if [ "$1" = "stable" ]; then replicas=2; else replicas=1; fi
  cat <<EOF
redirects:
  replicaCount: $replicas
EOF
}
```

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**Write the hooks in POSIX sh.** GitLab's jobs run on `alpine`, where the shell is busybox ash: no arrays and no `declare`. A hook that only works in bash passes on GitHub and fails on GitLab.
::

`environment_url.env` is for a job whose url is worked out in the job, such as a multi-site deploy. The template's own jobs don't read it, and their environment urls stay as they are. If your `project.sh` sets `DOMAIN`, you can point your GitLab deploy job's environment url at it: add the file as a `dotenv` report and use the variable as the url:

```yaml
  environment:
    url: $SITE_ENVIRONMENT_URL
  artifacts:
    paths: [ environment_url.txt ]
    reports:
      dotenv: environment_url.env
```

The cache warm and performance audit jobs pass no url, so `warm_cache` and `performance_audit` use `https://$DOMAIN`, and a `DOMAIN` set here reaches them. The GitHub **Performance audit** workflow sources `setup.sh` too.

## After each deploy

### Why every deploy clears the page cache

Cached pages link to the JavaScript and CSS files of the build that rendered them. A new front-end build gives those files new names and deletes the old ones. Without a purge, the cache keeps serving pages that point at files that no longer exist, so visitors see an unstyled page that does not work until the cached copy expires, which can take up to an hour.

`purge_rendered_html` prevents this. It waits until the new Nuxt pods have fully replaced the old ones, because an old pod could otherwise put an old page back into the cache. Then it runs `php bin/console silverback:api-components:purge-rendered-html` in the php pod. That command clears only the rendered pages, which share the `cwa-html` cache tag, and leaves cached API responses alone. It uses the pipeline's existing `kubectl` access, so it needs no extra credentials. If a site has no HTTP cache configured, the command does nothing and still succeeds.

If Cloudflare or another CDN caches your pages, this purge reaches it only when Souin's `CADDY_CACHE_CDN_CONFIG` is set to purge it. See [Purges must reach Cloudflare](/deployment/cloudflare#purges-must-reach-cloudflare).

When `CADDY_CACHE_CDN_CONFIG` contains `provider cloudflare`, `purge_rendered_html` runs `silverback:api-components:purge-http-cache` instead. Cloudflare can also hold API responses, through the optional [API rule](/deployment/cloudflare#api-responses-optional), and the `cwa-html` tag doesn't cover them. A full flush reaches Cloudflare as a purge of everything in the zone, so a release that changes API output doesn't leave stale responses at the edge. Staging uses the same variable, so a staging deploy also empties the edge for production; the cache warm and normal traffic refill it.

The flush also empties the `/_api` cache that the new php pod [warmed when it started](/deployment/kubernetes#warming-the-api-cache-on-start), moments before visitors arrive. So after the flush, `purge_rendered_html` warms `/_api` again in the API pod, the same two passes as the pod's start: [`warm-http-cache`](/api/console-commands#warm-http-cache) for the `gzip` entries server-side rendering uses, then `--accept-encoding=br` for the entries browsers and Cloudflare use. Each pass stops after `CWA_CI_API_WARM_HTTP_CACHE_MAX_TIME` seconds (60), and `0` skips both. A failed pass only prints a warning. The deploy job therefore takes up to twice `CWA_CI_API_WARM_HTTP_CACHE_MAX_TIME` longer with Cloudflare, and a large site may need a higher value: on one site with 111 routes, 60 seconds didn't cover one pass ([#175](https://github.com/components-web-app/components-web-app/issues/175), [`1818110`](https://github.com/components-web-app/components-web-app/commit/18181102a41d844bda3240cdc83fd1b46f4c7b9b)). *Since template 2.0.0-alpha.39 · [release notes](https://github.com/components-web-app/components-web-app/releases/tag/v2.0.0-alpha.39)*

Before alpha.39 nothing warmed `/_api` again after that flush, and the first visitor's component requests were load-shed.

### Generating image variants after a deploy

When a filter is added or changed, or the template's variants changed to WebP, every image is missing a variant, and each would otherwise be generated during a visitor's request. `generate_image_variants` makes them first, after a deploy and before the cache warm. On GitLab it's the first half of the [`image variants and warm <track>` job](#one-job-for-variants-and-the-warm). On GitHub it's a *Generate image variants* step, after the fixtures step. **Only production runs it by default**; set `CWA_CI_IMAGE_VARIANTS_PRODUCTION="false"` to turn it off there, and the other tracks opt in (see [CI/CD Variables → Image variants](/deployment/variables#image-variants)). *Since template 2.0.0-alpha.27 · [release notes](https://github.com/components-web-app/components-web-app/releases/tag/v2.0.0-alpha.27)*

It never runs in the API pod that serves the site, where generating many large images once ran php out of memory and the site returned `503`s ([#153](https://github.com/components-web-app/components-web-app/issues/153)). Instead:

1. It waits for the API rollout, because the Jobs use the release's image.
2. It creates a Job from the release's `<release>-image-variants` CronJob (see [Kubernetes → Image Variants Jobs](/deployment/kubernetes#image-variants-jobs)). The Job runs [`imagine:generate`](/api/console-commands#imaginegenerate) with `-v` and `--max-memory`, under its own memory limit (`CWA_CI_IMAGE_VARIANTS_MEMORY`, `1536Mi` by default).
3. When a Job stops at `--max-memory` with variants still missing (exit code `3`), it deletes that Job and starts another, up to `CWA_CI_IMAGE_VARIANTS_MAX_RUNS` Jobs (50). The log prints each Job's output, leaving out the variants that were already stored.
4. If any variant was generated, it runs `purge-http-cache` in the API pod, so cached API responses list the new variants, then warms `/_api` again, gzip then br, as after the [Cloudflare flush](#why-every-deploy-clears-the-page-cache) (from template 2.0.0-alpha.39). Each variant is stored with the field's `imagineCacheControl` (see [Cache-Control on stored files](/api/components/annotations/uploadable#cache-control-on-stored-files)).

A failure never fails the deploy: the GitLab job is `allow_failure: true`, and the step is `continue-on-error: true` on GitHub, where it also raises an `::error` annotation. The log ends with a banner that says why:

| Exit code | Banner | What to do |
|-----------|--------|------------|
| `3` | `IMAGE VARIANTS NOT FINISHED` | Variants are still missing after `CWA_CI_IMAGE_VARIANTS_MAX_RUNS` Jobs. The next deploy carries on, and a missing variant is still generated on its first read |
| `137` | `IMAGE VARIANTS FAILED: the Job ran out of memory` | The Job was OOM-killed. Raise `CWA_CI_IMAGE_VARIANTS_MEMORY`, or lower `CWA_CI_IMAGE_VARIANTS_MAX_MEMORY`. Visitors aren't affected |
| `124` | `IMAGE VARIANTS FAILED: Job … did not finish` | The Job wasn't scheduled, or passed its deadline. Run `kubectl describe job` on it |
| `1` or `2` | `IMAGE VARIANTS FAILED: imagine:generate exited …` | `1`: a variant failed, and the `-v` output above lists it. `2`: an unknown `--filter` or `--class` |

A failed Job is kept so you can read it with `kubectl logs`, and Kubernetes deletes it after a day. A release deployed with an older chart has no CronJob, so the job fails with `IMAGE VARIANTS NOT GENERATED` until the chart is deployed.

### Warming the cache after a deploy

A purge leaves the cache empty, so the first visitor to each page would wait for a server render. `warm_cache` fills it again after a deploy. On GitLab it's the second half of the [`image variants and warm <track>` job](#one-job-for-variants-and-the-warm). On GitHub it's a *Warm the page cache* step, after the fixtures and image variants steps, so a new environment is warmed once its content exists. **Only production is warmed by default**; the other tracks opt in (see [Cache warm](/deployment/variables#cache-warm)). The production deploy never waits for the warm. It reads `/sitemap.xml` from `https://$DOMAIN`, or the url passed to `warm_cache` (following one level of sitemap index), then requests every page anonymously, three at a time by default, and prints each page's status and time to first byte.

Any page that doesn't return `200` is listed under a `CACHE WARM FAILED` banner, and on GitHub it also raises an `::error` annotation on the run summary. The warm fails, but it is allowed to (`allow_failure: true` on GitLab, `continue-on-error: true` on GitHub), so the pipeline shows a warning instead of a failed deploy. By then the new release is already live, and the deploy and its cleanup steps have already run. Read the job's log when it warns.

The warm's switches (which tracks are warmed, how many pages at once, TLS verification) are listed in [CI/CD Variables → Cache warm](/deployment/variables#cache-warm).

This warm requests pages, so it refills the rendered HTML and the API responses those renders fetch. Separately, a new php pod warms its own `/_api` cache before it takes traffic, in a `postStart` hook, and the deploy warms `/_api` again after a full flush. Those cover API responses only, never HTML, and `purge_rendered_html` still drops every page after the deploy, so this warm is still needed. See [Kubernetes → Warming the API cache on start](/deployment/kubernetes#warming-the-api-cache-on-start).

### One job for variants and the warm

On GitLab, the image variants and the cache warm run in one job per track: `image variants and warm review`, `image variants and warm staging`, `image variants and warm canary` and `image variants and warm production`, each in the same stage as its deploy ([#160](https://github.com/components-web-app/components-web-app/issues/160), [`5f987be`](https://github.com/components-web-app/components-web-app/commit/5f987be09ccf7ecfda261be61662020f7d72ea67)). They used to be separate `image variants <track>` and `warm cache <track>` jobs, and the warm job waited about 50 seconds for a runner after every deploy. *Since template 2.0.0-alpha.31 · [release notes](https://github.com/components-web-app/components-web-app/releases/tag/v2.0.0-alpha.31)*

- The job calls `image_variants_and_warm`, which generates the variants first and then warms, the same order as before. The warm must never come first: its renders would make the serving API pod generate every missing variant at once, and [load shedding](/deployment/origin-protection#load-shedding) gave visitors `503`s for about five minutes ([#153](https://github.com/components-web-app/components-web-app/issues/153)).
- Each half keeps its own switch: `CWA_CI_IMAGE_VARIANTS_<TRACK>` and `CWA_CI_WARM_CACHE_<TRACK>`. Production's are on unless `"false"`, and the other tracks' are off unless `"true"`. The job is created when either switch is on, and skips the half that's off.
- If one half fails, the other still runs. Either failure fails the job, which is `allow_failure: true`, so a live deploy is never marked failed.
- The `performance audit <track>` jobs `needs:` the combined job.

GitHub didn't change: its two steps already run one after the other in the deploy job.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**A project job that `needs:` `image variants <track>` or `warm cache <track>` must use the new name**, `image variants and warm <track>`, or GitLab rejects the pipeline.
::

### Auditing performance after a deploy

`warm_cache` tells you how quickly the server answered. The manual `performance_audit` job runs Lighthouse against a few pages and tells you what a visitor experiences. It never fails a deploy. See [Performance Audit](/deployment/performance-audit).

## Fixtures on a deploy

Fixtures seed a new environment: the scaffold pages and the first admin user. They are off unless `CWA_CI_FIXTURES_ENABLED` is `"true"` (see [Pipeline flags](/deployment/variables#pipeline-flags)).

- **GitLab:** a **load fixtures** job appears for review apps and for production, after the deploy job. It never runs automatically; trigger it from the pipeline UI. With `CWA_CI_PRODUCTION_DISABLED="true"`, there is no production fixture job, because the job it waits for doesn't exist.
- **GitHub Actions:** a **Load fixtures** step runs after each review deploy, and after a manual production run, while the variable is `"true"`. GitHub has no manual jobs inside a push-triggered workflow, so set the variable for a new environment's first deploy, then remove it.

Staging has no fixture job on either. It runs under the production environment, so with an external database (`DATABASE_URL`) it uses production's database, and a fixture load there would write to production.

By default `load_fixtures` runs `doctrine:fixtures:load --append`, so it never deletes existing content. The admin user fixture can be run any number of times. On a database that already has content, appending creates only what is missing and keeps existing content. See [Appending to an Existing Site](/api/data-fixtures/appending#appending-to-an-existing-site).

After a successful load, `load_fixtures` flushes the whole HTTP cache (`silverback:api-components:purge-http-cache`), API responses and pages alike. The load changes the database underneath what Souin has cached since the deploy, and nothing else would purge it, so production could otherwise serve the old content for up to a year.

### Purging before a load

`CWA_CI_FIXTURES_PURGE` is for an early project whose database should be rebuilt from a changed scaffold. It runs `doctrine:fixtures:load` without `--append`, which **empties every table** first.

| Track | Purges with | Otherwise |
|-------|-------------|-----------|
| Review apps | `"true"` or `"force"` | Appends |
| Production | `"force"` only | `"true"` prints a notice and appends, so a project-wide `"true"` meant for review apps can't empty production |

Only the fixture job reads it. A deploy or a pod restart never purges.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
On GitHub the fixture step runs after every deploy while `CWA_CI_FIXTURES_ENABLED` is set. With `CWA_CI_FIXTURES_PURGE` set too, **every** review deploy empties the review database, and every manual production run with `"force"` empties production. Unset `CWA_CI_FIXTURES_PURGE` once the database has been rebuilt. Add `CWA_CI_FIXTURES_PURGE` to repository variables, not secrets: the workflows read `vars.CWA_CI_FIXTURES_PURGE`.
::

## Changing a live site's hostnames

Production's certificate covers its main hostname and every entry in `KUBE_INGRESS_ALIAS_DOMAINS`. You change that list when you launch a site, add `www`, or retire the preview hostname. To do it, edit the variables and deploy:

- **Add a hostname:** add it to `KUBE_INGRESS_ALIAS_DOMAINS`.
- **Retire a hostname**, such as the preview host: remove it from `KUBE_INGRESS_ALIAS_DOMAINS`. It then goes offline. The template has no redirect feature, by design.
- **Change the main hostname at launch**, for example `new.example.org` → `example.org`: the main hostname is the production environment URL, `https://$KUBE_INGRESS_BASE_DOMAIN`, so change `KUBE_INGRESS_BASE_DOMAIN` (or the `DOMAIN` your [`project.sh`](#project-hooks) sets). Staging and review apps are subdomains of it, so they move too. Keep the old host in `KUBE_INGRESS_ALIAS_DOMAINS` if it should still work.

When the list differs from the live certificate's, the deploy creates a new cert-manager `Certificate` for the new list. It waits until the certificate is issued, for up to `CWA_CI_TLS_CERTIFICATE_TIMEOUT` (default `600s`), and only then runs Helm. The ingress moves from one valid certificate to another, with no downtime. When the list is unchanged, which is almost every deploy, the deploy keeps the live certificate and nothing is reissued. The order and case of the hostnames don't matter.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**Point a new hostname's DNS at the cluster's ingress before you deploy.** Let's Encrypt's HTTP-01 challenge must reach it. If it can't, the certificate isn't issued and **the deploy fails before anything changes**. The live site keeps its current certificate, and the log lists the hostnames to check. Fix the DNS and run the deploy again.
::

::callout{icon="i-heroicons-light-bulb"}
**Why the certificate is issued first.** If the names on the live certificate change in place, cert-manager serves a temporary self-signed certificate while it gets the new one. That takes minutes, or up to an hour of back-off if a challenge fails. With HSTS, browsers refuse the connection outright, on every hostname, including the live one. Let's Encrypt also allows only 5 certificates for the same set of names per week, so don't switch the list back and forth.
::

Some details:

- The deploy compares against the certificate on the chart's own ingress, which it finds by the release name. This is why changing the main hostname at launch is still safe.
- Other ingresses in the namespace are ignored, even with the same chart labels. For example, a redirect ingress you added by hand for a retired hostname keeps its own certificate. The deploy doesn't compare against it or remove it.
- New certificates are named `<CWA_CI_TLS_SECRET_NAME>-stable-api-<hash>`, from a hash of the hostname list. After a successful deploy, older ones created this way are deleted, with their secrets. The one just replaced is kept, so a rollback still has a valid certificate. You don't change `CWA_CI_TLS_SECRET_NAME` by hand.
- Only production (the stable track) is covered. Review, staging and canary each serve one hostname that doesn't change. The first deploy of a release issues its certificate directly, because nothing is live yet.

### Permissions

The CI service account needs access to `certificates.cert-manager.io` in the namespace. The deploy creates, patches, gets, watches, lists and deletes Certificates, and deletes the secrets of the ones it removes. It checks only `create` up front. Without it, the deploy prints a warning and falls back to changing the live certificate in place, which causes the downtime described above.

With `CWA_CI_INGRESS_ENABLED` set to `"false"` there is no ingress, so none of this runs. Nor does it with an empty `CWA_CI_CLUSTER_ISSUER`.

### Changing hostnames by hand

Use this if the CI account can't manage Certificates, or your pipeline doesn't have `ensure_tls_certificate`.

1. Choose a new value for `CWA_CI_TLS_SECRET_NAME`, for example `letsencrypt-cert-2`. The production ingress uses the secret `<CWA_CI_TLS_SECRET_NAME>-stable-api`.
2. Apply a `Certificate` that writes that secret and covers the new hostnames:

    ```yaml
    apiVersion: cert-manager.io/v1
    kind: Certificate
    metadata:
      name: letsencrypt-cert-2-stable-api
    spec:
      secretName: letsencrypt-cert-2-stable-api
      issuerRef:
        group: cert-manager.io
        kind: ClusterIssuer
        name: letsencrypt-prod # your CWA_CI_CLUSTER_ISSUER
      dnsNames:
        - example.org
        - www.example.org
    ```

3. Wait until it is ready: `kubectl wait --for=condition=Ready certificate/letsencrypt-cert-2-stable-api -n <namespace> --timeout=600s`.
4. Set `CWA_CI_TLS_SECRET_NAME` to the new value, update the hostname variables, and deploy.
5. Keep the old Certificate and secret until the site works on the new one. Then delete them.
