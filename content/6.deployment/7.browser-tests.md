The template has opt-in browser tests, in `e2e/`. They take the php and app images this branch just built, start them in a throwaway stack, and use the site in Chromium the way visitors and editors do. When they're on, every deploy waits for them, so a build that breaks rendering a page or signing in never reaches a site ([#157](https://github.com/components-web-app/components-web-app/issues/157), [`3fd2c01`](https://github.com/components-web-app/components-web-app/commit/3fd2c01237578dd0f009de10699402b257f5bf7c), [`8c36f8c`](https://github.com/components-web-app/components-web-app/commit/8c36f8c89f9176495fc02f8f9480531c71eb4613)). *Since [template 2.0.0-alpha.34](https://github.com/components-web-app/components-web-app/releases/tag/v2.0.0-alpha.34)*

The template's `e2e/README.md` is the short version of this page.

## What they check

The template's tests assume only what every project has: the admin user and the pages its sitemap lists. They don't use the template's sample content, so a project can keep `e2e/` unchanged and the tests pass on its own site ([#177](https://github.com/components-web-app/components-web-app/issues/177), [`5db12c9`](https://github.com/components-web-app/components-web-app/commit/5db12c9e9992a1f02eaaf187f36ed56db965c13e)). *Since [template 2.0.0-alpha.42](https://github.com/components-web-app/components-web-app/releases/tag/v2.0.0-alpha.42)*

They cover:

- every page in the sitemap renders and hydrates;
- the first page in the sitemap is served from the cache on its second request;
- the loading bar shows while a page loads after a client-side navigation, from the first sitemap page to the second;
- the first sitemap page's OG image renders;
- an admin can log in and out;
- a password reset email links to a working reset page.

So the sitemap needs at least two pages, and its first page needs an `og:image` tag, or those tests fail.

Editing and publishing content isn't tested here: the module and the bundle test that. Up to template 2.0.0-alpha.41 the suite also checked a redirect's `308` and published a text component and an image, all from the sample content.

A run also fails when:

- an API write gets a `405`, `406` or `415`, which means the front end and the API disagree about a method or a content type;
- the page throws an uncaught error;
- the API sent an error mail ([Kubernetes & Helm › Error mail](/deployment/kubernetes#error-mail)), meaning it answered a request with a `5xx` that the UI may have hidden;
- not every listed test ran and passed (`check-all-ran.mjs`), so a skipped or filtered-out test can't pass a run.

Every timeout is bounded: 90 seconds a test, 30 seconds a navigation, 15 seconds an action and 10 seconds an assertion.

## Turning them on

Set the CI variable `CWA_CI_E2E_ENABLED` to `"true"` (see [CI/CD Variables › Pipeline flags](/deployment/variables#pipeline-flags)). Nothing runs until you do. `CWA_CI_TEST_DISABLED="true"` skips them along with the other tests.

- **GitLab:** a `browser tests` job in the `test` stage, after `build api` and `build app`. The review, staging, canary and production jobs `needs:` it, so none of them runs when it fails. It runs Docker in Docker (`docker:27-dind`).
- **GitHub:** the reusable workflow `.github/workflows/browser-tests.yml`. `ci.yml` calls it after the builds, before review and staging, and `production.yml` calls it on `main`'s images before the deploy. A failed run stops those deploys. It has a 30-minute limit.

The Playwright report, with traces, screenshots and videos of failed tests, is kept as a job artifact for 14 days. GitLab also reads its JUnit file, so the results show in the pipeline's test report.

## The test stack

`e2e/run.sh` starts `e2e/compose.yaml`, which has:

- the branch's php and app **production** images (`frankenphp_prod` and `prod`);
- PostgreSQL on `tmpfs`, so every run starts empty;
- a Cloud Storage emulator, reached through php's `GCLOUD_API_ENDPOINT`, for any file your fixtures or your own tests store;
- Mailpit, which catches every email, such as the password reset;
- the Playwright runner, built from `e2e/Dockerfile`.

It makes new secrets and a new JWT key pair for each run, waits for the API (migrations run on boot), loads the fixtures, flushes the HTTP cache and waits for the site. Then it runs the tests one at a time, and stops and deletes the stack.

The stack publishes no ports, so it can run beside your dev stack.

Each checkout gets its own stack, named `cwa-e2e-<directory>` after the checkout's directory, and its own tests container. So two projects can run their tests on one machine at once, and one run's clean-up never removes another's containers or volumes. `COMPOSE_PROJECT_NAME` sets a different name ([#178](https://github.com/components-web-app/components-web-app/issues/178), [`21a3745`](https://github.com/components-web-app/components-web-app/commit/21a3745552ac615fad28aea8df53ee105a1b9b85)). *Since [template 2.0.0-alpha.43](https://github.com/components-web-app/components-web-app/releases/tag/v2.0.0-alpha.43).* Before that, every project's stack was `cwa-e2e`.

`GCLOUD_API_ENDPOINT` is the only change the tests need in the API: `GoogleCloudStorageFactory` uses an emulator, with no credentials, when it's set. Leave it unset on every deploy, where empty means Google.

The stack also sets a review app's [storage path prefix](/deployment/variables#storage-path-prefix), `GCLOUD_PATH_PREFIX: review/e2e/`. After the tests, `run.sh` checks that every stored object is under it, then runs the same guarded `delete-stored-files` a stopped review app runs and checks the bucket is empty. Either failure fails the run. *Since template 2.0.0-alpha.37.* No template test uploads a file since template 2.0.0-alpha.42, so the check covers what your fixtures and your own tests store.

## Running them locally

You need Docker and openssl. Build the two production images, then run the tests against them:

```bash
docker build --target frankenphp_prod -t cwa-e2e-php:local api
docker build --target prod -t cwa-e2e-app:local app
E2E_PHP_IMAGE=cwa-e2e-php:local E2E_APP_IMAGE=cwa-e2e-app:local sh e2e/run.sh
```

| Variable | What it does |
|----------|--------------|
| `E2E_PHP_IMAGE` / `E2E_APP_IMAGE` | **Required.** The php and app images to test. CI passes this branch's tags |
| `E2E_ARGS` | Runs part of the suite: a file, such as `E2E_ARGS="tests/admin.spec.ts"`, or `--grep …`. The every-test-ran check is skipped then |
| `E2E_KEEP_STACK` | `true` leaves the stack running afterwards, and prints the admin password and the command that stops it: `docker compose -p <stack> -f e2e/compose.yaml down -v` |
| `COMPOSE_PROJECT_NAME` | The stack's name. Defaults to `cwa-e2e-<directory>`, after the checkout's directory |
| `E2E_SCALED` | `true` runs the tests against scaled mode: two php replicas sharing one Redis cache and one Mercure hub, from `e2e/compose.scaled.yaml`. In CI, set `CWA_CI_E2E_SCALED="true"`. See [Scaled Mode](/deployment/scaled-mode). *Since [template 2.0.0-alpha.43](https://github.com/components-web-app/components-web-app/releases/tag/v2.0.0-alpha.43)* |

The reports land in `e2e/playwright-report/` and `e2e/test-results/`. When a run fails, the script prints the last 80 lines of the php and app logs.

::callout{icon="i-heroicons-information-circle"}
**On an ARM Mac, set `DOCKER_DEFAULT_PLATFORM=linux/amd64`** to test images from your CI registry, which builds them for amd64 only. *Since template 2.0.0-alpha.36 ([`8949efe`](https://github.com/components-web-app/components-web-app/commit/8949efe89eb2ac19319fbc1278227fbd9d3c2610))*

## Writing your own tests

The template's tests check only what every CWA site has. Your project's own specs are where its pages and content get tested: add them under `e2e/tests/`, as `*.spec.ts` files.

```ts [e2e/tests/contact.spec.ts]
import { expect, logIn, test } from './fixtures'

test('an admin sees the contact page, and so does a visitor', async ({ page, visitor }) => {
  await logIn(page)
  await page.goto('/contact')
  await expect(page.getByRole('button', { name: 'Edit' })).toBeVisible()

  await visitor.goto('/contact')
  await expect(visitor.getByRole('heading', { name: 'Contact us', exact: true })).toBeVisible()
})
```

- **Import `test` and `expect` from `tests/fixtures.ts`**, never from `@playwright/test`. Its `page` fixture is what fails a test on a refused API write or an uncaught error. Importing types from `@playwright/test` is fine.
- **`logIn(page)` signs in as the admin.** The password is made for each run and loaded with the fixtures. It waits for `/login` to hydrate before it fills the form, because before that the form submits natively and reloads `/login` ([`5b6a605`](https://github.com/components-web-app/components-web-app/commit/5b6a6058fb59fc4f8c618f6ecf6f3b558d71e63c)). *Since template 2.0.0-alpha.42*
- **Use the `visitor` fixture to see a page as an anonymous visitor**, beside the signed-in `page`. It has its own browser context, is checked the same way as `page`, and is closed after the test. *Since template 2.0.0-alpha.36 ([`43ece66`](https://github.com/components-web-app/components-web-app/commit/43ece66d7a6a2c6e478904d45b2312a248fd634b))*
- **Tests share one database and run one at a time.** A test that edits content should use its own unique text, such as one with `Date.now()` in it, so it can't match another test's.

### Type checks, lint and conventions

The tests are type-checked and linted before they run, and every rule is an error, so a type or lint error fails the `browser tests` job. Playwright only strips types, so nothing else would catch them. *Since template 2.0.0-alpha.36 ([`43ece66`](https://github.com/components-web-app/components-web-app/commit/43ece66d7a6a2c6e478904d45b2312a248fd634b), [`08b40db`](https://github.com/components-web-app/components-web-app/commit/08b40db59ffd6f41fbdb3c716d5190bbbcd0a871))*

- `tsc`, with the strict `e2e/tsconfig.json`;
- ESLint, with `e2e/eslint.config.mjs`: `@nuxt/eslint-config`'s stylistic rules (the module's style), `eslint-plugin-playwright`, and typescript-eslint's `no-floating-promises`, which also catches a missing `await` on your own helpers.

Run them yourself in `e2e/`. `npm ci` also gives your editor the types:

```bash
cd e2e
npm ci
npm run typecheck
npm run lint
npm run lint:fix
```

The rules come with these conventions, from the template's `e2e/README.md`:

- **Await every Playwright call and every helper** that returns a promise.
- **Use retrying assertions**: `await expect(locator).toBeVisible()`, not `expect(await locator.isVisible())`.
- **No fixed waits and no forced clicks.** `waitForTimeout` and `force: true` are errors. Wait for the response, URL or element the test is about.
- **Find elements the way a person does**: `getByRole`, `getByLabel` or `getByText`, with exact names. Use a CSS selector only where the markup gives nothing better, with a comment that says why.

::callout{icon="i-heroicons-light-bulb"}
Keep the Playwright image in `e2e/Dockerfile` and `@playwright/test` in `e2e/package.json` on the same version.
::
