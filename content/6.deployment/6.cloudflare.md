Cloudflare can sit in front of a CWA site as a proxy: it hides the origin, ends TLS close to the visitor, and blocks some abusive traffic before it reaches your cluster. There are two ways to set it up:

- **Option A, proxy only.** Cloudflare passes requests through and caches no pages. Souin, in the php container, still does all the [page caching](/nuxt-module/page-caching). **This is the recommended setup.**
- **Option B, proxy with edge caching.** Cloudflare also caches page HTML. This is **not tested yet**, and it needs purges to reach Cloudflare.

Both end with a [per-site checklist](#per-site-checklist).

## Option A: proxy only

### DNS and TLS

1. In **DNS**, set the site's records to **Proxied** (the orange cloud).
2. In **SSL/TLS**, set the encryption mode to **Full (strict)**. Cloudflare then connects to your origin over HTTPS and checks its certificate. The template's ingress already serves a Let's Encrypt certificate (see [Ingress with TLS](/deployment/kubernetes#ingress-with-tls)), so strict mode works as soon as that certificate is issued.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**Get the origin certificate before you turn the proxy on.** With **Full (strict)**, Cloudflare refuses an origin whose certificate isn't valid, and visitors get a Cloudflare error page. For a new site or a new hostname, the simplest order is: leave the record **DNS only** (grey cloud), deploy, check that the site serves a valid certificate, then switch the record to **Proxied**.
::

### Leave Cloudflare's cache alone

Don't add Cache Rules in Option A. By default Cloudflare doesn't cache HTML or JSON, so pages and `/_api` responses pass straight through to Souin. Their `s-maxage` is meant for Souin, which is purged on every write. Cloudflare can't be purged in Option A, so it must not keep them.

Check it with any page:

```sh
curl -sI https://www.example.com/ | grep -i -E 'cf-cache-status|cache-status'
```

You should see `cf-cache-status: DYNAMIC` (Cloudflare didn't cache it) next to Souin's own `cache-status` header.

::callout{icon="i-heroicons-information-circle"}
Cloudflare's defaults still cache static files by file extension: images, scripts, stylesheets, PDFs and so on, for as long as their headers allow. That's safe for `/_nuxt/*`, whose names change with every build, and for uploads, whose stored names are unique. If you delete an upload and it must disappear at once, purge its URL in Cloudflare too.
::

### Real client IPs

Behind Cloudflare, every request reaches your cluster from a Cloudflare address. Cloudflare sends the visitor's address in the `CF-Connecting-IP` header. Anything keyed on the client IP needs that header: rate limits, access logs, and Symfony's `Request::getClientIp()`.

Two rules apply:

- **Trust `CF-Connecting-IP` only from [Cloudflare's published ranges](https://www.cloudflare.com/ips/).** Anyone can send the header to an origin directly, so honouring it from any other address lets a client choose its own IP.
- Symfony trusts `X-Forwarded-For` only from the addresses in `TRUSTED_PROXIES` (the chart's `php.trustedProxies`, private ranges by default). Don't add Cloudflare's ranges there to "fix" client IPs. The visitor's address has to be restored before the request reaches php.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**The template doesn't restore the visitor's IP yet.** Behind Cloudflare, php sees an address that isn't the visitor's. Cloudflare-aware client IPs and rate limiting in Caddy are tracked in [components-web-app#106](https://github.com/components-web-app/components-web-app/issues/106). Until that lands, don't rely on the client IP in your own code.
::

### Free protection worth turning on

| Setting | Where | What it does |
|---|---|---|
| **Rate limiting rule** | Security → WAF → Rate limiting rules | Blocks an IP that sends too many matching requests. |
| **Bot Fight Mode** | Security → Bots | Challenges traffic that Cloudflare identifies as automated. |
| **Under Attack Mode** | Overview, or Security → Settings | Emergency switch: every visitor gets an interstitial check before the site loads. |

**Rate limiting.** The Free plan allows one rule, counted per IP over 10 seconds, and its expression can match only on the path. Matching on the query string (to catch cache-busting requests) needs Pro or above. A rule on paths starting with `/_api` is a reasonable start. SSR reaches the API inside the cluster, not through Cloudflare, so this counts only browser requests. Set the threshold generously: editors in one office share an IP, and the admin makes many API calls while editing.

**Bot Fight Mode** can't be skipped by a WAF rule or limited to some paths. It may challenge non-browser clients, including your pipeline's cache warm and performance audit, an uptime monitor, or a [load test](/deployment/load-testing). After you turn it on, check that the next deploy's [cache warm](/deployment/ci-cd#warming-the-cache-after-a-deploy) still gets `200`s.

**Under Attack Mode** needs JavaScript to pass, so the same non-browser clients fail while it's on. Use it only during an attack, and turn it off afterwards.

## Option B: proxy with edge caching

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**Not tested, and not recommended yet.** Edge caching will be tried on `preview.cwa.rocks` before any site uses it. This section lists the requirements and limits known so far, so you can see what it involves. It is not a setup guide. Use [Option A](#option-a-proxy-only) until this page says otherwise.
::

### Purges must reach Cloudflare

In production, the API tells shared caches to keep responses for a year (`s-maxage=31557600`), and pages inherit it (see [How long a page is kept](/nuxt-module/page-caching#how-long-a-page-is-kept)). Cloudflare honours `s-maxage`. If purges don't reach Cloudflare, an edited page stays stale at the edge for up to a year. So does a page that points at the previous build's `/_nuxt/*` files after a deploy, which then never hydrates (see [Why every deploy clears the page cache](/deployment/ci-cd#why-every-deploy-clears-the-page-cache)).

Souin can purge Cloudflare itself. Its `cdn` block is set from `CADDY_CACHE_CDN_CONFIG`, which defaults to `strategy hard` (no CDN). For Cloudflare it would read:

```text
provider cloudflare
api_key $CLOUDFLARE_API_KEY
email you@example.com
zone_id <your zone ID>
strategy hard
```

What Souin v1.7.9, the version the template builds, does with it:

- **It stores tags for Cloudflare.** When Souin stores a response, it copies the `Surrogate-Key` tags into a `Cache-Tag` header and removes `Surrogate-Key`. Cloudflare indexes `Cache-Tag` and strips it before the response reaches the visitor, so you can't see it in a browser.
- **It purges by tag.** Every tag purge that Souin receives is also sent to Cloudflare's purge API, 30 tags per request.
- **It doesn't report failures.** The Cloudflare request runs in the background and its response is ignored, so a rejected or rate-limited purge leaves no log line.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**Souin needs your Global API Key, not an API token.** It authenticates with `X-Auth-Email` and `X-Auth-Key`, which Cloudflare accepts only for the Global API Key. A scoped token with the **Cache Purge** permission would be sent the wrong way and rejected. The Global API Key carries every permission your Cloudflare user has, across all accounts and zones, so treat it like a root password (see [Secrets](#secrets)).
::

Which purges reach Cloudflare:

| Purge | Reaches Cloudflare? |
|---|---|
| Saving content in the admin (tag purge of the changed IRIs) | Yes |
| Site settings → purge page cache, and `purge-rendered-html` | Yes, the `cwa-html` tag |
| The deploy purge, `purge_rendered_html` in `k8s.sh` | Yes, because it runs `purge-rendered-html`, which goes through Souin |
| **Purge all cached data**, and `purge-http-cache` | **No.** Souin's flush clears only its own store. Use **Purge Everything** in Cloudflare as well. |

**Rate limits.** Cloudflare's purge-by-tag limit is **5 requests per minute on Free** (bursts up to 25), 5 per second on Pro and 10 per second on Business. Each save in the admin is at least one request. An editor saving quickly on a Free zone can use up the allowance, and Souin drops the rejected purges without a word. Check the current figures in [Cloudflare's purge limits](https://developers.cloudflare.com/cache/how-to/purge-cache/).

**Checking that purges arrive.** Because Souin doesn't log the result, test it from outside. Request a page twice and see `cf-cache-status: HIT`. Edit something on that page in the admin, then request it again. You should get `MISS` or `EXPIRED`, with the new content.

### Cache pages only, never `/_api`

The API negotiates on the `Accept` header (JSON-LD, JSON, or the HTML docs). Cloudflare's cache key ignores `Accept`, and custom cache keys on headers are an Enterprise feature. API Platform's HTML docs response also sends no `Vary: Accept`. So a cached `/_api` response could be served in the wrong format, which is the problem Souin hit in [components-web-app#79](https://github.com/components-web-app/components-web-app/issues/79). Cache page HTML only, and leave `/_api` to Souin.

### The cache rules must match the template's exclusions

The template's `@use_cache` matcher in `api/frankenphp/Caddyfile` decides what Souin may cache. A Cloudflare Cache Rule must skip at least the same requests:

- any request whose `Cookie` header has a non-empty `api_component` cookie, or that has an `Authorization` header;
- `/.well-known/mercure`. This is a stream (SSE). A cached stream never completes, so connections pile up behind it;
- `/login`, `/forgot-password`, `/reset-password/*`, `/verify-email`, `/confirm-new-email`, `/user-area`, `/_cwa/*`, `/_api/me` and `/_api/logout`;
- `/_nuxt/*`, `/uploads/*` and `/bundles/*`, and any page-side path with a file extension other than `.xml`.

When the template's matcher changes, the Cloudflare rule has to change with it. Whether your plan's Cache Rules can match on cookies and headers isn't confirmed yet.

Cloudflare also doesn't cache any response that carries `Set-Cookie`. If pages stay `DYNAMIC` under a cache rule, check for that first.

### Edge lifetime

An Edge TTL override that's shorter than our year limits the damage of a missed purge. Two constraints:

- **The shortest Edge TTL depends on the plan:** 2 hours on Free, 1 hour on Pro, 1 second on Business and Enterprise. "Minutes" is possible only on Business and above.
- **"Ignore cache-control header and use this TTL" ignores the origin's `Cache-Control`.** According to Cloudflare's documentation, the override replaces the origin's directives, so `private, no-store` on a personalised response or an error page would no longer stop Cloudflare caching it. With an override, the exclusions above are the only protection.

### Secrets

The Global API Key must not appear in pipeline logs.

- **GitLab.** `CADDY_CACHE_CDN_CONFIG` has several lines, and GitLab can't mask a multi-line variable. Put the key in its own masked variable, such as `CLOUDFLARE_API_KEY`. Then write `api_key $CLOUDFLARE_API_KEY` in `CADDY_CACHE_CDN_CONFIG` and turn on **Expand variable reference** for that variable.
- **GitHub.** Store `CADDY_CACHE_CDN_CONFIG` as a secret. The workflows export repository *variables* to the deploy scripts automatically, but not secrets, so the deploy jobs' `env:` must also map it: `CADDY_CACHE_CDN_CONFIG: ${{ secrets.CADDY_CACHE_CDN_CONFIG }}`.

In the cluster, the chart stores the value in the release's Kubernetes Secret, not its ConfigMap.

## Per-site checklist

**Option A (every site):**

1. The origin serves a valid certificate on every hostname before its record is proxied.
1. DNS records are **Proxied**.
1. SSL/TLS mode is **Full (strict)**.
1. There are no Cache Rules, and a page and an `/_api` response both show `cf-cache-status: DYNAMIC`.
1. A rate limiting rule is in place, with a threshold editors won't hit.
1. Bot Fight Mode is on, and the next deploy's cache warm still gets `200`s.
1. Someone on the team knows where **Under Attack Mode** is and when to use it.
1. Nothing in the site's own code relies on the client IP until [components-web-app#106](https://github.com/components-web-app/components-web-app/issues/106) lands.

**Option B (only once this page recommends it):**

1. Everything in Option A.
1. `CADDY_CACHE_CDN_CONFIG` sets `provider cloudflare`, `zone_id`, `email` and `api_key`, and the key is masked (GitLab) or a secret (GitHub).
1. An edit in the admin turns a page's `cf-cache-status` from `HIT` to `MISS` or `EXPIRED`.
1. After a deploy, pages are `MISS` at the edge and hydrate.
1. The cache rule caches page HTML only and skips every exclusion listed above.
1. The team knows that **Purge all cached data** doesn't reach Cloudflare.
1. The plan's purge rate limit suits how often editors save.
