---
title: Upgrading the Template
description: The steps for bringing a project made from the components-web-app template up to each template release, newest first.
---

A project made with `create-cwa` is a copy of the [components-web-app](https://github.com/components-web-app/components-web-app) template at one release. The template doesn't update your project for you: you copy the changes you want. Each section below covers one template release, newest first, with what to copy, which CI variables to set or remove, which images to rebuild, and whether Cloudflare needs a **Purge Everything**. Work through every section between your project's release and the one you're moving to, oldest first. The other deployment pages describe the current template only.

The template's [`CHANGELOG.md`](https://github.com/components-web-app/components-web-app/blob/main/CHANGELOG.md) has the full list, with a link to each commit to copy from. A template release pins a bundle and a `@cwa/nuxt` release; their own steps are in [Upgrading the Bundle](/api/upgrading).

::callout{icon="i-heroicons-information-circle"}
**Rebuild the API image** whenever a step changes `api/Dockerfile`, `api/frankenphp/Caddyfile` or a Souin patch: `docker compose build php && docker compose up -d php` locally, or a normal pipeline run. A Caddyfile that uses a new Caddy module can't load on an old image.
::

## 2.0.0-alpha.18

Released 2026-10-10. The bundle moves to 2.0.0-alpha.10 with the newer Mercure packages, deploys get project hooks, and the load test counts more of what a visitor does.

- [ ] **Update `components-web-app/api-components-bundle` to 2.0.0-alpha.10, `symfony/mercure-bundle` to 0.6 and `symfony/mercure` to 0.9, and pin the cookie name in `api/config/packages/mercure.yaml`** ([api-components-bundle#384](https://github.com/components-web-app/api-components-bundle/issues/384), [`b71fd4d`](https://github.com/components-web-app/components-web-app/commit/b71fd4d1f6193ab6c80fd05c07a9cb3e576414fe)). Change `api/composer.json` to `"symfony/mercure-bundle": "^0.6"`, run `composer update components-web-app/api-components-bundle symfony/mercure-bundle symfony/mercure` in the php container, and add this line under `hubs.default`, beside `protocol_version`:

  ```yaml
  cookie_name: '__Secure-mercure_access_token'
  ```

  Without it, mercure-bundle 0.6 drops the `__Secure-` prefix while `kernel.debug` is on, as it is in dev, so the API sets a cookie the hub doesn't read and admins get no private updates locally. The bundle's own steps, including the removed `Publisher` services, are in [Upgrading the Bundle → 2.0.0-alpha.10](/api/upgrading#_200-alpha10). See [Bundle Setup → Mercure Hub](/api/bundle-setup#mercure-hub).
- [ ] Optional: **move any edits you made to `bin/devops/setup.sh` or `k8s.sh` into `bin/devops/project.sh`**, so later releases are plain file copies ([!14](https://gitlab.com/silverback-web-apps/cwa/components-web-app/-/merge_requests/14), [`1a7c30b`](https://github.com/components-web-app/components-web-app/commit/1a7c30b2793f9ad17d1fe4979905e842cd85dec8), [`ed4c725`](https://github.com/components-web-app/components-web-app/commit/ed4c725417aa64318bebbe7054fba5bfa29e61cd)). First copy, from `setup.sh`, the block that sources `project.sh` and the `DOMAIN` line after it, and from `k8s.sh`, `check_kube_domain`, `persist_environment_url` and the `project_values` lines in `deploy`. A project without a `project.sh` deploys as before. See [CI/CD → Project hooks](/deployment/ci-cd#project-hooks).
- [ ] Optional: copy `bin/load-test/launch.js` and its `README.md` ([!13](https://gitlab.com/silverback-web-apps/cwa/components-web-app/-/merge_requests/13), [`0dca073`](https://github.com/components-web-app/components-web-app/commit/0dca073be853d4700310dc8f519989e0b3691445)). ### Rename your CI variables

The deploy scripts and pipelines read the new names only ([`3a4ab9a`](https://github.com/components-web-app/components-web-app/commit/3a4ab9a2996c7b2639c93fa3f2afd9d90c157185), [`1960c43`](https://github.com/components-web-app/components-web-app/commit/1960c431e3688591ce1d87e5f11d6ffdb541c9c4), [`151fa6f`](https://github.com/components-web-app/components-web-app/commit/151fa6fb4e46b62fe711783f7f078f4064183d64), [`d64c278`](https://github.com/components-web-app/components-web-app/commit/d64c278997770b07fb0c2d04ed2fa7383059ab03)). An old name that is still set is ignored without a warning, and its setting goes back to the default.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**Rename before, or in the same change as, copying the new scripts.** Two renames matter most for a live site. Without `CWA_CI_CLUSTER_ISSUER=letsencrypt-prod`, production gets a `letsencrypt-staging` certificate, which browsers don't trust. Without `CWA_CI_POSTGRES_ENABLED=false`, a site on an external database deploys the in-cluster PostgreSQL and the API connects to that, empty, instead of `DATABASE_URL`.
::

### In-cluster PostgreSQL

- [ ] **Rename any `POSTGRES_USERNAME` CI variable to `POSTGRES_USER`**, and copy `yaml_squote`, `postgres_auth_yaml` and the `postgresql:` block of `deploy` from `k8s.sh`, and `database-url` from `helm/cwa/templates/secrets.yaml` ([`e15f168`](https://github.com/components-web-app/components-web-app/commit/e15f16818a61f9a3f68697808bea5998bf34b0dc)). With the in-cluster PostgreSQL, `POSTGRES_USER`, `POSTGRES_PASSWORD` and `POSTGRES_DB` never took effect before this: every in-cluster database ran as `example` / `!ChangeMe!` / `api`. Set a real `POSTGRES_PASSWORD`. See [CI/CD → Database](/deployment/ci-cd#database).
- [ ] On GitLab, a `POSTGRES_*` variable with the **All** environment scope now also reaches the `functional tests` job, for both its database and its URL. Scope these variables to your deploy environments.
- [ ] Optional: keep the in-cluster database's data on a volume with `CWA_CI_POSTGRES_PERSISTENCE=true`, and `CWA_CI_POSTGRES_PERSISTENCE_SIZE` and `CWA_CI_POSTGRES_STORAGE_CLASS` if the defaults (`1Gi`, `standard`) don't suit. Copy `postgres_persistence_yaml`, `check_postgres_persistence`, the call to it in `deploy` and `delete` from `k8s.sh` ([`7675190`](https://github.com/components-web-app/components-web-app/commit/767519054d9b8473a42eb30144ea6eaeae65d39a)). On a live release the first deploy stops and prints the commands to run, because Kubernetes can't add a volume to the running PostgreSQL. **Turning it on starts the database empty**, so `pg_dump` it first if you need the data. See [CI/CD → In-cluster PostgreSQL persistence](/deployment/ci-cd#in-cluster-postgresql-persistence). Stopping a review app now deletes its PostgreSQL volume too.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**If you already set `POSTGRES_USER` (or `POSTGRES_USERNAME`), `POSTGRES_PASSWORD` or `POSTGRES_DB`, the next deploy changes the in-cluster database.** Without persistence, a new user or database name restarts the PostgreSQL pod empty, so load fixtures again. A new password alone doesn't restart it, and the API can't connect until you run `kubectl delete pod <release>-postgresql-0` after the deploy, which also starts it empty. To keep today's database, delete the variables instead. With persistence, change the credentials in PostgreSQL first (`ALTER USER`, `ALTER DATABASE`), then deploy.
::

### Fixtures

- [ ] **Fix the seeded layout once** ([#126](https://github.com/components-web-app/components-web-app/issues/126), [`6c0b9d8`](https://github.com/components-web-app/components-web-app/commit/6c0b9d8514e64ea42e4162eeeda8f50dbb582ce3)). The scaffold passed `'CwaLayoutPrimary'` to the fixture builder, which adds the `CwaLayout` prefix itself, so the `main` layout was stored as `CwaLayoutCwaLayoutPrimary` and pages fell back to the default layout instead of `primary.vue`. In `api/src/DataFixtures/Parts/CoreScaffoldPart.php`, change `$cwa->layout('main', 'CwaLayoutPrimary')` to `$cwa->layout('main', 'Primary')`. Fixtures keep existing rows, so also fix the stored value: set the `main` layout's UI component to `CwaLayoutPrimary` in the admin, or run

  ```sql
  UPDATE _acb_layout SET ui_component = 'CwaLayoutPrimary' WHERE ui_component = 'CwaLayoutCwaLayoutPrimary';
  ```

  then `bin/console silverback:api-components:purge-http-cache`, so cached pages pick it up.
- [ ] **Projects made with `create-cwa` without fixtures:** delete `api/src/DataFixtures/` if it's still there, and the `UsersFixture` and `AppScaffold` service definitions and `env(ADMIN_*)` parameters in `api/config/services.php` ([#127](https://github.com/components-web-app/components-web-app/issues/127), [`78478ed`](https://github.com/components-web-app/components-web-app/commit/78478ed90647a427646e9305057bb6b8b78a0fd2)). Earlier CLIs removed only `DataFixtures/Parts/`, so `AppScaffold` referred to deleted classes and `doctrine:fixtures:load` failed. Create the first admin with `bin/console user:create --admin`. Projects with fixtures can copy the attribute wiring instead: `#[Autowire(env: 'default::ADMIN_*')]` in `UsersFixture`, and `#[AutowireIterator]` in place of `#[TaggedIterator]` in `AppScaffold`, then delete those definitions from `services.php`.
- [ ] On GitLab, copy the `load fixtures production` rule for `CWA_CI_PRODUCTION_DISABLED` from `.gitlab-ci.yml` ([`e7d1be3`](https://github.com/components-web-app/components-web-app/commit/e7d1be335105348503aaf74e0407598756d34760)). With production switched off and fixtures on, GitLab refused to create the `main` pipeline, because the fixture job needed a production job that didn't exist.

## 2.0.0-alpha.14

Released 2026-10-08.

- [ ] **Keep `CLUSTER_ISSUER=letsencrypt-prod` on every production site**, and check it exists **before** you copy `bin/devops/setup.sh`. An unset `CLUSTER_ISSUER` gives `letsencrypt-staging` again, whose certificates browsers don't trust. alpha.12's advice that it could be deleted is withdrawn. An empty value still turns cert-manager off. See [CI/CD → Kubernetes](/deployment/ci-cd#kubernetes).
- [ ] **Serve the service worker through `@vite-pwa/nuxt`.** Replace alpha.13's `routeRules` `/sw.js` block in `app/nuxt.config.ts` with `registerWebManifestInRouteRules: true` in the `pwa` block. It sends `/sw.js` and the manifest with `public, max-age=0, must-revalidate`. Without that header on `/sw.js`, add a Cloudflare Cache Rule that bypasses the cache for `/sw.js` only, or visitors get updates up to two hours late. See [PWA → Serving the service worker](/nuxt-module/pwa#serving-the-service-worker).
- [ ] **Cloudflare:** set Browser Cache TTL to **Respect existing headers** (Caching → Configuration). A 4-hour default turned `/sw.js`'s `max-age=0` into `max-age=14400` for browsers ([#120](https://github.com/components-web-app/components-web-app/issues/120)). See [Cloudflare → Leave Cloudflare's cache alone](/deployment/cloudflare#leave-cloudflares-cache-alone).

Images: rebuild the app image. Cloudflare: no purge needed.

## Before 2.0.0-alpha.1

`2.0.0-alpha.1` (2026-09-24) is the template's first tagged release. A project generated before it may also need these:

- [ ] **GitLab merge request pipelines** ([`cf9c665`](https://github.com/components-web-app/components-web-app/commit/cf9c665e4d3c319e35e50c090887981738a840aa)). Earlier projects also create a merge request pipeline that holds only the unit tests. It fails, because no image has been built for it, and **Pipelines must succeed** then blocks the merge request. Add a `workflow:` rule with `if: $CI_PIPELINE_SOURCE == "merge_request_event"` and `when: never`, and limit the `unit tests` job to `branches`.
- [ ] **Production waits for builds and tests** ([`1280520`](https://github.com/components-web-app/components-web-app/commit/12805209f2e63ab7d029133e675837617d9a0a1d)). Earlier, production and canary needed only `staging`, so with `STAGING_ENABLED=false` the manual deploy could start before the images were built, deploy the previous `main` image and ignore failing tests. Add `build api`, `build app`, `unit tests` and the test job to the `needs` of both jobs in `.gitlab-ci.yml`, each with `optional: true`.
- [ ] **Cache warm exit code `141`** ([`6123387`](https://github.com/components-web-app/components-web-app/commit/612338799a4f642d1fd687537f834b39bd4c85d2)). A GitLab warm job could fail with `141` after every page returned `200`: `warm_cache` ended with `sort | head -3`, and under `pipefail` the `SIGPIPE` failed the job. In `bin/devops/k8s.sh`, replace `head -3` with `sed -n '1,3s#^#  #p'` (and drop the `sed` after it), and use `sed -n 1p` instead of `head -1` in other pipes.
- [ ] Delete `.github/workflows/publish-create-cwa.yml` if your project has it. It publishes the template's scaffolding CLI.
