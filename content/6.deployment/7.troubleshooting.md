## Local development

### `create-cwa` says a port is in use

The stack publishes ports 80 and 443 (Caddy in `php`), 3001 (the Nuxt dev server in `app`) and 5432 (PostgreSQL in `database`). `create-cwa` checks them before it downloads anything, and names what holds each one it finds in use:

- **A container**, usually another CWA project's stack. The message gives the command, `docker compose -p <project> stop`, or `docker stop <container>` for a container outside Compose.
- **A process on your machine.** For 80 and 443 that's often Laravel Valet (`valet stop`), Herd, nginx or Apache. For 5432 it's a local PostgreSQL (Postgres.app, or `brew services stop postgresql`).

For 3001 and 5432 you can move the stack instead: change `published: 3001` under `app:`, or `published: 5432` under `database:`, in `compose.override.yaml`. The CLI creates the project without starting the stack, so run `docker compose up -d` in it once the port is free. A `docker compose up` that fails with `port is already allocated` or `address already in use` has the same cause. See [Installation › Scaffold your project](/getting-started/installation#_1-scaffold-your-project).

### `create-cwa` says `docker info` failed

Docker is installed but its daemon isn't running. Start Docker Desktop, or the Docker service on Linux, wait until `docker info` answers, then run `docker compose up -d` in the project the CLI created. When `docker` isn't installed at all, the CLI doesn't offer to start the stack.

### `create-cwa` warns that Docker has too little memory

Under about 3.5 GiB of memory for Docker, the CLI warns that the stack needs about 4 GiB, and still starts it. With too little, a container can run out of memory, for example while the `app` container runs `pnpm install` or a build runs. In Docker Desktop, raise the memory in **Settings › Resources**, apply, and run `docker compose up -d` again.

### php stays unhealthy

`docker compose ps` shows `php` as `unhealthy`, or `docker compose up -d --wait` fails on it. Its health check requests `/_api/_/health` on a loopback-only site at port 2080 inside the container (see [Docker › Waiting for the stack](/deployment/docker#waiting-for-the-stack)). Read the last checks, and request the route yourself:

```bash
docker inspect -f '{{json .State.Health}}' $(docker compose ps -q php)
docker compose exec php curl -sS http://127.0.0.1:2080/_api/_/health
```

- **`503` with `"reason":"database"`:** the database is down or unreachable. Check `docker compose ps database` and its logs.
- **The connection is refused:** Caddy isn't running yet, because the entrypoint is still running `composer install` or the migrations (`docker compose logs php`). The check allows 300 seconds for that; a first `composer install` on a slow connection can take longer, and `php` turns healthy once it answers. If the start finished and it's still refused, the image's `api/Dockerfile` is newer than its Caddyfile, which has no port 2080 site: copy both, with `app/Dockerfile`, and run `docker compose build php app`.
- **`400`:** Symfony refused the `Host`. The check sends `BROWSER_SERVER_NAME` (default `localhost`), so it must match `TRUSTED_HOSTS`.

### Every page returns 502 or 503 after you run `pnpm install` on the host

In development, `compose.override.yaml` bind-mounts `app/` and `app/node_modules` into the `app` container, and that container runs `pnpm install` and then `pnpm dev`. A `pnpm install` on your machine, such as for a dependency bump, rewrites the shared `node_modules` while the container's dev server is still running from it. The dev server then crash-loops with errors like `Cannot find module 'typescript'`, a missing `@nuxt/cli/dist/dev/index.mjs` or `Cannot resolve module "@nuxt/kit"`, and Caddy returns 502 or 503 for every page. Restart the container so it reinstalls from inside:

```bash
docker compose restart app
```

When you check its logs afterwards, only look at lines after the restart. The crash from before it is still in the log and looks like a new failure. See [Docker › Development Workflow](/deployment/docker#development-workflow).

### Every dev page takes about 30 seconds

This is almost always **missing PostgreSQL statistics**, not slow I/O. CWA's components use Doctrine `JOINED` inheritance, so loading a page emits a wide multi-table join. The component subclass tables hold only a handful of rows each — permanently below the threshold that triggers PostgreSQL's autoanalyze — so those tables are never analysed, the planner has no statistics, and it wildly over-estimates the join and throws parallel workers at a query that returns almost nothing. Fix it by analysing the database once:

```bash
docker compose exec database psql -U app -d app -c 'ANALYZE;'
```

The current template does this automatically in the `php` entrypoint on every `compose up`, so fresh projects don't hit it — but a project scaffolded before that change, or a new small fixture table, can still trigger it. See [Docker › Starting the Stack](/deployment/docker#starting-the-stack).

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
This is easy to misdiagnose because it's a pure query-planner problem with **no I/O**. A near-idle database, tiny tables, and a 99% cache-hit ratio are all true *and completely consistent with it* — none of them rule the database out. If dev is mysteriously slow, go straight to `EXPLAIN (ANALYZE, BUFFERS)` and check `SELECT relname, reltuples FROM pg_class` for tables reporting `-1` (never analysed).
::

### `composer update` fails with a `raw.githubusercontent.com` 404

If Composer dies downloading a Symfony Flex recipes index with an HTTP 404, the cause is usually a **stale GitHub token** in the container's `/config/composer/auth.json`, not a network or GitHub outage. GitHub returns **404, not 401**, for a bad token on `raw.githubusercontent.com` — and a plain `curl` of the same URL returns 200 because it sends no token, which misleadingly "proves" the network is fine. The `/config` volume (`caddy_config`, see [Docker › Volumes](/deployment/docker#volumes)) persists across `compose down`/`up`, so the bad token survives restarts. Clear it:

```bash
docker compose exec php rm -f /config/composer/auth.json
```

Then re-run `composer update` (or set a valid `GITHUB_TOKEN`).

### Composer or php reports a missing `ffi` extension

The project's Composer dependencies require `ext-ffi` for the libvips imagine driver (see [Docker › Image processing](/deployment/docker#image-processing)). An image built before you took that change has no libvips or `ffi`. Rebuild the dev php image:

```bash
docker compose build php && docker compose up -d php
```

### Caddy reports `unexpected EOF` after you edit the Caddyfile

If Caddy fails with `unexpected EOF` while `api/frankenphp/Caddyfile` looks valid on disk, it's a stale-config issue, not a syntax error. On macOS/Windows (Docker Desktop), a **single-file** bind mount caches the file's size, so an edit that makes the file *longer* — what most editors' atomic save does — is served to the container truncated. Edits that shrink or keep the length work, which makes it look random. Confirm by comparing byte counts:

```bash
wc -c < api/frankenphp/Caddyfile
docker compose exec php sh -c 'wc -c < /app/frankenphp/Caddyfile'
```

If they differ, recreate the container (`restart` isn't enough): `docker compose up -d --force-recreate php`. The CWA template avoids this by reading dev config through the `./api` **directory** mount rather than mounting single files — you'll only hit it if you reintroduce a single-file mount in `compose.override.yaml`. Production is unaffected: the image bakes the Caddyfile in.

### The dev server loads, but nothing on the page responds

On Nuxt 4.5, if pages render but never hydrate, so buttons do nothing and the login form reloads the page, check the browser console for a `SyntaxError` about `__unhead_devtoolsPlugin` being declared twice. `@unhead/bundler` 3.4.1 registers its DevTools runtime import once for each of Nuxt's client and server Vite servers. Turn off unhead's own DevTools panel in `nuxt.config.ts`:

```ts
export default defineNuxtConfig({
  unhead: {
    vite: {
      devtools: false,
    },
  },
})
```

This only affects development. Nuxt DevTools and `useSeoMeta` still work, and the production build is unchanged. The template sets this ([#95](https://github.com/components-web-app/components-web-app/issues/95)). Remove it once an unhead release fixes the duplicate.

### The rate limit never triggers on the dev stack

The rate limit never applies to private addresses, so your own browser may never trigger it locally. To try it, send an `X-Forwarded-For` header with a public address: the request comes from a trusted private address, so Caddy believes the header. See [Docker › Origin protection settings](/deployment/docker#origin-protection-settings).

## Caddy and Souin

**Check every Caddyfile change with `bin/test/caddy-validate.sh`.** `frankenphp adapt` only parses the Caddyfile, so errors raised while Caddy loads its modules, like several below, pass it. The script runs `frankenphp validate`, which loads every module, for both `SERVER_NAME` shapes the template uses: Helm's `:80` and compose's several ports. From [template 2.0.0-alpha.43](https://github.com/components-web-app/components-web-app/releases/tag/v2.0.0-alpha.43) it also checks each with php forwarding Mercure to a hub of its own (scaled mode, still being built), and the hub's own `mercure-hub.Caddyfile`. Run it locally with `docker compose exec -T php sh -s < bin/test/caddy-validate.sh`. It checks the Caddyfile at `/etc/caddy/Caddyfile`, which is the copy built into the image, so rebuild php after editing. CI runs it too: from template `2.0.0-alpha.6` ([`843082a`](https://github.com/components-web-app/components-web-app/commit/843082a54c663a44bc6267314f491647ec94275e)), the unit-tests job does.

How the template's Caddyfile caches is in [Docker › The HTTP Cache in Caddy](/deployment/docker#the-http-cache-in-caddy).

### php won't start with `unrecognized directive` after you copy the template's Caddyfile

From template `2.0.0-alpha.4` (`4cbe05a`), the Caddyfile uses two Caddy modules that older php images don't have: `query_allowlist`, the template's own handler for the query allowlist (see [Origin Protection › Query Parameters on Pages](/deployment/origin-protection#query-parameters-on-pages)), and `rate_limit`, from `mholt/caddy-ratelimit`. An old image refuses the file. In dev, the `--watch` reload keeps the old config running, and the next restart crash-loops. Rebuild the image, or let CI build it:

```bash
docker compose build php && docker compose up -d php
```

### php won't start after you copy the template's Caddyfile, because an import isn't found

From [template 2.0.0-alpha.43](https://github.com/components-web-app/components-web-app/releases/tag/v2.0.0-alpha.43), the Caddyfile's `mercure` block imports the hub's settings from `mercure-hub.caddy`, which sits beside it. Copy `api/frankenphp/mercure-hub.caddy` and `mercure-hub.Caddyfile` too, and the `api/Dockerfile` line that copies them to `/etc/caddy/`, then rebuild php. If you had changed the hub's settings in your Caddyfile, move the change to `mercure-hub.caddy`. See [Real-Time Updates (Mercure) › In the Template](/api/real-time#in-the-template).

### php keeps restarting with `token recognition error at: '#'`

Comments inside the `@use_cache` expression break Caddy, and `frankenphp adapt` does not warn you. The text between the backticks is a CEL expression, not Caddyfile syntax. CEL has no comments. A `#` line inside the backticks is a parse error, but `frankenphp adapt` does not check the text inside the backticks, so it reports no problem. The error only appears at runtime, and the php container keeps restarting. Put comments above the block. After changing it, run `adapt`, then recreate the container and check that it becomes healthy:

```bash
docker compose up -d --force-recreate php
docker compose ps php      # should reach "healthy", not "Restarting"
```

### A cache matcher never matches when a cookie is absent

If you edit the Souin `@use_cache` expression in the Caddyfile, note that an **absent cookie does not equal `""`** in Caddy matchers — unlike a missing *header*, which does. A clause like `{http.request.cookie.api_component} == ""` only matches when the cookie is *present but empty*, so requests with no cookie at all (SSR, curl, health checks) silently miss the cache. Match on the `Cookie` header instead, so an absent or empty cookie both count as "not authenticated":

```caddyfile
!{http.request.header.Cookie}.matches("api_component=[^;]+")
```

### Nothing is cached after a full flush

The php log shows `BADGER-INSERTION-ERROR` or `DB Closed`. Unpatched Souin v1.7.9 closes the badger and nuts storages on a full flush, and they stay closed until php restarts. A full flush is **Purge all cached data**, `purge-http-cache`, every fixture load, and every deploy with `provider cloudflare`. The default in-memory otter storage is not affected. Template `2.0.0-alpha.7` adds `v1.7.9-flush-no-close.patch`, which empties the store and leaves it open ([#114](https://github.com/components-web-app/components-web-app/issues/114), [`8ebf5e9`](https://github.com/components-web-app/components-web-app/commit/8ebf5e994687014d0496da33a209eafd2137cd93)). If you use badger or nuts, take the patch and the matching lines in `api/Dockerfile`, then rebuild the API image. Until then, restart php after each full flush.

### The first visitor after a flush or a rollout gets a `504`

A page that renders cold in more than Souin's backend timeout gets a `504` from the cache, and Cloudflare passes it on. Souin's own default is 10 seconds, and a heavy CMS page took about 12. From template 2.0.0-alpha.38 the Caddyfile sets 30 seconds; raise it with `CWA_API_CADDY_CACHE_BACKEND_TIMEOUT`. A `timeout` block in `CADDY_CACHE_EXTRA_CONFIG` replaces the Caddyfile's whole block and brings the 10 seconds back. See [Docker › The cache store and backend timeout](/deployment/docker#the-cache-store-and-backend-timeout). To avoid cold renders in the first place, purge one page instead of everything: see [Cloudflare › Purges must reach Cloudflare](/deployment/cloudflare#purges-must-reach-cloudflare).

### Requests that waited on a failed render get an empty `200`

Souin sends only one request upstream for a URL that isn't cached, and the others for that URL wait for its response. In unpatched Souin v1.7.9, when that response was a `500`, `502`, `503` or `504`, the waiting requests got a `200` with an empty body and no `Cache-Status` header, and an SSR render could cache a broken page. Template `2.0.0-alpha.20` adds `v1.7.9-singleflight-5xx.patch`, so they get the same error ([#137](https://github.com/components-web-app/components-web-app/issues/137), [`6df1b15`](https://github.com/components-web-app/components-web-app/commit/6df1b15050970bbc45e8348d10d0a9787477365c)). A `5xx` that is private or sets a cookie isn't shared: each waiting request goes upstream itself. `bin/test/souin-coalesced-5xx.sh`, in the unit-tests job, fails on an unpatched binary. To take it, copy the patch, add its `COPY` and `patch` lines to `api/Dockerfile` straight after the singleflight fix's, and rebuild the API image.

### php is OOMKilled while serving a large file

Souin reads the whole body of a cacheable response into memory before it decides anything, so a large file served through the cache can take php past its memory limit. Keep large files out of `@use_cache`: see [Docker › What the page cache stores](/deployment/docker#what-the-page-cache-stores).

### `PURGE` or `BAN` sent to the site returns `405`

That's intended: they never purged anything. See [Docker › `PURGE` and `BAN`](/deployment/docker#purge-and-ban-sent-to-the-site-return-405).

## Mercure

The module's own checks for live updates are in [Real-time Updates › Troubleshooting](/nuxt-module/component-helpers/real-time-updates#troubleshooting).

### php won't start after rebuilding with Mercure 1.0

FrankenPHP 1.13 ships Mercure 1.0, which treats unknown directives as errors and has removed `demo` and `ui`. If `MERCURE_EXTRA_DIRECTIVES` sets either, use `debugger` instead, in development only. The template's Caddyfile uses an `issuer` block, which a 0.x Mercure doesn't know, so rebuild the API image before you restart php with the new Caddyfile. Two errors mean the Caddyfile and the binary don't match:

- `the "publisher_jwt", "subscriber_jwt", … directives work only in compatibility mode`: the old top-level `publisher_jwt` and `subscriber_jwt` directives are still there. Move the keys into an `issuer` block, as described in [Hub Caddyfile](/api/real-time#hub-caddyfile).
- `an issuer identifier is required in modern mode`: the Caddyfile is still set up for compatibility mode (`protocol_version_compatibility` with top-level `publisher_jwt` and `subscriber_jwt`), but the binary was built without the `deprecated_topic` and `deprecated_claim` tags, so the hub runs in modern mode anyway. Remove the directive and move the keys into an `issuer` block.

`caddy adapt` reports neither error. Only a running hub does, so check php's logs after it starts.

### php won't start with `only one unnamed Mercure hub is allowed per configuration`

An API image built with Mercure 1.0.3 or later refuses the compose stack's Caddyfile unless the `mercure` block has a `name`. Compose's `SERVER_NAME` has several ports, so Caddy runs one server per port, each with its own hub. The healthcheck never passes, and the error only shows in the php container's log. Add `name cwa` to the `mercure` block, as template `2.0.0-alpha.5` does ([#113](https://github.com/components-web-app/components-web-app/issues/113)), then recreate php. From [template 2.0.0-alpha.43](https://github.com/components-web-app/components-web-app/releases/tag/v2.0.0-alpha.43) the line is in `mercure-hub.caddy`. See [Hub Caddyfile](/api/real-time#hub-caddyfile).

### Admins get no private updates locally

With a Mercure 1.0 hub, the cookie is `__Secure-mercure_access_token`, and browsers only accept it over HTTPS. The template's dev stack serves the hub at `https://localhost/.well-known/mercure`, so this works out of the box. `mercure.yaml` pins the name as `cookie_name`, because mercure-bundle 0.6 drops the `__Secure-` prefix when `kernel.debug` is on, as it is in dev, and the hub then wouldn't read the cookie (template `2.0.0-alpha.18`, [`b71fd4d`](https://github.com/components-web-app/components-web-app/commit/b71fd4d1f6193ab6c80fd05c07a9cb3e576414fe)). If you change `CADDY_MERCURE_PUBLIC_URL` to a plain `http://` URL, change that `cookie_name` to a prefix-less name, and set the same name as the hub's `cookie_name`, in `mercure-hub.caddy` from [template 2.0.0-alpha.43](https://github.com/components-web-app/components-web-app/releases/tag/v2.0.0-alpha.43) or the Caddyfile's `mercure` block before it (see [The subscriber cookie](/api/real-time#the-subscriber-cookie)).

If the API and the front end are on different subdomains, also check the cookie's `SameSite`: see [Docker › Environment Variables](/deployment/docker#environment-variables).

## Nuxt

### The sitemap is empty, or the Nuxt log shows `UND_ERR_HEADERS_OVERFLOW`

Node refuses a response whose headers pass 16 KB by default, and a large collection's `Surrogate-Key` can pass that. The app image raises Node's limit with `NODE_OPTIONS=--max-http-header-size=65536`; a deploy that sets its own `NODE_OPTIONS` replaces that. See [Cloudflare › Purges must reach Cloudflare](/deployment/cloudflare#purges-must-reach-cloudflare).

## Database

### The in-cluster PostgreSQL restarts empty, or the API can't connect after a credentials change

Without persistence, changing the user or database name on a live site restarts the PostgreSQL pod empty, and a new password alone leaves the API unable to connect. See [CI/CD Variables › Database](/deployment/variables#database).

## Kubernetes deploys

### The php image build hangs on `apt-get` or `install-php-extensions`

An uncached php build fetches packages from Debian. Over plain HTTP that fetch could stall until the CI job's one-hour limit, which happened on GitLab SaaS's small runners. From template 2.0.0-alpha.42 apt uses HTTPS, and each fetching step has a time limit and up to three attempts, logged as `retry-fetch: attempt <n> failed or passed <s>s: …`. A project on an older template can take `api/frankenphp/retry-fetch.sh` and the `frankenphp_base` changes in `api/Dockerfile`. See [Docker › PHP Dockerfile stages](/deployment/docker#php-dockerfile-stages).

### The review job is orange and says `No namespace '<name>'`

The branch has no Kubernetes namespace, so it has no review app. Create the namespace and its role bindings, then run the job again. See [CI/CD › Review Apps](/deployment/ci-cd#review-apps).

### The deploy fails before Helm runs

The deploy checks several things before it changes anything in the cluster, and its log says which one failed and what to change:

- **No `DOMAIN`, or one that starts or ends with a dot:** the environment url or `KUBE_INGRESS_BASE_DOMAIN` is empty. See `check_kube_domain` in [The Devops Scripts](/deployment/ci-cd#the-devops-scripts).
- **The php memory budget doesn't fit:** see [CI/CD Variables › php memory budget](/deployment/variables#php-memory-budget).
- **`Site environment variables (NUXT_*, CWA_API_*) that can't be passed through`:** see [Reserved names](/deployment/variables#reserved-names).
- **`CWA_ENVIRONMENT must be letters, digits, '.', '_' or '-'`:** see [The environment name](/deployment/variables#the-environment-name).
- **The PostgreSQL persistence settings differ from the live database:** see [In-cluster PostgreSQL persistence](/deployment/variables#in-cluster-postgresql-persistence).
- **`CADDY_CACHE_CDN_CONFIG is incomplete, so php would not start`:** see [Cloudflare › Secrets](/deployment/cloudflare#secrets).
- **`The Souin cache settings would be ignored or replaced`:** `CADDY_CACHE_EXTRA_CONFIG` names a store or holds a `timeout` block, or `CWA_API_CADDY_CACHE_BACKEND_TIMEOUT` isn't a Go duration. A project updated from before template 2.0.0-alpha.38 usually still has `CADDY_CACHE_EXTRA_CONFIG=otter`: delete it. See [CI/CD Variables › HTTP cache](/deployment/variables#http-cache).
- **`A storage path prefix cannot contain "."` (or `".."`), or `GCLOUD_PATH_PREFIX can't contain a 'review' segment`:** see [Storage path prefix](/deployment/variables#storage-path-prefix).
- **`The API's scaling settings can't be deployed`:** more than one API pod, or a `redis` cache store, without scaled mode, which is still being built. Keep the API at one pod. The message lists each problem; the other refusals are in [Scaled Mode › What the deploy refuses](/deployment/scaled-mode#what-the-deploy-refuses). See [Kubernetes & Helm › php stays at one replica](/deployment/kubernetes#php-stays-at-one-replica).
- **A new hostname's certificate wasn't issued:** point its DNS at the ingress first. See [Changing a live site's hostnames](/deployment/ci-cd#changing-a-live-sites-hostnames).

### The deploy stops with `MIGRATIONS PLAN FAILED`, `DATABASE BACKUP FAILED` or `MIGRATIONS FAILED`

These come from the optional database step before the rollout, and none of them changes the live site's code. A plan fails when the dry run of the migrations fails. (A migration that writes data from `up()` or `postUp()` instead of with `addSql()` no longer fails it: the plan lists it without SQL and the deploy warns, from [template 2.0.0-alpha.43](https://github.com/components-web-app/components-web-app/releases/tag/v2.0.0-alpha.43); see [Migrations and Backups › The migrations plan](/deployment/migrations-and-backups#the-migrations-plan).) A backup fails on a missing, public or media `CWA_CI_DATABASE_BACKUP_BUCKET`, or a missing or media `CWA_CI_DATABASE_BACKUP_GCLOUD_JSON`, and a dump bigger than `CWA_CI_DATABASE_BACKUP_STORAGE` (5Gi) gets its Job evicted. On GitLab, a Protected key variable never reaches a branch that isn't protected (see [Migrations and Backups › The backup bucket](/deployment/migrations-and-backups#the-backup-bucket)). If the log says **MAINTENANCE MODE IS ON**, a maintenance window was open: its last lines say how to restore the backup and turn maintenance off. The next production deploy ends the window, with or without `CWA_CI_MAINTENANCE_DURING_MIGRATIONS` (see [Migrations and Backups › When the window fails](/deployment/migrations-and-backups#when-the-window-fails)). See [Migrations and Backups](/deployment/migrations-and-backups).

### A review deploy stops with `REVIEW APP NOT DEPLOYED`

The review app's external `DATABASE_URL` names production's database (the same host, port and database), which a review app would migrate. On GitLab this usually means production's `DATABASE_URL` and `CWA_CI_POSTGRES_ENABLED="false"` are scoped to **All** environments. Scope them to `production`, or give review apps a database of their own. See [Migrations and Backups › A track on production's database](/deployment/migrations-and-backups#a-track-on-productions-database). *Since [template 2.0.0-alpha.43](https://github.com/components-web-app/components-web-app/releases/tag/v2.0.0-alpha.43).*

If the log instead warns `could not read production's database URL`, the check couldn't find production: set `RELEASE_PRODUCTION` or `KUBE_NAMESPACE_PRODUCTION` if production's release or namespace has another name, or give the review job read access to production's Secret.

### The deploy fails with `No digest for …`, or warns `Couldn't tag … as production`

`No digest for <image>:<tag>` stops the deploy before Helm runs. It means the pipeline had no build digest and the branch tag isn't in the registry, for example after `CWA_CI_BUILD_DISABLED` on a branch that was never built. See [CI/CD › Which build a deploy runs](/deployment/ci-cd#which-build-a-deploy-runs).

`Couldn't tag <image>@<digest> as production` comes after a deploy that succeeded, when the registry refused to copy the build to the track's tag (`:staging`, `:canary` or `:production`) three times. The deploy only warns, the pods run the new build, and the next deploy copies the tag. On GitHub, check that the deploy job's `permissions` include `packages: write`. Before template `724f51d` (on `main` after 2.0.0-alpha.42), the copy came before Helm and a refusal stopped the deploy.

### The deploy fails with `THE cwa ROLLOUT DID NOT FINISH`

The new API pods (or Nuxt pods, for `cwa-pwa`) didn't become ready within `CWA_CI_DEPLOY_ROLLOUT_TIMEOUT` seconds (900). The usual cause is a migration that fails when the pod starts. The old pods keep serving and the track's image tag stays on the last good build. The log prints the `kubectl describe` and `kubectl logs` commands to find out why. Fix forward and deploy again, or roll back with [Kubernetes & Helm › Rollback](/deployment/kubernetes#rollback). *Since [template 2.0.0-alpha.43](https://github.com/components-web-app/components-web-app/releases/tag/v2.0.0-alpha.43).*

### A GitLab review environment is stuck in *stopping*

On a template before 2.0.0-alpha.38, **stop review** checked out its branch, so once the branch was deleted it failed in `get_sources` with exit code `128`, and the review app kept running. Copy the template's `stop review` job, then clean up the stuck one by hand. See [CI/CD › Review Apps](/deployment/ci-cd#review-apps).

### A review app's uploads return `404` after a deploy

A review app deployed before template 2.0.0-alpha.37, or on alpha.37, moves to a new storage path on its next deploy, and its earlier uploads stay at the old one. Load its fixtures again with `CWA_CI_FIXTURES_PURGE=true`, or recreate it. See [Review app paths](/deployment/variables#review-app-paths).

### `helm rollback` still runs the newer code

On a template before 2.0.0-alpha.35, every release ran the moving branch tag with `pullPolicy: Always`, so a rollback pulled whatever that tag held. From alpha.35 each release is pinned by digest. See [Kubernetes › Rollback](/deployment/kubernetes#rollback).

### GitLab rejects the pipeline: a job needs `warm cache <track>` or `image variants <track>`

From template 2.0.0-alpha.31 those are one job, `image variants and warm <track>`. Change the `needs:` in your own job. See [CI/CD › One job for variants and the warm](/deployment/ci-cd#one-job-for-variants-and-the-warm).

### A new php pod takes longer to become ready

Its `postStart` hook warms the `/_api` cache first, in two passes (gzip, then br) of up to `CWA_CI_API_WARM_HTTP_CACHE_MAX_TIME` seconds (60) each, and Kubernetes starts no probe until the hook returns. From template 2.0.0-alpha.38 that's up to 60 seconds longer than before, for the `br` pass. The old pod keeps serving meanwhile. The warm's summary is in the pod's log. See [Kubernetes › Warming the API cache on start](/deployment/kubernetes#warming-the-api-cache-on-start).

### `var/log/prod.log` is missing, or the API's log is empty

From template 2.0.0-alpha.34, production logs to stderr as JSON: read it with `kubectl logs` or your cluster's log explorer. A request's lines are written only when it logs an error. See [Kubernetes › Logs](/deployment/kubernetes#logs).

### No error mail arrives

`CWA_API_ERROR_MAIL_TO` needs a working `MAILER_DSN` and a `MAILER_EMAIL` to send from. A failed send is dropped without a log line, only a `5xx` sends one, and each unique error sends at most one an hour per pod. See [Kubernetes › Error mail](/deployment/kubernetes#error-mail).

### The API pod stays unready, and every probe times out

The php probes request `/_api/_/site_config_parameters.jsonld`, a path that would pass through the Souin cache. Souin combines concurrent requests for the same cache key into one request to php. In unpatched Souin 1.7.9, a request that is given up while php is still working keeps hold of that key, so every later probe waits for the 10-second backend timeout and fails, and the pod stays unready for good. The template prevents this three ways:

- The template's Souin build applies the fix from [darkweak/souin#850](https://github.com/darkweak/souin/pull/850) (`api/frankenphp/souin/v1.7.9-singleflight-fix.patch`), so a request that times out releases the key. The patch can be removed once a Souin release includes it.
- The Caddyfile's `@use_cache` skips the probe path for the kubelet's `kube-probe/` user agent, so probes always reach php.
- Liveness uses the same request as readiness, so a pod whose php has stopped answering is restarted.

Also keep `timeoutSeconds: 5` on both probes. See [Kubernetes › Health Checks](/deployment/kubernetes#health-checks).

### Visitors get `502` while a deploy rolls out

A pod that closes its listener as soon as it's told to stop still gets requests for a few seconds, until the ingress and php's proxy drop its endpoint. The chart's `preStop` hooks hold both pods open for 5 seconds first. If your chart has no `lifecycle.preStop` blocks, copy them from the template's `deployment.yaml` and `pwa-deployment.yaml`. The first deploy with them still rolls the old pods without the hook. See [Kubernetes › Stopping a pod without 502s](/deployment/kubernetes#stopping-a-pod-without-502s).

### The image variants and warm job ends with `ran out of memory (exit 137)`

The Job generating variants went over its own memory limit. The site isn't affected, because the Job doesn't serve requests. Raise `CWA_CI_IMAGE_VARIANTS_MEMORY`, or lower `CWA_CI_IMAGE_VARIANTS_MAX_MEMORY` so each Job stops sooner and the next one carries on. See [CI/CD › Generating image variants after a deploy](/deployment/ci-cd#generating-image-variants-after-a-deploy).

### Visitors get `503` under load

php gives up on a request that waits too long for a free worker, rather than letting it queue into a `504`. See [Origin Protection › Load shedding](/deployment/origin-protection#load-shedding).

### The per-visitor rate limit never applies

Every visitor looks internal when the ingress controller's Service uses `externalTrafficPolicy: Cluster`. Set it to `Local`, and check `visitor_ip` in php's access log. See [Origin Protection › Ingress rate limits](/deployment/origin-protection#ingress-rate-limits).

## Browser tests

### The browser tests fail with `API writes the API refused as a mismatched request`

An API write got a `405`, `406` or `415`: the front end sent a method, `Accept` or `Content-Type` the API doesn't take for that resource. The message lists each request. See [Browser Tests › What they check](/deployment/browser-tests#what-they-check).

### The browser tests fail with `The API answered with a server error during the run`

Every test passed, but the API sent an error mail, so a request got a `5xx` that the UI didn't show. Find it in the php log the job prints, or keep the stack with `E2E_KEEP_STACK=true` and read its log. See [Running them locally](/deployment/browser-tests#running-them-locally).

### The browser tests fail with `Not every test ran and passed`

A test was skipped, or `--grep` or `test.only` left one out. Every listed test must run in CI. See [Browser Tests](/deployment/browser-tests#what-they-check).

### The browser tests fail on `pages in the sitemap`, `a second page in the sitemap` or `og:image`

The template's tests take their pages from the sitemap. The sitemap must list at least two pages, and the first one must have an `og:image` tag. Run the tests with `E2E_KEEP_STACK=true`, read the sitemap with `docker compose -p <stack> -f e2e/compose.yaml exec php curl -sk https://localhost/sitemap.xml`, and make sure your fixtures publish the pages it should list. See [Browser Tests › What they check](/deployment/browser-tests#what-they-check).

### The browser tests can't start the images on an ARM Mac

Images from your CI registry are amd64 only. Set `DOCKER_DEFAULT_PLATFORM=linux/amd64`, or build the images locally. See [Running them locally](/deployment/browser-tests#running-them-locally).

## Cloudflare

### Cloudflare returns `526` for a new hostname or after a staging deploy

The origin's certificate isn't valid yet. See [Cloudflare › DNS and TLS](/deployment/cloudflare#dns-and-tls) and [Each deploy track](/deployment/cloudflare#each-deploy-track).

### A certificate can never be issued or renewed behind Cloudflare

**Always Use HTTPS** redirects the HTTP-01 challenge. Turn it off. See [Each deploy track](/deployment/cloudflare#each-deploy-track).

### An edit doesn't show at the edge

See [Cloudflare › Checking purges](/deployment/cloudflare#checking-purges) for the log messages and how to check that purges arrive.

### Pages stay `DYNAMIC` under the Cache Rule

Cloudflare doesn't cache a response that carries `Set-Cookie`. See [The cache rules must match the template's exclusions](/deployment/cloudflare#the-cache-rules-must-match-the-templates-exclusions).

### Pages built from page data all show one page's content after client-side navigation

The API rule is missing the component positions exclusion. See [Cloudflare › API responses](/deployment/cloudflare#api-responses-optional).

### Browsing quickly gets a `429` from Cloudflare

A rate limiting rule is set too low. See [Free protection worth turning on](/deployment/cloudflare#free-protection-worth-turning-on).
