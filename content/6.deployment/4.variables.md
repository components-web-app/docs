The template's pipeline is configured with CI/CD variables. Set them in **Settings → CI/CD → Variables** in GitLab. On GitHub, set them as Actions variables, except the ones the workflows map from secrets (see [CI/CD › GitHub Actions](/deployment/ci-cd#github-actions)).

If you deploy with the template's pipeline, you only set variables. `bin/devops/k8s.sh` turns them into the chart's values and runs Helm. The **Helm value** column below says where each one ends up, so you can read it alongside [Kubernetes & Helm](/deployment/kubernetes). A `—` means the variable steers the pipeline and sets no chart value.

## Minimum for a new site

The deploy works out the settings that would otherwise be the same on every site: `CWA_CI_INGRESS_ENABLED`, `CORS_ALLOW_ORIGIN`, `TRUSTED_HOSTS`, `MERCURE_CORS_ORIGIN` and `DATABASE_SSL_MODE`. A variable you set still wins. The host-based defaults use the deploy's own hostname, plus `KUBE_INGRESS_ALIAS_DOMAINS` in production, so review apps and staging get their own instead of production's.

So a new site sets only what is its own:

- [ ] **The cluster connection:** `KUBE_CONTEXT` (GitLab agent context), or on GitHub the `KUBECONFIG` and `KUBE_CONTEXT` secrets and the `KUBE_NAMESPACE_PRODUCTION` secret. See [Kubernetes and hostnames](#kubernetes-and-hostnames).
- [ ] **The domain:** `KUBE_INGRESS_BASE_DOMAIN`.
- [ ] **The database:** `DATABASE_URL` with `CWA_CI_POSTGRES_ENABLED="false"`. See [Database](#database).
- [ ] **The media bucket:** `GCLOUD_JSON`, `GCLOUD_BUCKET` and optionally `GCLOUD_PUBLIC_URL`, plus `GCLOUD_PATH_PREFIX` if other apps use the bucket. See [Media storage](#media-storage).
- [ ] **The mailer:** `MAILER_DSN` and `MAILER_EMAIL`.
- [ ] **The first admin:** at least `ADMIN_PASSWORD`. See [Application](#application).
- [ ] **A trusted certificate:** `CWA_CI_CLUSTER_ISSUER=letsencrypt-prod`, once production's domain points at the cluster.
- [ ] Recommended for production: the [secrets](#secrets) (`APP_SECRET`, `MERCURE_JWT_SECRET` and the JWT key pair). They're optional: a deploy keeps the release's live values, and generates them only for a new release.

[Deploying a CWA Site](/deployment) walks through these in order.

## Naming rules

The variables follow three naming rules:

- **`CWA_CI_*`** are the template's own pipeline and deploy switches, such as `CWA_CI_STAGING_ENABLED` or `CWA_CI_PWA_AUTOSCALE_MIN`. The sizing of the php pod is `CWA_CI_API_*`.
- **`CWA_API_*`** and **`NUXT_*`** are settings the containers read at runtime, passed through by prefix. See [Site settings](#site-settings).
- Site values, secrets and names set by the platform keep their own names: `DATABASE_URL`, `POSTGRES_*`, `APP_SECRET`, `JWT_*`, `MERCURE_JWT_SECRET`, `MAILER_*`, `GCLOUD_*`, `ADMIN_*`, `CORS_ALLOW_ORIGIN`, `TRUSTED_HOSTS`, `MERCURE_CORS_ORIGIN`, `DATABASE_SSL_MODE`, `CADDY_CACHE_CDN_CONFIG`, `GITHUB_TOKEN`, `KUBERNETES_VERSION`, `HELM_VERSION`, and the `KUBE_*` and `CI_*` variables.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**Template 2.0.0-alpha.16 renamed the switches, and the old names are no longer read.** A project that still sets `POSTGRESQL_ENABLED`, `CLUSTER_ISSUER`, `ENABLE_DATABASE_FIXTURES` or another old name gets the default instead, without a warning. The full list is in [the template 2.0.0-alpha.16 release notes](https://github.com/components-web-app/components-web-app/releases/tag/v2.0.0-alpha.16).
::

::callout{icon="i-heroicons-information-circle"}
**GitLab environment scopes:** the staging job runs under `environment: production`, so a variable scoped to `production` reaches staging too, as well as canary and production.
::

## Kubernetes and hostnames

| Variable | Default | Helm value | Notes |
|----------|---------|------------|-------|
| `KUBE_CONTEXT` | **required** | — | GitLab agent context, e.g. `my-group/my-project:my-agent`. On GitHub it's a secret, used with the `KUBECONFIG` secret |
| `KUBE_NAMESPACE` | `$CI_PROJECT_NAME-$CI_ENVIRONMENT_SLUG` | — | The pre-created namespace for this environment. On GitHub, staging and production use the `KUBE_NAMESPACE_PRODUCTION` secret |
| `KUBE_INGRESS_BASE_DOMAIN` | **required** | `ingress.hosts`, through `DOMAIN` | Base domain for ingress URLs, e.g. `k8s.example.com`. Production is served at it, staging at `staging.<it>` and review apps at `<branch>-review.<it>` |
| `CI_ENVIRONMENT_URL` | set by GitLab | `ingress.hosts`, through `DOMAIN` | Full URL of this environment. `DOMAIN` is its host. Required unless `DOMAIN` is set; without either, the deploy fails |
| `CWA_CI_CLUSTER_ISSUER` | `letsencrypt-staging` | `ingress.annotations` `cert-manager.io/cluster-issuer` | The cert-manager ClusterIssuer. See below |
| `KUBE_INGRESS_ALIAS_DOMAINS` | — | `ingress.annotations` `server-alias`, `ingress.tls` | Comma-separated extra domains for production. Production's certificate covers them. See [Changing a live site's hostnames](/deployment/ci-cd#changing-a-live-sites-hostnames) |
| `CWA_CI_TLS_SECRET_NAME` | `letsencrypt-cert` | `ingress.tls[].secretName` | Prefix of the ingress's TLS secret. You don't need to change it when hostnames change |
| `CWA_CI_TLS_CERTIFICATE_TIMEOUT` | `600s` | — | How long a deploy waits for a new certificate when production's hostnames change |
| `CWA_CI_INGRESS_ENABLED` | `"true"` | `ingress.enabled` | Set `"false"` to deploy without an ingress |
| `CWA_CI_WWW_REDIRECT` | `"false"` | `ingress.annotations` `from-to-www-redirect` | Sets ingress-nginx's annotation, which redirects between `example.com` and `www.example.com` |
| `KUBERNETES_VERSION` | `1.31.0` | — | The kubectl version the deploy jobs install |
| `HELM_VERSION` | `3.19.0` | — | The Helm version the deploy jobs install |

**`CWA_CI_CLUSTER_ISSUER`** defaults to `letsencrypt-staging` (set by `setup.sh`), whose certificates browsers don't trust. **Set `letsencrypt-prod` for production** once the domain points at the cluster. Until then, a misconfigured domain fails against the staging issuer's much higher limits instead of using up Let's Encrypt's production limits. An empty value turns cert-manager off. Keep the variable on every production site. Both issuers must exist in the cluster under these names (see [Deploying a CWA Site](/deployment#prepare-the-cluster)).

On GitHub, the workflows' setup actions read `vars.KUBERNETES_VERSION` and `vars.HELM_VERSION`. On GitLab, `setup.sh` sets the defaults only when no CI variable sets them ([`13243ae`](https://github.com/components-web-app/components-web-app/commit/13243aea131252dd9be88174b9d57a5b35a44864)).

## Secrets

| Variable | Default | Helm value | Notes |
|----------|---------|------------|-------|
| `APP_SECRET` | kept, else generated | `php.appSecret` | Symfony's secret, which signs URLs and other tokens |
| `JWT_SECRET_KEY` | kept, else generated | `php.jwt.secret` | The private key's contents |
| `JWT_PASSPHRASE` | kept, else generated | `php.jwt.passphrase` | The private key's passphrase. If you set `JWT_SECRET_KEY`, set this too, or the deploy fails |
| `JWT_PUBLIC_KEY` | derived | `php.jwt.public` | When you supply `JWT_SECRET_KEY` and leave this empty, it's derived from the key with `JWT_PASSPHRASE`, and the deploy fails if the passphrase doesn't decrypt the key |
| `MERCURE_JWT_SECRET` | kept, else generated | `mercure.jwtKey.publisher.key`, `mercure.jwtKey.subscriber.key` | Signs the Mercure publisher and subscriber tokens |
| `NUXT_APP_SECRET` | kept, else generated | none (the `<release>-pwa-env` Secret) | Nuxt's `appSecret`, which signs OG image URLs. At least 32 characters, or the deploy fails. See [The OG image secret](/nuxt-module/configuration/site-config-and-seo#the-og-image-secret) |

All of them are optional. For each one that isn't a CI variable, `deploy_secrets` reads the value from the release's live Secret, and generates a new one only when the release doesn't have one yet ([#144](https://github.com/components-web-app/components-web-app/issues/144), [`816997e`](https://github.com/components-web-app/components-web-app/commit/816997eaebb7cfb167172e38065042ee5a42f710)). The JWT key is kept together with its own passphrase, and the public key is derived from them. So logins, signed URLs and Mercure cookies survive a deploy, and pods on either side of a rollout agree. They're passed to Helm with `--set`, so they win over a project's [`project_values`](/deployment/ci-cd#project-hooks).

Setting them as **protected, masked** CI variables (GitHub: secrets) is still worth it for production. A release that is uninstalled, for example with `CWA_CI_HELM_UNINSTALL` or a stopped review app, loses its Secret, and its next deploy generates new values. A CI variable also lets you rotate a value on purpose.

To rotate a value, set a new one as the CI variable and deploy. Removing the variable doesn't rotate it, because the deploy then keeps the live value. For the JWT key pair, set `JWT_SECRET_KEY` and `JWT_PASSPHRASE`, and leave `JWT_PUBLIC_KEY` empty to have it derived. **A new JWT key pair signs every user out** when it's deployed, because tokens signed with the old key no longer verify.

The `JWT_*` values hold the keys' contents, for the deploy. The `functional tests` job unsets them, so they never reach the tests (see [CI/CD › Test](/deployment/ci-cd#test)).

## Application

| Variable | Default | Helm value | Notes |
|----------|---------|------------|-------|
| `CORS_ALLOW_ORIGIN` | `^https://(?:<hosts>)$` | `php.corsAllowOrigin` | Regex. Set it only when another origin calls the API from a browser |
| `TRUSTED_HOSTS` | `^(?:<hosts>\|localhost)$` | `php.trustedHosts` | Symfony trusted hosts regex. Wrap the alternatives in one anchored group, `^(?:www\.example\.com\|php)$`, see the warning below |
| `MERCURE_CORS_ORIGIN` | `https://<host>` for each host | `mercure.corsOrigin` | Space-separated origins the Mercure hub accepts |
| `ADMIN_USERNAME` | `admin` | `php.admin.username` | The super admin's username. Fixture loads create this user |
| `ADMIN_PASSWORD` | `admin` | `php.admin.password` | The super admin's password. **Set it to a long random value, masked (a secret on GitHub).** Every fixture load resets the admin's password to it. Unset or `admin`, the deploy and each fixture load warn, and still run: see [The admin password](#the-admin-password) |
| `ADMIN_EMAIL` | `hello@cwa.rocks` | `php.admin.email` | The super admin's email address |
| `MAILER_DSN` | — (`null://null`) | `php.mailer.dsn` | SMTP or SES DSN for transactional email. Unset, nothing is sent |
| `MAILER_EMAIL` | — | `php.mailer.email` | From address for outgoing email. Production's [orphan scan](#orphan-scan) also emails it |

`<hosts>` is the deploy's own hostname, plus `KUBE_INGRESS_ALIAS_DOMAINS` in production, with dots escaped.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**Anchor every `TRUSTED_HOSTS` alternative.** Symfony doesn't anchor the pattern as a whole, so in `^localhost|caddy|example\.com$` only the first alternative is tied to the start and only the last to the end. The middle one matches anywhere in a hostname: the template's old default trusted `evil-caddy.attacker.net`. Group the alternatives, `^(?:localhost|caddy|example\.com)$`. The template's own defaults use this form. Check the value in your CI variables, and in `api/.env`, `compose.yaml` and `helm/cwa/values.yaml` if your project predates template `2.0.0-alpha.3`.
::

### The admin password

`admin` / `admin` is the development login. On a deployed site it lets anyone sign in as super admin. A deploy (every track, review apps included) checks `ADMIN_PASSWORD`, and so does a fixture load, which checks the API pod's own value because that's the one it writes. When it's unset or `admin`, each prints this banner, and on GitHub Actions also a **Public admin password** warning annotation:

```text
WARNING: the super-admin login on <domain> is admin/admin.
ADMIN_PASSWORD is unset, so anyone can sign in as super admin, and every
fixture load resets the admin password to it. Set ADMIN_PASSWORD to a
long random value (a masked CI variable or secret), then deploy.
```

The second line says `'admin'` instead of `unset` when the value is `admin`, and `unset or 'admin' in the API pod` for a fixture load. The deploy still runs, and the default stays `admin`: the chart's admin Secret needs a value. Set the variable, deploy, then load fixtures (or sign in and change the password, which the next fixture load undoes). *On `main` after template 2.0.0-alpha.43 ([`80f63f3`](https://github.com/components-web-app/components-web-app/commit/80f63f3758d6951c4e26ed9eddcf7a095ce5f4fc)).*

`compose.prod.yaml` requires `ADMIN_PASSWORD`, and passes `ADMIN_USERNAME` and `ADMIN_EMAIL` when you set them (see [Docker › Production Docker Compose](/deployment/docker#production-docker-compose)). The development stack keeps `admin` / `admin` with no warning.

## Media storage

| Variable | Default | Helm value | Notes |
|----------|---------|------------|-------|
| `GCLOUD_JSON` | `{}` | `php.gcloud.jsonKey` | Service-account key JSON for the bucket. Store it as a secret |
| `GCLOUD_BUCKET` | `no-gcloud-bucket` | `php.gcloud.bucket` | Google Cloud Storage bucket for uploads |
| `GCLOUD_PUBLIC_URL` | bucket URL | `php.gcloud.publicUrl` | Base URL for media links, e.g. `https://cdn.example.com/`. Must end in a slash. If empty, uses `https://storage.googleapis.com/<bucket>/`. See [Kubernetes › Media URLs](/deployment/kubernetes#media-urls) |
| `GCLOUD_PATH_PREFIX` | empty | `php.gcloud.pathPrefix` | Path inside the bucket for this app's objects, e.g. `site-a/`. Empty stores at the bucket root. Review apps add `review/<slug>/` to it. See [Storage path prefix](#storage-path-prefix) |

On GitHub, set `GCLOUD_JSON` as a **secret** and the others as **variables**.

php also reads an optional `GCLOUD_API_ENDPOINT`: a Cloud Storage emulator to use instead of Google, with no credentials. Only the [browser tests](/deployment/browser-tests)' stack sets it. Leave it unset on every deploy, where empty means Google.

### Storage path prefix

*Since [template 2.0.0-alpha.37](https://github.com/components-web-app/components-web-app/releases/tag/v2.0.0-alpha.37)*

`GCLOUD_PATH_PREFIX` keeps an app's objects in one path of the bucket. Uploads and their image variants are stored under it, and the [orphaned files scan](/api/orphaned-data#orphaned-files) only lists that path. Unset, the app stores at the bucket root, as before.

Media URLs include the prefix once: `GCLOUD_PUBLIC_URL` (or the bucket's own URL), then the prefix. With `https://cdn.example.com/` and `site-a/`, files are served from `https://cdn.example.com/site-a/…`. So don't add the prefix to `GCLOUD_PUBLIC_URL` as well.

php and the deploy tidy the value the same way: surrounding whitespace is trimmed, doubled slashes are squeezed, leading and trailing slashes are removed and one trailing slash is added. So `/site-a` and `site-a//` both become `site-a/`, and a review app of `site-a//` stores under `site-a/review/<slug>/`. The deploy fails before it changes anything in the cluster when the prefix has a `.` or `..` segment, or a whole `review` segment, such as `review/` or `site/review`: `review/` is where review apps store, and the lifecycle rule deletes objects there (see [Review app paths](#review-app-paths)). `reviews/` and `my-review/` are fine ([#168](https://github.com/components-web-app/components-web-app/issues/168), [`82438ab`](https://github.com/components-web-app/components-web-app/commit/82438ab5e5f00716c94b6ab66499d0b4fa4207f7)). *Since [template 2.0.0-alpha.38](https://github.com/components-web-app/components-web-app/releases/tag/v2.0.0-alpha.38)*

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**A prefix with a `review` segment now fails the deploy.** Rename it first, and move its objects with it, as in [Changing a live app's prefix](#changing-a-live-apps-prefix).
::

Set it as its own CI variable. It's reserved (see [Reserved names](#reserved-names)), so `CWA_API_GCLOUD_PATH_PREFIX` fails the deploy. Local development stores uploads in `api/public/uploads` and doesn't use the prefix.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**Give every app on a shared bucket its own prefix.** An app at the bucket root scans the whole bucket, so the other apps' files are listed in its orphaned files report. They have the bundle's stored names, so they count as orphaned, and deleting every orphaned file removes them.
::

#### Review app paths

A review app always stores under `<GCLOUD_PATH_PREFIX>review/<slug>/`, so a review app never writes into production's path. `<slug>` is the environment slug, `CI_ENVIRONMENT_SLUG`, without its leading `review-`, so a branch `feat-x` stores under `review/feat-x/`, or `site-a/review/feat-x/` with a prefix ([#173](https://github.com/components-web-app/components-web-app/issues/173), [`1a98d54`](https://github.com/components-web-app/components-web-app/commit/1a98d54ac752bf23e787ffd5fa63c27f740733b3)). On GitHub the slug is `review-<branch slug>`. On GitLab it's GitLab's slug for `review/<branch>`, which GitLab shortens and may give a random suffix. A review deploy without `CI_ENVIRONMENT_SLUG` fails. Template 2.0.0-alpha.37 kept the `review-`, as in `review/review-feat-x/`.

Stopping a review app deletes its stored files ([CI/CD › Review Apps](/deployment/ci-cd#review-apps)). That step can fail, for example when the API pod isn't running, so add a bucket lifecycle rule as a backstop. It deletes objects under the review path some time after they were created:

```json
{
  "rule": [
    {
      "action": { "type": "Delete" },
      "condition": { "age": 90, "matchesPrefix": ["review/"] }
    }
  ]
}
```

With a `GCLOUD_PATH_PREFIX`, the review path is inside it, so add one rule per prefixed app on the bucket, with `matchesPrefix: ["<GCLOUD_PATH_PREFIX>review/"]`, such as `["site-a/review/"]`. Use `["review/"]` only for an app with no prefix. **The age counts from each object's creation, not from when the review app stops**, so a review app that lives longer than that loses its older uploads while it's still running. Pick an age longer than your review apps live. Setting a bucket's lifecycle configuration replaces its existing rules, so add this one to any you have.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**Review apps from older templates lose their uploads on their next deploy.** A review app deployed before template 2.0.0-alpha.37 stored at the bucket root. Its next deploy moves it to the review path, where its earlier uploads aren't, so they return `404` and the [orphaned files scan](/api/orphaned-data#orphaned-files) no longer sees them. A review app deployed on alpha.37 moves too, from `review/review-<slug>/` to `review/<slug>/`. For either, load its fixtures again with `CWA_CI_FIXTURES_PURGE=true` on the review fixture job, or stop the review app and deploy it again. Then delete the old objects by hand: a pre-alpha.37 app's are at the bucket root, and an alpha.37 app's old path is left to the lifecycle rule ([#169](https://github.com/components-web-app/components-web-app/issues/169)).

Stopping a pre-alpha.37 review app deletes nothing and prints a warning, because it has no review prefix. An alpha.37 review app that isn't deployed again still deletes its own path when it stops, because the delete runs with the prefix its pod has.
::

#### Changing a live app's prefix

The paths stored in the database are relative to the prefix. Before you set or change `GCLOUD_PATH_PREFIX` on a live app, copy its objects under the new prefix, keeping each object's path below it. Then deploy. The old objects stay where they were until you remove them.

### How long media is cached

From api-components-bundle 2.0.0-alpha.15, every file written to the bucket gets its own `Cache-Control`. Originals get `public, max-age=31536000, immutable`, because a stored name is never reused. Image variants get `public, max-age=2592000`, because a regenerated variant keeps its path. Files stored before then keep GCS's one-hour default until you back-fill them (template 2.0.0-alpha.25's upgrade notes).

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**Google Cloud CDN caps these unless you raise its TTLs.** A backend bucket sends browsers at most its **client TTL** and keeps its own copy for at most its **max TTL**. The defaults are one hour and one day, so a CDN created with them serves every file with `max-age=3600` whatever the bucket says. Raising a cap never lengthens a file's own TTL, so a year is safe for both. Template 2.0.0-alpha.42's upgrade notes ask every site behind Cloud CDN to do this ([#154](https://github.com/components-web-app/components-web-app/issues/154)).
::

Create the CDN's backend bucket with both caps at a year, or raise them on an existing one:

```bash
gcloud compute backend-buckets update <backend-bucket> --max-ttl=31536000 --client-ttl=31536000
```

Changes reach the CDN's edges within a few minutes. Invalidate the CDN host afterwards so files it already holds pick up the new headers: `gcloud compute url-maps invalidate-cdn-cache <url-map> --host <cdn host> --path "/*"`. To check, `curl -sI` a variant through the CDN: it should send `max-age=2592000`.

## Database

| Variable | Default | Helm value | Notes |
|----------|---------|------------|-------|
| `CWA_CI_POSTGRES_ENABLED` | `true` | `postgresql.enabled` | Set `"false"` to use an external database, which turns off the in-cluster PostgreSQL |
| `DATABASE_URL` | — | `postgresql.url` | Connection string when using an external database. On GitLab, scope production's to the `production` environment, or give review apps their own: a review deploy on production's database is refused (see [Migrations and Backups › A track on production's database](/deployment/migrations-and-backups#a-track-on-productions-database)). *Since [template 2.0.0-alpha.43](https://github.com/components-web-app/components-web-app/releases/tag/v2.0.0-alpha.43)* |
| `DATABASE_SSL_MODE` | `prefer`, or `require` when `CWA_CI_POSTGRES_ENABLED` is `"false"` | `php.databaseSSL.mode` | `disable`, `prefer`, `require`, `verify-full`. An external database is reached over the network, so it gets TLS by default |
| `DATABASE_CA_CERT` | — | `php.databaseSSL.ca` | CA cert PEM for SSL verification |
| `DATABASE_CLIENT_CERT` / `DATABASE_CLIENT_KEY` | — | `php.databaseSSL.cert` / `php.databaseSSL.key` | A client certificate and key, for a database that asks for one |
| `POSTGRES_USER` | `example` | `postgresql.global.postgresql.auth.username` | In-cluster PostgreSQL only: the database user. The name the postgres image, compose and the test jobs use. `POSTGRES_USERNAME` is not read |
| `POSTGRES_PASSWORD` | `!ChangeMe!` | `postgresql.global.postgresql.auth.password` | In-cluster PostgreSQL only: the user's password. Any character is safe |
| `POSTGRES_DB` | `api` | `postgresql.global.postgresql.auth.database` | In-cluster PostgreSQL only: the database name |
| `CWA_CI_POSTGRES_PERSISTENCE` | unset (off) | `postgresql.primary.persistence.enabled` | In-cluster PostgreSQL only: `true` keeps its data on a volume, `false` turns that off. Any other value fails the deploy |
| `CWA_CI_POSTGRES_PERSISTENCE_SIZE` | `1Gi` | `postgresql.primary.persistence.size` | The volume's size |
| `CWA_CI_POSTGRES_STORAGE_CLASS` | `standard` | `postgresql.primary.persistence.storageClass` | The volume's storage class. `-` sets none (Bitnami's `storageClassName: ""`), which turns off dynamic provisioning |
| `CWA_CI_POSTGRES_IMAGE_TAG` | `14` | `postgresql.image.tag` | The in-cluster PostgreSQL image tag |

With the in-cluster PostgreSQL (`CWA_CI_POSTGRES_ENABLED` not `"false"`), the deploy writes the three `POSTGRES_*` variables that are set to the chart's `postgresql.global.postgresql.auth`. Bitnami's subchart creates the database from those values, and the chart builds the API's `database-url` from them, percent-encoding each part ([`e15f168`](https://github.com/components-web-app/components-web-app/commit/e15f16818a61f9a3f68697808bea5998bf34b0dc)). An unset variable keeps the chart's default.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**By default the in-cluster PostgreSQL has no volume.** Its data lives in the pod and is lost whenever the pod is replaced, for example after a node restart or a credentials change. Use an external database (`DATABASE_URL` with `CWA_CI_POSTGRES_ENABLED="false"`) for a real site, or turn on persistence (see [In-cluster PostgreSQL persistence](#in-cluster-postgresql-persistence)).
::

PostgreSQL creates the user and database only when it starts on an empty data directory. Without persistence, **changing the user or database name on a live site restarts the PostgreSQL pod empty**, so the content has to be loaded again. A new password alone doesn't restart the pod, so the API can't connect until you run `kubectl delete pod <release>-postgresql-0`, which also starts it empty.

With persistence, the volume keeps the user, password and database it was created with, and a deploy doesn't change them. Change them in PostgreSQL first, as the `postgres` superuser, with `ALTER USER` or `ALTER DATABASE` (renaming a user clears its password, so set it again), then set the new values and deploy.

On GitLab, a `POSTGRES_*` variable with the **All** environment scope also reaches the `functional tests` job, where it replaces the job's own `runner`/`password`/`test`, for both the test database and its URL. Scope these variables to your deploy environments. On GitHub, the deploy jobs don't map them from secrets, so set them as Actions variables; the test job sets its own and ignores them.

### In-cluster PostgreSQL persistence

The three `CWA_CI_POSTGRES_*` persistence variables go to the chart's `postgresql.primary.persistence`, and only the ones that are set. Unset, the chart's defaults apply: no volume, and `standard` at `1Gi` once it's turned on ([`7675190`](https://github.com/components-web-app/components-web-app/commit/767519054d9b8473a42eb30144ea6eaeae65d39a)).

Kubernetes can't change a StatefulSet's volume once it exists, so Helm would fail part way through. Before anything changes, the deploy compares the variables with the live PostgreSQL and **stops when they differ**, with the commands to run and what happens to the data. It never deletes anything itself:

| Change on a live release | What the deploy tells you to do |
|--------------------------|---------------------------------|
| Turn persistence on | `pg_dump` the data if you need it, run `kubectl delete statefulset <release>-postgresql -n <namespace> --cascade=orphan`, and deploy again. The new pod starts with an empty volume, so load fixtures or restore the dump |
| Turn persistence off | The same `kubectl delete statefulset … --cascade=orphan`, then deploy. The new pod starts empty. The volume `data-<release>-postgresql-0` keeps its data until you delete it with `kubectl delete pvc` |
| Change the size | Set it back, or delete the StatefulSet with `--cascade=orphan` and deploy: the volume and its data are kept at the old size. To grow it, if the storage class allows expansion, patch the volume with the `kubectl patch pvc` command the log prints |
| Change the storage class | Set it back, or `pg_dump`, delete the StatefulSet with `--cascade=orphan` and the volume with `kubectl delete pvc`, deploy, and restore the dump |

A first deploy, with no PostgreSQL yet, can use any settings. If the CI can't read the StatefulSet, the deploy prints a warning and skips the check.

Helm leaves volumes behind when it uninstalls a release. **Stopping a review app also deletes its PostgreSQL volume**, so a branch deployed again starts with fresh data and credentials. Staging and canary keep theirs: a persistent staging volume outlives `delete staging`, so delete it by hand with `kubectl delete pvc data-<release>-staging-postgresql-0`. On GitLab, a `CWA_CI_POSTGRES_PERSISTENCE` scoped to `production` reaches staging and canary too.

### php memory budget

These size the php container's memory ([#136](https://github.com/components-web-app/components-web-app/issues/136), [`1868035`](https://github.com/components-web-app/components-web-app/commit/1868035b41a4edd48d42b84c2de736026c8f5ce6)):

| Variable | Default | Helm value | Notes |
|----------|---------|------------|-------|
| `CWA_CI_API_WORKERS` | `4` | `php.workers` | FrankenPHP's worker threads (`FRANKENPHP_WORKER_NUM`) |
| `CWA_CI_API_PHP_MEMORY_LIMIT` | `128Mi` | `php.memoryLimit` | Each request's PHP `memory_limit` (`FRANKENPHP_MEMORY_LIMIT`, as `128M`) |
| `CWA_CI_API_IMAGINE_MEMORY_LIMIT` | `320Mi` | `php.imagineMemoryLimit` | The limit the bundle raises a request to while it generates an imagine filter. Keep it equal to the bundle's `imagine.memory_limit`, whose default is `320M` |
| `CWA_CI_API_RESERVED_MEMORY` | `160Mi` | `php.reservedMemory` | opcache, APCu, the binaries and a console command run in the pod |

The budget is:

```
workers × PHP memory limit + (imagine limit − PHP memory limit) + reserved + Go ≤ CWA_CI_API_MEMORY_LIMIT
```

Go (Caddy, Souin and Mercure) gets what is left, as `GOMEMLIMIT`: with the defaults, 4 × 128 + 192 + 160 = 864Mi, which leaves Go 160Mi of 1Gi. The imagine limit counts once: the budget allows for one request generating a filter at a time.

**The deploy fails before it changes anything in the cluster** when the budget leaves Go under 64Mi, or when a value isn't a whole number or an `Mi`/`Gi` quantity. The log shows the sum and what to change. With a `CWA_CI_API_MEMORY_LIMIT` in another form, such as `1G`, the check is skipped and `GOMEMLIMIT` is left unset unless `CWA_CI_API_GOMEMLIMIT` sets it. So when you raise the workers or the PHP memory limit, raise `CWA_CI_API_MEMORY_LIMIT` too.

Console commands, such as the orphan scan or a `kubectl exec` into the pod, don't use `FRANKENPHP_MEMORY_LIMIT`. They run at the `memory_limit` of `256M` in `api/frankenphp/conf.d/10-app.ini`.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**Set the worker count with `CWA_CI_API_WORKERS`, not `CWA_API_FRANKENPHP_WORKER_NUM`.** `FRANKENPHP_WORKER_NUM` and `FRANKENPHP_MEMORY_LIMIT` are [reserved names](#reserved-names), so the deploy refuses them as site settings.
::

The template's `Image` entity accepts uploads up to 30 megapixels: what the 320M imagine limit can thumbnail with the template's libvips driver. If you switch the driver back to GD, lower it to 20 megapixels. See [Capping Uploads to Fit the Budget](/api/components/annotations/uploadable#capping-uploads-to-fit-the-budget).

Node also rarely hands memory back, and an HPA only scales down when every metric is under its target, so a memory target would add pods under normal load and then keep them. Set `CWA_CI_PWA_AUTOSCALE_MEMORY_PERCENT` if you want one anyway. If you set a variable, your value is used in every environment.

| `CWA_API_CADDY_TRUSTED_PROXIES` | `private_ranges` | `siteEnv.apiSecret` | Proxies whose `X-Forwarded-For` is believed. Add a public proxy's ranges, e.g. a Google load balancer: `private_ranges 35.191.0.0/16 130.211.0.0/22` |
| `CWA_API_CLOUDFLARE_IP_RANGES` | Cloudflare's published ranges | `siteEnv.apiSecret` | Only requests from these addresses are counted by `CF-Connecting-IP`. Update it if Cloudflare changes [its ranges](https://www.cloudflare.com/ips/) before a template release does |
| `CWA_API_FRANKENPHP_MAX_WAIT_TIME` | `5s` | `siteEnv.apiSecret` | A request that waits this long for a free php worker gets a `503` at once instead of queueing into a `504`. `0` turns it off. See [Origin Protection › Load shedding](/deployment/origin-protection#load-shedding) |
| `CWA_CI_INGRESS_RATE_LIMIT_RPS` | unset (off) | `ingress.annotations` `limit-rps` | ingress-nginx `limit-rps`. See [Origin Protection › Ingress rate limits](/deployment/origin-protection#ingress-rate-limits) before you set it |
| `CWA_CI_INGRESS_RATE_LIMIT_BURST_MULTIPLIER` | unset (nginx's default, 5) | `ingress.annotations` `limit-burst-multiplier` | Used only with `CWA_CI_INGRESS_RATE_LIMIT_RPS` |
| `CWA_CI_INGRESS_RATE_LIMIT_CONNECTIONS` | unset | `ingress.annotations` `limit-connections` | Used only with `CWA_CI_INGRESS_RATE_LIMIT_RPS` |

See [Rate limit on cache misses](/deployment/origin-protection#rate-limit-on-cache-misses) for what is counted and how the visitor's address is found.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**The per-visitor rate limit needs the cluster's ingress controller to keep the client address.** Set `externalTrafficPolicy: Local` on the ingress controller's own Service, ideally with 2 replicas and a PodDisruptionBudget, as the template's own cluster runs it. With the default `Cluster`, every request seems to come from a node's private address, so every visitor looks internal and the limit never applies ([#135](https://github.com/components-web-app/components-web-app/issues/135)). Check `visitor_ip` in php's access log. See [Origin Protection › Ingress rate limits](/deployment/origin-protection#ingress-rate-limits).
::

::callout{icon="i-heroicons-information-circle"}
`CADDY_EDGE` isn't a deploy variable. Only `compose.prod.yaml` sets it, and the chart doesn't pass it, so on Kubernetes it stays `false`. That's right there, because Caddy sits behind the ingress.
::

## HTTP cache

Souin's store and how long it waits for php or Nuxt, in the Caddyfile's `cache` block. See [Docker › The cache store and backend timeout](/deployment/docker#the-cache-store-and-backend-timeout). *Since [template 2.0.0-alpha.38](https://github.com/components-web-app/components-web-app/releases/tag/v2.0.0-alpha.38)*

| Variable | Default | Helm value | Notes |
|----------|---------|------------|-------|
| `CWA_API_CADDY_CACHE_BACKEND_TIMEOUT` | `30s` | `siteEnv.apiSecret` | How long Souin waits for a response before it answers `504`. A Go duration, such as `45s` or `1m30s`; the deploy refuses anything else, because Souin would ignore it and wait its own 10 seconds |
| `CWA_API_CADDY_CACHE_STORAGE` | `otter` | `siteEnv.apiSecret` | The store, one of those built into the image (see [Docker › PHP Dockerfile stages](/deployment/docker#php-dockerfile-stages)). The deploy doesn't check it, so a store the image doesn't have only shows up when Caddy starts. Check the image's build first. A store that names `redis` fails the deploy: a shared Redis is part of scaled mode. In scaled mode it must be unset, because the store is the release's own Redis, and a value fails the deploy (see [Scaled Mode › What the deploy refuses](/deployment/scaled-mode#what-the-deploy-refuses)). *Since [template 2.0.0-alpha.43](https://github.com/components-web-app/components-web-app/releases/tag/v2.0.0-alpha.43)* |
| `CADDY_CACHE_EXTRA_CONFIG` | empty | `php.caddy.extraConfig` | Other Souin directives for the `cache` block, one per line. Never a store or a `timeout` block: the deploy refuses both and names the variable to set instead |

Locally, compose passes the bare `CADDY_CACHE_BACKEND_TIMEOUT` and `CADDY_CACHE_STORAGE` through when they're set. The store is otter everywhere, on the dev stack, in the browser tests and on every deploy.

**Why the deploy refuses a store or `timeout` in `CADDY_CACHE_EXTRA_CONFIG`.** Souin accepts both without an error, and the result isn't what the Caddyfile says. A second store line leaves two stores configured, and a second `timeout` block replaces the first one whole, so `timeout { cache 1s }` alone puts the backend timeout back to 10 seconds. The check reads the first word of each line, and fails like this:

```
The Souin cache settings would be ignored or replaced:
  'otter' is a store: set CWA_API_CADDY_CACHE_STORAGE instead (default otter)
CADDY_CACHE_EXTRA_CONFIG is for other Souin directives only; delete it if it only restated these.
```

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**Older projects: take the store line and any `timeout` block out of `CADDY_CACHE_EXTRA_CONFIG` in the same deploy as the template update, and delete the variable if nothing is left.** Before template 2.0.0-alpha.38 the variable held the store: the deploy defaulted it to `otter`, so a project that set it had to repeat `otter`, and one that didn't silently lost otter for Souin's unbounded default store. The new deploy refuses an `otter` line. The chart's `php.caddy.storageConfig` is now `php.caddy.extraConfig`, and its Secret key `caddy-cache-storage-config` is now `caddy-cache-extra-config`, written only when the variable is set. There's no fallback to the old names.
::

## Site settings

A site's own settings, such as an analytics ID for Nuxt or an API key for a Symfony service, are CI variables. The Kubernetes deploy passes them to the containers by their prefix, so adding one needs no change to `k8s.sh`, the chart or a workflow ([#125](https://github.com/components-web-app/components-web-app/issues/125), [`497e8ac`](https://github.com/components-web-app/components-web-app/commit/497e8ac74cf3ba8b066982df0192bff238abd906), [`75a416b`](https://github.com/components-web-app/components-web-app/commit/75a416bc14edcdd601918bf44fa291f391abcbcf)).

| CI variable | Reaches | As | Stored in |
|-------------|---------|----|-----------|
| `NUXT_PUBLIC_<NAME>` | The Nuxt pods | `NUXT_PUBLIC_<NAME>`, unchanged | The ConfigMap `<fullname>-pwa-env` (`siteEnv.pwa`) |
| Any other `NUXT_<NAME>` | The Nuxt pods | `NUXT_<NAME>`, unchanged | The Secret `<fullname>-pwa-env` (`siteEnv.pwaSecret`) |
| `CWA_API_<NAME>` | The php pod and the orphan scan CronJob | `<NAME>`, without the prefix | The Secret `<fullname>-api-env` (`siteEnv.apiSecret`) |

The chart adds them to the containers with `envFrom` (see [Kubernetes › Site Settings](/deployment/kubernetes#site-settings)). The API's settings need the `CWA_API_` prefix because its own names, such as `DATABASE_URL` or `APP_SECRET`, are too generic to pass through whole.

**An empty `CWA_API_` value is left out**, and the log says so (`api: <NAME> left unset, CWA_API_<NAME> is empty`). An empty variable would replace the Caddyfile's `{$NAME:default}` and Symfony's defaults, so leaving it out keeps them. An empty `NUXT_*` value is still delivered, because Nuxt applies an empty value on purpose.

### The API's optional settings

The template's own optional API settings go through the same passthrough. Set them as `CWA_API_<NAME>` in CI; the local compose stack uses the bare `<NAME>`. Unset, the default in the Caddyfile or in Symfony applies ([`d64c278`](https://github.com/components-web-app/components-web-app/commit/d64c278997770b07fb0c2d04ed2fa7383059ab03)).

| CI variable | What it sets |
|-------------|--------------|
| `CWA_API_CACHE_QUERY_ALLOWLIST`, `CWA_API_RATE_LIMIT_ENABLED`, `CWA_API_RATE_LIMIT_EVENTS`, `CWA_API_RATE_LIMIT_WINDOW`, `CWA_API_CADDY_TRUSTED_PROXIES`, `CWA_API_CLOUDFLARE_IP_RANGES`, `CWA_API_FRANKENPHP_MAX_WAIT_TIME` | Origin protection. See [Origin protection](#origin-protection) |
| `CWA_API_CLOUDFLARE_PURGE_PLAN`, `_REQUESTS`, `_WINDOW`, `_BURST` | Cloudflare purge pacing. See [CDN purging](#cdn-purging) |
| `CWA_API_CADDY_CACHE_BACKEND_TIMEOUT`, `CWA_API_CADDY_CACHE_STORAGE` | Souin's backend timeout and store. See [HTTP cache](#http-cache). *Since template 2.0.0-alpha.38* |
| `CWA_API_CADDY_GLOBAL_CONFIG` | Extra lines for the Caddyfile's global options block, such as `debug` |
| `CWA_API_JWT_COOKIE_SAMESITE` | The `SameSite` attribute of the session, JWT and refresh token cookies. Default `lax` |
| `CWA_API_MERCURE_JWT_ALGORITHM` | The algorithm Symfony signs Mercure tokens with. Default `hmac.sha256` |
| `CWA_API_ERROR_MAIL_TO` | An address that gets one email per unique `5xx` per hour, subject `<WEBSITE_NAME> API error`. Needs a working `MAILER_DSN` and `MAILER_EMAIL`. Empty sends none. See [Kubernetes › Error mail](/deployment/kubernetes#error-mail). *Since template 2.0.0-alpha.34* |
| `CWA_API_WEBSITE_NAME` | The site's name in emails (the bundle's `website_name`). Default `New Website`, from `api/.env`. A multi-site project can export it per site from [`project.sh`](/deployment/ci-cd#project-hooks) ([`c1a3201`](https://github.com/components-web-app/components-web-app/commit/c1a3201e24378ef54e7bd64393110bb6b1a0cfce)) |

Their bare CI names, such as `RATE_LIMIT_EVENTS` or `CLOUDFLARE_PURGE_PLAN`, are no longer read by the deploy.

Each side reads them as it reads any environment variable:

- **Nuxt** uses a `NUXT_*` variable only for a key you declare in `runtimeConfig` in `app/nuxt.config.ts`. `NUXT_PUBLIC_ANALYTICS_ID` sets `runtimeConfig.public.analyticsId`, and `NUXT_MAPS_KEY` sets the server-only `runtimeConfig.mapsKey`.
- **Symfony** reads `CWA_API_MAPS_KEY` as `MAPS_KEY`, through `'%env(MAPS_KEY)%'`. Give it a default in `api/.env` so the local stack still boots.

```ts
// app/nuxt.config.ts
export default defineNuxtConfig({
    runtimeConfig: {
        mapsKey: '',          // NUXT_MAPS_KEY, server only
        public: {
            analyticsId: '',  // NUXT_PUBLIC_ANALYTICS_ID, sent to browsers
        },
    },
})
```

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**`NUXT_PUBLIC_*` values aren't secret.** Nuxt sends public runtime config to every browser, in the page HTML. Put keys and tokens in a `NUXT_*` name without `PUBLIC_`, which stays on the server.
::

::callout{icon="i-heroicons-information-circle"}
**Site settings are runtime only, never build args.** The values reach the containers when they start. The image builds get only what `build_api` and `build_app` name, so one image serves every environment. Don't add a `--build-arg` or build secret for a site setting, and don't read one in a Dockerfile: read it at runtime, through `runtimeConfig` in Nuxt or `%env()%` in Symfony.
::

On GitLab, every CI variable already reaches the deploy job. Remember that staging runs under `environment: production`, so a setting scoped to `production` reaches staging too. Use [the environment name](#the-environment-name) where the two must behave differently.

The deploy log prints `Environment name: <name>` and one line for each setting, such as `pwa config NUXT_PUBLIC_ANALYTICS_ID (from NUXT_PUBLIC_ANALYTICS_ID)` or `api secret MAPS_KEY (from CWA_API_MAPS_KEY)`. It never prints a value.

### Reserved names

The deploy fails, before it changes anything in the cluster, when a site setting uses a name the chart or its image already sets on that container. The chart's own `env:` entry would win over `envFrom`, so the value would be ignored without a word. It also fails on a name that isn't usable, such as `CWA_API_` with nothing after it, or a `<NAME>` that starts with a digit. The log lists every problem:

```
❌ Site environment variables (NUXT_*, CWA_API_*) that can't be passed through:
  CWA_API_DATABASE_URL: DATABASE_URL is reserved on the api container: the chart or its image sets it (use its own CI variable, if it has one, or delete this one)
```

Reserved on the Nuxt container (`SITE_ENV_RESERVED_PWA` in `k8s.sh`):

`NUXT_CWA_API_URL`, `NUXT_PUBLIC_CWA_API_URL`, `NUXT_PUBLIC_CWA_API_URL_BROWSER`, `NUXT_SITE_URL` and `NUXT_PUBLIC_CWA_ENVIRONMENT`. The deploy sets `NUXT_SITE_URL` to `https://$DOMAIN`, so cached pages' canonical URL and `og:url` use the site's own host, not whichever host rendered the page. A multi-site project gives each site its host through `DOMAIN` ([#140](https://github.com/components-web-app/components-web-app/issues/140), [`45a3794`](https://github.com/components-web-app/components-web-app/commit/45a379404852fc164b15f706d0aac3479c61b6ab)). The chart sets the API URLs itself (see [Kubernetes › `apiUrl` should stay unset](/deployment/kubernetes#apiurl-should-stay-unset)). `NUXT_PUBLIC_CWA_API_URL` is the deprecated name of `NUXT_CWA_API_URL`, and as public config it would put the internal API URL in every page.

Reserved on the php container (`SITE_ENV_RESERVED_API`), as the `<NAME>` in `CWA_API_<NAME>`:

`ADMIN_EMAIL`, `ADMIN_PASSWORD`, `ADMIN_USERNAME`, `APP_DEBUG`, `APP_ENV`, `APP_SECRET`, `APP_UPSTREAM`, `BROWSER_SERVER_NAME`, `CACHE_URL`, `CADDY_CACHE_CDN_CONFIG`, `CADDY_CACHE_EXTRA_CONFIG`, `CORS_ALLOW_ORIGIN`, `CWA_ENVIRONMENT`, `DATABASE_BACKUP_GCLOUD_JSON`, `DATABASE_CA_CERT`, `DATABASE_CLIENT_CERT`, `DATABASE_CLIENT_KEY`, `DATABASE_SSL_MODE`, `DATABASE_URL`, `FRANKENPHP_CONFIG`, `FRANKENPHP_MEMORY_LIMIT`, `FRANKENPHP_WORKER_NUM`, `GCLOUD_BUCKET`, `GCLOUD_JSON`, `GCLOUD_PATH_PREFIX`, `GCLOUD_PUBLIC_URL`, `GOMEMLIMIT`, `JWT_PASSPHRASE`, `JWT_PUBLIC_KEY`, `JWT_SECRET_KEY`, `MAILER_DSN`, `MAILER_EMAIL`, `MERCURE_CORS_ORIGIN`, `MERCURE_EXTRA_DIRECTIVES`, `MERCURE_HUB_UPSTREAM`, `MERCURE_JWT_SECRET`, `MERCURE_PUBLIC_URL`, `MERCURE_PUBLISHER_JWT_ALG`, `MERCURE_PUBLISHER_JWT_KEY`, `MERCURE_SUBSCRIBER_JWT_ALG`, `MERCURE_SUBSCRIBER_JWT_KEY`, `MERCURE_URL`, `RESET_DATABASE`, `SERVER_NAME`, `SKIP_MIGRATIONS`, `TRUSTED_HOSTS` and `TRUSTED_PROXIES`. `DATABASE_BACKUP_GCLOUD_JSON`, `MERCURE_HUB_UPSTREAM` and `SKIP_MIGRATIONS` are reserved *since [template 2.0.0-alpha.43](https://github.com/components-web-app/components-web-app/releases/tag/v2.0.0-alpha.43)*, so a `CWA_API_DATABASE_BACKUP_GCLOUD_JSON` site setting can't put the backup key into the API pods ([`705d5a7`](https://github.com/components-web-app/components-web-app/commit/705d5a7)).

`CWA_API_CADDY_CACHE_CDN_CONFIG` and `CWA_API_CADDY_CACHE_EXTRA_CONFIG` fail with `set the CI variable CADDY_CACHE_CDN_CONFIG instead` (or `CADDY_CACHE_EXTRA_CONFIG`): the chart writes both from the plain CI variables.

Most of these have their own CI variable, such as `MAILER_DSN` or `CORS_ALLOW_ORIGIN` (or `CWA_CI_API_GOMEMLIMIT` for `GOMEMLIMIT`, `CWA_CI_API_WORKERS` for `FRANKENPHP_WORKER_NUM`, `CWA_CI_API_PHP_MEMORY_LIMIT` for `FRANKENPHP_MEMORY_LIMIT`, and `CWA_CI_RESET_DATABASE` for `RESET_DATABASE`), so set that one instead.

If your own chart values add `env:` entries to a container, reserve their names too, without editing `k8s.sh`: set `SITE_ENV_RESERVED_API_EXTRA` or `SITE_ENV_RESERVED_PWA_EXTRA` to a space-separated list in [`project.sh`](/deployment/ci-cd#project-hooks) or as a CI variable ([#133](https://github.com/components-web-app/components-web-app/issues/133)).

```sh [bin/devops/project.sh]
export SITE_ENV_RESERVED_API_EXTRA="MAPS_REGION"
```

### On GitHub

Variables named `NUXT_*` or `CWA_API_*` reach the deploy through `github-export-vars.sh`, like every other variable. GitHub can't list secrets, so each deploy job (review, staging, canary and production) also runs `bin/devops/github-export-secrets.sh`, in the step *Expose NUXT_\* and CWA_API_\* secrets to the deploy*. It receives every secret and exports only the `NUXT_*` and `CWA_API_*` ones to the later steps, masked, including each line of a multi-line value. It runs after the kubectl and Helm setup actions, so those never see the values, and no build job runs it. So a site secret needs no workflow edit: add it under **Settings → Secrets and variables → Actions → Secrets**.

The step adds a warning to the run in two cases:

- **Public value stored as a secret:** a `NUXT_PUBLIC_*` secret. It is still exported, but browsers receive it, so make it a variable.
- **Secret shadowed:** a variable, or the job's `env:`, already sets the name, so the secret isn't used. Delete one of the two.

### The environment name

The deploy names the environment it serves, from its track, and sets it as `CWA_ENVIRONMENT` on the php pod and the orphan scan, and as `NUXT_PUBLIC_CWA_ENVIRONMENT` on the Nuxt pods (Helm value `cwaEnvironment`):

| Track | Name |
|-------|------|
| Production | `production` |
| Staging | `staging` |
| Canary | `canary` |
| Review apps | `review` |

So staging is told apart from production, although its GitLab job runs as `environment: production`. A `CWA_ENVIRONMENT` CI variable replaces the name on every track it reaches; on GitLab, a value scoped to `production` reaches staging and canary too. It may hold only letters, digits, `.`, `_` and `-`, or the deploy fails with `CWA_ENVIRONMENT must be letters, digits, '.', '_' or '-', not '<value>'.`

Nuxt sees the name only once you declare it, as `runtimeConfig.public.cwaEnvironment`. Symfony reads it with `'%env(CWA_ENVIRONMENT)%'`; give it a default in `api/.env` for the local stack.
