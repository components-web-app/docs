The CWA template repository ships a complete Docker Compose stack. Clone the template and you have a fully wired local environment — PHP, Nuxt, Mercure and PostgreSQL — ready in minutes. For first-time local setup, follow [Installation](/getting-started/installation); this page is the reference for the stack itself. When something goes wrong, see [Troubleshooting](/deployment/troubleshooting).

## Services

Three services, and no separate proxy or hub container: FrankenPHP is the front door, and the Mercure hub runs inside it as a Caddy module.

| Service | Image | Role |
|---------|-------|------|
| `php` | FrankenPHP | Symfony API, Caddy front door, embedded Mercure hub; proxies non-API traffic to `app` |
| `app` | Node 26 alpine | Nuxt SSR application (port 3000, published on 3001 in dev) |
| `database` | PostgreSQL 16 alpine | Primary database |

::callout{icon="i-heroicons-information-circle"}
The Nuxt service is called `app`, not `nuxt` — so it's `docker compose exec app …`.
::

### Volumes

`compose.yaml` declares three named volumes. They survive `docker compose down`, so data and certificates persist between restarts:

| Volume | Mounted at | Holds |
|--------|------------|-------|
| `caddy_data` | `/data` in `php` | Caddy's data, including the local certificate authority your browser trusts for `https://localhost` |
| `caddy_config` | `/config` in `php` | Caddy's saved config, and Composer's `/config/composer/auth.json` |
| `database_data` | `/var/lib/postgresql/data` in `database` | The PostgreSQL data |

`docker compose down -v` deletes them, and with them the database and the local CA. `compose.yaml` notes you can bind-mount a host directory for the database instead, so it's harder to remove by accident.

In development, `compose.override.yaml` also mounts your source (see [Development workflow](#development-workflow)).

## Local Development

### Environment Variables

Create `.env.local` alongside `.env` — **never commit `.env.local`**:

```ini
# Database
DATABASE_URL=postgresql://app:secret@database:5432/app?serverVersion=16&charset=utf8

# JWT Authentication
JWT_SECRET_KEY=%kernel.project_dir%/config/jwt/private.pem
JWT_PUBLIC_KEY=%kernel.project_dir%/config/jwt/public.pem
JWT_PASSPHRASE=your_jwt_passphrase
JWT_COOKIE_SAMESITE=lax

# Mercure (embedded in the php container — override with CADDY_MERCURE_*)
MERCURE_URL=http://php.local/.well-known/mercure
MERCURE_PUBLIC_URL=https://localhost/.well-known/mercure
CADDY_MERCURE_JWT_SECRET=your_mercure_secret

# Nuxt (server-side API URL = internal Docker network; browser URL = public)
NUXT_CWA_API_URL=https://php.local/_api
NUXT_PUBLIC_CWA_API_URL_BROWSER=https://localhost/_api

# Email
MAILER_DSN=smtp://smtp-relay:25
```

These are the template's own defaults. The two CWA API URL variables are intentionally different in Docker Compose: `NUXT_CWA_API_URL` is how the Nuxt container reaches PHP over the Docker network (`php.local` is a link alias on the `app` service), while `NUXT_PUBLIC_CWA_API_URL_BROWSER` is the public-facing URL clients use from their browsers. They must stay different whenever the API is on an internal Docker hostname. Override them with `API_URL` and `API_URL_BROWSER`, and the Mercure URLs with `CADDY_MERCURE_URL` / `CADDY_MERCURE_PUBLIC_URL`.

**Mercure cookie SameSite:** set `JWT_COOKIE_SAMESITE=none` (`CWA_API_JWT_COOKIE_SAMESITE` as a CI variable in a Kubernetes deploy) and `Secure: true` if your API and front-end are on different subdomains. On the same domain, `strict` is safe.

### Starting the Stack

From the project root:

```bash
docker compose up -d
```

The `php` entrypoint installs Composer dependencies if needed, generates dev JWT keys, waits for the database, runs migrations and runs `ANALYZE`, all before Caddy accepts traffic. Loading fixtures or creating the first admin is a one-off step: see [Installation](/getting-started/installation).

### Development Workflow

`compose.override.yaml` mounts source directories into the containers:

- **PHP**: your `api/` directory is mounted; PHP changes are reflected immediately (no build step)
- **Nuxt** (`app` service): `app/` is mounted; Vite HMR updates the browser on save
- **Xdebug**: installed in the dev image but off by default (`XDEBUG_MODE=off`); run with `XDEBUG_MODE=debug` to enable it, then connect via your IDE on port 9003

The dev config is read through the `./api` **directory** mount, never single-file mounts, which Docker Desktop can serve truncated (see [Troubleshooting](/deployment/troubleshooting#caddy-reports-unexpected-eof-after-you-edit-the-caddyfile)).

## JWT Keys

In development you don't generate keys. Outside `APP_ENV=prod`, the `php` entrypoint runs `lexik:jwt:generate-keypair --skip-if-exists`, which writes `api/config/jwt/private.pem` and `public.pem` (both gitignored) encrypted with the `JWT_PASSPHRASE` from `api/.env`. The template ships a working passphrase for local use.

The production image carries no key files and never generates them. `compose.prod.yaml` takes the key **contents** in `JWT_SECRET_KEY` and `JWT_PUBLIC_KEY`, with `JWT_PASSPHRASE`, and the CI deploy generates them when they aren't set (see [CI/CD Variables › Secrets](/deployment/variables#secrets)). Never bake private keys into an image: the template's `api/.dockerignore` keeps them out (see [What stays out of the images](#what-stays-out-of-the-images)).

::callout{icon="i-heroicons-shield-exclamation" color="warning"}
**Use your own passphrase anywhere public.** Generate one with `docker compose exec php php -r "print bin2hex(random_bytes(26));"`. The passphrase and the keys must always match — change one without the other and every login fails. To regenerate a key pair for a new passphrase locally, set it in `api/.env.local` and run `docker compose exec php bin/console lexik:jwt:generate-keypair --overwrite`.
::

## Images

Multi-stage Dockerfiles produce lean production images:

```bash
# Build PHP image
docker build --target frankenphp_prod -t ghcr.io/your-org/app-php:latest ./api

# Build Nuxt image
docker build --target prod -t ghcr.io/your-org/app-nuxt:latest ./app
```

To be able to roll back, tag each build with its git SHA instead of `latest`: see [Kubernetes › Rollback](/deployment/kubernetes#rollback).

### PHP Dockerfile stages

1. `builder` — custom FrankenPHP build (`xcaddy`). It adds these Caddy modules:
   - Mercure 1.0, Vulcain, and Souin with its otter, badger and nuts storages
   - `caddy-cbrotli`, for Brotli compression
   - `mholt/caddy-ratelimit`, for the [rate limit on cache misses](/deployment/origin-protection#rate-limit-on-cache-misses)
   - `queryallowlist`, the template's own handler for the query allowlist (see [Origin Protection › Query Parameters on Pages](/deployment/origin-protection#query-parameters-on-pages)), from `api/frankenphp/caddy/queryallowlist`

   Souin is built from a copy of v1.7.9 with five patches from `api/frankenphp/souin/`, applied in this order:
   - `v1.7.9-purge-fix.patch`: purging one cache tag no longer drops the index of every tag that contains it
   - `v1.7.9-singleflight-fix.patch`: a request that times out no longer blocks its URL for the life of the process (see [Troubleshooting](/deployment/troubleshooting#the-api-pod-stays-unready-and-every-probe-times-out))
   - `v1.7.9-singleflight-5xx.patch`: requests that waited on another request's `5xx` get that `5xx`, not an empty `200` (see [Troubleshooting](/deployment/troubleshooting#requests-that-waited-on-a-failed-render-get-an-empty-200))
   - `v1.7.9-flush-no-close.patch`: a full flush no longer closes the badger or nuts storage (see [Troubleshooting](/deployment/troubleshooting#nothing-is-cached-after-a-full-flush))
   - `v1.7.9-cloudflare-purge.patch`: makes the Cloudflare purge work (see [Purges must reach Cloudflare](/deployment/cloudflare#purges-must-reach-cloudflare)). It also queues purges, paces them to the plan's rate limit and retries refused ones (see [Queued and paced purges](/deployment/cloudflare#queued-and-paced-purges))

   The build also adds Souin's Redis store (`darkweak/storages/go-redis`), with `api/frankenphp/storages/go-redis-v0.0.20-atomic-sets.patch` applied so that php pods sharing one Redis all drop every page under a purged tag. It's there for running more than one php pod, which needs a cache the pods share ([#85](https://github.com/components-web-app/components-web-app/issues/85)). **Nothing uses it yet:** the Caddyfile's `cache` block has no `redis` store, so the cache stays in each pod's memory and php still runs one replica (see [php stays at one replica](/deployment/kubernetes#php-stays-at-one-replica)). `bin/test/souin-redis-shared-purge.sh` runs in the unit-tests job against a Redis service to check the patch. *Since [template 2.0.0-alpha.23](https://github.com/components-web-app/components-web-app/releases/tag/v2.0.0-alpha.23)*
2. `frankenphp_base` — shared runtime, extensions and Caddy config. Every step that fetches from Debian (the base packages and each `install-php-extensions` call) runs through `api/frankenphp/retry-fetch.sh`, which gives the step a hard time limit and tries it up to three times: 240 seconds for the base packages, 480 for the main extensions and 120 for `pdo_pgsql`. apt fetches `deb.debian.org` over HTTPS, and retries with 30-second timeouts and no pipelining. Before this, a fetch over plain HTTP could stall an uncached build until the CI job's one-hour limit, as it did on GitLab SaaS's small runners ([#176](https://github.com/components-web-app/components-web-app/issues/176), [`841ea0f`](https://github.com/components-web-app/components-web-app/commit/841ea0f6416e421253c11059f23cc2ec517b7c05), [`7fc4ac5`](https://github.com/components-web-app/components-web-app/commit/7fc4ac58a1cbef543d97886410fed8262d31b6b6), [`48b5c7c`](https://github.com/components-web-app/components-web-app/commit/48b5c7c21e3d50f3deb3a3048f15ab04dffaa3f3)). *Since template 2.0.0-alpha.42*

   It installs libvips (`libvips42t64`) and the `ffi` extension for the libvips imagine driver (see [Image processing](#image-processing)), with these defaults. Each can be overridden at runtime; on a Kubernetes deploy, set it as `CWA_API_` plus the name:
   - `VIPS_BLOCK_UNTRUSTED=1`: no ImageMagick, PDF or SVG loaders for uploads
   - `VIPS_CONCURRENCY=2`: two threads per image, where libvips would otherwise use one per CPU, and memory grows with the thread count
   - `MALLOC_ARENA_MAX=2` and `MALLOC_MMAP_THRESHOLD_=1048576`: glibc hands freed image buffers back to the system. Without them, php kept 200 to 300 MB more memory after several images were processed at once

   It also installs the `brotli` PHP extension. [`warm-http-cache --accept-encoding=br`](/api/console-commands#warm-http-cache) needs it to decode the responses it warms; without it, the `br` pass of the start-up warm ([Kubernetes & Helm › Warming the API cache on start](/deployment/kubernetes#warming-the-api-cache-on-start)) warmed only the route responses, never their manifests or components, and from api-components-bundle 2.0.0-alpha.26 it fails instead. `api/tests/Unit/BrotliExtensionTest.php` checks the extension is there ([#175](https://github.com/components-web-app/components-web-app/issues/175), [`c52bb7a`](https://github.com/components-web-app/components-web-app/commit/c52bb7a95a52dd6a90668456f4b08e031221990b)). *Since [template 2.0.0-alpha.39](https://github.com/components-web-app/components-web-app/releases/tag/v2.0.0-alpha.39)*
3. `frankenphp_dev` / `frankenphp_prod` — the two targets you build

Migrations are **not** baked into the image. They are run at container start: the template's `php` entrypoint waits for the database, runs `doctrine:migrations:migrate --no-interaction --all-or-nothing`, then `ANALYZE`s. That's safe with one `php` container; with more, see [Kubernetes › Running Migrations](/deployment/kubernetes#running-migrations).

### Nuxt Dockerfile stages

1. `base` — corepack/pnpm setup. Its `apk add` is limited to 90 seconds and tried three times, switching to another Alpine mirror after a failure, so a stalled mirror no longer hangs the build
2. `dev` — `pnpm dev` with HMR
3. `builder` — `pnpm build` (outputs `.output/`)
4. `prod` — copies `.output/` into `/srv/app` and runs `node server/index.mjs` as an unprivileged user

### What stays out of the images

- **`api/.dockerignore`** keeps `config/jwt/*.pem`, decrypted Symfony secrets and `public/uploads/` out of the API image. They're gitignored, so a CI build never has them, but an image built on a developer's machine would otherwise copy them in.
- **`app/.dockerignore`** leaves out `.env`, `.env.local` and `.env.*.local`, because `nuxt build` reads `app/.env`, so a local file with real keys would end up in an image built on a developer's machine. It also leaves out `.pnpm-store/`, `node-compile-cache/`, logs, OS files, the Dockerfile and the compose files, so a local build matches CI's ([#139](https://github.com/components-web-app/components-web-app/issues/139), [`2e2ae16`](https://github.com/components-web-app/components-web-app/commit/2e2ae160dee8e8834dc99038062b9004b494a369)).

### Image processing

The API makes thumbnails with libvips instead of GD: `driver: vips` in `api/config/packages/liip_imagine.yaml`, through `rokka/imagine-vips` and `jcupitt/vips` ([#141](https://github.com/components-web-app/components-web-app/issues/141), [`8255e8c`](https://github.com/components-web-app/components-web-app/commit/8255e8c72529a20dcd0d5106a5fa1cf7cb9b97f4)). A 12 MP thumbnail takes about 200 ms and 50 MB instead of 320 ms and 140 MB. libvips' memory is outside PHP's `memory_limit`, so large originals no longer exhaust it, and image uploads are accepted up to 30 MP.

- `jcupitt/vips` binds libvips through FFI, so `conf.d/10-app.ini` sets `ffi.enable = true`. The web server only allows FFI with `true`.
- `api/config/preload_vips.php` starts libvips once, before FrankenPHP starts its threads. libvips' start-up isn't thread-safe, so without it the first images processed at the same time in worker mode segfault with `cannot retrieve class for invalid (unclassed) type`. The production image runs it from `config/preload.php`, and the dev image preloads it directly from `conf.d/20-app.dev.ini`. **Keep it while the driver is vips.**
- Every filter set in the template's `liip_imagine.yaml` saves WebP (`format: webp`, `quality: 80`), whatever the upload's format. See [WebP and Other Output Formats](/api/components/annotations/uploadable#webp-and-other-output-formats).
- GD is still installed, and `liip_imagine.yaml` has a commented `# driver: gd` line above `driver: vips`. Both drivers read AVIF uploads: libvips through libheif, and GD through Debian's libavif. So switching needs no image rebuild ([`4341396`](https://github.com/components-web-app/components-web-app/commit/434139660c906afbc2a4a46474bef38e79fc2fa7)). *Since template 2.0.0-alpha.42* To switch back, set `driver: gd` and lower the `maxPixels` limit on `Image::$file`, and on any other image field, to 20 MP. A field with [`#[UploadedImage]`](/api/components/annotations/uploadable#capping-uploads-to-fit-the-budget) and no `maxPixels` takes its limit from `uploadable.image_max_pixels` instead.

The dev php image needs rebuilding after you take these changes: see [Troubleshooting](/deployment/troubleshooting#composer-or-php-reports-a-missing-ffi-extension).

## Production Docker Compose

For production, use `compose.prod.yaml` in place of the dev override:

```bash
docker compose -f compose.yaml -f compose.prod.yaml --env-file .env.production up -d
```

It selects the `frankenphp_prod` and `prod` build targets. It refuses to start unless `SERVER_NAME` (the site's domain), `APP_SECRET`, `POSTGRES_PASSWORD`, `CADDY_MERCURE_JWT_SECRET`, `JWT_SECRET_KEY`, `JWT_PUBLIC_KEY` and `JWT_PASSPHRASE` are set.

The Nuxt container renders over `http://php.local/_api` and warms the page cache over `https://php.local`, where `php.local` is a network alias of the `php` service. Plain HTTP works there because `php.local:80` is in Caddy's `SERVER_NAME`; any other internal host, such as `http://php`, gets a `308` to HTTPS. Listing several ports there is also why the Caddyfile's Mercure hub needs a `name` (see [Hub Caddyfile](/api/real-time#hub-caddyfile)). Keep it if you edit `SERVER_NAME`. See [Choosing the warm origin](/nuxt-module/page-caching#choosing-the-warm-origin) for why the two URLs differ.

`compose.prod.yaml` also sets `CADDY_EDGE=true`, because Caddy faces the internet itself here. The rate limit ([Origin Protection › Rate Limit on Cache Misses](/deployment/origin-protection#rate-limit-on-cache-misses)) then counts a direct client by its own address and never believes an `X-Forwarded-For` header it sends, so a client can't avoid the limit by inventing one. Cloudflare is still recognised by its address ranges. Set `CADDY_EDGE=false` only if a proxy other than Cloudflare sits in front, and add that proxy's ranges to `CADDY_TRUSTED_PROXIES`.

### Origin protection settings

`compose.yaml` passes these to the php container only when you set them in the shell or `.env`. Otherwise the defaults in `api/frankenphp/Caddyfile` and `worker.Caddyfile` apply:

```ini
CACHE_QUERY_ALLOWLIST="page search order tab"
RATE_LIMIT_EVENTS=1200
FRANKENPHP_MAX_WAIT_TIME=3s
```

The full list is `CACHE_QUERY_ALLOWLIST`, `RATE_LIMIT_ENABLED`, `RATE_LIMIT_EVENTS`, `RATE_LIMIT_WINDOW`, `CADDY_TRUSTED_PROXIES`, `CLOUDFLARE_IP_RANGES` and `FRANKENPHP_MAX_WAIT_TIME`. See [CI/CD Variables › Origin protection](/deployment/variables#origin-protection) for what each one does. Compose uses these bare names; a Kubernetes deploy sets the same settings as CI variables named `CWA_API_` plus the name, such as `CWA_API_RATE_LIMIT_EVENTS`. The Cloudflare purge settings (`CLOUDFLARE_PURGE_*`) are passed the same way (see [CI/CD Variables › CDN purging](/deployment/variables#cdn-purging)).

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**Leave a setting out rather than setting it empty.** Caddy uses its default only when a variable is unset, and treats an empty value as a value. That's why `compose.yaml` lists them bare (`RATE_LIMIT_EVENTS:`) and never as `${RATE_LIMIT_EVENTS:-}`. Keep that form if you add your own.
::

`FRANKENPHP_MAX_WAIT_TIME` only applies to the production image: see [Origin Protection › Load shedding](/deployment/origin-protection#load-shedding). The rate limit never applies to private addresses, so your own browser may never trigger it on the dev stack. To try it locally, send an `X-Forwarded-For` header with a public address: the request comes from a trusted private address, so Caddy believes the header.

## The HTTP Cache in Caddy

Souin, inside the php container's Caddy, caches API responses and the page HTML Nuxt renders. This section explains how the template's Caddyfile sets it up. See [Page Caching](/nuxt-module/page-caching) for how long a page is kept, and [Purging Every Rendered Page](/api/http-caching#purging-every-rendered-page) for the API side. If you edit the Caddyfile, check it with `bin/test/caddy-validate.sh` (see [Troubleshooting › Caddy and Souin](/deployment/troubleshooting#caddy-and-souin)).

### What the page cache stores

The template's `@use_cache` matcher has two branches. The first caches `/_api` responses. The second caches the HTML pages that Nuxt renders. The module tags these pages by default; set `cwa.pageCache.enabled: false` to turn this off. The module adds the IRI of every resource used on the page, and the constant key `cwa-html`. When the API saves a resource, its existing purge removes every page that used that resource. Saving site config removes every page, through `cwa-html`.

The HTML branch skips some paths on purpose. Keep these exclusions if you edit it:

- `/.well-known/` — Mercure uses server-sent events. A cached SSE response never finishes, so connections build up and the site looks like it has gone down.
- `/_nuxt/` — these files are already immutable, and caching large bundles would push useful entries out of the in-memory cache.
- `/uploads/`, `/bundles/`, `/_cwa/`, and the login, `/forgot-password`, `/reset-password`, email-verification and user-area pages — their content depends on the user, or they are not rendered by Nuxt.

The HTML branch also caches only paths with no file extension, which are pages, and `.xml`, which is the sitemap. Any other file, such as a PDF or image in Nuxt's `public/` folder, goes past the cache and is streamed. Souin reads the whole body of a cacheable response into memory before it decides anything, so one download of a 187 MB PDF through the cache took the php container past its 1Gi memory limit and it was OOMKilled. The `/_api` branch skips `.pdf` files for the same reason. Caddy's `{file.ext}` includes the dot, so compare against `".pdf"`, not `"pdf"`.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**Don't rely on Souin's `max_cacheable_body_bytes` to protect memory.** Souin checks it only after it has buffered the whole body, so a large file still uses that much memory. Keep large files out of `@use_cache` instead.
::

If Cloudflare caches pages in front of Souin, its cache rules must mirror these exclusions. See [Cloudflare](/deployment/cloudflare#the-cache-rules-must-match-the-templates-exclusions).

### Compressed cache entries

The Caddyfile has `order cache before encode`, so a page is compressed once, on the miss, and a hit is served as it was stored ([#145](https://github.com/components-web-app/components-web-app/issues/145), [`3add461`](https://github.com/components-web-app/components-web-app/commit/3add4619edd1e7949b3baadc09e3a8abbe9a942a)). With the cache inside `encode` instead, Caddy compresses every cache hit again, and Brotli caps a php pod at about 110 page views a second. Projects on template `2.0.0-alpha.21` or earlier have that order: see [the template 2.0.0-alpha.22 release notes](https://github.com/components-web-app/components-web-app/releases/tag/v2.0.0-alpha.22).

To keep the number of entries down, the Caddyfile first rewrites `Accept-Encoding` to `br`, `gzip` or nothing (the `@encoding_*` matchers and `request_header`), and the cache key ends with the same value. So a page is stored at most three times, whatever the browser sends, and a tag purge removes every copy. `encode` no longer offers zstd. If you edit the Caddyfile, keep the encoding matchers, the `request_header` lines and `{http.vars.cwa_cache_encoding}` in the key together. `bin/test/cache-encoding.sh`, in the unit-tests job, runs the Caddyfile against a stub app and fails on the old order. See [Deployment requirements](/nuxt-module/page-caching#deployment-requirements).

### The cache store and backend timeout

The `cache` block names its store and its backend timeout on their own lines ([#170](https://github.com/components-web-app/components-web-app/issues/170), [`a728acb`](https://github.com/components-web-app/components-web-app/commit/a728acbb28ddc12e9e91cb8b0b7fe362e0ae3b52)):

```caddyfile [api/frankenphp/Caddyfile]
timeout {
	backend {$CADDY_CACHE_BACKEND_TIMEOUT:30s}
}

{$CADDY_CACHE_STORAGE:otter}

{$CADDY_CACHE_EXTRA_CONFIG}
```

- **The backend timeout is 30 seconds**, where Souin's own default is 10. After a full flush or a rollout, a CMS page with about 70 resources took about 12 seconds to render cold, so its first visitor got a `504`, and Cloudflare passed it on. 30 seconds covers that, and stays under ingress-nginx's 60 seconds and Cloudflare's 100, so a render that is really stuck still gets Souin's own error first. It doesn't change [load shedding](/deployment/origin-protection#load-shedding): a request that waits for a php worker still gets a `503` after `FRANKENPHP_MAX_WAIT_TIME`. `bin/test/souin-backend-timeout.sh`, in the unit-tests job, checks that a 12-second render is served and cached once.
- **The store is otter**, Souin's in-memory store, capped at 10,000 entries by count, not by size. It's the same on the dev stack, in the browser tests and on every deploy.
- **`CADDY_CACHE_EXTRA_CONFIG` is for any other Souin directive.** It's empty by default, and must never name a store or hold a `timeout` block.

On a deploy, set them as `CWA_API_CADDY_CACHE_BACKEND_TIMEOUT`, `CWA_API_CADDY_CACHE_STORAGE` and `CADDY_CACHE_EXTRA_CONFIG`. See [CI/CD Variables › HTTP cache](/deployment/variables#http-cache), which also explains why the deploy refuses a store or `timeout` in the extra config. *Since [template 2.0.0-alpha.38](https://github.com/components-web-app/components-web-app/releases/tag/v2.0.0-alpha.38)*

### `/_nuxt` files are compressed when the app is built

php's Caddy passes every `/_nuxt/` request on to Nuxt, and its `encode` compresses any response that isn't already compressed. Compressing every JavaScript file with Brotli on every request ran php out of memory at about 100 first visits a second ([#117](https://github.com/components-web-app/components-web-app/issues/117), [`5e732e9`](https://github.com/components-web-app/components-web-app/commit/5e732e9d36688fcbdb59b656f47ccbae1ccfd8e2)). So `app/nuxt.config.ts` writes a `.br` and a `.gz` copy of each build asset under `/_nuxt` at build time. Nitro serves the copy that matches the browser's `Accept-Encoding`, and Caddy leaves a response that is already compressed alone. Don't remove it.

It's a small inline module that runs a `precompressBuildAssets` helper, defined at the top of the file, on Nitro's `nitro:build:public-assets` hook:

```ts
modules: [
  // ...
  (_options, nuxt) => { // [!code focus]
    nuxt.hook('nitro:build:public-assets', nitro => precompressBuildAssets(join(nitro.options.output.publicDir, nuxt.options.app.buildAssetsDir))) // [!code focus]
  }, // [!code focus]
],
```

The helper compresses JavaScript, CSS, SVG, JSON, HTML, text, XML and font files of 1 KB or more, at maximum Brotli and gzip quality. **Don't use Nitro's `compressPublicAssets` instead.** It also compresses everything in `public/`, and one 178 MB PDF there made an app build take about seven minutes instead of one ([#155](https://github.com/components-web-app/components-web-app/issues/155), [`c9da319`](https://github.com/components-web-app/components-web-app/commit/c9da31999e01bd848cd179d03ecd8aa9ac2b186f)). Nitro now serves files in `public/` uncompressed. Caddy's `encode` compresses one on the way out when its type is in the Caddyfile's `match` list, such as text, JSON, JavaScript or SVG, and leaves a PDF or image as it is. *Since [template 2.0.0-alpha.28](https://github.com/components-web-app/components-web-app/releases/tag/v2.0.0-alpha.28)*

::callout{icon="i-heroicons-light-bulb"}
**Put large downloads in the media bucket, not `public/`.** Every file in `public/` is copied into the app image on each build, and it reaches visitors through php's Caddy, which streams it. Upload PDFs and videos to the [media storage](/deployment/variables#media-storage) instead, through an uploadable field.
::

### Tracking parameters

The Caddyfile's `uri @tracking_query query { … }` block removes `utm_*`, `gclid`, `fbclid` and other tracking parameters, so they don't split the cache. Nuxt and php never receive them. It runs only when the query contains one of them, and never for `/_nuxt/*`. See [Tracking parameters](/deployment/origin-protection#tracking-parameters) for the list and how to change it.

### Caddy's admin API

The admin API on port `2019` replaces Caddy's config and purges or flushes the Souin cache. The template listens on `localhost:2019` only and doesn't publish the port, so run admin requests inside the container, for example `docker compose exec php curl -s -X PURGE http://localhost:2019/souin-api/souin/flush`. `CACHE_URL` is `http://localhost:2019/souin-api/souin`.

### `PURGE` and `BAN` sent to the site return `405`

They never purged anything. The Caddyfile answers them with `405` instead of passing them on to Nuxt or php ([#138](https://github.com/components-web-app/components-web-app/issues/138), [`1c87cc0`](https://github.com/components-web-app/components-web-app/commit/1c87cc0e0ea92b26c16bb846df36b5e659ca8f93)). The app's own purges use the admin API above. To purge one page, see [Purging one page](/nuxt-module/page-caching#purging-one-page).
