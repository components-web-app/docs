CWA is live by default. When an admin publishes a component, every open browser session is told about it via the Mercure hub — no page reload, no polling, no WebSocket code on your end.

## How It Works

1. An admin publishes a component via the CMS
2. The Symfony API sends an update to the Mercure hub (because `mercure: true` is on the entity)
3. The hub broadcasts the update to all subscribed browser connections
4. The Nuxt module receives the event and **stages** the new resource in the store — the rendered page is untouched
5. A small "content is outdated" notice appears
6. When the reader accepts, `mergeNewResources()` applies the staged resources and Vue re-renders

You write **none** of this plumbing. It's in the module.

::callout{icon="i-heroicons-information-circle"}
Staging is deliberate: content is never swapped out from under someone mid-read. Nothing on the page changes until the update is accepted.
::

## Prerequisites

### PHP Side

Add `mercure: true` to the `#[ApiResource]` attribute on any entity you want to broadcast:

```php
#[ApiResource(mercure: true)]
class Title extends AbstractComponent { ... }
```

Without this, the resource updates silently (the API saves the change, but no Mercure event fires).

### Infrastructure

[Mercure](https://mercure.rocks/) runs as a Caddy module **inside the FrankenPHP `php` container** — there is no separate hub service to run or deploy. The template's Compose file explicitly suppresses the Flex recipe's standalone hub service for this reason.

The relevant environment variables, with the template's defaults:

```ini
# API → hub (internal, server-side)
MERCURE_URL=http://php.local/.well-known/mercure

# Browser → hub (public-facing)
MERCURE_PUBLIC_URL=https://localhost/.well-known/mercure

# Shared secret — set once, used for both the publisher and subscriber JWT keys
CADDY_MERCURE_JWT_SECRET=your_secure_secret
```

In production, `MERCURE_PUBLIC_URL` becomes your public domain plus `/.well-known/mercure` — it is derived from `SERVER_NAME` by default. Override the two URLs with `CADDY_MERCURE_URL` and `CADDY_MERCURE_PUBLIC_URL` if you need to.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**The hub must be Mercure 1.0** (FrankenPHP 1.13 or later). From `@cwa/nuxt` `2.0.0-alpha.4`, the module subscribes with the Mercure 1.0 protocol, and from api-components-bundle `2.0.0-alpha.8`, the API speaks only 1.0. A 0.x hub rejects the subscription and live updates stop. There's no switch back to 0.x, so upgrade the hub, the bundle and the module together. The template does all three after its `2.0.0-alpha.3` release. The API and hub configuration is under [Bundle Setup → Mercure Hub](/api/bundle-setup#mercure-hub).
::

## No Front-End Code Needed

The module subscribes to the Mercure hub in its Nuxt plugin, and filters what arrives against the resources on the current page. You never write `EventSource` or WebSocket code.

The subscription lifecycle:
- On page load: the module opens a single `EventSource` connection to `MERCURE_PUBLIC_URL`
- Topics: one wildcard subscription (`?match=*`, Mercure 1.0's match-all) — incoming messages are then matched against `cwa.resources.currentIds` client-side, and anything for another page is discarded
- On navigation: the subscription URL is unchanged; only the client-side filter moves with you
- On sign-in: Mercure re-initialises so private topics (admin resources) are included
- On reconnect: the module sends the last event ID it saw as `last_event_id`, and also fetches the page's resources again (see [Offline and real-time updates](/nuxt-module/pwa#offline-and-real-time-updates))

`@cwa/nuxt` `2.0.0-alpha.3` and earlier subscribe with `?topic=*` and send `Last-Event-ID`, the 0.x protocol, so they need a 0.x hub or a 1.0 hub in compatibility mode.

::callout{icon="i-heroicons-information-circle"}
**Admins not seeing live updates to drafts?** Updates to drafts and to resources that aren't live yet are private. They only reach the topics listed in the admin's Mercure cookie, `__Secure-mercure_access_token` (`mercureAuthorization` before Mercure 1.0). Before [api-components-bundle#305](https://github.com/components-web-app/api-components-bundle/pull/305), those topics left out the API's route prefix (`/_api` in the template), while updates were published with it, so admins missed every private update. Public updates were not affected. After updating the bundle, admins get the corrected topics when the cookie is next issued: at their next sign-in or JWT refresh.
::

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
Because the subscription is a wildcard, every public update published anywhere on the site, and every private update the visitor's cookie allows, is delivered to every connected browser before being filtered. Worth knowing when sizing the hub.
::

## The Visitor Notification

When a Mercure update arrives for a resource on the current page, a small notice appears reading *The content on this page is outdated*, with an **Update** button. Clicking it calls `mergeNewResources()`, which applies the staged resources and re-renders.

There is no dismiss control — the notice disappears once the update is applied. Admins get the same notice, rendered inside the admin header rather than floating over the page.

## Troubleshooting

**No live updates arriving in the browser:**
1. Check that `MERCURE_PUBLIC_URL` is reachable from browsers — not an internal Docker hostname
2. Confirm `mercure: true` is on the PHP entity
3. Open DevTools → Network → Filter by `EventSource` — you should see a persistent connection to the hub
4. Check the hub logs for authentication errors
5. A `400` on the `EventSource` request means the hub and module disagree on the protocol: a 0.x hub rejects `match=*`, and a 1.0 hub outside compatibility mode rejects `topic=*`. See the Mercure 1.0 callout above.
6. A `401` on publish or subscribe means the hub rejected the token. Check that the hub's `issuer` matches the API's `iss` claim (`cwa` in the template) and that `resource_identifier` is the public hub URL. See [Hub Caddyfile](/api/bundle-setup#hub-caddyfile).

**Signed-in users get no private updates on a plain-HTTP setup:**
- The cookie is `__Secure-mercure_access_token`, and browsers only accept that name over HTTPS. With an `http://` hub URL, the API fails to build the cookie at all. Set a prefix-less `cookie_name` on the API and the hub, as described under [The subscriber cookie](/api/bundle-setup#the-subscriber-cookie). The template's dev stack uses `https://localhost`, so it isn't affected.

**Hub 401 errors:**
- `CADDY_MERCURE_JWT_SECRET` feeds both `MERCURE_PUBLISHER_JWT_KEY` and `MERCURE_SUBSCRIBER_JWT_KEY` — check it is set (and identical) everywhere the `php` service is configured, including `compose.prod.yaml`
- On a Mercure 1.0 hub, the `iss` claim in `mercure.yaml` must equal the Caddyfile's `issuer` name, and every publish is a 401 unless `resource_identifier` is pinned to the public hub URL, because the API publishes through the internal one. See [Hub Caddyfile](/api/bundle-setup#hub-caddyfile).

**Updates arrive but the component doesn't re-render:**
- Confirm the component uses `useCwaComponent` (or `useCwaResource`) — both react to store updates
- Bare `$fetch` calls are not reactive; use `cwa.resources.getResource(iri)` for reactive lookups

## Advanced: Acting on Other Updates

The module's own subscription is already a wildcard, so there is no extra topic to register — everything published to the hub reaches the browser. What the module *doesn't* do is act on messages for resources outside the current page: those are filtered out and dropped.

If you need to react to them (a live "new comment" counter, say), open your own `EventSource` in a Nuxt plugin alongside the module's, with `withCredentials: true` so the browser sends the Mercure cookie. Use the Mercure 1.0 parameters: `match=` for an exact topic, or `match_urlpattern=` for a URL Pattern such as `https://www.example.com/_api/_/component_groups/:id`. The real constraint is hub-side: private updates only reach you if the cookie grants their topic. The grants are listed as URL Patterns in `_metadata.mercureSubscribeTopics` on the user from `GET /me` (`…/:id\?` for published resources, `…/:id\?draft=1` for drafts).

The resources store is reactive, so anything you write into it re-renders the components bound to that IRI, regardless of which connection delivered it. The module writes to the store with `storeResource`:

```ts
// Stage it, exactly as the module's own Mercure handler does
$cwa.resourcesManager.storeResource({ resource, isNew: true, path })

// Or write it straight into the current page state
$cwa.resourcesManager.storeResource({ resource })
```

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
`storeResource` is internal to the module and can change without notice. It only updates the local store and makes no API request, so never use it to save content — use `createResource` / `updateResource` / `deleteResource` or `useCwaResourceModel` for that. It was called `saveResource` in earlier releases.
::

There is no built-in CWA API for registering custom topics today.
