---
title: Categorise and Restrict
description: Best practice for the components you give editors — an icon and a group on every component, descriptions written for editors, and limits on what each component group and UI variant offers.
---

Editors build pages from the add component dialog. Every component you write appears there, so a site with twenty components and no organisation gives them a long list of names to guess from. A few minutes in each component's `defineCwaConfig`, and in each `<CwaComponentGroup>`, keeps the choice short and clear.

::callout{icon="i-heroicons-photo"}
IMAGE: the add component dialog with its search, the "Already in this group" chips, and the list in sections (Layout, Media, Text), each row with an icon
::

## Give Every Component an Icon and a Group

```ts
// app/app/cwa/components/Title/Title.vue
defineCwaConfig({
  name: 'Title',
  description: 'The main heading of a page',
  icon: 'heading',
  group: 'Text',
})
```

- **`group`** sorts the dialog into sections, listed A to Z. Once any component has a group, those without one are listed under **Other**, so give every component a group. Keep the set small and reuse the same words: Text, Media, Layout, Forms.
- **`icon`** is shown in the component's row and beside its name. A row of icons is scanned faster than a list of names. Use a built-in kind such as `'heading'` or `'image'`, a Lucide icon, or an `icon.svg` in the component's folder; see [Component Files › Icons and Previews](/nuxt-module/building-your-ui/creating-components#icons-and-previews).
- **`image`**, or a `preview.webp` beside the component, shows what the component looks like in the detail view. Add one where the name alone doesn't make that clear.

## Write Descriptions for Editors

The dialog's search matches the name first, then the group, then the description. Write the description for the person adding the component, not the developer who built it:

| Instead of | Write |
|------------|-------|
| `Renders the HtmlContent entity` | `Paragraphs, headings, lists and links, styled to match the site` |
| `Uploadable Image with imagine filters` | `A picture uploaded to the site, with **alt text** for screen readers` |
| `Collection of BlogArticleData` | `A paged list of articles. The page's search and filters apply to it` |

Say what it's for and where it suits, in one or two short sentences. The list shows it as plain text and the detail view formats it, so keep Markdown light: a word in bold or a link to your own help. Give the component a `name` an editor would use too: "Body Text", not "Html Content".

## Restrict What Each Component Group Holds

Most component groups suit only some components. A navigation bar holds links, and a header button group holds one button. List them on the group:

```vue
<CwaComponentGroup
  reference="top"
  :location="$cwa.resources.layoutIri.value"
  :allowed-components="[CwaComponentNames.NavigationLink]"
/>

<CwaComponentGroup
  reference="headerButton"
  :location="$cwa.resources.layoutIri.value"
  :allowed-components="[CwaComponentNames.HeaderButton]"
  :max-components="1"
/>
```

- **`allowed-components`** hides every other component from the dialog for that group, and the API refuses them. `CwaComponentNames` is type-checked, so a typo or a removed component fails `vue-tsc`.
- **`max-components`** caps how many components the group holds.
- An entry can be `{ component, ui, styles }` instead of a name, to limit the UIs and styles that component may use in the group. A sidebar might take Quote only as its Card UI: `{ component: CwaComponentNames.Quote, ui: ['Card'] }`.
- A component that belongs in only a few places can be **opt-in**: mark its PHP class with `#[Silverback\ExplicitAllowOnly]`, and it's offered only where a group lists it.

[`<CwaComponentGroup>` › Allowed Components](/nuxt-module/cwa-components/cwa-component-group#allowed-components) covers each rule, including the list naming every type already placed in the group, and [`<CwaComponentGroup>` › Limiting UIs and Styles](/nuxt-module/cwa-components/cwa-component-group#limiting-uis-and-styles) covers the object entries.

## Restrict Styles per UI Variant

A UI variant often suits only some of the primary component's styles. Declare the ones it suits in the variant's own `defineCwaConfig`, and the admin offers only those while the variant is picked:

```ts
// app/app/cwa/components/UiComponent/ui/JournalPageLayout.vue
defineCwaConfig({
  name: 'Journal Page',
  styles: {
    'top-rule': { label: 'Rule above', classes: 'border-t border-stone-700 pt-10' },
  },
})
```

A variant without `styles` offers the primary component's. Switching UI keeps only the stored styles the new variant defines, so an editor never ends up with a style that does nothing. Leave `allowMultiple` off unless the styles are made to combine.

This limits styles by UI, everywhere the component is placed. To limit them by place instead, list the allowed styles in the component group's entry (see [Restrict What Each Component Group Holds](#restrict-what-each-component-group-holds)). An editor is then offered only the styles both allow.

## Start New Components Filled In

A new component with empty fields shows nothing until an editor fills it in. Give it `defaultData`, so it shows something they can recognise and change:

```ts
defineCwaConfig({
  name: 'Quote',
  group: 'Text',
  icon: 'quote',
  defaultData: { quote: 'Add the quote here', author: 'Who said it' },
})
```

A component with no text of its own, such as an image, can show `<LazyCwaUiEditPlaceholder>` in edit mode instead; see [Component Files › Part 3: Editing on the Page](/nuxt-module/building-your-ui/creating-components#part-3-editing-on-the-page).
