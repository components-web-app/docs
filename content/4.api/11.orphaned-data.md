---
title: Orphaned Data
description: Find and delete component groups, positions and components that nothing uses, and stored files that no row references.
---

Over time a site collects content nothing shows: a component removed from its last group, a group whose page was deleted, a file whose row is gone. The bundle has two reports for this, one for resources and one for files. Each is refreshed by a scan, read by the admin, and cleaned up through a delete endpoint that checks again before it deletes anything.

::callout{icon="i-heroicons-photo"}
Image: the admin's `/_cwa/orphaned` page, showing the orphaned resources report above the orphaned files report.
::

## Orphaned Resources

### Scanning

Run [`scan-orphaned`](/api/console-commands#scan-orphaned), or send `POST /_/orphaned_resources/scan` as an admin, to scan for orphaned component groups, empty component positions and unused components and store the report. Neither deletes anything.

```bash
php bin/console silverback:api-components:scan-orphaned
```

The command prints the number of orphans of each kind. Add `-v` to list their IRIs as well:

```
Component groups: 1
Component positions: 2
Components: 3
```

The command takes no arguments, only the [`--no-notify`](#emailing-when-orphans-change) option, and always exits with `0`. It runs the same scan as `POST /_/orphaned_resources/scan`, but always during the command, even when you route the scan message to a Messenger worker. That makes it suitable for a cron job or a deploy step that keeps the report fresh.

`silverback:api-components:clean-orphaned` is an alias of `scan-orphaned`, so it only scans too. To delete orphans, use [`POST /_/orphaned_resources/delete`](#deleting-orphans) or send `DELETE` to each IRI.

### Orphaned Resource Report

The report endpoints need `ROLE_ADMIN`:

| Request | Result |
|---------|--------|
| `POST /_/orphaned_resources/scan` | No body. Refreshes the report and returns `202`. |
| `GET /_/orphaned_resources` | The stored report, sent `private, no-store`. `404` until the first scan. |
| `POST /_/orphaned_resources/delete` | Deletes orphans; see [Deleting Orphans](#deleting-orphans). |

The report has a `generatedAt` time, to the microsecond, and three lists of IRIs:

- `componentGroups`: groups that nothing live owns. A group is live when a page or layout owns it, or a live component does. A group owned only by orphaned components is orphaned.
- `componentPositions`: positions in an orphaned group, and every position with neither a component nor a page data property.
- `components`: components in no live position and no page data property. A component referenced only by one of your own relations is listed too.

The tree starts at pages, layouts and page data component properties, and anything nothing live reaches is an orphan. That includes a chain orphaned only through its parent, such as a group owned by an orphaned component and the positions and components inside it, and cycles like a component placed in a group it owns.

A draft copy is never listed; it's judged by its published version. A draft whose published version is orphaned has its own groups listed. A component held by a page data property counts as used even when the property is typed as a parent class, such as `AbstractComponent`. So does the `/usage` count.

The report, the command and the delete endpoint all use the same definition of an orphan.

In the Nuxt module's admin, site settings can start a scan and `/_cwa/orphaned` lists the report with buttons to view and delete each resource; see [Orphaned Resources](/nuxt-module/cwa-layer/maintenance#orphaned-resources).

The scan runs during the request by default, which is three queries. To queue it instead, install `symfony/messenger`, route the message to an async transport and run a worker with `php bin/console messenger:consume async`:

```yaml
# config/packages/messenger.yaml
framework:
    messenger:
        transports:
            async: '%env(MESSENGER_TRANSPORT_DSN)%'
        routing:
            'Silverback\ApiComponentsBundle\Message\ScanOrphanedResourcesMessage': async
```

When queued, `POST` returns before the scan finishes: check `generatedAt` to see whether the report has been refreshed.

The report is one row of the `_acb_orphaned_resource_report` table (with the default `table_prefix`), updated in place by each scan. Every pod and worker reads the same report, and it survives cache clears and deploys. Only the latest report is kept.

### Emailing When Orphans Change

When `orphaned_resources.notify.recipients` is set, the command emails those addresses when its scan differs from the last alert. The recipients, admin page path and subject are in [Configuration](/api/configuration#full-configuration):

```yaml
# config/packages/silverback_api_components.yaml
silverback_api_components:
    orphaned_resources:
        notify:
            recipients: '%env(ORPHANED_RESOURCES_NOTIFY_RECIPIENTS)%'
```

`recipients` is a list, or one comma-separated string such as `ops@example.com,dev@example.com`, so a plain `%env()%` can supply it. With no recipients, nothing is sent and the command prints nothing about it.

A recipient can be a bare address or the `Name <address>` form, such as `My Website <website@example.com>`, and `null` counts as no recipients.

The [components-web-app template](/deployment/kubernetes#daily-orphan-scan) schedules this command on production, daily at 03:00 London time, with `recipients: '%env(string:default::MAILER_EMAIL)%'`, so the alert goes to the site's own email address, and an empty `MAILER_EMAIL` sends nothing.

The result has changed when any of the three lists holds different IRIs from the last alert. Order doesn't matter. With no alert yet, a result counts as a change only if it has orphans. The email gives the count of each kind, the IRIs that are new since the last alert, how many are no longer orphaned, and a **Review Orphaned Resources** button that opens the admin page.

::callout{icon="i-heroicons-information-circle"}
Only `scan-orphaned` sends the email, and it compares with the **last alert**, not with the stored report. `POST /_/orphaned_resources/scan` and the refresh after [`POST /_/orphaned_resources/delete`](#deleting-orphans) replace the stored report but never email and never move the last alert. So a change an admin has already seen in the admin is still emailed on the next run.

The last alert moves forward when an email is sent, and when the result matches it. It stays put when a send fails, so the next run tries again. It also stays put when there are no recipients or the run has `--no-notify`.
::

`--notify` is on by default. Pass `--no-notify` to scan and store the report without emailing. The last alert doesn't move, so the next run with notifications on still emails anything that changed.

After the counts, the command prints one of:

- `The report has changed: a notification was sent.`
- `The report has not changed: no notification was sent.`
- `The report has changed, but the notification could not be sent. The error has been logged.`

The report is saved before the email is sent, and a failed send still exits with `0`. A mailer transport failure is logged at error level as a `MailerTransportException`, as for user emails. An invalid address from the environment variable is logged too, and nothing is sent to anyone.

The button links to `admin_page_path` (default `/_cwa/orphaned`) on [`user.email_links.default_origin`](/api/users/user-emails#links-in-emails). It never uses a request's origin, because the command has none. Without a usable `default_origin`, the email is sent without the button and a warning is logged.

### Deleting Orphans

`POST /_/orphaned_resources/delete` deletes orphans. It needs `ROLE_ADMIN`. Send either the IRIs to delete, or `all` to delete every orphan:

```json
{ "iris": ["/_/component_groups/0199…", "/component/html_contents/0199…"] }
```

```json
{ "all": true }
```

::callout{icon="i-heroicons-information-circle"}
Send exactly one of `iris` and `"all": true`. An empty body, `{"all": false}`, or both together return `422` and delete nothing. There is no "delete everything when no list is sent", so a truncated body can't empty the site.
::

The endpoint doesn't trust the stored report or your list. It scans again during the request and deletes only IRIs that are orphans in that fresh scan. Everything is deleted in one transaction, cache purges and Mercure updates go out as for any other write, and the stored report is refreshed afterwards.

It returns `200` with what was deleted, grouped by kind, and what was refused:

```json
{
  "deleted": {
    "componentGroups": ["/_/component_groups/0199…"],
    "componentPositions": ["/_/component_positions/0199…"],
    "components": ["/component/html_contents/0199…"]
  },
  "rejected": [
    { "iri": "/component/html_contents/0199…", "reason": "not_orphaned" }
  ]
}
```

- `deleted` includes everything the delete took with it, each IRI once. Deleting an orphaned group, for example, also lists its positions and the components used only there.
- `rejected` lists each requested IRI that wasn't deleted, with a reason. It is always empty for `"all": true`.
  - `not_orphaned`: the resource exists but isn't in the fresh scan. Something uses it now, or it is a draft.
  - `not_found`: the IRI resolves to nothing, because it was already deleted or isn't a resource.

One refused IRI doesn't stop the rest: the others are still deleted. A report can be minutes old, so something may have been reused since.

The delete cascades so that it leaves nothing for the next scan:

- **A group** takes its positions, and any component in them that isn't used anywhere else.
- **A component** takes the groups it owns, recursively, unless an owner that isn't being deleted also has them.
- **A published component** takes its draft too, unless the draft is itself placed or held by page data.

An API `DELETE` of a group, page, layout or page data cascades the same way. The one difference is a `DELETE` sent to a published component itself: its draft is kept, because the draft holds the pending content and takes over its positions.

## Orphaned Files

Run [`scan-orphaned-files`](/api/console-commands#scan-orphaned-files), or send `POST /_/orphaned_files/scan` as an admin, to scan the upload filesystems for stored files that no row references, for rows whose file is gone, and for files that break their field's current validation rules. It stores the report and never modifies or deletes anything.

```bash
php bin/console silverback:api-components:scan-orphaned-files
```

It prints the number of files in each list. Add `-v` to list them as `adapter: path`, with the resource IRI after each missing file, and the resource IRI, field and each violation after each invalid file:

```
Orphaned files: 2
Unknown files: 1
Missing files: 0
Invalid files: 1
```

It takes no options, sends no email and always exits with `0`. Like `scan-orphaned`, it scans during the command even when you route the scan message to a Messenger worker.

::callout{icon="i-heroicons-information-circle"}
`scan-orphaned` and its email cover component groups, positions and components only. Files have their own scan, and nothing emails about them.
::

### Orphaned Files Report

The report endpoints need `ROLE_ADMIN`:

| Request | Result |
|---------|--------|
| `POST /_/orphaned_files/scan` | No body. Refreshes the report and returns `202`. |
| `GET /_/orphaned_files` | The stored report, sent `private, no-store`. `404` until the first scan. |
| `POST /_/orphaned_files/delete` | Deletes orphaned files; see [Deleting Orphaned Files](#deleting-orphaned-files). |

The report has a `generatedAt` time and four lists:

```json
{
  "generatedAt": "2026-10-02T09:15:42.123456+00:00",
  "orphanedFiles": [
    { "adapter": "local", "path": "photo-3f9a1c2e.jpg" }
  ],
  "unknownFiles": [
    { "adapter": "local", "path": "robots-backup.txt" }
  ],
  "missingFiles": [
    { "resource": "/component/images/0199…", "adapter": "local", "path": "hero-8b2d4e6f.png" }
  ],
  "invalidFiles": [
    {
      "resource": "/component/images/0198…",
      "field": "file",
      "adapter": "local",
      "path": "beach-1c4e9a07.jpg",
      "violations": [
        "This image is too large (45000000 pixels). Please resize it to at most 30000000 pixels and upload it again."
      ]
    }
  ]
}
```

- `orphanedFiles`: stored files that no row references and that the bundle can show it wrote. Either the name has the bundle's [stored-name pattern](/api/components/annotations/uploadable#stored-filenames) (`<stem>-<8 hex characters>.<ext>`, or the UUID name of a data URI upload), or the file has a row in the bundle's file info table. **These are the only files the API deletes.**
- `unknownFiles`: stored files that no row references, but that the bundle can't show it wrote. It never deletes them. Remove them yourself if they aren't needed, or add their prefix to `excluded_paths`.
- `missingFiles`: rows whose stored file doesn't exist on their filesystem, with the resource's IRI. Nothing deletes these; re-upload the file or delete the resource.
- `invalidFiles`: stored files that a row references but that break the field's current constraints, with the resource's IRI, the field and each violation message. For example, an original uploaded before you added a `maxPixels` limit. Nothing modifies or deletes these. [Upload a replacement through the resource](/api/components/annotations/uploadable#replacing-a-stored-file).

A file counts as referenced when any uploadable field of any row holds its path, drafts included.

::callout{icon="i-heroicons-information-circle"}
**What is scanned.** Only the filesystems that an `#[UploadableField]` uses, and only under each field's `prefix`. A field with no `prefix` makes its whole filesystem part of the scan. The LiipImagine cache prefix is always left out, and so is every prefix in [`orphaned_files.excluded_paths`](/api/configuration#full-configuration). Files modified less than `orphaned_files.minimum_age` seconds ago (default one hour) are skipped, because an upload is stored before its row is saved.
::

A path that is orphaned on more than one filesystem is listed once for each.

The report is one row of the `_acb_orphaned_file_report` table (with the default `table_prefix`), updated in place by each scan. As with the resource report, the scan runs during the request unless you route `Silverback\ApiComponentsBundle\Message\ScanOrphanedFilesMessage` to an async transport (see [Orphaned Resource Report](#orphaned-resource-report)). When queued, check `generatedAt` to see whether the report has been refreshed.

In the Nuxt module's admin, `/_cwa/orphaned` lists this report below the resource report; see [Orphaned Resources](/nuxt-module/cwa-layer/maintenance#orphaned-resources). It shows invalid files in a read-only section.

#### How Invalid Files Are Checked

Each referenced file that exists is checked against the `Default` group's constraints on its `#[UploadableField]` property (`file`, not the stored filename). `Assert\File` and `Assert\Image` are checked, including inside a composite such as `Assert\When` or `Assert\Sequentially`. Other constraints are skipped, because they would need the uploaded file.

| Checked | Not checked |
|---------|-------------|
| Empty files, `maxSize`, `mimeTypes`, and every `Assert\Image` width, height, pixel, ratio and orientation option (an SVG skips width, height and pixels, as Symfony does) | `extensions`, filename length and charset, `detectCorrupted` |

The scan reads the original's row in the file info table for the type, size and dimensions. Without a row, it asks the storage for the type and size, and reads the dimensions from the file only when an option needs them. It never decodes the image. If the storage fails while a file is checked, a warning is logged and that file is left out of the list.

In an `Assert\When` expression, `value` is the stored file. It has `getMimeType()`, `getSize()`, `getFilename()` and `getPath()`, so the template's `value.getMimeType() !== "image/svg+xml"` works. Anything else fails the scan, and `this` is `null`.

### Deleting Orphaned Files

`POST /_/orphaned_files/delete` deletes orphaned files. Send either the paths to delete, or `all` to delete every orphaned file:

```json
{ "paths": ["photo-3f9a1c2e.jpg"] }
```

```json
{ "all": true }
```

::callout{icon="i-heroicons-information-circle"}
Send exactly one of `paths` and `"all": true`. An empty body, `{"all": false}`, both together, or a blank path return `422` and delete nothing.
::

As with orphaned resources, the endpoint scans again during the request and deletes only paths that are orphaned in that fresh scan. A path is deleted on every filesystem where it's orphaned. Deleting a file also removes its LiipImagine variants and its file info rows. The stored report is then replaced by the fresh scan, minus what was deleted.

It returns `200`:

```json
{
  "deleted": [
    { "adapter": "local", "path": "photo-3f9a1c2e.jpg" }
  ],
  "rejected": [
    { "path": "robots-backup.txt", "reason": "unknown" }
  ]
}
```

`rejected` lists each path that wasn't deleted, with a reason:

- `unknown`: the file is in `unknownFiles`, which are never deleted.
- `not_orphaned`: the file exists on a scanned filesystem but isn't orphaned in the fresh scan. Something references it again, or it's newer than `minimum_age` or under an excluded prefix.
- `not_found`: no scanned filesystem has the file. It was already deleted, or it's a missing file.
- `delete_failed`: the storage refused the delete. The error is logged. This one can also appear for `"all": true`.

Invalid files are never deleted, even with `"all": true`, because a row still references them. One rejected path doesn't stop the rest. Files aren't deleted in a transaction, so anything deleted before a failure stays deleted.
