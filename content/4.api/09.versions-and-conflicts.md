title: Versions & Conflicts
description: Each component and page data write gets a version number, a save based on an old copy is refused with 412, and the collaboration state store keeps the shared editing state of a field.
---

Two admins can edit the same component at the same time. The bundle numbers every write of a component or page data, so a save made from an old copy is refused instead of silently replacing someone else's work. It also stores the shared editing state that the Nuxt module's co-editing loads when an admin opens a field (see [Collaboration States](#collaboration-states)). How the admin uses both is covered in [Real-Time Updates › Co-Editing in the Admin](/nuxt-module/component-helpers/real-time-updates#co-editing-in-the-admin).

## The Version Number

Every component and page data record has a version: a whole number that is 1 when the record is created and goes up by one on every write. It's in `_metadata.version` on every response, for every caller, and on both Mercure updates (see [Real-Time Updates (Mercure) › Public and Admin Updates](/api/real-time#public-and-admin-updates)):

```json
{
    "@id": "/component/html_contents/0190…",
    "html": "<p>Hello</p>",
    "_metadata": {
        "version": 4
    }
}
```

- Doctrine keeps it, with `#[ORM\Version]` on `AbstractComponent` and `AbstractPageData`. It's stored in a `resource_version` column, and it isn't a field you can write.
- Every write raises it, however it's made: a `PATCH`, a `PUT`, a publish, or a move that changes page data.
- **A draft is its own record, with its own version.** A new draft starts at 1, and its published component keeps its own number. Only compare versions of the same `@id`.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**The version needs a column on two tables.** Generate a migration with `doctrine:migrations:diff` and run it before you deploy. It adds `resource_version` (an integer, default 1) to `_acb_abstract_component` and `_acb_abstract_page_data`, with the default `table_prefix`.
::

### The `ETag` header

A signed-in caller's successful response for one component or page data record also carries the version as a strong `ETag`, on reads and writes alike:

```http
ETag: "4"
Cache-Control: no-store, private
```

That response is then `private, no-store`, so no shared cache keeps it (see [HTTP Caching › HTTP Cache Safety](/api/http-caching#http-cache-safety)). A collection response and a `204` have no version `ETag`. Anonymous responses keep API Platform's own `ETag` and stay cacheable.

## Saving with `If-Match`

Send the version you last read in an `If-Match` header on a `PATCH`, `PUT` or `DELETE`:

```http
PATCH /component/html_contents/0190…
Content-Type: application/merge-patch+json
If-Match: "4"

{ "html": "<p>Hello, world</p>" }
```

The API compares it with the version of the record the URL names. When they match, the write goes ahead, and the response carries the new version (`ETag: "5"`). When they don't, nothing is written and the answer is a **412**.

- The comparison is strong. `"4"` matches version 4, a list such as `"3", "4"` matches either, and `*` matches any version. A weak tag such as `W/"4"` never matches.
- The check runs after the access checks, so only a caller allowed to make the write learns the current version.
- A write without `If-Match` isn't compared, but it can still lose a race (see [When a save is refused](#when-a-save-is-refused)).

### What a 412 contains

**Every 412 has the current resource as its body**, in the shape a `GET` of the same URL and query returns, with its `_metadata.version`. The response is `private, no-store`. A client can show the editor both versions, or apply its change again on top and resend it with the new version. If the resource can't be read any more, the response is that error instead, such as a `404`.

### When a save is refused

| Situation | Result |
|-----------|--------|
| The `If-Match` version isn't the record's current version | **412**. Nothing is written |
| Another save changed the record after this request read it and before this one was committed, with or without `If-Match` | **412**, with the record as the other save left it. Nothing is written |
| An `If-Match` on a write to a published component's IRI, when the API sends that write to its existing draft | **412**, with the draft |
| Two first edits of the same published component arrive together, and each would create its draft | The second is a **412**, with the draft the first one created |

The third row needs a word. A caller who can see drafts and writes to a published IRI edits its draft (see [Publishable › How It Works at the API Level](/api/components/annotations/publishable#how-it-works-at-the-api-level)). A live record and its draft can have the same number, so the API can't tell which one the client read, and refuses any `If-Match`. Send the write to the draft's own IRI with the draft's version instead. Without `If-Match`, a write to the published IRI still edits the draft.

Publishing is a write to the draft's IRI too: a `PATCH` of `publishedAt` with a stale `If-Match` is a 412, and nothing is published. Publishing raises the published component's version.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**A `DELETE` is only checked against `If-Match`.** A delete without the header goes ahead even when the record changed after you read it. Send `If-Match` to delete only the version you saw.
::

::callout{icon="i-heroicons-information-circle"}
**The order and move endpoints ignore `If-Match`.** `PATCH /_/component_groups/{id}/order` and `POST {component IRI}/move` never compare it. The page data a move changes still gets a new version. See [Component Groups & Positions › Reordering a group in one request](/api/components/component-groups#reordering-a-group-in-one-request) and [Component Groups & Positions › Moving a Component](/api/components/component-groups#moving-a-component).
::

### Your own entities

The 412 isn't only for components and page data. When any API write fails because Doctrine's `#[ORM\Version]` check found the row changed (an `OptimisticLockException`), the bundle answers 412 with the current resource. `If-Match` and the version `ETag` work only for components, page data and collaboration states. An `OptimisticLockException` outside an API Platform write keeps API Platform's `409`; see [Debugging & Errors › Error Status Codes](/api/debugging#error-status-codes).

## CORS for `ETag` and `If-Match`

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**A front end on another origin needs both headers in CORS.** The browser hides `ETag` from code unless the API exposes it, and blocks a write that sends `If-Match` unless the API allows it. With NelmioCorsBundle, as in the template:

```yaml [api/config/packages/nelmio_cors.yaml]
nelmio_cors:
    defaults:
        allow_headers: ['Content-Type', 'Authorization', 'Preload', 'Fields', 'Path', 'X-CWA-Client-Id', 'If-Match'] # [!code focus]
        expose_headers: ['Link', 'Retry-After', 'ETag'] # [!code focus]
```
::

A front end on the API's own origin needs nothing. `X-CWA-Client-Id` is explained in [Real-Time Updates (Mercure) › Who saved a change: `X-CWA-Client-Id`](/api/real-time#who-saved-a-change-x-cwa-client-id), and `Retry-After` in [User Emails › Throttled and Failed Email Requests](/api/users/user-emails#throttled-and-failed-email-requests).

## Collaboration States

When several admins edit one rich text field together, their editors share a [Yjs](https://yjs.dev){target="_blank"} document. `/_/collaboration_states` stores that document for one field of one component or page data record, so an admin who opens the field later loads it from the API. The Nuxt module's co-editing reads and writes it; you don't need it unless you build your own editor.

::callout{icon="i-heroicons-lock-closed"}
**Admins only.** Every operation needs `ROLE_ADMIN`: an anonymous request is a `401`, and a signed-in user without the role gets a `403`. Every response is `private, no-store`, and a state is never published over Mercure.
::

| Field | Description |
|-------|-------------|
| `component` | The IRI of the component the state belongs to |
| `pageData` | The IRI of the page data the state belongs to. A state has exactly one of `component` and `pageData` |
| `field` | The name of the field, such as `html`. Up to 255 characters. The bundle doesn't check it against the resource's fields |
| `state` | The Yjs document, base64 encoded. Required, up to 8,388,608 characters. The bundle doesn't decode it |
| `htmlHash` | A hash of the HTML the state was made from. Required, up to 255 characters. Stored as sent and never checked: the client uses a state only when the hash matches the HTML it loaded, which covers every other way the field can change |
| `_metadata.version` | The state's version, as for components (see [The Version Number](#the-version-number)) |

### Reading and writing a state

| Request | Does |
|---------|------|
| `GET /_/collaboration_states?component=<IRI>&field=html` | Finds a component's state for one field. The collection is empty when there's none |
| `GET /_/collaboration_states?pageData=<IRI>&field=html` | The same for page data |
| `POST /_/collaboration_states` | Creates a state. **201** |
| `GET /_/collaboration_states/{id}` | Reads one state |
| `PATCH /_/collaboration_states/{id}` | Updates the state, usually its `state` and `htmlHash`. Send `If-Match` with the version you read: a stale one is a **412** with the current state |
| `DELETE /_/collaboration_states/{id}` | Deletes the state. **204** |

```http
POST /_/collaboration_states
Content-Type: application/ld+json

{
    "component": "/component/html_contents/0190…",
    "field": "html",
    "state": "AQKl…",
    "htmlHash": "9f2c…"
}
```

These are a **422**:

- both `component` and `pageData`, or neither: "A state belongs to either a component or a page data.";
- a second state for the same component and field ("This component already has a state for this field.", on `component`), or the same page data and field (on `pageData`);
- a `state` longer than 8,388,608 characters, or a missing `field`, `state` or `htmlHash`.

A `component` or `pageData` IRI that doesn't exist is refused with a `400` or `422`.

### Drafts and deletes

**A draft shares its published component's state.** A state posted with a draft's IRI, or with a published IRI that an admin would read as its draft, is stored under the published component. So a draft and its published component hold one state per field, and you find it with the published component's IRI, even while a draft exists. Publishing keeps the state. A draft that has never been published is stored as itself, and keeps its state when it's first published. This follows [Publishable › A Reference to a Draft Stores the Published Component](/api/components/annotations/publishable#a-reference-to-a-draft-stores-the-published-component).

**Deleting a component or page data deletes its states**, however it's deleted: through the API, by an orphan delete, or in SQL. A state doesn't count as a use of its component, so it doesn't keep a component out of the [Orphaned Data](/api/orphaned-data) report or add to its usage. `generate-fixtures` leaves states out.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**The store needs its own table.** Generate a migration with `doctrine:migrations:diff` and run it before you deploy. It creates `_acb_collaboration_state` (with the default `table_prefix`), with one unique index on component and field and one on page data and field. Each foreign key is `ON DELETE CASCADE`. On MySQL, the `state` column is a `MEDIUMTEXT`.
::
