The bundle works with a shared HTTP cache in front of the API, such as Souin in the template's FrankenPHP image. It marks what must never be shared, tags what can be, and purges the tags when content changes. The settings live under `http_cache` in [Configuration](/api/configuration#full-configuration). Front-end page caching is covered in [Page Caching](/nuxt-module/page-caching).

## HTTP Cache Safety

Some resources look different depending on who's asking. When an admin is signed in, `GET /_/routes/{path}`, the resource manifest, and any draft of a Publishable component return the **draft** view — the same URL a signed-out visitor uses to get the **published** view (the API decides from the auth cookie, not the URL). If a shared cache stored the admin's response, it could later serve that draft to the public.

The bundle prevents this at the source. On a `GET`/`HEAD` for an **authenticated** user, when the resource is in the affected set, a `kernel.response` listener overrides API Platform's default `public` caching:

```
Cache-Control: private, no-store
```

It also strips the long shared `s-maxage` from that response. Anonymous requests, and any resource not in the affected set (a `Layout`, say), are untouched and stay publicly cacheable — so the only variant a shared cache ever holds is the published one.

**The affected set** is the configured `personalised_resource_classes` (default `Route`, `ResourceManifest`, `ComponentPosition`) **plus every Publishable resource**, matched dynamically — you don't list your Publishable components. Subclasses of a listed class match too. Add your own resource classes if they vary by session:

```yaml
silverback_api_components:
    http_cache:
        personalised_resource_classes:
            - 'Silverback\ApiComponentsBundle\Entity\Core\Route'
            - 'Silverback\ApiComponentsBundle\ApiResource\ResourceManifest'
            - 'Silverback\ApiComponentsBundle\Entity\Core\ComponentPosition'
            - 'App\Entity\MyPersonalisedComponent'
```

::callout{icon="i-heroicons-information-circle"}
This is deliberately done **without** `Vary: Cookie`. Varying on the cookie would collapse the cache hit-rate for anonymous visitors (cookies churn), and it isn't needed — the unsafe responses are marked non-cacheable outright rather than cached under a cookie key. The cacheable anonymous variant carries no cookie to vary on.
::

This header is the API-side contract a service worker relies on to cache CWA responses safely — a `no-store`/`private` response is the signal to **not** store it. See [Progressive Web App & Offline](/nuxt-module/pwa) on the front-end for the full picture.

## Cache Tags and Purging

With API Platform's HTTP cache invalidation turned on, every cacheable response is tagged with the IRIs of the resources it contains. With the template's Souin purger, the tags go in a `Surrogate-Key` header. When a resource is written, the bundle sends its IRI to the shared cache as a purge, so every cached response that used the resource is dropped.

Two IRIs are never tagged, because nothing can purge them: JSON-LD blank nodes (`/.well-known/genid/…`) and `/_/resource_metadatas`.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**A failed purge doesn't fail the write.** If the cache refuses the purge or can't be reached, the write still gets its normal response and Mercure still publishes. The failure is logged at error level, with the tags, as `The HTTP cache purge after a write failed, so these tags may still be cached`. Those responses can stay stale until they expire or you fix the cache and purge again, so alert on that log.
::

Tags are IRIs generated by Symfony's router, so a route import prefix such as the template's `/_api` is included whether the write comes over HTTP or from the CLI (fixtures, console commands, messenger workers). A `Route` write, for example, purges `/_api/_/routes` and `/_api/_/routes//my-route`.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**Serving the API from a sub-directory?** Set `framework.router.default_uri` to a URL that includes that path. A request's base path is only known over HTTP, so without it every write made from the CLI purges unprefixed tags and misses the cache. The template doesn't need this: `/_api` is a route prefix, not a base path.
::

### Resource Manifests Are Tagged per Page

A resource manifest (`GET /_/resource_manifest/{id}`) is the exception. Its body is only a list of IRIs, so it changes only when the page's **structure** changes: which component sits in which group, which layout a page uses, or which page a route publishes. Instead of the IRI of every resource it lists, a manifest carries one grouping key per rendering depth:

```
Surrogate-Key: manifest:/_/pages/8f3c…
```

A nested page carries one key for each ancestor depth as well as its own. A page-data manifest also carries the key of the template page it renders through. A manifest requested by route path and the same manifest requested by ID carry identical keys, so one purge drops both.

A write to any of these purges the manifests that contain it: `Route`, `Page`, any `AbstractPageData`, `Layout`, `ComponentGroup` and `ComponentPosition`. The bundle works upward from the written resource to the pages that contain it, so adding a component to a group in a shared layout purges the manifest of every page using that layout. A change inside a template page purges the manifest of every page data that uses it.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**Editing a component's content doesn't purge any manifest.** The manifest lists the component's IRI, and that IRI hasn't changed. The component's own IRI is purged, so the component's response, and any cached page tagged with it, refresh straight away. Don't rely on a component save to refresh a manifest.
::

One exception: a component placed through a `pageDataProperty` still purges the manifests of the page data that references it, because the bundle treats that write as a change to the page data itself.

A manifest carries a handful of keys whatever the size of the page, so its `Surrogate-Key` header stays well under Souin's 1500-byte batch.

## Scheduled Publication and Cache Lifetime

A scheduled publication changes what a response should contain at a set time, with no write to trigger a purge. The bundle handles this by shortening the cache lifetime instead, on **anonymous**, successful `GET` responses that already have an `s-maxage` or `max-age`.

**`Expires` caps the cache lifetime.** A component with a future `publishedAt` sends an `Expires` header set to that date, including on anonymous requests, so the front end can see a change coming without seeing the draft. Shared caches give `s-maxage` priority over `Expires`, so the bundle also lowers `s-maxage` and `max-age` to the time left until `Expires` whenever that's sooner. This applies to any response that sets `Expires`, not only publishable components.

**Route go-live dates cap the classes in `scheduled_expiry_resource_classes`.** For these responses, `s-maxage` and `max-age` are capped at the **soonest future `liveAt` across all routes**, whether or not the response mentions that route. That's deliberate: a route going live changes pages that never mention it (a navigation menu, for example), and no cache tag can express that. The default list covers routes, pages and page data (`RoutableInterface`) and the resource manifest, which is where a page render starts:

```yaml
silverback_api_components:
    http_cache:
        scheduled_expiry_resource_classes:
            - 'Silverback\ApiComponentsBundle\Entity\Core\Route'
            - 'Silverback\ApiComponentsBundle\Entity\Core\RoutableInterface'
            - 'Silverback\ApiComponentsBundle\ApiResource\ResourceManifest'
```

Subclasses and implementations of a listed class match too.

::callout{icon="i-heroicons-information-circle"}
A collection response carries no `Expires`. A collection that contains a resource with a pending publication is only capped if its class is in `scheduled_expiry_resource_classes`.
::

Because every scheduled change shortens the responses it affects, the front end can take a page's lifetime from the shortest `s-maxage` among the API responses it used, without reading publication dates it can't see anonymously. That's what the Nuxt module does — see [Page Caching](/nuxt-module/page-caching). It makes a long `shared_max_age` safe.

A route that isn't live yet is never cached at all. See [Routes → Caching](/api/routes#caching).

## Purging Every Rendered Page

The Nuxt module tags each cached page with the IRIs of the resources it rendered, so a write to any of them drops the affected pages. Some resources change every page without being one of those resources. Site config is the main case: changing `siteName` would leave every cached page showing the old name until it expired.

A write to a class listed in `purge_rendered_html_classes` therefore also purges the surrogate key **`cwa-html`**, which the module adds to every page it caches. The default list is `SiteConfigParameter`, and subclasses match:

```yaml
silverback_api_components:
    http_cache:
        purge_rendered_html_classes:
            - 'Silverback\ApiComponentsBundle\Entity\Core\SiteConfigParameter'
```

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**This drops every cached page at once, on purpose.** All the traffic then reaches Nuxt SSR together. That's fine for a rare admin action, which is why the list should stay short. **List only leaf resources**: ones that aren't reachable as a Doctrine association of another resource. Otherwise unrelated writes will drop the whole page cache.
::

The purge is sent once per write request. Saving several site config parameters is several requests and several purges, which is harmless because the key is already gone after the first. Creating, updating and deleting a site config parameter (`/_/site_config_parameters`) all need `publishable.permission` (usually `ROLE_ADMIN`).

::callout{icon="i-heroicons-information-circle"}
`cwa-html` is a contract shared by the bundle and the Nuxt module. Both sides must use the same name. A mismatch fails silently: the purge matches nothing and pages stay stale until they expire.
::

### Purging the Pages After a Deploy

To drop every cached page yourself, for example after a front-end deploy, run [`purge-rendered-html`](/api/console-commands#purge-rendered-html), or send `POST /_/rendered_html/purge` as an admin (`204`). Both purge `cwa-html` and leave cached API responses alone. With no HTTP cache purger configured, they do nothing and still succeed. A failed purge makes the command exit with `1` and the endpoint return `502`, so a deploy script can rely on it.

## Flushing the Whole HTTP Cache

Tag purges only reach resources the API has seen change. After a direct database edit, a data fix or an import, flush every cached response instead:

```bash
php bin/console silverback:api-components:purge-http-cache
```

or, as an admin, `POST /_/http_cache/purge` with no body. It returns `204`. Both drop every cached response, API responses and rendered page HTML together. There is no option to flush only the API responses. To drop one page or one tag instead, use the command's `--path` or `--tag` options; see [Purging One Page or Tag](#purging-one-page-or-tag). The Nuxt module's site settings has a **Purge all cached data** button that sends the same request; see [Purging all cached data](/nuxt-module/page-caching#purging-all-cached-data).

The flush is sent to Souin's flush endpoint, `<invalidation url>/flush`, for each URL in `api_platform.http_cache.invalidation.urls`.

| Situation | Command | Endpoint |
|-----------|---------|----------|
| Flushed | exits `0` | `204` |
| The purger is not Souin, or no invalidation URL is set | exits `0`, flushes nothing, and says so | `501` |
| The cache refused or couldn't be reached | exits `1` with the error | `502` |

::callout{icon="i-heroicons-information-circle"}
To clear pages after a front-end deploy, keep using `purge-rendered-html` ([Purging the Pages After a Deploy](#purging-the-pages-after-a-deploy)). It drops only the pages, so the API responses stay cached. A full flush sends every request back to PHP and Nuxt until the cache refills.
::

## Purging One Page or Tag

To drop only some cached responses, pass `--path` or `--tag`. Both can be repeated, and they can be combined:

```bash
# One page, by its path
php bin/console silverback:api-components:purge-http-cache --path /about-us

# Any cache tag, such as the rendered pages' tag or a resource IRI
php bin/console silverback:api-components:purge-http-cache --tag cwa-html --tag /_api/component/titles/0199…
```

- `--path </path>` purges the tag that a write to the route at that path purges: `<route import prefix>/_/routes/<path>`. With the template's `/_api` prefix, `--path /about-us` purges `/_api/_/routes//about-us`. It works whether or not a route still exists at that path, so it also drops a page whose route has gone.
- `--tag <tag>` purges that tag as it is.

With either option, only those tags are purged, through the same purger that writes use. It never flushes the whole cache. With Souin, it's a surrogate-key purge, so with the template's Cloudflare provider it also purges the page at Cloudflare. The command lists the tags it purged.

| Result | Exit code |
|--------|-----------|
| Purged | `0` |
| No HTTP cache purger is configured: nothing is purged, and the command says so | `0` |
| The purge request failed | `1` |
| A tag contains a space or a comma, or a `--path` doesn't start with `/` | `2`, and nothing is purged |

In the template's Kubernetes deploys, run it in the API deployment's `cwa-php` container. The deployment has the chart's full name: the release name, with `-cwa` added unless the release name already contains `cwa`.

```bash
kubectl exec -n <namespace> deploy/<deployment> -c cwa-php -- bin/console silverback:api-components:purge-http-cache --path /about-us
```

`POST /_/http_cache/purge` takes no body and always flushes the whole cache. Purging by path or tag is only available from the command.
