A component group is a named, ordered list of components that belongs to a layout, page or component. Each component in it sits in a `ComponentPosition`, and the group lists its positions in order. The fields of both resources are in the [API overview](/api#componentgroup). This page covers the rules the API applies when positions are added, moved and reordered.

## Limiting How Many Components a Group Holds

Set `maxComponents` on a group to cap how many components it holds. `null`, the default, is unlimited. Otherwise it must be a positive whole number: `0` or a negative value is a **422**.

```json
{
  "allowedComponents": ["/component/header_buttons"],
  "maxComponents": 1
}
```

It's read and written on the group, like `allowedComponents`, and returned with the groups embedded in a layout or page.

### What counts

The limit counts the positions the group lists:

- A position with a component counts as one. A published component and its draft share one position, so they count once.
- A dynamic position, bound to a page data property, counts as one.
- A position hidden by `allowedComponents` doesn't count. The group doesn't list it, so it isn't shown either.

### When a write is refused

When the group already lists `maxComponents` positions, these writes are a **422** with a violation on `componentGroup`:

- creating a position in the group (`POST /_/component_positions`);
- moving a position into the group, by a `PATCH` that changes its `componentGroup`;
- creating a component with a new position in the group, as the admin adds a component (`"componentPositions": [{"componentGroup": "…"}]`). The violation is on `componentPositions[0].componentGroup`.

The message names the group and the limit:

```text
The component group `header_/_/layouts/0190…` is full: it holds at most 1 component.
```

A position already in the group can always be moved within it, and its component can still be edited.

::callout{icon="i-heroicons-information-circle"}
Lowering `maxComponents` below what a group holds removes nothing. The group keeps every component and takes no more until it's under the limit.
::

In fixtures, pass `max:` to `group()` on a layout, page or component builder, for example `->group('header', allow: [HeaderButton::class], max: 1)`. `generate-fixtures` writes it for a group that has a limit. The fixture builder doesn't validate, so a scaffold can seed more components than the limit.

In the front end, set it with the [`max-components` prop](/nuxt-module/cwa-components/cwa-component-group#limiting-the-number-of-components).

`maxComponents` is stored in the `max_components` column of the component group table (`_acb_component_group` with the default `table_prefix`).

### Positions written inside a component

A new position sent inside a component write, in its `componentPositions`, is checked against the group's `allowedComponents` and [`#[ExplicitAllowOnly]`](/api/components/annotations/explicit-allow-only) as well as its limit, as a position created on its own is. This applies to a component `POST` and to a component `PATCH` that adds a new position.

A position written with a draft of a published component stores the published component. See [Publishable › A Reference to a Draft Stores the Published Component](/api/components/annotations/publishable#a-reference-to-a-draft-stores-the-published-component).

## A Component Can't Contain Itself

A component can't be placed inside its own subtree: in one of its own groups, or in a group further down, inside a component placed in one of them. Such a write is a **422** with a violation on `component`:

```text
The component cannot be placed in the component group `<reference>`: the group is inside the component.
```

This applies when a write sets where a component goes:

- creating a position (`POST /_/component_positions`);
- a `PATCH` that changes a position's `component` or `componentGroup`;
- a position sent inside a component write. The violation is on `componentPositions[0].component`.

Giving a group an owner from inside that group's own subtree, by adding a component to the group's `components`, is a **422** on `components`: "The component group `<reference>` cannot be owned by a component inside it."

::callout{icon="i-heroicons-information-circle"}
**Only a path back to the component itself is refused.** One component can still be shared in several places, such as two sibling containers. A published component and its draft count as one component, so placing a container's draft inside the published container, or the other way round, is refused too.
::

A position is only checked when its `component` or `componentGroup` changes. Content that already holds a cycle, written by fixtures or SQL, can still be read and edited: the security check and the manifest stop at the cycle. The fixture builder doesn't check for cycles.

## How Positions Are Ordered

The server orders every position. `sortValue` is in every position response, lowest first, but it is **read-only**: the API ignores a `sortValue` in a request body. To place a position, send an anchor. To reorder a group, send its new order to the order endpoint.

::callout{icon="i-heroicons-information-circle"}
A `sortValue` sent on its own is ignored, so the position stays where it was. In your own PHP code, the `ComponentPositionOrderer` service places and reorders positions. The admin needs `@cwa/nuxt` 2.0.0-alpha.19 or later, which reorders through the order endpoint.
::

### Placing a position: `after` and `before`

Send `after` or `before` with the IRI of a position in the same group. The position goes right after or right before it. With neither, a new position goes at the end of the group.

```http
POST /_/component_positions
Content-Type: application/ld+json

{
  "componentGroup": "/_/component_groups/0190…",
  "component": "/component/html_contents/0190…",
  "after": "/_/component_positions/0190…"
}
```

An anchor works in three places:

- creating a position, `POST /_/component_positions`;
- a position inside a component write: `"componentPositions": [{"componentGroup": "…", "after": "…"}]`;
- a `PATCH` on a position that moves it within its group, or into another group. A move into another group with no anchor goes to the end. A `PATCH` with no anchor and no change of group leaves the position where it is.

These are a **422**:

| Request | Violation on |
|---------|--------------|
| An anchor that isn't a position of the group: in another group, deleted, or not a position IRI | `after` or `before` |
| A position anchored to itself | `after` or `before` |
| An anchor sent with a `sortValue` | `after` or `before` |
| Both `after` and `before` | `before` |

`after` and `before` are write-only. They aren't stored or returned.

### Reading a group's order

`GET /_/component_groups/{id}/order` returns the group's positions in order, with their sort values. `{id}` is the group's id or its `reference`, so the path is the group's `@id` followed by `/order`.

```json
{
  "componentGroup": "/_/component_groups/0190…",
  "componentPositions": [
    "/_/component_positions/0190…a",
    "/_/component_positions/0190…b"
  ],
  "sortValues": {
    "/_/component_positions/0190…a": 0,
    "/_/component_positions/0190…b": 1
  }
}
```

It lists every position the group lists. Positions hidden by `allowedComponents` are left out. An unknown group is a **404**.

### Reordering a group in one request

`PATCH /_/component_groups/{id}/order` with `Content-Type: application/merge-patch+json` reorders the group. Send the positions in their new order:

```json
{
  "componentPositions": [
    "/_/component_positions/0190…b",
    "/_/component_positions/0190…a"
  ]
}
```

Only `componentPositions` is writable. The rules:

- You don't have to list every position. One you leave out moves with the listed position it currently follows, and stays right after it. Positions before the first listed one stay at the start.
- An IRI of a position that no longer exists is ignored, so a list made before another editor deleted a position still works.
- A position of another group, or an IRI listed twice, is a **422** on `componentPositions[n]`.
- `maxComponents` doesn't apply, because a reorder adds nothing.

The response has the same shape as the `GET`, and lists every position in the group, including ones another editor added since you read it. There's no ETag, so update your copy from the response.

The endpoint has no security of its own. A `PATCH` goes through your app's access rules, as a `PATCH` on the group does. In the template, a write needs a signed-in user, and an anonymous `PATCH` is a **401**.

### How sort values are chosen

You don't need these rules to use the API, but they explain the numbers you see:

- The server keeps as many existing values as it can, and gives the positions between them consecutive values.
- A value is never below 0, and every value in a group is unique.
- Positions that share a value, from data written before this release, are ordered by id. The next write that orders the group gives them unique values.
- A new group's first position gets 0, and each position added at the end gets the last value plus one.

For example, moving the second of five positions (`0 1 2 3 4`) to after the fourth gives `0 2 3 4 5`: only the moved position and the one after its new place change.

A Mercure update is published only for the positions whose `sortValue` changed.

## Moving a Component

`POST {component IRI}/move` moves a component from one place to another in a single request: between component positions, between a position and a page data component property, or between two page data properties. Every component resource has it, beside [`/usage`](#where-a-component-is-used), under the same prefix as the component, such as `/_api/component/html_contents/0190…/move` in the template.

It runs as one database write. A component is never left in two places, and a dropped connection can't leave it deleted, as it could with a `DELETE` followed by a `POST` from the client.

```http
POST /component/html_contents/0190…/move
Content-Type: application/ld+json

{
  "from": { "componentPosition": "/_/component_positions/0190…a" },
  "to": { "componentGroup": "/_/component_groups/0190…", "after": "/_/component_positions/0190…b" }
}
```

`from` is where the component is now, and `to` where it goes. Each takes one of two shapes:

| Key | Shape | Means |
|-----|-------|-------|
| `from` | `{ "componentPosition": "<position IRI>" }` | The position holding the component |
| `from` | `{ "pageData": "<page data IRI>", "property": "<name>" }` | The page data property holding the component |
| `to` | `{ "componentGroup": "<group IRI>" }`, with `after` or `before` if you like | A place in a group. `after` and `before` work as in [Placing a position](#placing-a-position-after-and-before); with neither, the component goes at the end |
| `to` | `{ "pageData": "<page data IRI>", "property": "<name>" }` | A page data component property |

### What a move does

| From | To | Result |
|------|----|--------|
| A position | A group | The **same position** moves, so its IRI doesn't change. It is placed as a `PATCH` of its `componentGroup` with `after` or `before` would place it. Within the same group, it's a reorder |
| A position | A page data property | The property is set and the position is removed. The component isn't deleted, even if that position was its only use |
| A page data property | A group | A new position is created for the component and placed, and the property is set to `null` |
| A page data property | Another property | One is set and the other set to `null`, on the same page data or across two |

A dynamic position, one bound to a page data property, is never changed by a move. To move the component a dynamic position shows, move the page data property.

The response is a **200**:

```json
{
  "from": { "componentPosition": "/_/component_positions/0190…a" },
  "to": { "componentGroup": "/_/component_groups/0190…", "after": "/_/component_positions/0190…b" },
  "componentPosition": "/_/component_positions/0190…a"
}
```

`componentPosition` is the IRI of the position that was moved or created, or `null` when the component went into a page data property. `from` and `to` are your request. The response doesn't carry the new order or the page data, so read the groups' [`/order`](#reading-a-groups-order) and the page data again for the new state. The positions, groups and page data the move changed are purged from the cache and published over Mercure as the separate writes would be.

### Drafts

A published component and its draft count as one. Sending the move to the draft's IRI moves the published component, and `from` matches a position or property holding either of them. What is stored is the published component; see [Publishable › A Reference to a Draft Stores the Published Component](/api/components/annotations/publishable#a-reference-to-a-draft-stores-the-published-component).

### When a move is refused

A move is checked as the separate writes would be, and nothing changes when it's refused. These are a **422**, with the violation at the part of the body that caused it:

| Request | Violation on |
|---------|--------------|
| `from` or `to` missing, not an object, or with neither shape or both. `to` with page data takes no `after` or `before` | `from` or `to` |
| A position, group or page data IRI that doesn't exist or is another type: ``The IRI `…` is not a component position.`` | `from.componentPosition`, `to.componentGroup`, `from.pageData`, `to.pageData` |
| An `after`, `before` or `property` that isn't a string | `to.after`, `to.before`, `from.property`, `to.property` |
| A dynamic source position: "A dynamic position cannot be moved: move the page data property instead." | `from.componentPosition` |
| A source position with no component, or one holding another component | `from.componentPosition` |
| A source property with no component, or one holding another component | `from.property` |
| A property that isn't a component property of the page data, or can't hold this component's class | `from.property` or `to.property` |
| The target is the source property: "The component is already held by this property." | `to` |
| A target property that already holds a component. It's refused, never replaced | `to.property` |
| An anchor that isn't a position of the target group, an anchor to the moved position itself, or both `after` and `before` | `to.after` or `to.before` |
| A target group that doesn't allow the component (`allowedComponents`, [`#[ExplicitAllowOnly]`](/api/components/annotations/explicit-allow-only)), is full (see [Limiting How Many Components a Group Holds](#limiting-how-many-components-a-group-holds)), or is inside the component (see [A Component Can't Contain Itself](#a-component-cant-contain-itself)) | `to.componentGroup` |
| The page data fails its own validation after the change | `from.property`, `to.property`, `from.pageData` or `to.pageData` |

A move within a full group is allowed, because it adds nothing to the group.

The caller must be granted every write the move stands for: the `PATCH`, `POST` or `DELETE` of the position, and a `PATCH` of each page data resource it changes. When one isn't granted, the move is a **403**. For example, a user who fails `routable_security` can't move a component into or out of page data that no live route reaches; see [Access Control › `routable_security`](/api/users/access-control#routable_security). An anonymous request is a **401** in the template, whose `access_control` requires a signed-in user for every `POST`.

## Where a Component Is Used

`GET {component IRI}/usage` says how many places use a component, and lists them. The Nuxt module's admin reads it to show where a shared component is placed, and to offer deleting a component from every place.

```json
{
  "positionCount": 2,
  "pageDataCount": 1,
  "total": 3,
  "locations": [
    {
      "componentPosition": "/_/component_positions/0190…a",
      "pageDataProperty": null,
      "pageData": null,
      "property": null,
      "layout": { "iri": "/_/layouts/0190…", "reference": "primary" },
      "renderedOn": [],
      "renderedOnCount": 0
    },
    {
      "componentPosition": "/_/component_positions/0190…b",
      "pageDataProperty": null,
      "pageData": null,
      "property": null,
      "layout": null,
      "renderedOn": [
        { "iri": "/_/pages/0190…", "title": "About", "routePath": "/about" }
      ],
      "renderedOnCount": 1
    },
    {
      "componentPosition": null,
      "pageDataProperty": null,
      "pageData": "/page_data/blog_article_datas/0190…",
      "property": "image",
      "layout": null,
      "renderedOn": [
        { "iri": "/page_data/blog_article_datas/0190…", "title": "First post", "routePath": "/blog/first-post" }
      ],
      "renderedOnCount": 1
    }
  ]
}
```

| Field | Description |
|-------|-------------|
| `positionCount` | The component positions holding the component, across every group. A dynamic position whose fallback is the component counts |
| `pageDataCount` | The page data properties holding it. A property typed as a parent class, such as `AbstractComponent`, counts |
| `total` | `positionCount` plus `pageDataCount` |
| `locations` | One entry for each counted use, up to 50. `total` minus the number listed is how many weren't listed |

A published component and its draft are one component here: the draft's IRI gives the published component's usage.

### Each location

| Field | Description |
|-------|-------------|
| `componentPosition` | The position, for a use in a group. Otherwise `null` |
| `pageDataProperty` | Set when that position is dynamic, and the component is its fallback |
| `pageData`, `property` | The page data and property name, for a use in a page data property. Otherwise `null` |
| `layout` | `{ iri, reference }` of the layout, when the use is in a layout's group or inside a component placed in one. Otherwise `null` |
| `renderedOn` | The pages and page data the use renders on, each `{ iri, title, routePath }`, up to 20 |
| `renderedOnCount` | How many there are in all |

`routePath` is the route's own path, such as `/about`, without the API's route prefix. It's `null` when the page or page data has no route.

What `renderedOn` lists:

- **A position on a page** renders on that page. A position on a **template page** renders on the template and on every page data that uses it.
- **A dynamic position's fallback** renders only on the page data that leave that property empty. A page data whose property for the position holds a component shows that component instead, so it isn't listed, and `renderedOnCount` doesn't count it. The same goes up a nested chain: if the component sits inside a component that is the fallback of a dynamic position higher up, a page data that fills that property isn't listed either.
- **A position inside a component** renders wherever that component is placed, and up the chain through every component that holds it.
- **A use in a layout** shows on every page that uses the layout, so the layout is given in `layout` and its pages aren't listed: `renderedOn` is usually empty. If the use is in a layout through more than one path, the layout with the first `reference` is given.
- **A page data property** renders on that page data.

### Order and limits

Uses in a layout come first, by layout `reference`. Then come routed uses, by the first route path they render on, then unrouted uses, by title. Inside each location, `renderedOn` is ordered by route path, then unrouted entries by title.

At most 50 locations, and 20 `renderedOn` entries for each, are listed. `total` and `renderedOnCount` are always exact.

The response is `Cache-Control: private, no-store`, so a shared cache never stores it. Nothing purges it when a placement changes.

### Who can read it

Only `ROLE_ADMIN`. An anonymous request is a **401**, and any other signed-in user gets a **403**.
