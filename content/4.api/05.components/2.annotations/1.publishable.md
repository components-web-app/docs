---
title: Publishable
description: Add a draft/publish workflow to any component so admins can edit content privately before making it live.
---

`#[Silverback\Publishable]` gives your component a twin-resource draft/publish lifecycle. An admin edits the draft privately; visitors always see the published version. Publishing is atomic — the switch happens at the database level with no stale cache window.

## Setup

```php
use Silverback\ApiComponentsBundle\Annotation as Silverback;
use Silverback\ApiComponentsBundle\Entity\Core\AbstractComponent;
use Silverback\ApiComponentsBundle\Entity\Utility\PublishableTrait;

#[Silverback\Publishable]
#[ORM\Entity]
#[ApiResource(mercure: true)]
class Title extends AbstractComponent
{
    use PublishableTrait;

    #[ORM\Column(type: 'text', nullable: true)]
    public ?string $title = null;
}
```

That's all that's required. The trait and annotation together wire up the full lifecycle.

## What PublishableTrait Adds

| Property | Type | Description |
|----------|------|-------------|
| `publishedAt` | `?DateTimeInterface` | `null` = unpublished draft |
| `publishedResource` | `?self` | Points from draft → published twin |
| `draftResource` | `?self` | Points from published → draft twin |

The bundle creates and maintains these twins automatically. You never create the published twin manually.

## How It Works at the API Level

The bundle intercepts requests and routes based on the caller's role and the `published` query parameter:

| Caller | Gets |
|--------|------|
| Anonymous visitor | Published version (or 404 if never published) |
| Caller matching `publishable.permission` | Draft version if one exists, otherwise the published one |
| Direct `?published=true` | Published version explicitly |

You don't add the parameter yourself. The Nuxt module sends none when it loads a page, so the caller's role decides, whether or not edit mode is on. Its admin writes to a live component add `?published=true` only when the editor turns on the Publish tab's **Edit live version** toggle; otherwise the write goes to the draft. See [`useCwaResourceEndpoint`](/nuxt-module/composables/utilities/use-cwa-resource-endpoint#the-publish-query).

### Positions Holding an Unpublished Component

A caller who can't see drafts never sees a publishable component that isn't published yet, whose `publishedAt` is null or in the future, through a component position either. The position comes back with **no `component` key** and no `_metadata.staticComponent`, and the page's resource manifest leaves the component out (see [HTTP Caching › Resource Manifests Are Tagged per Page](/api/http-caching#resource-manifests-are-tagged-per-page)). Admins still get the draft.

::callout{icon="i-heroicons-information-circle"}
**Treat a position with no `component` as empty.** A front end reading positions itself must not request or render anything for it. The Nuxt module renders nothing there.
::

The response stays cacheable and up to date:

- It still carries the hidden component's cache tag.
- For a scheduled component, its `Expires` and `s-maxage` end when the component goes live.
- Publishing or rescheduling the component purges, and publishes over Mercure, the positions holding it and the manifests of the pages that place it.

### A Reference to a Draft Stores the Published Component

A published component and its draft are one component to the rest of the site. So nothing stores the draft of a published component as a reference: when a write names such a draft, the published component is stored instead. That covers:

- a component position's `component`: `POST` and `PATCH` on `/_/component_positions`, and positions embedded in a component write;
- a page data component property, written by a page data `PATCH`;
- a component field on another component, or any to-one field of your own that holds a component;
- a component group's owner (see below).

It doesn't matter how the draft is named. An admin who sends the published IRI gets the draft, because the API reads the draft for a caller who can see drafts, and that is resolved back to the published component too. The bundle does it when Doctrine flushes, so the fixture builder and your own Doctrine code get the same result. Admins still see the draft through the position.

A draft that has **never been published** has no published component, so it's stored as it is. Publishing it for the first time keeps the same row and IRI, so every position and property holding it still does.

**Groups owned by a component follow the same rule.** A group given a draft of a published component as its owner, through the group's `components` or the draft's own groups, is owned by the published component. Publishing a draft keeps the groups its published component owns and adds the draft's own, so a group added to either one since the draft was made isn't orphaned. The fixture builder also gives a group declared on a draft to its published component, and names the group after it.

## Publishing a Resource

Send a `PATCH` with `publishedAt` set to a date string:

```json
PATCH /component/titles/018e-...
Content-Type: application/merge-patch+json

{
    "publishedAt": "2024-01-15T10:30:00+00:00"
}
```

The bundle creates or updates the published twin and broadcasts a Mercure update if `mercure: true` is on the entity.

A future date schedules the draft: it stays a draft until that moment, then replaces the published version on the next request that reads it. The admin's **Publish** tab sets this date for you, see [Scheduling a Publish](/core-concepts/admin-panel#scheduling-a-publish).

There is no unpublish switch. Once a resource is live, a `PATCH` to it with `"publishedAt": null` (or any other change) creates or updates a **draft** and leaves the published version live, and a past date on a live resource is ignored. To take a published resource offline, `DELETE` it with `?published=true`: that removes the published version and keeps any draft.

### Publishing Now

To publish straight away, send the exact string `now` instead of a date. The server replaces it with its own clock, on a `POST`, `PUT` or `PATCH`:

```json
PATCH /component/titles/018e-...
Content-Type: application/merge-patch+json

{
    "publishedAt": "now"
}
```

Don't send the client's current time for this. If the client's clock is ahead of the server's, that date is still in the future when it arrives, so the resource stays a draft scheduled a moment ahead. The Nuxt module sends `now` for every immediate publish.

`now` follows the same rules as a date. A caller who doesn't match `publishable.permission` can't set it, so it's ignored like any `publishedAt` they send. On `?published=true` it's a `422`, like any change to a live resource's publication date.

## Publish-Only Validation

Some fields should only be required when going live, not while saving a draft:

```php
#[ORM\Column(type: 'text', nullable: true)]
#[Assert\NotBlank(groups: ['Title:published'])]
public ?string $title = null;
```

The convention for the publish validation group is `ClassName:published`. The bundle applies this group automatically when `publishedAt` is being set.

Customise the group name:

```php
#[Silverback\Publishable(validationGroups: ['my_custom_group'])]
```

## Filtered Collections

A collection of a publishable resource returns drafts only to callers who may read them, and that holds when the request carries filter parameters too. The same goes for routes that aren't live yet and for route security: filters only ever **narrow** a collection.

### Writing Safe Filters

That only holds if your filters add their conditions with `AND`. API Platform applies the query extensions (drafts, go-live dates, route security) *before* filters, so an `OR` at the top level of the query undoes them, and drafts and scheduled records show up in the results.

- **Always wrap `OrFilter` in `FreeTextQueryFilter`**: `new FreeTextQueryFilter(new OrFilter(new PartialSearchFilter()))`. A bare `OrFilter` ORs against the whole `WHERE` clause. See [Searching and Sorting](/api/dynamic-pages#searching-and-sorting) for a full example.
- **Never call `orWhere()`** in a Doctrine filter you write yourself. It ORs against everything already on the query. Collect your clauses and apply them once with `andWhere()` wrapping an `Expr\Orx`:

```php
$orX = $queryBuilder->expr()->orX();
foreach ($values as $value) {
    $param = $queryNameGenerator->generateParameterName($property);
    $orX->add($queryBuilder->expr()->like("$alias.$property", ':' . $param));
    $queryBuilder->setParameter($param, '%' . $value . '%');
}
$queryBuilder->andWhere($orX); // [!code focus]
```

## Configuring Who Can Publish

Set the security expression in the bundle config. Only users matching this expression can set `publishedAt`:

```yaml
silverback_api_components:
    publishable:
        permission: "is_granted('ROLE_ADMIN')"
```

Users who don't match it never see drafts (a draft IRI is a 404 for them), and their writes skip the draft stage: a `POST` is published straight away with `publishedAt` set for them, and a `PATCH` updates the published version directly.

To override the permission for a single resource, pass `isGranted` on the attribute. It takes precedence over `publishable.permission` for that class only:

```php
#[Silverback\Publishable(isGranted: "is_granted('ROLE_EDITOR')")]
```

## Custom Property Names

The default property names (`publishedAt`, `publishedResource`, `draftResource`) match what `PublishableTrait` declares. Override them when names conflict with your own fields:

```php
#[Silverback\Publishable(
    fieldName: 'publicationDate',
    associationName: 'original',
    reverseAssociationName: 'draft'
)]
```

If you customise names, don't use `PublishableTrait` — declare the properties yourself using the matching names.

## Migration Notes

`PublishableTrait` adds:

- 1 nullable datetime column (`published_at`)
- 1 nullable self-referencing foreign key (`published_resource_id`)

`draftResource` is the inverse side of the same one-to-one relation, so it adds no column of its own — don't go looking for a `draft_resource_id` in the migration.

Always review the generated Doctrine migration. The foreign key sits on the draft and uses `ON DELETE SET NULL`, so deleting the published version keeps its draft and just clears the draft's pointer.

## API Response Metadata

Every publishable component response includes a `_metadata.publishable` object:

```json
{
  "@id": "/component/titles/018e-...",
  "title": "My Heading",
  "_metadata": {
    "publishable": {
      "published": true,
      "publishedAt": "2024-01-15T10:30:00+00:00",
      "locationCount": 3
    }
  }
}
```

| Field | Type | Description |
|-------|------|-------------|
| `published` | `boolean` | Whether **this** resource is live: its `publishedAt` is set and not in the future. A draft reports `false` even when it has a published twin |
| `publishedAt` | `string \| null` | This resource's publication date (a future date on a scheduled draft), or `null` for a draft with no date |
| `locationCount` | `integer \| null` | Total number of places this component appears — counts both direct `ComponentPosition` references and `AbstractPageData` instances that hold it as a typed property (resolved via `pageDataProperty` positions at render time). Useful for showing admins "used in N places" before deleting. |

`locationCount` is `null` for component types that have no `getComponentPositions()` method.

A draft and its published component each have their own `_metadata.version`, and a write sent to the published IRI that lands on the draft refuses any `If-Match`. See [Versions & Conflicts › When a save is refused](/api/versions-and-conflicts#when-a-save-is-refused).

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
`_metadata.publishable` is returned to every caller, including anonymous visitors — don't treat its presence as an authentication signal. What the publish permission gates is the soft-validation output: `_metadata.violations` is only populated for callers who satisfy the `publishable.permission` expression.
::

## Interaction with Mercure

When a resource is published, if `mercure: true` is on the `#[ApiResource]`, the API broadcasts an update to the hub. Every browser that has loaded the resource receives the new content in real time with no page reload needed. The public update carries what an anonymous visitor would read. A draft's updates, and the writer's view of a published resource, are sent privately on `<iri>?draft=1`, to signed-in users who may see drafts. Moving a live resource's publication date to the future publishes a public delete. See [Public and Admin Updates](/api/real-time#public-and-admin-updates).
