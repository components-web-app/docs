---
title: Uploadable
description: Add file upload support to any component with Flysystem adapters and optional Imagine image processing.
---

`#[Silverback\Uploadable]` with `#[Silverback\UploadableField]` turns a component into a file host. Files are stored via Flysystem, served via a public URL, and optionally processed through LiipImagineBundle to generate multiple image variants (thumbnail, hero, square, etc.).

## Flysystem Setup

First, install a Flysystem adapter:

```bash
# Local filesystem
composer require league/flysystem-local

# Google Cloud Storage
composer require league/flysystem-google-cloud-storage

# S3-compatible
composer require league/flysystem-aws-s3-v3
```

Register the adapter as a service with the CWA tag:

```yaml
# config/services.yaml
services:
    League\Flysystem\Local\LocalFilesystemAdapter:
        arguments:
            - '%kernel.project_dir%/var/storage/default'
        tags:
            - { name: silverback.api_components.filesystem_adapter, alias: 'local' }
```

The `alias` becomes the adapter name you use in `#[UploadableField]`, and the tag creates an `api_components.filesystem.{alias}` service. The tag also accepts an optional `config` map, which is passed straight to the Flysystem filesystem — for example `config: { public_url: 'https://cdn.example.com/' }`.

## Add to Your Entity

```php
use ApiPlatform\Metadata\ApiResource;
use Doctrine\ORM\Mapping as ORM;
use Silverback\ApiComponentsBundle\Annotation as Silverback;
use Silverback\ApiComponentsBundle\Entity\Core\AbstractComponent;
use Silverback\ApiComponentsBundle\Entity\Utility\PublishableTrait;
use Silverback\ApiComponentsBundle\Entity\Utility\UploadableTrait;
use Symfony\Component\HttpFoundation\File\File;
use Symfony\Component\Validator\Constraints as Assert;

#[Silverback\Publishable]
#[Silverback\Uploadable]
#[ORM\Entity]
#[ApiResource(mercure: true)]
class Image extends AbstractComponent
{
    use PublishableTrait;
    use UploadableTrait;

    #[Silverback\UploadableField(adapter: 'local', urlGenerator: 'public', imagineFilters: ['thumbnail'])]
    #[Assert\File(maxSize: '5M')]
    public ?File $file = null;
}
```

`imagineFilters: ['thumbnail']` names a LiipImagine filter set, which generates a resized variant of each image. Configure the filter sets as in [LiipImagineBundle Integration](#liipimaginebundle-integration), or leave `imagineFilters` out if you don't need variants.

## UploadableField Parameters

| Parameter | Default | Description |
|-----------|---------|-------------|
| `adapter` | — | **Required.** The Flysystem adapter alias |
| `urlGenerator` | `'api'` | How to generate the file URL — see below |
| `property` | `'filename'` | The entity property (and column) that stores the file's stored path |
| `prefix` | `null` | Optional path prefix inside the storage (e.g. `'images/'`). It is prepended as-is, so include the trailing `/` |
| `imagineFilters` | `[]` | LiipImagine filter names to apply at upload time |
| `requiredOnPublish` | `false` | Block publishing until a file is present. See [Requiring a File on Publish](#requiring-a-file-on-publish) |
| `requiredOnPublishMessage` | `null` | Your own message for `requiredOnPublish` |
| `cacheControl` | `null` | The `Cache-Control` written on the stored file. `null` uses the configured default, `false` writes none. See [Cache-Control on Stored Files](#cache-control-on-stored-files) |
| `imagineCacheControl` | `null` | The same, for this field's Imagine variants |

### `urlGenerator` Values

- **`'api'`** (default) — the file is served through the owning resource's own download route, `GET /{resource}/{id}/download/{property}` (e.g. `/component/images/018e-.../download/file`). Works with any adapter regardless of whether it supports direct URL generation.
- **`'public'`** — calls Flysystem's `publicUrl()` method to return a direct CDN or storage URL. Works when the adapter implements Flysystem's `PublicUrlGenerator` interface (e.g. `league/flysystem-aws-s3-v3`, `league/flysystem-google-cloud-storage`) **or** when the adapter tag's `config` sets `public_url` (see above), so a local adapter served from a web root works too. Falls back to `'api'` only if neither can generate a public URL.
- **`'temporary'`** — calls Flysystem's `temporaryUrl()` method to return a pre-signed URL with an expiry (default: `+3 days`). Requires the adapter to implement Flysystem's `TemporaryUrlGenerator` interface. Falls back to `'api'` if not supported. The primary use case is S3 pre-signed URLs for private/access-controlled files.

```php
// S3 pre-signed URL — valid for 3 days, falls back to API route if adapter doesn't support it
#[Silverback\UploadableField(adapter: 's3', urlGenerator: 'temporary')]
public ?File $file = null;

// CDN public URL — direct S3/GCS link
#[Silverback\UploadableField(adapter: 'gcs', urlGenerator: 'public')]
public ?File $image = null;
```

## Uploading a File

**Option 1 — Base64 in the JSON body** (preferred for REST clients):

```json
POST /component/images
Content-Type: application/ld+json

{
    "file": "data:image/jpeg;base64,/9j/4AAQSkZJRgAB..."
}
```

A data URI is validated like a multipart upload: the field's `Assert\File`, `Assert\Image` or `#[UploadedImage]` checks the decoded file, and a failure is a `422` on the field. *Since bundle 2.0.0-alpha.23 ([#459](https://github.com/components-web-app/api-components-bundle/pull/459)).*

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
On 2.0.0-alpha.22 and earlier, any `Assert\File` or `Assert\Image` on the field refused every data-URI upload with "The file could not be uploaded.", even a valid file. Use the multipart upload for those fields until you update the bundle.
::

**Option 2 — Multipart form upload**:

```
POST /component/images/{id}/upload
Content-Type: multipart/form-data

file=<binary>
```

## The `_metadata` Response

After upload, the resource includes a `_metadata.mediaObjects` map:

```json
{
    "@id": "/component/images/018e-...",
    "_metadata": {
        "mediaObjects": {
            "file": [
                {
                    "contentUrl": "https://cdn.example.com/images/018e-....jpg",
                    "fileSize": 245120,
                    "mimeType": "image/jpeg",
                    "width": 1920,
                    "height": 1080,
                    "imagineFilter": null
                },
                {
                    "contentUrl": "https://cdn.example.com/images/018e-...thumbnail.jpg",
                    "mimeType": "image/jpeg",
                    "width": 300,
                    "height": 200,
                    "imagineFilter": "thumbnail"
                }
            ]
        }
    }
}
```

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
Each field maps to an **array**, not a single object. Element `[0]` is the stored original; each Imagine variant is a further element, identified by its own `imagineFilter` name. There is no nested object keyed by filter name.
::

## Multiple Files on One Resource

A single component can host several files — a poster and a thumbnail, a document plus its cover, etc. Declare **one `#[UploadableField]` per transient `File` property**, and give each one a **distinct `property:`** — the name of the column that stores its filename.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
`property` **defaults to `'filename'` for every field**. If two `#[UploadableField]`s share the same storage property, the bundle **throws `UnsupportedAnnotationException` at metadata load** (boot). Give each field on a multi-file entity its own `property:`.
::

```php
use ApiPlatform\Metadata\ApiResource;
use Doctrine\ORM\Mapping as ORM;
use Silverback\ApiComponentsBundle\Annotation as Silverback;
use Silverback\ApiComponentsBundle\Entity\Core\AbstractComponent;
use Symfony\Component\HttpFoundation\File\File;
use Symfony\Component\Validator\Constraints as Assert;

#[Silverback\Uploadable]
#[ORM\Entity]
#[ApiResource(mercure: true)]
class MediaBlock extends AbstractComponent
{
    #[Silverback\UploadableField(adapter: 'local', property: 'posterFilename', imagineFilters: ['hero'])] // [!code focus]
    #[Assert\File(maxSize: '5M')]
    public ?File $poster = null;

    #[Silverback\UploadableField(adapter: 'local', property: 'thumbnailFilename', imagineFilters: ['thumbnail'])] // [!code focus]
    #[Assert\File(maxSize: '2M')]
    public ?File $thumbnail = null;

    // Storage columns — auto-mapped by the bundle; no #[ORM\Column] needed
    public ?string $posterFilename = null; // [!code focus]
    public ?string $thumbnailFilename = null; // [!code focus]
}
```

Two things differ from the single-file setup:

- **No `UploadableTrait`.** The trait provides a single `filename` column, so it only fits one field. For multiple files, declare your own `?string` storage property per field instead.
- **No `#[ORM\Column]` on the storage properties.** The bundle's `UploadableListener` auto-maps each configured `property:` as a nullable string column — you just declare the `?string` property.

Each field is then fully independent:

- Its own entry under `_metadata.mediaObjects` — keyed by the **transient property name** (`poster`, `thumbnail`), each an array holding the original plus its own Imagine variants.
- Its own download route: `GET /{resource}/{id}/download/{property}`.
- Multipart uploads key each file by its transient property name (`poster`, `thumbnail`) — the same name you'd pass as the second argument to [`useCwaResourceUpload`](/nuxt-module/composables/admin-manager/use-cwa-resource-upload) on the front-end.

See [Images & Media → Multiple File Fields](/nuxt-module/component-helpers/images-and-uploads#multiple-file-fields) for displaying and editing several fields in the Nuxt app.

## Stored Filenames

Uploaded files are stored under a **unique tokenised name** derived from the original — `<original-stem>-<token>.<ext>` (e.g. an uploaded `hero.jpg` is stored as `hero-3f9a2b7c.jpg`). Data-URI / base64 uploads instead keep a UUID-based name.

The extension comes from the file's detected content type, not the name it was uploaded with. A PNG uploaded as `holiday.jpg` is stored as `holiday-3f9a2b7c.png`, and a PNG uploaded with no extension gets `.png`. The uploaded extension is kept when it's valid for the type (`.jpeg` stays `.jpeg`), and when the type is plain text or unrecognised (`.md`, `.csv`). *Since bundle `2.0.0-alpha.13` · [upgrade notes](https://github.com/components-web-app/api-components-bundle/releases/tag/2.0.0-alpha.13)*

::callout{icon="i-heroicons-shield-check"}
Every upload becomes its own stored object. Because the stored name is unique, editing, replacing, or deleting the file on one resource can never overwrite or remove the file another resource references — even if two uploads share the same original filename.
::

The stored name is therefore **not predictable** and does not equal the uploaded filename. Read the real URL from `_metadata.mediaObjects.<field>[0].contentUrl` (above) rather than constructing it from the uploaded name.

On a component that is also `#[Publishable]`, editing a published resource makes a draft with its own copy of the file. The copy is written beside the original, under the same field `prefix:` and the same tokenised naming. If the original is missing from storage, the draft keeps the original path rather than losing it.

## Cache-Control on Stored Files

On Google Cloud Storage and S3, the bundle writes a `Cache-Control` on each file it stores. A browser or CDN that loads the file straight from the bucket (`urlGenerator: 'public'`) then caches it. *Since bundle `2.0.0-alpha.15` · [release notes](https://github.com/components-web-app/api-components-bundle/releases/tag/2.0.0-alpha.15)*

| Stored file | Default `Cache-Control` | Why |
|-------------|-------------------------|-----|
| An uploaded original | `public, max-age=31536000, immutable` (a year) | A stored name is never reused, so the file at a path never changes |
| An Imagine variant | `public, max-age=2592000` (30 days) | A variant is written again at the same path when its filter is generated again |

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**A regenerated variant can stay stale for up to 30 days.** A browser or CDN that cached the old variant keeps it until its `max-age` runs out, because the URL hasn't changed. Variants are stored under their filter's name (`cache/<filter>/<stored name>`), so to make every client fetch the new one straight away, rename the filter set: its variants get new URLs.
::

::callout{icon="i-heroicons-information-circle"}
**Only the Google Cloud Storage and S3 adapters get a `Cache-Control`:** `GoogleCloudStorageAdapter`, `AwsS3V3Adapter` and `AsyncAwsS3Adapter`. Other adapters, such as the local filesystem, ignore the setting. A local file's caching is up to the web server that serves it. Variants get theirs only when the cache resolver is the bundle's `FlysystemCacheResolver` (see [LiipImagineBundle Integration](#liipimaginebundle-integration)).
::

Change the defaults with [`uploadable.cache_control`](/api/configuration#full-configuration). `null` writes no `Cache-Control`:

```yaml
# config/packages/silverback_api_components.yaml
silverback_api_components:
    uploadable:
        cache_control:
            original: 'public, max-age=31536000, immutable'
            imagine: 'public, max-age=86400'
```

A field can override either value. `cacheControl` sets its originals and `imagineCacheControl` its variants. `false` writes none for that field:

```php
#[Silverback\UploadableField(
    adapter: 'gcs',
    urlGenerator: 'public',
    cacheControl: 'private, max-age=0', // [!code focus]
    imagineCacheControl: false, // [!code focus]
)]
public ?File $file = null;
```

The header is set when the file is written. Files stored before you changed a value keep the one they were written with until they are written again, or until you update them in the bucket.

## Requiring a File on Publish

On a component that is both `#[Publishable]` and `#[Uploadable]`, set `requiredOnPublish: true` to block publishing until a file is present — either a transient upload in the request or an already-stored filename:

```php
#[Silverback\Publishable]
#[Silverback\Uploadable]
#[ORM\Entity]
#[ApiResource(mercure: true)]
class Banner extends AbstractComponent
{
    use PublishableTrait;
    use UploadableTrait;

    #[Silverback\UploadableField(adapter: 'local', requiredOnPublish: true)] // [!code focus]
    #[Assert\File(maxSize: '5M', mimeTypes: ['image/*'])]
    public ?File $file = null;
}
```

Attempting to publish without a file produces a validation violation on the file property, grouped under `{ShortName}:published` (e.g. `Banner:published`). The default message is:

```text
A file must be uploaded for the `{{ property }}` field before publishing.
```

Override it per field with `requiredOnPublishMessage`. The `{{ property }}` placeholder is substituted for the field name:

```php
#[Silverback\UploadableField(
    adapter: 'local',
    requiredOnPublish: true,
    requiredOnPublishMessage: 'Please attach a banner image before publishing.', // [!code focus]
)]
public ?File $file = null;
```

Each flagged field validates **independently**, so on a multi-file entity you can require some fields and not others, each with its own message. This composes with `#[Assert\File]` — the file-type and size checks still run when a file *is* supplied. For "at least N of these fields" or other conditional rules, add an `#[Assert\Callback]` to the `{ShortName}:published` group.

If you set custom `validationGroups` on `#[Silverback\Publishable]`, `requiredOnPublish` is checked in those groups too, so the file is still required when publishing.

## Replacing a Stored File

To change a file, upload a replacement through the API or the admin, as you uploaded the original. The new file gets a new stored name and new file info, its variants are generated from it, and the old file is deleted once nothing references it. Anything left behind shows up in the [orphaned files report](/api/orphaned-data#orphaned-files-report).

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**Never overwrite a stored file in place**, for example with `gsutil cp` or `aws s3 cp` to the same name. The file info row (type, size, dimensions) and any stored variants still describe the old file, so the API reports the wrong dimensions and keeps serving the old variants.
::

An image over the field's current limits, such as the pixel limit of [`#[UploadedImage]`](#capping-uploads-to-fit-the-budget), must be resized before you upload it again. The [orphaned files report](/api/orphaned-data#orphaned-files-report) lists stored files that break the field's current rules as invalid files, so you can find the ones to replace.

## Deleting a File

Send `null` for the field property in a PATCH:

```json
PATCH /component/images/{id}
Content-Type: application/merge-patch+json

{ "file": null }
```

The bundle removes the file from storage and clears the media object data.

### Removing the Resource

Removing a resource deletes its stored files too, however it's removed: a direct `DELETE`, a cascade from deleting a group, page, layout or page data, [`POST /_/orphaned_resources/delete`](/api/orphaned-data#deleting-orphans), or `remove()` and `flush()` in your own code. Each file, its LiipImagine variants and its file info rows are deleted after the flush succeeds, so a delete that is rejected or rolled back keeps the file. A path that another row of the same class still holds in the same field is kept. If the storage refuses the delete, the error is logged and the request still succeeds.

## LiipImagineBundle Integration

LiipImagine generates image variants automatically at upload time. A variant that isn't stored yet, such as one for a filter you've just added, is generated the first time the resource is read. To generate them before visitors ask, see [Generating Variants Ahead of Time](#generating-variants-ahead-of-time).

::callout{icon="i-heroicons-information-circle"}
`imagineFilters` are only applied to **raster images** — a mime type of `image/*` that isn't `image/svg+xml`. A non-image upload (PDF, docx, SVG) to a field that declares filters skips Imagine and returns its primary media object. This makes a mixed field, or a document uploaded to an otherwise image-ish field, safe.
::

::callout{icon="i-heroicons-information-circle"}
**A missing source file doesn't break the resource.** If a file's metadata is still cached but the file itself is missing from storage, for example after restoring production data into a local database without the files, each Imagine filter is skipped and the bundle logs a `warning`: `Skipped the imagine filter "…" because its source image "…" could not be loaded.` The response still includes the original media object and its download URL. In production, this warning means a stored file has gone missing.
::

::callout{icon="i-heroicons-information-circle"}
**A filter that fails doesn't break the resource either.** If generating a variant throws, for example because the driver lacks the image's codec or the image is corrupt, that filter is skipped and the bundle logs an `error`: `Skipped the imagine filter "…" for "…" because generating it failed: <exception message>`. The upload or `GET` still succeeds, `mediaObjects` lists the original without that variant, and the Nuxt module shows the original. The page manifests that contain the resource still load too.
::

LiipImagineBundle ships as a dependency of the API bundle, so it is already installed — you only need to configure it to use CWA's Flysystem data loader:

```yaml
# config/packages/liip_imagine.yaml
liip_imagine:
    data_loader: silverback.api_components.liip_imagine.binary.loader
    filter_sets:
        thumbnail:
            quality: 80
            filters:
                thumbnail: { size: [300, 300], mode: outbound }
        hero:
            quality: 90
            filters:
                thumbnail: { size: [1200, 630], mode: outbound }
```

Configure the cache resolver to write back through Flysystem:

```yaml
services:
    app.imagine.cache.resolver.local:
        class: Silverback\ApiComponentsBundle\Imagine\FlysystemCacheResolver
        arguments:
            $filesystem: '@api_components.filesystem.local'
            $rootUrl: 'https://cdn.example.com'
        tags:
            - { name: 'liip_imagine.cache.resolver', resolver: local }

liip_imagine:
    cache: local
```

The service `api_components.filesystem.{alias}` is created automatically for each registered adapter.

Variants are stored under the cache prefix (`media/cache` by default) as `<prefix>/<filter>/<stored name>`. Each variant's type, size and dimensions are kept in the file info table, `_acb_imagine_cached_file_metadata` with the default `table_prefix`, and reported in `mediaObjects`. If a variant's row is missing, for example after its rows were lost or with a bucket shared by another database, `FlysystemCacheResolver` reads the stored variant and saves its row. A width and height of `-1` with an empty `mimeType` only come from another cache resolver, or a variant that is missing or isn't an image.

Each time a variant is stored, its row is replaced. So after you change a filter's format, quality or size and its variants are generated again, `mediaObjects` reports the variant that is actually stored. *Since bundle `2.0.0-alpha.17` · [release notes](https://github.com/components-web-app/api-components-bundle/releases/tag/2.0.0-alpha.17)*

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
Variant rows written by an earlier bundle weren't replaced, so they can still describe an old variant: the wrong type, size or dimensions. `@cwa/nuxt` picks `srcset` candidates by `fileSize`, so a stale row can make it serve the original instead of a much smaller variant. Delete every variant row, then [purge the HTTP cache](/api/console-commands#purge-http-cache). Each row is read again from its stored variant the next time a resource is rendered. Originals' rows have an empty `filter` and are kept:

```text
DELETE FROM _acb_imagine_cached_file_metadata WHERE filter <> '';
```

Use your own table name if you changed `table_prefix`.
::

### WebP and Other Output Formats

To store a filter's variants in another format, set `format` (and `quality`) on the filter set:

```yaml
liip_imagine:
    filter_sets:
        thumbnail_webp:
            format: webp
            quality: 80
            filters:
                thumbnail: { size: [300, 300], mode: inset }
```

The variant is stored and served with that format's extension and content type: `media/cache/thumbnail_webp/photo-1a2b3c4d.webp` with the default prefix.

Without a `format`, a variant keeps the original's format, with one exception. **Variants of an AVIF, HEIC or HEIF original are saved as WebP** on every driver, because vips can't encode those formats and the other drivers often can't. A filter set with a `format` uses that format instead.

::callout{icon="i-heroicons-information-circle"}
The bundle does this by replacing the class of liip's `liip_imagine.filter.manager` service with `Silverback\ApiComponentsBundle\Imagine\FilterManager`. If your application sets its own class on that service, the bundle leaves it alone, and AVIF, HEIC and HEIF variants keep their format.
::

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
Don't use liip's `webp.generate` option. The bundle never resolves its `.webp` copy, so every filter would be generated twice.
::

### Clearing Variants

To delete a filter's stored variants, run liip's command:

```bash
# One filter (repeat --filter for several)
php bin/console liip:imagine:cache:remove --filter=thumbnail

# Every filter
php bin/console liip:imagine:cache:remove
```

It deletes the variants and their file info rows, and keeps the originals and their rows. Each variant is generated again the next time its resource is read, or by [`imagine:generate`](#generating-variants-ahead-of-time). Use it after you change a filter's options, such as its size, quality or format, because variants already stored are otherwise served as they are.

### Generating Variants Ahead of Time

When you add a filter, or clear a filter's variants, every image is missing a variant. Each one would be generated during a visitor's request. To generate them first, run [`silverback:api-components:imagine:generate`](/api/console-commands#imaginegenerate) after the deploy, then [purge the HTTP cache](/api/console-commands#purge-http-cache) so cached responses list the new variants. *Since bundle `2.0.0-alpha.15` · [release notes](https://github.com/components-web-app/api-components-bundle/releases/tag/2.0.0-alpha.15)*

```bash
php bin/console silverback:api-components:imagine:generate --dry-run   # how many are missing
php bin/console silverback:api-components:imagine:generate
php bin/console silverback:api-components:purge-http-cache
```

It generates one image at a time within the [imagine memory budget](#the-imagine-memory-budget), and skips variants already stored. Each variant gets its field's `imagineCacheControl`.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**Run it as a one-off job, not in a pod that serves requests.** Generating many large variants uses a lot of memory, and vips allocates it outside PHP's `memory_limit`. On a site with many images, use `--max-memory` and run it again in a new process while it exits with `3`. See [the command's options](/api/console-commands#imaginegenerate).
::

## Dynamic Filter Selection

For cases where the required filters depend on runtime data (request context, entity state), implement `ImagineFiltersInterface`:

```php
use Silverback\ApiComponentsBundle\Entity\Utility\ImagineFiltersInterface;
use Symfony\Component\HttpFoundation\Request;

class Image extends AbstractComponent implements ImagineFiltersInterface
{
    public function getImagineFilters(string $property, ?Request $request): array
    {
        return ['thumbnail', 'hero', 'square'];
    }
}
```

`$request` is `null` when called during upload processing outside a web request (e.g. in a fixture).

Filters returned from `getImagineFilters()` are **appended to** the field's `imagineFilters`, not a replacement for them — declare a filter in both places and it is generated twice.

## Large Images and PHP Memory

To make an Imagine variant, the driver decodes the whole image, so the memory it needs depends on the pixel count, not the file size. A 24-megapixel JPEG of a few MB needs hundreds of MB to thumbnail. The bundle generates every filter, on upload and on read, within a memory budget, so a large image can't exhaust PHP's memory.

### The Imagine Memory Budget

[`imagine.memory_limit`](/api/configuration#full-configuration) sets the budget. It defaults to `320M`. While a filter is generated, PHP's `memory_limit` is raised to it, then restored. A `memory_limit` that is already higher is kept, and `null` generates under the current limit. This lets the workers run with a lower global `memory_limit`: the template's requests run under `128M`.

```yaml
# config/packages/silverback_api_components.yaml
silverback_api_components:
    imagine:
        memory_limit: '512M'
```

Before it generates a filter that isn't stored yet, the bundle estimates the cost from the original's pixel count and the configured driver:

| `liip_imagine.driver` | Estimate per megapixel | Largest source under the `320M` default |
|-----------------------|------------------------|-----------------------------------------|
| `gd` (liip's default) | about 12 MB | about 23 megapixels |
| `imagick` | about 14 MB | — |
| `vips` | about 8 MB | about 35 megapixels |

Any other driver is estimated at 14 MB per megapixel. If the memory already in use plus the estimate is over the budget, that filter is skipped and a warning is logged:

```text
Skipped the imagine filter "general" for "beach-1c4e9a07.jpg": generating it needs about 540 MB, more than the memory limit allows.
```

The upload or `GET` still succeeds. The field's `mediaObjects` lists the original without that variant, and the Nuxt module shows the original instead.

Imagick and vips allocate their memory outside PHP, so PHP's `memory_limit` never stops them. They're still budgeted, because that memory counts against the pod's limit. Size the pod for every worker at its `memory_limit`, plus one generation at the budget. See [Kubernetes → Resource Requests and Limits](/deployment/kubernetes#resource-requests-and-limits).

### Capping Uploads to Fit the Budget

An image over the budget is stored with no variants. To refuse it with a clear `422` instead, add `#[UploadedImage]` to the field:

```php
use Silverback\ApiComponentsBundle\Validator\Constraints\UploadedImage; // [!code focus]

#[Silverback\UploadableField(adapter: 'local', imagineFilters: ['thumbnail'])]
#[Assert\File(maxSize: '20M')]
#[UploadedImage] // [!code focus]
public ?File $file = null;
```

*Since bundle 2.0.0-alpha.23 ([#456](https://github.com/components-web-app/api-components-bundle/pull/456)).*

`#[UploadedImage]` is an `Assert\Image`, so every `Image` option still works, such as `maxWidth`, `mimeTypes` or `maxSize`. Like `Assert\Image`, it only accepts `image/*` types by default. It adds three things:

- **An SVG is accepted.** It skips the width, height, pixel, ratio, orientation and corruption checks, because it has no pixel size. `maxSize` and `mimeTypes` still apply. Set `allowSvg: false` to refuse SVGs, and `svgNotAllowedMessage` to change that message.
- **A default pixel limit.** Without `maxPixels`, the limit is [`uploadable.image_max_pixels`](/api/configuration#full-configuration), which defaults to 30,000,000. Set it once for the project instead of on every field. `null` means no limit. A `maxPixels` on the field overrides it.
- **A clearer message.** It gives the limit and an approximate size, for example: `The image is too large (35000000 pixels). Resize it to at most 30000000 pixels (about 6708 x 4472) and upload it again.` A custom `maxPixelsMessage` can use `{{ max_width }}` and `{{ max_height }}`, as well as Symfony's `{{ pixels }}`, `{{ max_pixels }}`, `{{ width }}` and `{{ height }}`.

::callout{icon="i-heroicons-information-circle"}
**`#[UploadedImage]` doesn't make the file required.** An empty field passes. To require a file, set `requiredOnPublish: true` on the `#[Silverback\UploadableField]` (see [Requiring a File on Publish](#requiring-a-file-on-publish)).
::

The 30-megapixel default fits the `320M` budget with vips. GD and Imagick need more memory per megapixel, so with either of them set the limit to 20 megapixels:

```yaml
# config/packages/silverback_api_components.yaml
silverback_api_components:
    uploadable:
        image_max_pixels: 20000000
```

To accept larger images on GD, raise the budget with the limit: `512M` covers about 40 megapixels.

Adding or lowering a limit doesn't touch files already stored. The [orphaned files report](/api/orphaned-data#orphaned-files-report) checks stored files against the same limit and lists the ones that now break it as invalid files.

::callout{icon="i-heroicons-clock"}
**On bundle 2.0.0-alpha.22 or earlier**, there is no `#[UploadedImage]`. Wrap an `Assert\Image` in `Assert\When` so that SVGs skip it, because `Assert\Image` refuses an SVG outright:

```php
#[Assert\When(
    expression: 'value !== null && value.getMimeType() !== "image/svg+xml"',
    constraints: [new Assert\Image(maxPixels: 30_000_000)],
)]
```
::

### In the Template

The template uses libvips through FFI. Its `liip_imagine.yaml` sets `driver: vips`, with the `rokka/imagine-vips` and `jcupitt/vips` packages, the `ffi` extension and `ffi.enable = true`. `config/preload.php` loads `preload_vips.php`, which starts libvips once before FrankenPHP starts its threads. Keep it while the driver is vips, or concurrent uploads segfault in worker mode. GD is still installed: set `driver: gd` to switch back, and lower the limit to 20 megapixels. The template's `Image` entity still sets its 30-megapixel limit with the older `Assert\When` and `Assert\Image` pair, not `#[UploadedImage]`.

Keep these limits in step:

| Setting | Template value |
|---------|----------------|
| `upload_max_filesize` / `post_max_size` (PHP ini) | `20M` / `21M` |
| `#[Assert\File(maxSize: ...)]` on `Image::$file` | `20M` |
| `memory_limit` per request (`FRANKENPHP_MEMORY_LIMIT`) | `128M` (console commands `256M`) |
| `imagine.memory_limit` | `320M`, the bundle's default |
| Largest image accepted (`maxPixels`) | 30 megapixels with vips, 20 with GD |
| Admin uploads resized in the browser ([`cwa.upload.image`](/nuxt-module/configuration/nuxt-config#image-uploads), a module default) | over 2560 px on the longest edge or over 20 megapixels |

The template's `Image` entity generates three filters, `thumbnail` (500 px), `general` (1200 px, the size its `Image` component displays) and `large` (2400 px, `general` at twice the size for high-density screens). Each fits the image inside that box. Every filter set has `format: webp` and `quality: 80`, so every variant is WebP, whatever the upload's format. WebP keeps transparency, so a PNG logo stays transparent:

```yaml
# api/config/packages/liip_imagine.yaml (one of the three filter sets)
liip_imagine:
    filter_sets:
        general:
            format: webp
            quality: 80
            filters:
                thumbnail: { size: [1200, 1200], mode: inset }
```

According to the template, vips always saves WebP at quality 80, because liip never passes it a WebP quality, so `quality: 80` only makes GD match. In production the template stores files on Google Cloud Storage through `FlysystemCacheResolver`, so originals and variants get the default [`Cache-Control`](#cache-control-on-stored-files), and its deploys can run `imagine:generate` in a one-off Kubernetes Job (see [CI/CD → Generating image variants after a deploy](/deployment/ci-cd#generating-image-variants-after-a-deploy)). The field also sets `requiredOnPublish: true`, so publishing an image component without a file is a `422` on `file`.

### Browser-Side Resizing

The Nuxt module resizes large JPEG, PNG and WebP images in the browser before an admin upload sends them. By default, anything over 2560 px on its longest edge or over 20 megapixels is resized to fit both. A 2560 px image is at most 6.6 megapixels, well under the template's 30-megapixel cap, so a resized photo needs about 53 MB to thumbnail with vips, or 80 MB with GD. See [useCwaResourceUpload](/nuxt-module/composables/admin-manager/use-cwa-resource-upload#large-images-are-resized-before-upload) for the options.

The two sets of numbers work together. If you change one, check the other:

- If you raise the module's `maxEdge` or `maxPixels` to keep larger originals, check the result still fits under `maxSize` and `maxPixels` here.
- If you lower the limits here, lower the module's options too, or the API will refuse some resized admin uploads.

Keep the server limits even with browser resizing on. The browser only resizes uploads made through the admin. A direct API request, an old browser, or a field with resizing turned off still sends the original file.
