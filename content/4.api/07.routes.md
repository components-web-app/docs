A `Route` maps a URL path to one Page or PageData record. Everything on this page applies to every route, static or dynamic, nested or not. Pages and page data themselves are covered in [Page Data & Nested Pages](/api/dynamic-pages).

## The Route Resource

| Field | Description |
|-------|-------------|
| `path` | The URL path, such as `/blog/my-first-post`. Unique, up to 255 characters, and it must begin with its required start (see [The Required Start of a Path](#the-required-start-of-a-path)) |
| `name` | A unique name, used by fixtures and redirects. Up to 255 characters |
| `page` / `pageData` | The record this route publishes. Set one, not both |
| `redirect` | Another route this one redirects to (see [Redirects](#redirects)) |
| `liveAt` | The go-live date (see [Scheduling and Taking Routes Offline](#scheduling-and-taking-routes-offline)). Admin only |

A `path` or `name` over 255 characters is a 422 with a violation on the field ([Length Limits](/api#length-limits)). A `path` containing any whitespace, `?` or `#` is a 422 on `path` (`route.path` for an embedded route), `A path cannot contain whitespace, "?" or "#".`, wherever a path is written: a route `POST` or `PATCH`, a redirect, an embedded route, a cascade, a page move and fixture route generation. The path is never tidied for you, and a stored path isn't checked again until it changes. A cascade (see [Cascading Route Changes](#cascading-route-changes)) that would push any descendant over the limit is a 422 naming it, with nothing moved.

A route can be requested by its IRI or by its path: `GET /_/routes//blog/my-first-post`. The collection, `GET /_/routes`, takes a `search` parameter that matches part of the `path`, and `order[createdAt]` or `order[path]`. It lists newest first by default.

### Finding the Routes of Pages

To get the routes of some pages or page data in one request, list their IRIs in `pages[]` or `pageData[]`:

```
GET /_/routes?pages[]=/_/pages/018e…&pages[]=/_/pages/018f…&perPage=100
GET /_/routes?pageData[]=/page_data/blog_article_datas/018e…
```

- The parameter is `pages`, not `page`, because `page` is the pagination parameter. A single value without brackets works too: `pages=/_/pages/018e…`.
- Send up to 100 values, with `perPage=100` so every match comes back on one page. More than 100 values is a 422 with a violation on the parameter.
- A page or page data with no route has no row.
- A value that isn't an IRI matches nothing, and neither does any value after it in the list.
- Sending both parameters returns only the routes that match both. That is always none, because a route has a page or a page data, never both.

Who sees what is the same as for the unfiltered collection. Admins see draft, scheduled and held-back routes, with `liveAt` and `_metadata.effectiveLiveAt`. Anonymous callers see only live routes, and neither field (see [What Visitors and Admins See](#what-visitors-and-admins-see)).

## Creating a Route

Creating a Page or `PageData` record doesn't create a route for it by itself. Give it one in either of these ways:

- **Create the route.** Send `POST /_/routes` with the `path`, a `name`, and the record's IRI as `page` or `pageData`.
- **Embed a new route when you create the record.** `POST /_/pages`, or a page data class's `POST`, can carry the new route as an object (see [Embedding a New Route](#embedding-a-new-route)).

```json
POST /_/routes

{
  "path": "/blog/my-first-post",
  "name": "blog-my-first-post",
  "pageData": "/page_data/blog_article_datas/018e…"
}
```

A taken path is a 422 on `path`: "This path is already in use." A taken name is a 422 on `name`: "This route name is already in use." The API uses the path you send as it is: it adds no `-1` and doesn't build a path from the title. The path must begin with the record's required start, described next. The Nuxt module's admin suggests the required start followed by the title's slug, then saves the route this way.

To give a record a different path later, change its route with `PATCH /_/routes/{id}`. The old path becomes a redirect (see [Redirects](#redirects)).

Writing a route needs the publishable permission, like any other content write (see [Sites with Non-Admin Users › What Only Editors Can Write](/api/users/non-admin-users#what-only-editors-can-write)).

### The Required Start of a Path

A route's path must begin with its **required start** and go on after it. The required start is made of:

1. the path of the record's nearest ancestor that has a route, skipping parents with none;
2. then the page data class's route prefix, if it declares one (see [A Route Prefix for a Page Data Class](#a-route-prefix-for-a-page-data-class));
3. then `/`.

| Record | Nearest routed ancestor | Prefix | Required start |
|---|---|---|---|
| A page with no parent | none | none | none: any path |
| A page under `/about` | `/about` | none | `/about/` |
| `AnnouncementData` with no parent | none | `/announcements` | `/announcements/` |
| `UpdateData` under the announcement `/announcements/summer-fair` | `/announcements/summer-fair` | `/updates` | `/announcements/summer-fair/updates/` |

A record with no routed ancestor and no prefix can have any path. A path that is only the required start, such as `/about/`, is refused too.

The rule is checked whenever a route is written: a new route, a change to its `path`, or a route given to a page or page data, including one embedded on create. A path that breaks it is a 422 on `path` (or `route.path` when embedded): "This path must start with "/about/" and continue after it." Routes that already exist aren't checked again until one of those writes, so an older child route outside its parent's path keeps working. A redirect, a route with no page or page data, is never checked. Neither is an explicit `route:` in a fixture.

::callout{icon="i-heroicons-information-circle"}
**Moving a page to another parent moves its route.** Changing its `parentPage` or `parentPageData` rewrites the route under the new required start (see [Moving a Page](#moving-a-page)).
::

### A Route Prefix for a Page Data Class

To keep every record of a page data class under a fixed path, give the class `#[Silverback\RoutePrefix]`:

```php
use Silverback\ApiComponentsBundle\Annotation as Silverback;

#[Silverback\RoutePrefix('/announcements')]
#[ApiResource]
#[ORM\Entity]
class AnnouncementData extends AbstractPageData
{
}
```

- The prefix must start with `/` and not end with one. It can have several segments, such as `/news/announcements`. `''` or `/` throws `InvalidRoutePrefixException` the first time the attribute is read: "The route prefix "/" is invalid: it must start with a slash, must not end with one and cannot be a lone slash."
- It goes after the nearest routed ancestor's path, so prefixes build up down a chain: an `UpdateData` (prefix `/updates`) under an announcement gets `/announcements/summer-fair/updates/<slug>`.
- A subclass inherits its parent class's prefix.
- It applies only to page data. A `Page` has no prefix.
- The API docs list it as `routePrefix` on the class's Hydra `supportedClass`. The Nuxt module's admin reads it from there, so nothing is configured in Nuxt.
- Fixture route generation uses it as well (see [Route Generation](#route-generation)).

### Embedding a New Route

Send `route` as an object instead of an IRI when you create a page or page data:

```json
POST /_/pages

{
  "layout": "/_/layouts/018e…",
  "reference": "about-team",
  "uiComponent": "Primary",
  "isTemplate": false,
  "route": { "path": "/about/team", "name": "about-team", "liveAt": null }
}
```

- `path` is required.
- `name` is optional. A missing or `null` name is made from the path: each `/` becomes `-`, and a `-` at either end is dropped, so `/about/team` gives `about-team` and `/` gives `root`. If that name is taken, `-1`, `-2` and so on is added.
- `liveAt` is optional, and only `ROLE_ADMIN` can set it. Left out, the route is live straight away. `null` makes a draft route that keeps the URL reserved, and a future date schedules it.
- `route` can still be the IRI of an existing route instead.

The response is a `201`. Its `route` is the new route's IRI, a string, as in every page and page data response.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**The embedded route is validated with the record.** If a rule fails, the response is a 422 and nothing is created, neither the record nor the route. The violations are on `route.path` and `route.name`:
- `route.path`: "This path is already in use." for a taken path, "This value should not be blank." for an empty one, or "This path must start with "…" and continue after it." for one outside its required start;
- `route.name`: "This route name is already in use." for a name you sent that is taken;
- either field, when it is over 255 characters.
::

## Route Generation

Only [data fixtures](/api/data-fixtures/getting-started) generate routes. `CwaFixtureBuilder` uses `RouteGenerator::create()` for a page or page data you don't give an explicit `route:`. It takes the slug of the record's title, puts it after the required start (see [The Required Start of a Path](#the-required-start-of-a-path)), and adds `-1`, `-2` and so on when that path is taken. If the record already had a route, the old route becomes a redirect to the new one.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**A route can only be generated from a title.** For a record with no `title`, or a title that gives no slug (only punctuation, say), generation fails with "A title is needed to generate a route.", and so does the fixture load. Nothing is created, and an existing route is not turned into a redirect. Set a title, or give the record an explicit `route:`.
::

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**A custom route generator must implement `generatePath()`.** `RouteGeneratorInterface::generatePath(RoutableInterface $object): ?string` returns the path `create()` would give the record, before any `-1` suffix for a conflict, or `null` when the record has no usable title. The fixture builder uses it to find existing page data on an appended load (see [Appending & Multiple Scaffolds › Appending to an Existing Site](/api/data-fixtures/appending#appending-to-an-existing-site)). If your application replaces or decorates the `RouteGeneratorInterface` service with a class of its own, it needs the method, or PHP refuses to load the class. A decorator can pass the call on to the inner generator.
::

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**A custom route generator shapes fixture routes only.** Replacing or decorating `silverback.helper.route_generator` changes the paths `CwaFixtureBuilder` generates, but the admin builds a new page's path itself and never asks the generator. To keep a page data class under a fixed path everywhere, such as `/announcements/<slug>`, use `#[Silverback\RoutePrefix]` instead (see [A Route Prefix for a Page Data Class](#a-route-prefix-for-a-page-data-class)): the API enforces it and the admin follows it.
::

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**A route can only be generated when the parent has one.** For a record with a `parentPage` or `parentPageData` whose parent has no Route, the fixture throws `UnroutedParentException` on `flush()`. Give the parent a route first, or give the child an explicit `route:`. This is stricter than the API's check, which skips parents without a route (see [The Required Start of a Path](#the-required-start-of-a-path)): a generated path would take the unrouted parent's place, and the child would no longer sit under the parent once it got a route.
::

A generated path is held to the 255-character limit too: if the required start plus the title's slug is too long, the load fails.

A blog article titled "My First Post" gets the route `/my-first-post` (or `/parent-path/my-first-post` when nested) unless you set one explicitly:

```php
$cwa->pageData($article, 'blog-detail', '/blog/custom-path', 'blog_article_custom')
```

A nested record's generated route starts with its parent's path, then its class's prefix. See [Page Data & Nested Pages › Route Auto-Prefixing](/api/dynamic-pages#route-auto-prefixing).

## Redirects

There is no separate redirect entity. A redirect **is** a `Route` whose `redirect` property points at another `Route`. The API resolves the whole chain when it serialises a route and exposes the final destination as `redirectPath`; the Nuxt module's route middleware then issues a `308` to it (suppressed while the admin is in edit mode, so redirecting routes stay navigable). A circular chain throws a `CircularReferenceException`. See the [admin panel Redirects section](/core-concepts/admin-panel#redirects) for the runtime behaviour.

Changing a route's `path` with `PUT` or `PATCH` creates a redirect from the old path to the route, and in a fixture, generating a new route for a record (see [Route Generation](#route-generation)) turns its old route into a redirect. With `cascadeChildPaths`, every child route gets one too (see [Cascading Route Changes](#cascading-route-changes)), and so does every route a move rewrites (see [Moving a Page](#moving-a-page)). To seed redirects in fixtures, use [`$cwa->redirect()`](/api/data-fixtures/builder-reference#seeding-redirects).

## Cascading Route Changes

When an admin renames a parent route, `PATCH /_/routes//events` with `cascadeChildPaths: true` updates the entire subtree and creates redirects from every old path:

```json
PATCH /_/routes//events
Content-Type: application/merge-patch+json

{
  "path": "/happenings",
  "cascadeChildPaths": true
}
```

Result:
- `/events` → redirects to `/happenings`
- `/events/2024` → redirects to `/happenings/2024`
- `/events/2024/spring-conference` → redirects to `/happenings/2024/spring-conference`

The cascade also passes through pages that have no Route. They add no path segment, so their routed descendants are updated against the nearest routed ancestor.

If the cascade would move any descendant onto a path already in use, the `PATCH` is a 422 on `path`, and nothing is renamed.

Without `cascadeChildPaths: true` only the one route is updated. Child routes keep working at their old paths, but those paths no longer share the parent's prefix and no redirects are created for them.

## Moving a Page

Changing a page's or page data's `parentPage` or `parentPageData` with `PUT` or `PATCH` moves its route under the new parent, and its descendants' routes with it:

```json
PATCH /page_data/blog_article_datas/018e…
Content-Type: application/merge-patch+json

{ "parentPage": "/_/pages/<news page>" }
```

- **The new path** is the new required start followed by the part of the old path after the old required start: `/blog/my-post` moved from `/blog` to `/news` becomes `/news/my-post`. A path that didn't begin with its old required start keeps only its last segment. At the root, with no prefix, the required start is `/`, so `/about/team` moved from the root under `/company` becomes `/company/about/team`.
- **Descendants move too.** Each routed descendant whose path is under the old path moves with it, through pages with no route. Moving a page that has no route moves its nearest routed descendants.
- **Every old path becomes a redirect** to its route, and each moved route's `name` becomes its new path.
- **A move that can't be done changes nothing.** If any new path is taken, too long, or is only its required start (the home page `/` moved under `/news`, for example), the response is a 422 on the parent field you changed, `parentPage` or `parentPageData`, and nothing is written. The message names the route: "Moving this page would change the route "/blog/my-post" to "/news/my-post". This path is already in use."

## Fetching a Route's Children

Retrieve the full child tree for a route (requires `ROLE_ADMIN`):

```
GET /_/routes//events/children
```

Response:

```json
{
  "children": [
    {
      "route": "/_/routes/018e4d02-…",
      "path": "/events/2024",
      "children": [
        {
          "route": "/_/routes/018e4d7f-…",
          "path": "/events/2024/spring-conference",
          "children": []
        }
      ]
    },
    {
      "route": "/_/routes/018e4e11-…",
      "path": "/events/2025",
      "children": []
    }
  ]
}
```

Each node has the route IRI, the resolved path, and a recursive `children` array. A page with no Route adds no node of its own, but the walk passes through it: its routed descendants appear under the nearest routed ancestor.

## Scheduling and Taking Routes Offline

Every `Route` has a **`liveAt`** date. It decides whether the page behind that URL is public, which makes it the way to schedule a launch, and the way to take a page offline without deleting its Route and losing the path, its redirects and the children hanging off it.

| `liveAt` | State | Public visitors |
|----------|-------|-----------------|
| A past date | **Live** | See the page |
| A future date | **Scheduled** | Get a 404 until that moment, then see the page. Nothing needs to run at go-live |
| `null` | **Not live** (draft, or taken offline) | Get a 404. The path stays reserved |

`liveAt` is readable and writable only by `ROLE_ADMIN`. A new route defaults to "now", however it's created (the API, `RouteGenerator`, `CwaFixtureBuilder`), so it's live until someone sets a date or `null`. Set it with a normal update:

```json
PATCH /_/routes//events/conference
Content-Type: application/merge-patch+json

{
  "liveAt": "2026-10-01T09:00:00+01:00"
}
```

Send `"liveAt": null` to take a page offline. In the admin, the same control is the route's **Go live** setting — see [The Admin Panel › Visibility](/core-concepts/admin-panel#visibility).

### Inheritance

A route's go-live date is inherited down the page hierarchy. The **effective** date is the **latest** of the route's own `liveAt` and the `liveAt` of every ancestor page that has a Route. If any of them is `null`, the route is not live. Ancestors with **no Route** are skipped, not treated as drafts.

| Ancestors | Child's own `liveAt` | Child goes live |
|-----------|----------------------|-----------------|
| Parent live since January | 1 November | 1 November, its own date |
| Parent scheduled for 1 November | Already past | 1 November, held back by the parent |
| Parent 1 November | 1 December | 1 December, the later date |
| Parent `null` | Any date | Not until the parent has a date |
| Parent has no Route | Already past | Now, because the parent is skipped |
| Grandparent 1 November, parent has no Route | Already past | 1 November |

Scheduling a parent therefore schedules its whole subtree, and taking a parent offline takes every child offline with it.

### What Visitors and Admins See

For anyone who fails the `publishable.permission` expression (typically `ROLE_ADMIN`), a route that is not live, whether by its own date or an ancestor's, behaves like this:

| Request | Response |
|---------|----------|
| `GET /_/routes/{path}` | **404** |
| `GET /_/resource_manifest/{id}` | **404** |
| `GET /_/routes` | Omitted, and `totalItems` counts only what is returned |
| `GET /_/pages` and page-data collections | Omitted, when [`routable_security`](/api/users/access-control#routable_security) is set |
| The route's Page, PageData or components, fetched directly | **401**, when `routable_security` is set |

Without `routable_security`, only the route and its manifest are gated; the records behind them stay readable by IRI. The template app sets it.

The 401 is a known boundary: only the route and manifest endpoints turn the denial into a 404. A component's access is checked through an internal sub-request, which deliberately still sees the underlying 403.

A route that **redirects** to a gated target still returns its `redirectPath`. The client follows it and gets the 404 there.

Admins resolve, preview and edit gated routes throughout, and see every route in `GET /_/routes`, so a scheduled page can be picked in link and route selectors before launch. Admin route responses also carry `_metadata.effectiveLiveAt`, the inherited date that actually applies.

::callout{icon="i-heroicons-information-circle"}
**The sitemap follows automatically.** The Nuxt module builds the sitemap from an anonymous `GET /_/routes`, so scheduled and offline routes, and routes held back by an ancestor, never reach search engines. The collection query uses a recursive CTE, so check your database server meets the minimum versions in [Bundle Setup › Database Servers](/api/bundle-setup#database-servers).
::

### Caching

A request for a route or manifest that is not live is marked `private, no-store`, so a shared cache never stores either the 404 or an admin's preview. And because nothing is written at the moment a scheduled route goes live, anonymous route, page, page-data and manifest responses that carry `s-maxage` or `max-age` have `s-maxage` and `max-age` capped at the **soonest upcoming `liveAt` across all routes**. A cached navigation therefore refreshes when any page launches, not only one it links to. The list of capped resource classes is configurable: see [Scheduled Publication and Cache Lifetime](/api/http-caching#scheduled-publication-and-cache-lifetime).

## The Resource Manifest

When the Nuxt module resolves a nested URL, it fetches a depth-grouped manifest from `/_/resource_manifest/{id}` (accepts both the route path and the admin UUID). The `resource_iris` field is an array indexed by rendering depth, root first. Each element is a single recursive `{ iri, children }` node that mirrors the containment of the resources at that depth:

```json
{
  "resource_iris": [
    {
      "iri": "/_/pages/018e4b9a-…",
      "children": [
        { "iri": "/_/component_groups/018e4c11-…", "children": [] }
      ]
    },
    {
      "iri": "/_/routes/018e4d01-…",
      "children": [
        { "iri": "/page_data/event_year_datas/018e4d02-…", "children": [] }
      ]
    }
  ]
}
```

The last depth is rooted at the requested Route and holds its Page or PageData. Each depth before it is rooted at an ancestor Page or PageData, root first. `parentPage`/`parentPageData` references are what split one depth from the next, so a parent never appears inside its child's tree.

A depth also includes its page's layout, with the layout's component groups, their positions and their components. A component's own component groups are included too, to any depth of nesting. A layout that a parent and a child page share is listed once, at the shallowest depth that uses it. A template page shared across depths is still listed at each depth. `GET /_/layouts/{id}` and a component's own response are unchanged and still return bare group IRIs. The groups are only expanded in the manifest.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**Known limitation: a template page shared by a parent and a child page data.** The same template page is listed at both depths, but the module records one depth per resource, the deepest. Each depth renders its own dynamic components from the manifest, but the position is re-fetched with the deepest depth's path only. If the parent's page data changes which component it holds, the parent's depth shows the change after the next navigation. The module logs `Manifest resources are listed at more than one depth` when this happens.
::

The module keeps the tree (for laying out placeholders while resources load) and flattens each depth node into a flat IRI list to fetch in parallel, passing the right IRI to each `<CwaPage />` level.
