Use these patterns inside a scaffold's `build()`. The builder itself is covered in [Builder Reference](/api/data-fixtures/builder-reference).

## Seeding HTML Content

When seeding components that have HTML body fields (e.g. a rich-text `HtmlContent` entity), you need structured placeholder HTML rather than a raw lorem ipsum string. The bundle ships `HtmlContentPlaceholder` as a registered service — inject it directly into your fixture class:

```php
use Silverback\ApiComponentsBundle\Fixture\AbstractCwaScaffold;
use Silverback\ApiComponentsBundle\Fixture\CwaFixtureBuilder;
use Silverback\ApiComponentsBundle\Fixture\Placeholder\HtmlContentPlaceholder;

class AppFixtures extends AbstractCwaScaffold
{
    public function __construct(
        CwaFixtureBuilder $cwa, // [!code focus]
        private readonly HtmlContentPlaceholder $placeholder,
    ) {
        parent::__construct($cwa); // [!code focus]
    }

    public function build(CwaFixtureBuilder $cwa): void
    {
        $content = new HtmlContent();
        $content->html = $this->placeholder->generate([
            'paragraphs'      => 4,
            'paragraphLength' => HtmlContentPlaceholder::LENGTH_MEDIUM,
            'includeHeadings' => true,
            'includeLists'    => true,
            'includeQuotes'   => false,
            'includeCode'     => false,
            'includeLinks'    => true,
            'format'          => HtmlContentPlaceholder::FORMAT_HTML,
        ]);

        $cwa->component($content);
    }
}
```

No `services.yaml` entry needed — the bundle registers it automatically as `silverback.api_components.fixture.html_content_placeholder`.

### Options

| Option | Type | Default | Description |
|--------|------|---------|-------------|
| `paragraphs` | `int` | `3` | Number of paragraphs to generate |
| `paragraphLength` | `string` | `'medium'` | Sentence density per paragraph |
| `includeHeadings` | `bool` | `false` | Inject `<h2>` elements between paragraphs |
| `includeLists` | `bool` | `false` | Inject `<ul>`/`<ol>` elements |
| `includeQuotes` | `bool` | `false` | Inject `<blockquote>` elements |
| `includeCode` | `bool` | `false` | Inject `<pre><code>` blocks |
| `includeLinks` | `bool` | `true` | Insert `<a>` tags inside paragraph text |
| `format` | `string` | `'html'` | `'html'` or `'plaintext'` |

### Constants

```php
HtmlContentPlaceholder::LENGTH_SHORT    // 1–2 sentences per paragraph
HtmlContentPlaceholder::LENGTH_MEDIUM   // 3–4 sentences (default)
HtmlContentPlaceholder::LENGTH_LONG     // 5–7 sentences

HtmlContentPlaceholder::FORMAT_HTML      // returns HTML tags
HtmlContentPlaceholder::FORMAT_PLAINTEXT // returns plain text
```

The data arrays (`$paragraphTemplates`, `$headings`, `$listItems`, `$codeSnippets`, `$quotes`, `$links`) are `protected`, so you can extend the class and swap in your own copy. The rendering methods are `private` and cannot be overridden.

You can also call `setOptions()` to set defaults for all subsequent `generate()` calls on the same instance:

```php
$this->placeholder->setOptions(['paragraphLength' => HtmlContentPlaceholder::LENGTH_SHORT]);
$shortHtml  = $this->placeholder->generate();
$shortHtml2 = $this->placeholder->generate(); // same defaults apply
```

## Seeding Uploadable Files

Components with an `#[UploadableField]` property (images, documents, etc.) can be seeded with a real example file straight from a local path. Set a `Symfony\Component\HttpFoundation\File\File` on the field's `File` property and add the component to a group as usual. The builder writes the file to that field's configured filestore during `flush()`, so there are no extra builder methods.

Put the file in your project first. `src/DataFixtures/assets/` is the convention, and it's where [`generate-fixtures`](/api/data-fixtures/generating-fixtures) exports files:

```text
api/src/DataFixtures/
├── AppFixtures.php
└── assets/
    └── hero.jpg
```

Then attach it in the scaffold:

```php
use App\Entity\Image;
use Symfony\Component\HttpFoundation\File\File;

$image = new Image();
$image->file = new File(__DIR__ . '/assets/hero.jpg'); // [!code focus]
$image->setPublishedAt(new \DateTime()); // [!code focus]

$cwa->page('home', 'PrimaryPageTemplate', layout: 'main', route: '/')
    ->title('Home')
    ->group('hero')->add($image); // [!code focus]
```

`flush()` copies the file to the filestore and fills the entity's stored filename property (`filename` with `UploadableTrait`), so the resource is valid and renderable. The file is only picked up on entities the bundle recognises as `#[Uploadable]`. Non-uploadable components, and a `null` file, are left untouched.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**Three things that stop a seeded image appearing:**
- **It isn't in a group.** `$cwa->component($image)` on its own stores the image and its file, but no page shows it. Add it to a page, layout or component group with `->add()`.
- **It isn't published.** If the component is `#[Silverback\Publishable]` (the template's `Image` is), it stays a draft until you call `setPublishedAt()`. Visitors don't see drafts. `requiredOnPublish` isn't checked here, because fixtures skip validation.
- **Its group already exists.** With `--append`, which the template's CI uses, a group that's already in the database is kept and nothing you add to it is created. That means no file is written either. See [Appending to an Existing Site](/api/data-fixtures/appending#appending-to-an-existing-site).
::

`__DIR__` is the directory of the PHP file that contains the line. In the template, each part is in `src/DataFixtures/Parts/`, so from a part the path is `__DIR__ . '/../assets/hero.jpg'`. A wrong path throws Symfony's `FileNotFoundException` as soon as `new File()` runs. The template's `ImageScaffoldPart` already adds an empty `Image` to the home page's primary group. Setting `file` and `setPublishedAt()` on that `Image` is the quickest way to try this.

Imagine variants (`thumbnail`, `general`, …) aren't generated during the load. Each one is generated the first time the resource is read, the same as for an image whose variants were cleared. To generate them straight after the load, run [`imagine:generate`](/api/console-commands#imaginegenerate).

::callout{icon="i-heroicons-information-circle"}
Each seeded file becomes its own stored object under a **unique tokenised name** (`hero-3f9a2b7c.jpg`), so two fixtures pointing at the same source file get independent stored copies — replacing or deleting one never affects the other. The file lands in whatever adapter the field resolves to in the current environment (a local/in-memory store under test, your real store when seeding a prod-like environment).
::

## Working with IRIs

API Platform identifies every resource by its IRI (Internationalized Resource Identifier) — the URL path the API exposes it at, e.g. `/_/routes/018e4b…` or `/_/pages/018e4c…`. `CwaFixtureBuilder` uses IRIs internally for `ComponentGroup.location` and `ComponentGroup.allowedComponents`, but you may need them directly in your own fixture code when a custom entity stores an IRI string field pointing to another API Platform resource.

See the [API Platform IRI documentation](https://api-platform.com/docs/core/iri/) for the full reference on how IRIs are generated and resolved.

Inject `ApiPlatform\Metadata\IriConverterInterface` into your fixture class alongside the builder:

```php
use ApiPlatform\Metadata\IriConverterInterface;
use Silverback\ApiComponentsBundle\Fixture\AbstractCwaScaffold;
use Silverback\ApiComponentsBundle\Fixture\CwaFixtureBuilder;

class AppFixtures extends AbstractCwaScaffold
{
    public function __construct(
        CwaFixtureBuilder $cwa, // [!code focus]
        private readonly IriConverterInterface $iriConverter,
    ) {
        parent::__construct($cwa); // [!code focus]
    }

    public function build(CwaFixtureBuilder $cwa): void
    {
        // ...
    }
}
```

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
`AbstractCwaScaffold` takes `CwaFixtureBuilder` as its own constructor argument. If you declare a constructor, you **must** accept the builder and pass it to `parent::__construct()` — otherwise `load()` fatals with an uninitialised typed property.
::

### Getting the IRI of a Persisted Entity

```php
$page = $cwa->page('home', 'PrimaryPageTemplate', layout: 'main', route: '/');
$cwa->flush();

// After flush() the page entity has a database ID and a resolvable IRI
$pageIri = $this->iriConverter->getIriFromResource($page->getPage());
// e.g. "/_/pages/018e4b9a-…"
```

Each sub-builder exposes its own entity getter — `PageBuilder::getPage()`, `PageDataBuilder::getPageData()`, `LayoutBuilder::getLayout()`, `ComponentBuilder::getComponent()`.

### Getting the IRI of a Class (Collection Endpoint)

If you need the collection endpoint IRI for a resource class — for example to populate a custom `$targetCollection: string` field on a component — pass the class name and a `GetCollection` operation:

```php
use ApiPlatform\Metadata\GetCollection;
use ApiPlatform\Metadata\UrlGeneratorInterface; // [!code focus]

$collectionIri = $this->iriConverter->getIriFromResource(
    BlogArticleData::class,
    UrlGeneratorInterface::ABS_PATH,
    (new GetCollection())->withClass(BlogArticleData::class)
);
// e.g. "/page_data/blog_article_datas" — an AbstractComponent subclass gets "/component/…",
// and only the bundle's own core resources use the "/_/" prefix
```

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
`ABS_PATH` is an **API Platform** constant — import `ApiPlatform\Metadata\UrlGeneratorInterface`, not Symfony's routing interface, which has no such constant.
::

::callout{icon="i-heroicons-information-circle"}
`IriConverterInterface::getIriFromResource()` needs an entity that has been saved. Convert a layout, page or page data after `$cwa->flush()`, or inside an [`afterRoutes()`](/api/data-fixtures/builder-reference#afterroutes) callback, which runs after they are saved. Don't call `flush()` inside a callback.
::
