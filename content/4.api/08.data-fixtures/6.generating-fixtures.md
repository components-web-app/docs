## Generating Fixtures From an Existing Database

Rather than hand-writing a scaffold, you can capture a populated database as one. The `generate-fixtures` command reads every layout, page, page data record and route and writes an `AbstractCwaScaffold` class that, loaded into an empty database, gives back the same site:

```bash
bin/console silverback:api-components:generate-fixtures
```

By default it writes to `src/DataFixtures/GeneratedScaffold.php`. Use `--output` (`-o`) to change the path:

```bash
bin/console silverback:api-components:generate-fixtures -o src/DataFixtures/SnapshotFixtures.php
```

The class is named after the file, so this writes a `SnapshotFixtures` class. Its namespace is `App\DataFixtures` unless you pass `--namespace`. The namespace doesn't follow the directory, so set it whenever you write outside `src/DataFixtures`:

```bash
bin/console silverback:api-components:generate-fixtures \
  -o src/DataFixtures/Snapshots/SiteSnapshot.php --namespace 'App\DataFixtures\Snapshots'
```

A file name that isn't a valid PHP class name, such as `site-snapshot.php`, makes the command fail without writing anything, and so does an invalid namespace.

| Option | Default | Description |
|--------|---------|-------------|
| `--output`, `-o` | `src/DataFixtures/GeneratedScaffold.php` | The file to write. The class is named after it |
| `--namespace` | `App\DataFixtures` | The generated class's namespace. It doesn't follow `--output` |
| `--keep-timestamps` | off | Write every publish date and go-live date exactly. See [Dates](#dates) |
| `--assets-store` | the configured store | Store uploaded files in this [asset store](#keeping-files-in-an-asset-store) for this run: `local` or `flysystem` |
| `--assets-dir` | the configured folder | Store uploaded files in this local folder for this run. Only with the `local` store |

### What the Scaffold Looks Like

The command writes the scaffold a developer would write by hand, in the style described in [Writing a Scaffold](/api/data-fixtures/writing-a-scaffold):

- one private method for each layout, page and page data, called from `build()`, with each child in its own method passed to its parent's `nested()`;
- named variables, such as `$homeNavigationLink`, named after a component's label, title, reference or first heading, and a typed property for a component used in more than one method;
- `linkRoute()` and `linkIri()` next to each component that refers to a route or holds an IRI;
- `$cwa->publish()` and `->draft()` for published components and their drafts;
- long HTML split at its block tags, or written as a nowdoc, without changing a byte of it.

You can commit it as it is or edit it. Loading it into an empty database and generating again gives the same file.

*Since bundle 2.0.0-alpha.22 ([#453](https://github.com/components-web-app/api-components-bundle/pull/453)). Earlier versions kept components in `$c[]` arrays and set relations and drafts in `afterRoutes()` callbacks.*

### What It Carries

- **Published state and drafts.** A draft is linked to its published component with [`draft()`](/api/data-fixtures/builder-reference#componentbuilder-from-cwa-component).
- **Uploaded files.** Each stored file is copied into an `assets/` directory beside the scaffold (`src/DataFixtures/assets/` by default), and the scaffold attaches it with the [`File` pattern](/api/data-fixtures/seeding-content#seeding-uploadable-files). The copy is named the way the reload stores it, without the token: `hero-3f9a2b7c.jpg` becomes `assets/hero.jpg`. Different files with the same name get `-2`, `-3`, and so on. Files with the same bytes are written once, under the first one's name, and every `new File(...)` for them names that copy (*since bundle 2.0.0-alpha.23, [#470](https://github.com/components-web-app/api-components-bundle/pull/470)*). So generating again writes the same asset names. For a site with many files, keep them in an [asset store](#keeping-files-in-an-asset-store) instead.
- **Groups owned by a component**, and groups shared through `locationReference`, with their `allow:` lists.
- **Component positions**, including `pageDataPosition()` calls in template pages.
- **Page hierarchy**, through `nested()`.
- **Relations**: a route in a field is a `linkRoute()`, and the IRI of a page, layout, page data or route of the site inside a field value is a `linkIri()`, so the reload writes the new ids.
- **Field values**: dates, enums, inherited fields, and fields that are only reachable through a public setter.
- **Page titles, meta descriptions and `uiClassNames`.**
- **Routes**: every route by path and name, scheduled and offline routes through `liveAt()`, routeless pages and page data through `withoutRoute()`, pages that are public without a route through `reachableWithoutRoute()`, redirects through `redirect()`, and a page or page data whose own route redirects through [`redirectTo()`](/api/data-fixtures/builder-reference#a-page-that-redirects). *`redirectTo()` since bundle 2.0.0-alpha.23 ([#468](https://github.com/components-web-app/api-components-bundle/pull/468)). Before, that redirect was dropped and not reported.*

`createdAt` and `modifiedAt` are not carried: loading stamps them afresh.

### What It Leaves Out

- **Site config parameters.** They are configuration for each environment, not content, so they are never exported. Set them in each environment as usual.
- **Orphaned components.** The command reads the site from its layouts, pages and page data, so a component that nothing places isn't in the scaffold. See [Orphaned Data](/api/orphaned-data).

### Dates

By default, a publish date or go-live date in the past becomes "at load time":

| Date in the database | Written as |
|----------------------|------------|
| A component's publish date in the past | `$cwa->publish($component)`, published when the fixtures load |
| A component's publish date in the future | `$cwa->publish($component, at: new \DateTimeImmutable('…'))` |
| A route's go-live date in the past | Nothing, so the route is live when the fixtures load |
| A route's go-live date in the future, or none (offline) | `->liveAt(…)` |

With `--keep-timestamps`, every publish and go-live date is written exactly as it is stored.

### Could Not Be Reproduced

The command prints the scaffold's path, then how many stored files it exported, then anything it **could not reproduce**:

```text
Fixture class written to src/DataFixtures/GeneratedScaffold.php
3 stored file(s) exported to src/DataFixtures/assets
2 item(s) could not be reproduced:
  - The collection App\Entity\Gallery::$images (4 components).
  - App\Entity\EventCard::$venue refers to /venues/018e…, which is not part of the generated site.
```

A message that would repeat for each component, such as a collection field, a value it can't write as PHP or a field with no setter, is printed once for each class and field, with a count. Messages that name an IRI, a file or a group are printed one by one.

The things it lists:

- a group used by more than one owner without a `locationReference`, or a group reference the builder can't express
- a group owned by a draft
- an `allowedComponents` entry that matches no component class
- the fallback component of a page data position
- a to-many relation (a collection) on a component or page data
- a relation to anything outside the generated site, such as a user
- an IRI in a field that isn't a page, layout, routed page data or route of the site. It is copied as it is
- a value that can't be written as PHP, or a field with no public property or setter
- a stored file that can't be read
- a redirect whose target has no page
- a page or page data whose route redirects to a route that isn't part of the site
- a redirect that isn't live, because a redirect the builder creates always is
- a page nested under a page that is nested under it

### Keeping Files in an Asset Store

By default, the command writes a readable copy of every uploaded file to `assets/` beside the scaffold. For a site with many files, you can keep the files in an asset store instead, and commit only the scaffold and a small manifest. *Since bundle 2.0.0-alpha.23 ([#466](https://github.com/components-web-app/api-components-bundle/pull/466)).*

Configure the store under `fixtures.assets`:

```yaml
# config/packages/silverback_api_components.yaml
silverback_api_components:
  fixtures:
    assets:
      store: flysystem   # or local, the default
      adapter: gcloud    # flysystem: one of your filesystem adapter aliases
      prefix: fixtures   # flysystem: the folder within the adapter
```

| Key | Default | Description |
|-----|---------|-------------|
| `store` | `local` | `local`, a folder, or `flysystem`, one of your application's filesystem adapters. An environment variable works, such as `'%env(FIXTURE_ASSETS_STORE)%'` |
| `path` | `null` | The `local` store's folder. `null` is an `assets/` folder beside the scaffold class |
| `adapter` | `null` | The `flysystem` store's adapter alias. Required for `flysystem` |
| `prefix` | `''` | The `flysystem` store's folder within the adapter |

Writing the block turns the store on. `enabled: false` turns it off again. Generating writes to the store and loading reads from it, so the generating environment needs write access and the loading one read access. See also the [configuration reference](/api/configuration#full-configuration).

With a store, the command:

- stores each file once, named by the SHA-256 of its bytes, and skips a file the store already has;
- writes `$cwa->asset('<hash>')` in the scaffold where the default writes `new File(...)`. The same bytes uploaded under another name are written as `$cwa->asset('<hash>', name: 'other-name.jpg')`;
- writes a manifest, `<ClassName>.assets.json`, beside the class. It lists each file's name, MIME type, size and the fields that use it. Commit it with the class.

```php
$heroImage = new Image();
$heroImage->file = $cwa->asset('2beb03392db998dae1af8544147f347c861c506797b8e6a59ceefa3c741252c6'); // [!code focus]
```

`--assets-store` and `--assets-dir` choose a store for one run, even with nothing configured. `--assets-dir` is a local folder, and can't be used with `--assets-store flysystem`. An invalid store or a `flysystem` store without an adapter exits with `2` and writes nothing.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**Loading always reads the configured store.** `--assets-store` and `--assets-dir` change only where the command writes. Unless the configuration points at the same place, the load looks in `assets/` beside the class and fails.
::

#### Loading

`doctrine:fixtures:load` reads each hash from the store through the class's manifest, checks the file's SHA-256, and uploads it under the name in the manifest, or the `name:` given. The load fails with a `RuntimeException` when:

- the manifest is missing or isn't valid;
- the hash isn't in the manifest;
- the store doesn't have the file. The message names the store;
- the file's bytes don't match its hash.

A scaffold you write by hand can call `$cwa->asset()` too, with a manifest beside the class. `asset()` only works while an `AbstractCwaScaffold` loads, because the scaffold tells the builder where its manifest is.

#### Pruning

Generating into a `local` store deletes only the files that the scaffold's previous manifest listed and the new one doesn't. A file that another manifest in the same directory as the class still lists is kept, so scaffolds can share a local folder. If the previous manifest or another one in that directory isn't valid, nothing is deleted and the command says so. A file that no manifest lists is left alone; [`prune-fixture-assets`](/api/console-commands#prune-fixture-assets) removes it. *Since bundle 2.0.0-alpha.25 ([#486](https://github.com/components-web-app/api-components-bundle/pull/486)) and 2.0.0-alpha.26 ([#490](https://github.com/components-web-app/api-components-bundle/pull/490)). In 2.0.0-alpha.23 and alpha.24, generating deleted every file the new manifest didn't list, including another scaffold's. In alpha.25 it deleted only its own previous manifest's files, but still deleted one of them that another manifest also listed.* A `flysystem` store is never pruned while generating, and the command reminds you to run [`prune-fixture-assets`](/api/console-commands#prune-fixture-assets):

```bash
php bin/console silverback:api-components:prune-fixture-assets \
  src/DataFixtures/GeneratedScaffold.assets.json src/DataFixtures/Snapshots/SiteSnapshot.assets.json
```

It deletes from the store every file that none of the given manifests lists. List every manifest that a branch or deployment still loads. Only files named by a hash, directly under the folder or prefix, are ever deleted.

Because the scaffold reloads as the same site, you can use it to keep a site's content through a database purge, or to copy a site to another environment:

1. **Capture it** while the content is still in the database:

   ```bash
   bin/console silverback:api-components:generate-fixtures
   ```

2. **Review the output.** Everything in the `could not be reproduced` list has to be added back by hand, either in the scaffold or after loading it. Site config parameters aren't in the scaffold either, so note them before the purge.
3. **Keep the scaffold and its `assets/` directory together.** The scaffold reads the files from `__DIR__ . '/assets/'`. With an [asset store](#keeping-files-in-an-asset-store), keep the manifest beside the scaffold, and keep the files in the store until the reload is done.
4. **Reload.** `doctrine:fixtures:load` empties the database and runs every fixture class it finds:

   ```bash
   bin/console doctrine:fixtures:load
   ```

   To load it into a database that already has content, add `--append`. It then creates only what is missing (see [Appending to an Existing Site](/api/data-fixtures/appending#appending-to-an-existing-site)), and loading it back into the database it came from creates nothing.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**The scaffold holds content, not users.** Keep your [users fixture](/api/data-fixtures/getting-started#seeding-users), because the purge removes users too. And move the hand-written scaffold that the capture replaces out of the fixtures directory, or it loads as well. The two load together without an error (see [More Than One Scaffold](/api/data-fixtures/appending#more-than-one-scaffold)), but the old scaffold creates any of its content that isn't in the capture, such as a page an editor deleted.
::
