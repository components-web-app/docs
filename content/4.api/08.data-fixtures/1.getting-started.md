The API bundle ships a fluent fixture scaffold that handles all the complexity of seeding CWA data: entity persistence ordering, phase-aware flushing, route generation, and ComponentPosition wiring. You describe what you want, call `flush()`, and the builder handles the rest.

## Setup

Install `doctrine/doctrine-fixtures-bundle` if not already present:

```bash
composer require --dev doctrine/doctrine-fixtures-bundle
```

Extend `AbstractCwaScaffold` instead of implementing `FixtureInterface` directly:

```php
<?php

namespace App\DataFixtures;

use Silverback\ApiComponentsBundle\Fixture\AbstractCwaScaffold;
use Silverback\ApiComponentsBundle\Fixture\CwaFixtureBuilder;

class AppFixtures extends AbstractCwaScaffold
{
    public function build(CwaFixtureBuilder $cwa): void
    {
        $cwa->layout('main', 'Primary');
        $cwa->page('home', 'PrimaryPageTemplate', layout: 'main', route: '/');
    }
}
```

`AbstractCwaScaffold` implements `FixtureInterface`. Its `load()` method injects the `ObjectManager`, calls your `build()`, then calls `flush()`, so you don't call it yourself. `CwaFixtureBuilder` is injected automatically via Symfony's service container.

With `autoconfigure: true` (the Symfony default), your fixture class is detected and tagged as a Doctrine fixture automatically — no `services.yaml` entry needed. If `autoconfigure` is disabled, register manually:

```yaml
# config/services.yaml
App\DataFixtures\AppFixtures:
    tags:
        - { name: doctrine.fixture.orm }
```

`bin/console make:cwa-scaffold` writes a starter class like this one, with a layout, a home page and a navigation link. See [`make:cwa-scaffold`](/api/console-commands#makecwa-scaffold).

Run your fixtures:

```bash
bin/console doctrine:fixtures:load
```

That empties the database first. To add a scaffold's content to a database that already has some, append instead. See [Appending to an Existing Site](/api/data-fixtures/appending#appending-to-an-existing-site).

### What a Load Leaves Until Later

While `doctrine:fixtures:load` runs, with or without `--append`, the bundle propagates no change. It publishes nothing to Mercure and sends no cache tag purge as each write is saved. So no image variant is generated during the load either. This applies to every fixture class the command runs, not only scaffolds.

When the load ends, the bundle flushes the whole HTTP cache once and prints `Flushed the HTTP cache`. The full flush needs Souin. With another purger, or no invalidation URL, it prints `The configured HTTP cache purger cannot flush the whole cache, so nothing was flushed`. A failed flush is logged at `error` and printed, and the load still succeeds. The flush runs even when the load fails. See [Flushing the Whole HTTP Cache](/api/http-caching#flushing-the-whole-http-cache).

After loading a site with images, generate the variants, then flush the cache again so cached responses list them:

```bash
bin/console silverback:api-components:imagine:generate
bin/console silverback:api-components:purge-http-cache
```

When Imagine is enabled and the load succeeds, the command reminds you: `Image variants are not generated while fixtures load. Run silverback:api-components:imagine:generate to generate the image variants.` For a large site, run `imagine:generate` with `--max-memory` in a loop until it stops exiting with `3` (see [`imagine:generate`](/api/console-commands#imaginegenerate)). Any variant you don't generate is made the first time the image is read.

::callout{icon="i-heroicons-information-circle"}
The bundle recognises a load by the console command's name, so only `doctrine:fixtures:load` run from the console is affected. Fixtures loaded from your own code, without the console application, still propagate every write.
::

*Since bundle 2.0.0-alpha.23 ([#465](https://github.com/components-web-app/api-components-bundle/pull/465)). Before, every write was serialized for Mercure during the load, and that generated every variant of every loaded image in one process.*

## Complete Example

This example creates a layout with a shared nav, a home page with a hero component, a blog template with two articles, nav links pointing to each page, and a redirect. It follows the style in [Writing a Scaffold](/api/data-fixtures/writing-a-scaffold): one method for each layout, page and page data.

```php
<?php

namespace App\DataFixtures;

use App\Entity\BlogArticleData;
use App\Entity\Hero;
use App\Entity\NavigationLink;
use Silverback\ApiComponentsBundle\Fixture\AbstractCwaScaffold;
use Silverback\ApiComponentsBundle\Fixture\CwaFixtureBuilder;

class AppFixtures extends AbstractCwaScaffold
{
    public function build(CwaFixtureBuilder $cwa): void
    {
        $this->mainLayout($cwa);
        $this->homePage($cwa);
        $this->blogPage($cwa);
        $this->firstPostPageData($cwa);
        $this->secondPostPageData($cwa);
        $this->redirects($cwa);
    }

    private function mainLayout(CwaFixtureBuilder $cwa): void
    {
        $homeLink = new NavigationLink();
        $homeLink->label = 'Home';
        $cwa->component($homeLink)->linkRoute('route', routeName: 'home'); // [!code focus]

        $blogLink = new NavigationLink();
        $blogLink->label = 'Blog';
        $cwa->component($blogLink)->linkRoute('route', routeName: 'article-1'); // [!code focus]

        $cwa->layout('main', uiComponent: 'Primary')
            ->group('nav', allow: [NavigationLink::class], locationReference: 'global-nav')
            ->add($homeLink)
            ->add($blogLink);
    }

    private function homePage(CwaFixtureBuilder $cwa): void
    {
        $welcomeHero = new Hero();
        $welcomeHero->headline = 'Welcome';

        // ->group() returns a GroupBuilder, so a second group starts
        // from the page builder again
        $page = $cwa->page('home', uiComponent: 'PrimaryPageTemplate', layout: 'main', route: '/', routeName: 'home')
            ->title('Home');

        $page->group('hero')
            ->add($welcomeHero);

        $page->group('content');
    }

    private function blogPage(CwaFixtureBuilder $cwa): void
    {
        // A template page gets no route
        $cwa->page('blog-template', uiComponent: 'BlogPageTemplate', layout: 'main', isTemplate: true)
            ->group('body')
            ->pageDataPosition(BlogArticleData::class, 'body');
    }

    private function firstPostPageData(CwaFixtureBuilder $cwa): void
    {
        $pageData = new BlogArticleData();
        $pageData->setTitle('First Post');

        $cwa->pageData($pageData, template: 'blog-template', route: '/blog/first-post', routeName: 'article-1');
    }

    private function secondPostPageData(CwaFixtureBuilder $cwa): void
    {
        $pageData = new BlogArticleData();
        $pageData->setTitle('Second Post');

        $cwa->pageData($pageData, template: 'blog-template', route: '/blog/second-post', routeName: 'article-2');
    }

    private function redirects(CwaFixtureBuilder $cwa): void
    {
        // An old URL that now points at the first article
        $cwa->redirect('/blog/hello-world', to: 'article-1');
    }
}
```

`linkRoute()` sets each link's `route` once the routes exist, before the nav positions are created. `AbstractCwaScaffold::load()` calls `flush()` after `build()`, so this scaffold needs no `flush()` of its own.

## Seeding Users

Create users with `UserFactory`, not by constructing the entity yourself — it hashes the password and applies the role flags:

```php
use Silverback\ApiComponentsBundle\Factory\User\UserFactory;

class UsersFixture extends AbstractCwaScaffold
{
    public function __construct(
        CwaFixtureBuilder $cwa,
        private readonly UserFactory $factory,
    ) {
        parent::__construct($cwa);
    }

    public function build(CwaFixtureBuilder $cwa): void
    {
        $this->factory->create(
            'admin', 'admin', 'hello@example.com',
            inactive: false, superAdmin: true,
            overwrite: true, // [!code focus]
        );
    }
}
```

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**Pass `overwrite: true`, or a second fixture run fails.** `UserFactory::create()` defaults it to `false`, and only looks up the existing user when it is `true`. Otherwise it builds a new user, which fails the `#[UniqueEntity]` check on `username` and `emailAddress`, and `create()` throws a `ValidationFailedException`. With `overwrite: true` the fixture can run any number of times.

The columns have no database unique index, so the validation is the only guard: a duplicate username makes login fail with a **500** (`NonUniqueResultException`).
::

`overwrite: true` also means every run sets the password again, so **never hard-code a password a public site would use**. The template's `api/src/DataFixtures/UsersFixture.php` reads the account from `ADMIN_USERNAME`, `ADMIN_PASSWORD` and `ADMIN_EMAIL`, falling back to `admin`, `admin` and `admin@example.com` (`hello@cwa.rocks` up to template 2.0.0-alpha.43, changed in [`8e07ddd`](https://github.com/components-web-app/components-web-app/commit/8e07dddbe541c8fee79d83732be2737e8f7fbf0b)). That fallback is for development only. A template deploy, and each fixture load it runs, warns when `ADMIN_PASSWORD` is unset or `admin`, and `compose.prod.yaml` requires it (see [CI/CD Variables › The admin password](/deployment/variables#the-admin-password)). *Since [template 2.0.0-alpha.44](https://github.com/components-web-app/components-web-app/releases/tag/v2.0.0-alpha.44) ([`80f63f3`](https://github.com/components-web-app/components-web-app/commit/80f63f3758d6951c4e26ed9eddcf7a095ce5f4fc)).* A fixture load you run yourself with `bin/console doctrine:fixtures:load` doesn't check the password.

## Tips

- You don't need to call `$manager->persist()` or `$manager->flush()` yourself — the builder handles it
- Timestamps (`createdAt`, `modifiedAt`) are populated automatically
- Call `flush()` again any time you register new entities or positions after a previous call. See [Flush Phases](/api/data-fixtures/builder-reference#flush-phases)
- [`locationReference`](/api/data-fixtures/builder-reference#locationreference-shared-groups) is the correct way to share a group between two layouts — don't try to manually link the same `ComponentGroup` to two owners
