title: Console Commands
description: Symfony console commands provided by the API Components Bundle for managing users, scanning for orphaned data, generating image variants, and generating component entities.
---

Most commands use the `silverback:api-components:` prefix. Run them via the Symfony console:

```bash
php bin/console silverback:api-components:<command>
```

In a Docker Compose setup, prefix with the service name:

```bash
docker compose exec php php bin/console silverback:api-components:<command>
```

## `user:create`

Create a user account directly from the command line, without going through the registration API. Useful for creating the first admin on a fresh installation before the front-end is set up.

```bash
php bin/console silverback:api-components:user:create
```

The command prompts interactively for username, email, and password. You can also pass them as positional arguments:

```bash
php bin/console silverback:api-components:user:create alice alice@example.com s3cr3t --admin
```

### Options

| Option | Effect |
|--------|--------|
| _(none)_ | Roles set to `['ROLE_USER']`. The account can't open the admin panel |
| `--admin` | Roles set to `['ROLE_ADMIN']` |
| `--super-admin` | Roles set to `['ROLE_SUPER_ADMIN']` |
| `--inactive` | Creates the account disabled. It can't log in until `enabled` is set |
| `--overwrite` | Updates the existing user with that username. Without it, a username or email address that is already taken fails validation: the command prints each violation and exits with an error, and nothing is saved |

The role is **set**, not added: `--admin` stores `ROLE_ADMIN` on its own and picks up `ROLE_USER` through `role_hierarchy`. Users created this way are marked email-verified, so they can log in even with `deny_unverified_login: true`.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
A plain `doctrine:fixtures:load` empties the database, users included. Load fixtures before you create the user, or load them with `--append`.
::

## `refresh-tokens:expire`

Expire all refresh tokens, or all tokens for a specific user. Use this to force re-login after a security incident or account change.

```bash
# Expire all tokens for all users
php bin/console silverback:api-components:refresh-tokens:expire

# Expire tokens for one user (by username)
php bin/console silverback:api-components:refresh-tokens:expire alice

# Expire by email address instead of username
php bin/console silverback:api-components:refresh-tokens:expire alice@example.com --field emailAddress
```

`--field` accepts only `username` (the default) or `emailAddress`; any other value is rejected. The user is looked up through your `UserRepositoryInterface`, so a custom user repository works. If the value matches one user's username and a different user's email address, the command stops and reports it without expiring any tokens.

## `scan-orphaned`

Scan for orphaned component groups, empty component positions and unused components, store the report, and email the configured recipients when the orphans change. It never deletes anything. `clean-orphaned` is an alias of it.

```bash
php bin/console silverback:api-components:scan-orphaned
```

Options: `--no-notify` scans without emailing. It always exits with `0`. See [Orphaned Data → Orphaned Resources](/api/orphaned-data#orphaned-resources).

## `scan-orphaned-files`

Scan the upload filesystems for orphaned, unknown, missing and invalid files, and store the report. It takes no options, never modifies or deletes anything, and always exits with `0`.

```bash
php bin/console silverback:api-components:scan-orphaned-files
```

See [Orphaned Data → Orphaned Files](/api/orphaned-data#orphaned-files).

## `deduplicate-file-info`

Prepare the file info table, `_acb_imagine_cached_file_metadata` (with the default `table_prefix`), for its unique index on `(path, filter)`. Run it once before the migration that adds the index.

```bash
php bin/console silverback:api-components:deduplicate-file-info
```

It gives every original's row an empty filter instead of `NULL`, and removes duplicate rows for the same path and filter, keeping the first. It prints how many rows it changed and removed, and is safe to run again:

```
Set an empty filter on 12 original file info rows and removed 3 duplicate rows.
```

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
Don't empty the table instead. The [orphaned files report](/api/orphaned-data#orphaned-files-report) uses these rows to tell orphaned files from unknown ones. Without its row, an orphaned file whose name doesn't have the bundle's stored-name pattern is listed as unknown, and the API never deletes it.
::

## `imagine:generate`

Generate every Imagine variant of the uploaded images that isn't stored yet, one image at a time. Stored variants and originals are left alone, so it's safe to run again. It walks every uploadable record with a stored file, drafts included. A field's filters are its `imagineFilters`, plus what `getImagineFilters()` returns on an entity that implements `ImagineFiltersInterface`. SVGs and files that aren't images are skipped. *Since bundle `2.0.0-alpha.15` · [release notes](https://github.com/components-web-app/api-components-bundle/releases/tag/2.0.0-alpha.15)*

```bash
php bin/console silverback:api-components:imagine:generate
```

Run it after a deploy that adds a filter, then run [`purge-http-cache`](#purge-http-cache) so cached responses list the new variants. Each variant is generated within the [imagine memory budget](/api/components/annotations/uploadable#the-imagine-memory-budget) and written with its field's `imagineCacheControl`.

| Option | Effect |
|--------|--------|
| `--filter=<name>` | Only generate this filter. Repeat it for several |
| `--class=<FQCN>` | Only walk this uploadable class and its subclasses. Repeat it for several |
| `--dry-run` | Count the missing variants without generating them. `--limit` and `--max-memory` don't apply |
| `--limit=<N>` | Stop after N variants. Every variant it tries counts, including one that fails or is skipped |
| `--max-memory=<size>` | Stop once the process's resident memory reaches this size, such as `768M` or `1G` |
| `-v` | List each variant with its result |

It prints a count for each result: generated (or "To generate" with `--dry-run`), already stored, skipped over the memory budget, failed, and original missing. Only raster images get variants, so SVGs and other files are left out.

| Exit code | Meaning |
|-----------|---------|
| `0` | Done. A variant skipped over the memory budget is counted but doesn't fail the run |
| `1` | At least one variant failed. Add `-v` to see which, and check the log for the error |
| `2` | `--filter` names no configured filter, `--class` names no uploadable class, or `--limit` or `--max-memory` isn't valid |
| `3` | `--limit` or `--max-memory` stopped the run while variants were still missing |

::callout{icon="i-heroicons-information-circle"}
**Exit `3` means "run me again".** Start a new process each time, and repeat until it exits with `0` (or `1`). A run that stops reports `3` even if a variant in it failed, so a failure shows up in a later run. *Since bundle `2.0.0-alpha.16` · [release notes](https://github.com/components-web-app/api-components-bundle/releases/tag/2.0.0-alpha.16)*
::

```bash
while :; do
    php bin/console silverback:api-components:imagine:generate --max-memory=768M
    status=$?
    [ "$status" -ne 3 ] && break
done
exit "$status"
```

`--max-memory` reads the process's resident memory (`VmRSS` in `/proc/self/status`). That includes what libvips allocates outside PHP, which `memory_limit` can't see. Where `/proc` isn't available, such as on macOS, it falls back to PHP's own `memory_get_usage(true)`. The check runs before each variant after the first, so every run generates at least one, and a run can go over the size by one variant. Set it below the container's memory limit by at least the cost of your largest variant.

The libvips operation cache is switched off for the run, so libvips doesn't keep decoded images in memory between variants.

## `purge-rendered-html`

Purge every cached page of rendered front-end HTML by its `cwa-html` cache tag, leaving cached API responses alone. Run it after a front-end deploy. It takes no options, and exits with `1` if the purge fails.

```bash
php bin/console silverback:api-components:purge-rendered-html
```

See [HTTP Caching → Purging the Pages After a Deploy](/api/http-caching#purging-the-pages-after-a-deploy).

## `purge-http-cache`

With no options, flush every cached response, API responses and rendered page HTML together, for example after a direct database edit or an import. The full flush needs Souin; with another purger it flushes nothing and still succeeds. `--path` and `--tag` purge only one page or tag instead. It exits with `1` if the purge fails.

```bash
php bin/console silverback:api-components:purge-http-cache
php bin/console silverback:api-components:purge-http-cache --path /about-us
```

See [HTTP Caching → Flushing the Whole HTTP Cache](/api/http-caching#flushing-the-whole-http-cache) and [Purging One Page or Tag](/api/http-caching#purging-one-page-or-tag).

## `form-cache-purge`

Purge the HTTP cache for Form components by setting each form's `modified` timestamp to the last-modified date of its `FormType` file.

```bash
php bin/console silverback:api-components:form-cache-purge
```

It takes no arguments or options. Run it after deploying changes to a `FormType` so cached form views are regenerated rather than served stale.

## `generate-fixtures`

Walk the live database and write an `AbstractCwaScaffold` class that loads back as the same site. `--output` (`-o`) sets the file and `--namespace` the class's namespace.

```bash
php bin/console silverback:api-components:generate-fixtures
```

See [Generating Fixtures](/api/data-fixtures/generating-fixtures) for what it carries, what it can't reproduce, and how to capture a site before a purge.

## `prefix-page-ui-components`

Rewrite every page whose `uiComponent` is stored with the short name, such as `PrimaryPageTemplate`, to the full component name, `CwaPagePrimaryPageTemplate`. Pages already stored with the full name, and pages with no `uiComponent`, are left alone. Layouts and components aren't touched.

```bash
php bin/console silverback:api-components:prefix-page-ui-components
```

It takes no options. It prints how many pages it changed, for example `Prefixed the uiComponent of 3 pages with CwaPage.` Running it again changes nothing.

The API stores a page's full name on every write, so only pages saved before that change need it. The command writes to the database directly, so cached API responses keep the short name until they expire or you run [`purge-http-cache`](#purge-http-cache). The module renders both forms, so nothing breaks in the meantime. See [How `uiComponent` Names Resolve](/nuxt-module/building-your-ui/creating-layouts#how-uicomponent-names-resolve).

*On the bundle's `main` branch after 2.0.0-alpha.17 ([#431](https://github.com/components-web-app/api-components-bundle/pull/431)).*

## Maker Commands

These commands use the standard `make:` prefix from [Symfony MakerBundle](https://symfony.com/bundles/SymfonyMakerBundle/current/index.html) and are only registered when MakerBundle is installed.

### `make:api-component`

Generate a new `AbstractComponent` entity with the correct namespace, attributes, and optional behaviour traits wired up automatically.

```bash
php bin/console make:api-component
```

The command prompts interactively for the class name and which behaviours to add. You can also pass everything as arguments:

```bash
php bin/console make:api-component HeroBlock --timestamped --publishable
```

#### Options

- **`--timestamped`** — Add `#[Timestamped]`: generates `createdAt` / `modifiedAt` columns via `TimestampedTrait`
- **`--publishable`** — Add `#[Publishable]`: wires up the draft/publish lifecycle via `PublishableTrait`
- **`--uploadable`** — Add `#[Uploadable]`: includes a `$file` property and `UploadableTrait` for file handling

#### Example Output (With All Three Flags)

```php
#[Silverback\Timestamped]
#[Silverback\Publishable]
#[Silverback\Uploadable]
#[ApiResource]
#[ORM\Entity]
class HeroBlock extends AbstractComponent
{
    use TimestampedTrait;
    use PublishableTrait;
    use UploadableTrait;

    #[Silverback\UploadableField(adapter: 'local')]
    public ?File $file = null;
}
```

Then generate the migration with `doctrine:migrations:diff`, review the SQL and delete its `down()` (migrations are [upward-only](/api/bundle-setup#database-setup)). The traits add columns and, for publishable, a self-referencing foreign key. The command's own hint names `make:migration`, which also works.

### `make:page-data`

Generate a new `AbstractPageData` entity with typed properties pre-wired, plus console output showing the matching `nuxt.config` snippet and fixture stub.

```bash
php bin/console make:page-data
```

Run with no options, the command prompts for the class name and then for each property: enter a name, accept or change the type (default `?string`), and press return on an empty name to stop.

To skip the prompts, pass the properties with `--properties`, either as one comma-separated list:

```bash
php bin/console make:page-data ConferenceData \
    --properties headline:?string,body:?string,heroImage:?string
```

or by repeating the flag once per property:

```bash
php bin/console make:page-data ConferenceData \
    --properties headline:?string \
    --properties body:?string \
    --properties heroImage:?string
```

Properties are defined as `name:type` pairs, with the `?` prefix for nullable types. Leave off `:type` and the type defaults to `?string`.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
Don't separate properties with spaces after a single flag (`--properties headline:?string body:?string`). Symfony reads everything after the first value as extra command arguments, and the command aborts with "Too many arguments" before it runs. Use a comma or repeat the flag.
::

#### Example Output

```php
#[ApiResource]
#[ORM\Entity]
class ConferenceData extends AbstractPageData
{
    #[ORM\Column(nullable: true)]
    public ?string $headline;

    #[ORM\Column(nullable: true)]
    public ?string $body;

    #[ORM\Column(nullable: true)]
    public ?string $heroImage;
}
```

After generation the command prints:

- A `nuxt.config.ts` snippet to paste under `cwa.pageData`
- A fixture scaffold stub: `$cwa->pageData(new ConferenceData(), template: 'my-template')`
- `->pageDataPosition(ConferenceData::class, 'propertyName')` calls for each property, ready to paste into a template group

The `nuxt.config.ts` snippet gives the data type a display `name` and maps each property name to a readable label, which the admin shows when you bind a dynamic position to a property:

```ts
ConferenceData: {
  name: 'Conference Data',
  properties: {
    headline: 'Headline',
    body: 'Body',
    heroImage: 'Hero Image',
  },
},
```

Labels are generated from the property names (`heroImage` becomes `Hero Image`). Change them to whatever you want editors to see. See [nuxt.config](/nuxt-module/configuration/nuxt-config) for the full `pageData` options.

If you give no properties at all, the command warns that the entity only has the inherited page data fields and prints `properties: {}`.

Each `string` property is mapped as a plain `VARCHAR(255)` column with no `Length` constraint. Add `#[Assert\Length(max: 255)]`, or change free text to `type: 'text'`, before you generate the migration; see [String Columns Need a Length Limit](/api/components/creating-components#string-columns-need-a-length-limit).

Then generate the migration with `doctrine:migrations:diff`, review the SQL and delete its `down()`, as for `make:api-component`.

### `make:cwa-scaffold`

Generate a starter `AbstractCwaScaffold` subclass pre-wired with a layout, a home page, and commented-out nav link stubs.

```bash
php bin/console make:cwa-scaffold
```

The command prompts interactively for the class name, layout reference key, and layout UI component name. You can pass everything inline:

```bash
php bin/console make:cwa-scaffold AppScaffold --layout-ref main --layout-component Primary
```

#### Options

| Option | Default | Description |
|--------|---------|-------------|
| `--layout-ref` | `main` | Reference key passed to `$cwa->layout()` |
| `--layout-component` | `Primary` | Layout UI suffix (e.g. `Primary` → stores `CwaLayoutPrimary`) |

#### Example Output

```php
class AppScaffold extends AbstractCwaScaffold
{
    public function build(CwaFixtureBuilder $cwa): void
    {
        $navGroup = $cwa->layout('main', 'Primary')
            ->group('top');

        $cwa->page('home', 'PrimaryPage', layout: 'main', route: '/', routeName: 'home-page',
            configure: fn (PageBuilder $page) => $page
                ->title('Home')
                ->group('primary')
        );

        // $navGroup->add(...) — nav links go here after routes exist
    }
}
```

After generation the command prints a `config/services.yaml` snippet that tags the class as a Doctrine fixture. With `autoconfigure: true`, the Symfony default, you don't need it: the class is tagged automatically (see [Getting Started with Fixtures](/api/data-fixtures/getting-started#setup)).

Then run `php bin/console doctrine:fixtures:load` to seed the database. See [Builder Reference](/api/data-fixtures/builder-reference) for the full builder API.

### `make:rename-component`

Generate a Doctrine migration to rename a CWA component type. Use this when you need to rename a PHP entity class that is already stored in the database — it updates the discriminator column (`dtype`) of the component table and replaces old collection IRIs in the component groups' `allowed_components`.

```bash
php bin/console make:rename-component
```

The command prompts interactively for the old and new class names, FQCNs, and `dtype` values (defaulting to lowercase class names):

```bash
php bin/console make:rename-component HtmlContent RichText
```

If your app configures more than one Doctrine Migrations namespace, pass `--namespace` to choose one. Without it, the command asks, defaulting to the first configured namespace.

#### When It Asks for a Collection IRI

The migration rewrites `allowedComponents`, which stores **collection IRIs** such as `/component/html_contents`, so the command needs the collection IRI of both the old and the new component. It asks API Platform for each one from the class, which only works while that class exists and is an API resource. That usually fails in one of two cases:

- **You've already renamed the PHP class.** `HtmlContent` no longer exists, but the database still stores `/component/html_contents` in `allowedComponents` and `html_content` in `dtype`.
- **You run the command before creating the new class**, so its IRI can't be resolved yet.

When an IRI can't be resolved, the command says so and asks for it. Enter it exactly as `allowedComponents` stores it. To find the old one, look at an existing `allowed_components` value in the component group table, or at the component's collection path in the API docs from before the rename. In a non-interactive run, such as CI, pass `--old-iri` and `--new-iri` instead. Without them, the command fails and names the missing option.

```bash
# HtmlContent has already been renamed to RichText in the code
php bin/console make:rename-component HtmlContent RichText \
    --old-iri=/component/html_contents \
    --new-iri=/component/rich_texts
```

The value must be a path starting with `/`. API Platform blank nodes (`/.well-known/genid/…`) are refused, because written into the migration they would match nothing. Check the generated migration's `allowed_components` values before you run it.

#### What It Does

1. Generates a Doctrine migration through Doctrine Migrations itself, as `doctrine:migrations:generate` does: a `Version<timestamp>` class in your configured migrations path (`migrations/` in the template), so it runs in order with your other migrations
2. The migration updates the `dtype` column of the component table and `allowed_components` on the component group table, using the table names from your ORM mapping, including the bundle's `table_prefix` (`_acb_abstract_component` and `_acb_component_group` by default)
3. After generation, the command prints any `ComponentGroup` records whose `allowedComponents` array references the old IRI — these need front-end updates too

#### Front-End Checklist (Printed After Generation)

1. Rename the Vue component file from the old name to the new name
2. Update any imports or registrations referencing the old name
3. Run `php bin/console doctrine:migrations:migrate`

Also update any `allowed-components` prop in your front-end templates that names the old component or lists its old collection IRI. While a user is signed in, the module syncs that prop to the API, so a stale entry is written back over the migrated list.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
This command writes the migration for you — do **not** run `doctrine:migrations:diff` or `make:migration` afterwards, or you will get a second, unrelated diff migration. Review the generated SQL in the new `Version…php` file, then apply it with `php bin/console doctrine:migrations:migrate`.
::
