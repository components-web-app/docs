The API Components Bundle is the [Symfony](https://symfony.com){target="_blank"} backend of CWA. It wires together [API Platform](https://api-platform.com){target="_blank"}, [Doctrine ORM](https://www.doctrine-project.org/projects/orm.html){target="_blank"}, [LexikJWTAuthenticationBundle](https://github.com/lexik/LexikJWTAuthenticationBundle){target="_blank"}, [Mercure](https://mercure.rocks){target="_blank"}, and a suite of content management abstractions so you spend your time building your app rather than infrastructure.

## Prerequisites

- PHP 8.5+
- Symfony 7.4+ or 8.1+, with `symfony/expression-language` 7.4.21+ or 8.1.9+, the releases that fix CVE-2026-109449.
- Doctrine ORM 3.7+ (with DBAL 4.4+)
- API Platform 4.4.5+ or 5.0.4+ (`^4.4.5 || ^5.0.4`).
- A database server that supports recursive CTEs (see below)

API Platform 4.4 and 5 differ in two ways that clients can see. On API Platform 5, a request body with the wrong type for a property that has validation constraints returns a `422` with violations, where 4.4 returns a `400`. A unique-constraint violation from the database returns a `422` on API Platform 5 and a `500` on 4.4 (see [Error Status Codes](/api/debugging#error-status-codes)). On both versions, `GET /me` returns `@context: /contexts/User`.

### Database Servers

The bundle resolves a route's inherited go-live date with a recursive CTE (`WITH RECURSIVE`), so the database server must support one:

| Server | Minimum | Recommended |
|--------|---------|-------------|
| PostgreSQL | 8.4 | **12+** |
| MySQL | **8.0** | 8.0+ |
| MariaDB | 10.2 | **10.6+** |
| SQLite | 3.8.3 | 3.8.3+ |

The **Recommended** column is Doctrine DBAL 4's own floor: below it DBAL still connects but raises a deprecation, and DBAL 5 drops support. The CWA template runs PostgreSQL 16.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**MySQL 5.7 and MariaDB 10.0/10.1 cannot run CWA.** They have no CTE support, and neither Composer nor the container can check this: the application boots normally, then every anonymous request to `GET /_/routes`, `GET /_/pages` or a page-data collection returns a 500. The sitemap is built from `GET /_/routes`, so it fails too.
::

## Installation

```bash
composer require "components-web-app/api-components-bundle:^2.0@alpha"
```

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**Include the version constraint.** CWA 2 is released as alphas. Without `^2.0@alpha`, a project with the usual `minimum-stability: stable` gets `1.1.11`, the last 1.x release, which these docs don't describe. To follow unreleased changes, require `2.x-dev`: `main` is aliased to it.
::

The bundle has no Flex recipe in `symfony/recipes-contrib` (earlier submissions were never merged), so Flex runs no recipe for it. **Create these files yourself.** The CWA template app (`components-web-app`) has a working copy of each under `api/`:

- `config/bundles.php` — register `Silverback\ApiComponentsBundle\SilverbackApiComponentsBundle::class => ['all' => true]`
- `src/Entity/User.php` — your user entity extending `AbstractUser` (see [Authentication](/api/users/authentication#abstractuser))
- `src/Entity/RefreshToken.php` — the refresh token entity
- `config/packages/silverback_api_components.yaml` — the bundle configuration (see [Core Configuration](#core-configuration))
- `config/routes/silverback_api_components.yaml` — imports `@SilverbackApiComponentsBundle/Resources/config/routing/all.php`, with the same prefix as API Platform in `config/routes/api_platform.yaml` (`/api` on a fresh Flex install, `/_api` in the template)
- `config/packages/security.yaml` — the security configuration (see [Authentication › Security Configuration](/api/users/authentication#security-configuration))
- `config/packages/mercure.yaml` — a Mercure hub named `default` (see [Mercure Hub](#mercure-hub))

::callout{icon="i-heroicons-information-circle"}
The Composer package is `components-web-app/api-components-bundle`, but the PHP namespace is `Silverback\ApiComponentsBundle\` — the mismatch is historical, not a typo.
::

::callout{icon="i-heroicons-information-circle"}
The bundle works whether API Platform's `use_symfony_listeners` is on or off, and leaves it at API Platform's default (off), as the template does. If your own code listens on API Platform's kernel events (`EventPriorities::PRE_WRITE` and the rest), set `use_symfony_listeners: true` in your `api_platform.yaml`, because those events only run with it on.
::

Each release's changes are in the bundle's [`CHANGELOG.md`](https://github.com/components-web-app/api-components-bundle/blob/main/CHANGELOG.md), and the same notes are on its [GitHub releases](https://github.com/components-web-app/api-components-bundle/releases). Changes not yet released are listed under **Unreleased**. The [Releases](/getting-started/releases) page shows these notes with the other packages' releases.

## Generate JWT Keys

The bundle uses cookie-based JWT tokens for authentication. Generate a key pair once per environment. The template's development entrypoint does this for you:

```bash
mkdir -p config/jwt
openssl genpkey -out config/jwt/private.pem -aes256 -algorithm rsa -pkeyopt rsa_keygen_bits:4096
openssl pkey -in config/jwt/private.pem -out config/jwt/public.pem -pubout
```

Add the passphrase to `.env.local` — **never commit this file**:

```ini
JWT_PASSPHRASE=your_secure_passphrase
```

Add the key paths to `.env`:

```ini
JWT_SECRET_KEY=%kernel.project_dir%/config/jwt/private.pem
JWT_PUBLIC_KEY=%kernel.project_dir%/config/jwt/public.pem
```

## Core Configuration

Open `config/packages/silverback_api_components.yaml`. This is the configuration the CWA template app ships with:

```yaml
silverback_api_components:
    website_name: My CWA App
    user:
        class_name: App\Entity\User
        email_links:
            default_origin: '%app.email_link_default_origin%'  # the site's public origin
        email_verification:
            default_value: false
            verify_on_register: true
            verify_on_change: true
            deny_unverified_login: true
            email:
                redirect_path_query: null
                default_redirect_path: /verify-email/{{ username }}/{{ token }}
        password_reset:
            email:
                redirect_path_query: null
                default_redirect_path: /reset-password/{{ username }}/{{ token }}
        new_email_confirmation:
            email:
                redirect_path_query: null
                default_redirect_path: /confirm-new-email/{{ username }}/{{ new_email }}/{{ token }}
    publishable:
        permission: "is_granted('ROLE_ADMIN')"
    refresh_token:
        handler_id: silverback.api_components.refresh_token.storage.doctrine
        options:
            class: App\Entity\RefreshToken
        cookie_name: api_component  # must match Lexik's cookie name
        ttl: 604800  # 1 week in seconds
        database_user_provider: database
    route_security:
        - { route: "/user-area*", security: "is_granted('ROLE_USER')" }
    routable_security: "is_granted('ROLE_ADMIN')"
    mercure:
        cookie:
            samesite: '%env(JWT_COOKIE_SAMESITE)%'
```

`/user-area*` is a prefix: it matches `/user-area` and every path that starts with it, but not `/other/user-area`. A `route_security` pattern matches the whole path, with `*` as its only wildcard. See [Access Control › How a pattern matches](/api/users/access-control#how-a-pattern-matches).

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
`user.email_verification` is **off** if you leave it out: users start unverified, no verification email is sent, and unverified users can still sign in. The template turns it on. If you set `verify_on_register` or `verify_on_change`, you must also set `email.default_redirect_path` (or `email.redirect_path_query`), or the container won't compile. The redirect paths are front-end routes, so keep them in step with the pages your Nuxt app actually serves. See [Configuration Reference](/api/configuration) for which keys are required.
::

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
Set `user.email_links.default_origin` to the origin your front end is served from, such as `https://www.example.com`. Without it, password reset and verification emails are refused. The template builds `%app.email_link_default_origin%` in `config/services.php` from `EMAIL_LINK_DEFAULT_ORIGIN`, falling back to `https://<BROWSER_SERVER_NAME>`. See [Links in Emails](/api/users/user-emails#links-in-emails).
::

## Mercure Hub

The bundle requires Mercure and installs it with itself (`symfony/mercure` ^0.8 or ^0.9, `symfony/mercure-bundle` ^0.5 or ^0.6). It speaks only the **Mercure 1.0** protocol, so the hub must be Mercure 1.0: FrankenPHP 1.13 or later, or a standalone hub at 1.0 or later.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**Configure a default Mercure hub.** The bundle decorates the `mercure.hub.default` service, so `config/packages/mercure.yaml` must define a hub named `default`. Without it, the container fails to compile with `non-existent service "mercure.hub.default"`.
::

[Real-Time Updates](/api/real-time) has the `mercure.yaml` settings, the hub's Caddyfile, the subscriber cookie and the template's configuration.

## Database Setup

The bundle adds tables for layouts, pages, routes, component groups, component positions, site config parameters, uploaded-file info (`FileInfo`), refresh tokens, and your user and component entities.

```bash
bin/console doctrine:migrations:diff
bin/console doctrine:migrations:migrate
```

**The template's migrations are upward-only.** Delete the generated `down()` from each new migration. Doctrine's inherited `down()` then aborts with `No down() migration implemented`, so a mistaken `migrations:migrate prev` can't drop tables or data. To undo a schema change, write a new migration that reverses it.

## Environment Variables

Set the variables in [Configuration › Environment Variables](/api/configuration#environment-variables): the database, the JWT keys and passphrase, the Mercure hub URLs and secret, `APP_SECRET` and `MAILER_DSN`. Keep `JWT_PASSPHRASE`, `APP_SECRET` and the Mercure secret in `.env.local` (never committed) or your deployment's secrets.

## Verifying the Install

Start your Symfony server and visit the API documentation UI — in the CWA template that is `/_api/docs`, since API Platform is mounted under the `/_api` prefix set in `config/routes/api_platform.yaml`. You should see every available resource listed.

The API entrypoint is the API root itself (`/_api/`), which returns the IRI of every resource collection. The Nuxt module fetches that entrypoint and discovers the Hydra documentation URL from its `Link` header.

If you've defined fixtures, load them first. A plain `doctrine:fixtures:load` empties the database before it loads, so it would delete a user created before it:

```bash
bin/console doctrine:fixtures:load
```

Then create your first admin user — pass `--admin` so the account has `ROLE_ADMIN` access:

```bash
bin/console silverback:api-components:user:create --admin
```

Follow the prompts to set username, email, and password. Without the flag the account is created with `ROLE_USER` only and cannot access the admin panel; see [`user:create`](/api/console-commands#usercreate) for every option. To load fixtures again later without losing the user, use `doctrine:fixtures:load --append` (see [Appending to an Existing Site](/api/data-fixtures/appending#appending-to-an-existing-site)).

## What Gets Auto-Registered

You don't need to register the core resources — layouts, pages, routes, component groups, component positions, site config parameters, and the Collection and Form components. They are listed, with their endpoints and fields, in [API Bundle Overview › Core Resources](/api#core-resources).

Your custom components are registered when you create entity classes extending `AbstractComponent`. See [Creating Components](/api/components/creating-components).
