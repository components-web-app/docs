When an API resource changes, the bundle publishes it to a [Mercure](https://mercure.rocks){target="_blank"} hub, and every open browser that shows it gets the new content. A resource is published when its `#[ApiResource]` has `mercure: true`. Each write publishes what a visitor would see on the public topic, and the writer's view privately for admins; see [Public and Admin Updates](#public-and-admin-updates). How the Nuxt module applies updates is covered in [Real-Time Updates](/nuxt-module/component-helpers/real-time-updates).

## Requirements

The bundle requires Mercure and installs it with itself. It accepts `symfony/mercure` ^0.8 or ^0.9 and `symfony/mercure-bundle` ^0.5 or ^0.6, and speaks only the **Mercure 1.0** protocol. The Nuxt module subscribes with the 1.0 protocol too.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**The hub must be Mercure 1.0.** That means FrankenPHP 1.13 or later (the template's hub is the Mercure module inside FrankenPHP), or a standalone Mercure hub at 1.0 or later. A 0.x hub rejects the module's subscription and live updates stop. There is no setting in the bundle or the module that brings back the 0.x protocol.
::

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**Configure a default Mercure hub.** The bundle decorates the `mercure.hub.default` service, so `config/packages/mercure.yaml` must define a hub named `default`. Without it, the container fails to compile with `non-existent service "mercure.hub.default"`.
::

The hub's URLs and secrets come from the `MERCURE_*` variables in [Environment Variables](/api/configuration#environment-variables).

## `mercure.yaml`

Set `protocol_version: '1.0'` on the hub. `symfony/mercure-bundle` 0.5 defaults to the 0.x protocol, and 0.6 defaults to 1.0, so the setting is only required on 0.5. Set it on 0.6 too, so the config doesn't depend on the bundle's version. Mercure 1.0 tokens are OAuth access tokens, so add the `iss`, `sub` and `client_id` claims:

```yaml [config/packages/mercure.yaml]
mercure:
    hubs:
        default:
            url: '%env(MERCURE_URL)%'
            public_url: '%env(MERCURE_PUBLIC_URL)%'
            protocol_version: '1.0' # [!code focus]
            cookie_name: '__Secure-mercure_access_token'
            jwt:
                secret: '%env(MERCURE_JWT_SECRET)%'
                publish: '*'
                claims: # [!code focus]
                    iss: 'https://www.example.com' # [!code focus]
                    sub: 'api' # [!code focus]
                    client_id: 'api' # [!code focus]
```

- With `protocol_version: '1.0'` and any of the three claims missing, the container won't compile. On mercure-bundle 0.6, a `jwt.secret` hub needs the three claims even without `protocol_version`, because 1.0 is the default.
- On 0.5, a hub without `protocol_version: '1.0'` makes the bundle fail when it builds the Mercure cookie, at sign-in and on `/me`.
- `iss` can be any stable identifier, such as your site's URL, as long as the hub's `issuer` block uses the same value. `aud` is set for you: it defaults to `public_url`.
- On 0.6, `url` and `public_url` default to null, and an empty `url` publishes through FrankenPHP's built-in hub. Set both explicitly, as above.
- Pin `cookie_name` on 0.6. See [The Subscriber Cookie](#the-subscriber-cookie).
- Use `HubInterface`, `TraceableHub` and `StaticTokenProvider` (`mercure.hub.*.jwt.provider`). mercure-bundle 0.6 has no `Publisher`, `PublisherInterface`, `TraceablePublisher` or `StaticJwtProvider`.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**Decorating the hub yourself?** `HubInterface` has `getProtocolVersion()` and `getCookieName()`, and `getUrl()` is on `RemoteHubInterface`. A class that decorates `mercure.hub.default` without these methods breaks `cache:clear` with a fatal error. Implement `RemoteHubInterface` and forward the methods to the inner hub. The template's `api/src/Mercure/SkipAwareMercureHub.php` shows how, and so does the bundle's own `PublishableAwareHub`.
::

The bundle's own Mercure settings are `mercure.hub_name`, `mercure.cookie.samesite` and `mercure.secure_subscriptions`; see [Configuration](/api/configuration#full-configuration).

## Hub Caddyfile

A Mercure 1.0 hub verifies tokens per issuer. The keys go in an `issuer` block, whose name must equal the `iss` claim. This is the whole `mercure` block; the template keeps everything inside it in `mercure-hub.caddy` (see [In the Template](#in-the-template)):

```caddyfile [api/frankenphp/Caddyfile]
mercure {
    name cwa
    transport bolt {$MERCURE_TRANSPORT_URL:bolt:///data/mercure.db}
    issuer https://www.example.com {
        publisher {
            jwt {env.MERCURE_PUBLISHER_JWT_KEY} {env.MERCURE_PUBLISHER_JWT_ALG}
        }
        subscriber {
            jwt {env.MERCURE_SUBSCRIBER_JWT_KEY} {env.MERCURE_SUBSCRIBER_JWT_ALG}
        }
    }
    resource_identifier {$MERCURE_PUBLIC_URL}
    anonymous
    subscriptions
    cors_origins {$MERCURE_CORS_ORIGIN:*}
}
```

`resource_identifier` is the audience the hub expects in a token's `aud`. The bundle's tokens carry the public hub URL. The API publishes through the internal `MERCURE_URL`, though, and without `resource_identifier` the hub expects the URL each request came in on. **Pin `resource_identifier` to the public hub URL, or every publish from the API gets a 401.**

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**Name the hub if Caddy runs more than one server.** A `SERVER_NAME` with several ports, such as the template compose stack's `localhost, php.local:80, php.local:443`, makes one server per port, each with its own copy of the `mercure` block. Mercure 1.0.3 and later refuse a second unnamed hub, so php doesn't start. Copies with the same `name` share one hub, so the API's publish on `php.local:80` still reaches browsers subscribed on `:443`. The template's Helm deploys use `SERVER_NAME=:80`, one server, so they don't need it.
::

Don't set `protocol_version_compatibility`. That directive keeps a 1.0 hub accepting 0.x clients, it only works in a binary built with the `deprecated_topic` and `deprecated_claim` tags, and it turns off the 1.0 token checks. In a modern-mode hub, the old top-level `publisher_jwt` and `subscriber_jwt` directives are a configuration error. Unknown directives are errors too, so a 0.x `demo` or `ui` in `MERCURE_EXTRA_DIRECTIVES` stops the php container from starting. Use `debugger`, and only in development.

## In the Template

The template keeps the hub's settings in a file of their own, `api/frankenphp/mercure-hub.caddy`, and its Caddyfile imports them into the `mercure` block ([`d51851c`](https://github.com/components-web-app/components-web-app/commit/d51851c8fecb429aca2702c871198eec9c663cb6)). *Since [template 2.0.0-alpha.43](https://github.com/components-web-app/components-web-app/releases/tag/v2.0.0-alpha.43).*

```caddyfile [api/frankenphp/Caddyfile]
@local_hub expression `"{$MERCURE_HUB_UPSTREAM}" == ""`
mercure @local_hub {
    import mercure-hub.caddy
}
```

`mercure-hub.caddy` holds what the `mercure` block held before: `name cwa`, the transport, the `issuer` block, `resource_identifier`, `anonymous`, `subscriptions`, `MERCURE_EXTRA_DIRECTIVES` and `cors_origins`. The same file is imported by `mercure-hub.Caddyfile`, for scaled mode's hub in its own pod, so the two hubs can't drift apart. Outside scaled mode `MERCURE_HUB_UPSTREAM` is unset, and php runs its own hub as before.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**Upgrading: copy `api/frankenphp/mercure-hub.caddy` and `mercure-hub.Caddyfile` with the Caddyfile**, and the line in `api/Dockerfile` that copies them to `/etc/caddy/`. The Caddyfile imports the hub's settings from `mercure-hub.caddy`, so without it php doesn't start. If you changed the hub's settings in your Caddyfile, move the change to `mercure-hub.caddy`, and edit them only there from now on. Check the result with `bin/test/caddy-validate.sh` (see [Troubleshooting › Caddy and Souin](/deployment/troubleshooting#caddy-and-souin)).
::

The template runs Mercure 1.0 in modern mode, and both sides use the fixed issuer `cwa`:

```yaml [api/config/packages/mercure.yaml]
mercure:
    hubs:
        default:
            protocol_version: '1.0'
            cookie_name: '__Secure-mercure_access_token' # [!code focus]
            # url, public_url, jwt.secret, publish and algorithm as above
            jwt:
                claims:
                    iss: 'cwa' # must equal the hub's issuer # [!code focus]
                    sub: 'cwa-api'
                    client_id: 'cwa-api'
```

```caddyfile [api/frankenphp/mercure-hub.caddy]
issuer cwa { # [!code focus]
    publisher {
        jwt {env.MERCURE_PUBLISHER_JWT_KEY} {env.MERCURE_PUBLISHER_JWT_ALG}
    }
    subscriber {
        jwt {env.MERCURE_SUBSCRIBER_JWT_KEY} {env.MERCURE_SUBSCRIBER_JWT_ALG}
    }
}
resource_identifier {$MERCURE_PUBLIC_URL:https://localhost/.well-known/mercure} # [!code focus]
```

- `cookie_name` is pinned because the dev stack runs with `kernel.debug`, which would otherwise make the API set a prefix-less cookie that the hub doesn't read.
- `resource_identifier` follows `MERCURE_PUBLIC_URL`, the tokens' `aud`, because the API publishes through the internal `http://php.local/…` or in-cluster URL. Don't remove it: every publish would get a `401`.
- The issuer is fixed on both sides, because the hub trusts only its own API, so there is nothing to configure. If you change it, change `iss` in `mercure.yaml` and the hub's `issuer` together: if they differ, the hub rejects every token with a `401`.

Projects created from older templates may have a `MERCURE_JWT_ISSUER` variable or compatibility mode; see [Releases](/getting-started/releases).

### Where the hub runs

Mercure runs as a Caddy module inside the FrankenPHP `php` container. There is no separate hub service locally (on Kubernetes, scaled mode runs the hub in its own pod: see [Scaled Mode › The Mercure hub](/deployment/scaled-mode#the-mercure-hub)): the template's `compose.yaml` keeps the Flex recipe's `mercure-bundle` blocks empty, so the recipe doesn't add a standalone hub.

In compose, the two URLs default to:

```ini
MERCURE_URL=http://php.local/.well-known/mercure
MERCURE_PUBLIC_URL=https://${SERVER_NAME:-localhost}/.well-known/mercure
```

Override them with `CADDY_MERCURE_URL` and `CADDY_MERCURE_PUBLIC_URL`. On a single server, `compose.prod.yaml` sets the public URL to `https://<SITE_HOST>/.well-known/mercure`, the site's host plus the hub's path, so `CADDY_MERCURE_PUBLIC_URL` doesn't change it there (see [Docker › Production Docker Compose](/deployment/docker#production-docker-compose)). *Since [template 2.0.0-alpha.45](https://github.com/components-web-app/components-web-app/releases/tag/v2.0.0-alpha.45) ([`5bfc71f`](https://github.com/components-web-app/components-web-app/commit/5bfc71f4d89fdccb5fce3578f1c23eab69f7cabd)).* On Kubernetes, the chart's `mercure.publicUrl` sets the public URL (see [Kubernetes & Helm](/deployment/kubernetes)).

`CADDY_MERCURE_JWT_SECRET` feeds both `MERCURE_PUBLISHER_JWT_KEY` and `MERCURE_SUBSCRIBER_JWT_KEY`, and the API's `MERCURE_JWT_SECRET`. If the hub answers `401`, check that it's set, and the same, everywhere the `php` service is configured, `compose.prod.yaml` included.

::callout{icon="i-heroicons-information-circle"}
**Size the hub for every update.** The module subscribes with `match=*`, so every public update, and every private update the cookie allows, reaches every connected browser. Each browser then keeps only the updates for resources it shows.
::

## Public and Admin Updates

A created or updated resource can publish two updates, in this order:

| Update | Topic | Payload |
|--------|-------|---------|
| Public | `<iri>` | What an anonymous `GET` of the resource returns |
| Admin (private) | `<iri>?draft=1` | The writer's view, as the request that wrote it would read it. Sent only when it differs from the public payload |

A draft is published only as the private admin update. A deleted resource publishes `{"@id": "<iri>"}` on the public topic.

Admins are granted `<pattern>\?draft=1` for every resource class with `mercure: true`. Here an admin is anyone who passes `publishable.permission`, or a class's own [`#[Publishable(isGranted:)]`](/api/components/annotations/publishable#configuring-who-can-publish). See [The Subscriber Cookie](#the-subscriber-cookie).

When anonymous callers can't read the resource (any response but a `200`, such as a `401`, `403` or `404`), what goes out publicly depends on whether the write hid it:

- **The write hid it:** a public delete, `{"@id": "<iri>"}`, so open pages drop it. That's a publication date or a route's `liveAt` moved from the past to the future or cleared, a page's route unset, or a page's parent page or parent page data changed.
- **Otherwise:** nothing is published publicly. The admin update still goes out.

A resource hidden without being written itself, such as a page under a parent whose route was unset, gets no message.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**Routing `Update` to an async transport?** Also route `Silverback\ApiComponentsBundle\Message\PublishMercureUpdatesMessage`, which carries a resource's public and private updates together, in order:

```yaml [config/packages/messenger.yaml]
framework:
    messenger:
        routing:
            Symfony\Component\Mercure\Update: async
            Silverback\ApiComponentsBundle\Message\PublishMercureUpdatesMessage: async
```
::

- **A public delete reveals an IRI.** Every subscriber sees the delete's `@id`, even for a resource that was never public. A route's IRI contains its path.
- **Each update costs a sub-request.** The public payload is read with one internal anonymous `GET` per created or updated resource.

*Since bundle 2.0.0-alpha.27 ([#497](https://github.com/components-web-app/api-components-bundle/pull/497)). Before, the public topic carried the writer's view, so an admin's write could publish content visitors can't read.*

## The Subscriber Cookie

The bundle sets a cookie that lists the topics a signed-in user may receive privately. It sets it at sign-in and whenever the JWT is refreshed. Signing out, an invalid or expired JWT, and a failed `/me` expire it; a failed `/me` expires it whenever the request carries it. An anonymous visitor gets no Mercure cookie, and public updates need none. *Since bundle 2.0.0-alpha.27 ([#495](https://github.com/components-web-app/api-components-bundle/pull/495)). Before, these responses issued a new cookie, and a signed-out visitor got one from `/me`.*

The cookie and the token in it expire after [`refresh_token.ttl`](/api/users/authentication#refresh-token-configuration), so they last as long as the session can. `mercure.default_cookie_lifetime` no longer applies to this cookie. *Since bundle 2.0.0-alpha.28 ([#499](https://github.com/components-web-app/api-components-bundle/pull/499)). Before, the cookie lasted 10 years and its token `default_cookie_lifetime`, usually an hour.*

The cookie name comes from the hub: with Mercure 1.0 it is **`__Secure-mercure_access_token`**. On `symfony/mercure-bundle` 0.6, a hub with no `cookie_name` uses `mercure_access_token` instead while `kernel.debug` is on (the `dev` environment), and a hub with the default `__Secure-mercure_access_token` name doesn't read it, so admins get no private updates in development. So on 0.6, pin the name:

```yaml [config/packages/mercure.yaml]
mercure:
    hubs:
        default:
            cookie_name: '__Secure-mercure_access_token'
```

Browsers only accept a `__Secure-` cookie over HTTPS. If your hub's `public_url` is plain `http://`, `symfony/mercure` throws when it builds the cookie. In that case, set the same prefix-less name on both sides, for local development only:

```yaml [config/packages/mercure.yaml]
mercure:
    hubs:
        default:
            cookie_name: 'mercure_access_token'
```

```caddyfile [api/frankenphp/mercure-hub.caddy]
cookie_name mercure_access_token
```

Before the template moved the hub's settings to `mercure-hub.caddy`, this line went in the Caddyfile's `mercure` block.

The template's development stack serves the hub at `https://localhost/.well-known/mercure`, so it keeps the `__Secure-` name.

The topics in the cookie are URL Patterns: `https://www.example.com/_api/_/component_groups/:id\?` for published resources, plus `…/:id\?draft=1` for users who may see drafts. They're also returned as `_metadata.mercureSubscribeTopics` on the user from `GET /me`. Each pattern ends in an explicit query part: a pattern without one would also match `?draft=1` and send draft updates to everyone with the cookie.

The cookie's `SameSite` attribute is `mercure.cookie.samesite` in the bundle config (default `strict`). The template reads it from `JWT_COOKIE_SAMESITE`.

## Secure Subscriptions

By default the subscriber cookie includes every resource topic — Mercure will push updates for any resource the front end subscribes to, regardless of the current user's access level. This is fine for public content but leaks real-time updates for resources that have server-side security expressions.

Set `mercure.secure_subscriptions: true` to scope it: the bundle evaluates each API resource's security expression when it issues the cookie and omits topics the current user cannot access:

```yaml
silverback_api_components:
    mercure:
        secure_subscriptions: true
```

**Caveats:**

- Security expressions that reference `object` (item-level security, e.g. `object.owner == user`) cannot be evaluated at that point, because there is no concrete entity instance. Those resource topics are always included — you cannot scope to specific items, only to the class/role level.
- The cookie is written at sign-in and re-issued whenever the JWT is refreshed. A role change mid-session therefore doesn't take effect immediately — the scope widens or narrows at the next refresh. Sign out and back in if you need it applied straight away.

Enable it in production for any application with role-gated resources. Leave `false` (the default) for fully public sites.

## The Admin Real-Time Channel

Admins' browsers can tell each other things that aren't saved, such as who is editing which component. `POST /_/realtime` (`/_api/_/realtime` in the template) takes an event from an admin and publishes it privately to every other signed-in admin. Nothing is stored. *Since [bundle 2.0.0-alpha.35](https://github.com/components-web-app/api-components-bundle/releases/tag/2.0.0-alpha.35) ([#560](https://github.com/components-web-app/api-components-bundle/pull/560)).*

### Sending an event

The endpoint needs `ROLE_ADMIN` and answers `202` with no body. The body is a JSON object of 16 KB at most:

```json
{
  "clientId": "0f3c2b9e-6a41-4d55-9b3e-2c7d8e1f4a60",
  "event": "presence",
  "iri": "/_/components/1ec4…",
  "data": { "state": "editing" }
}
```

| Field | Rules |
|-------|-------|
| `clientId` | Required. A UUID, one per browser tab |
| `event` | Required. Lowercase, at most 64 characters, starting with a letter; only `a-z`, `0-9`, `_`, `.`, `:` and `-` |
| `iri` | Optional. A string |
| `data` | Optional. Any JSON value |

Send it as `application/json` (or `application/ld+json`). A `text/plain` body is accepted only for one event: a presence event whose `data.state` is `left`, so a tab can say it's leaving with `navigator.sendBeacon`, which can't send JSON. Anything else is refused:

| Status | When |
|--------|------|
| `413` | The body is over 16 KB |
| `415` | Not JSON, and not a `text/plain` leaving beacon |
| `422` | A field breaks its rule; there's one violation per field |
| `403` | A `text/plain` body from another site (`Sec-Fetch-Site: cross-site`) |
| `429` | Too many events; see [Rate limits](#rate-limits) |

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**A front end on another site must send JSON.** A cross-site `text/plain` body is a request any page can send without asking, so it's refused with a `403`. A cross-site JSON body is accepted, as long as the API's CORS config allows the front end's origin. So that front end should send its leaving event with `fetch(url, { method: 'POST', keepalive: true, credentials: 'include', headers: { 'Content-Type': 'application/json' }, body })` instead of `sendBeacon`.
::

### What admins receive

The event goes out as a private update, with no SSE `type`, on one topic for the whole site: the endpoint's absolute URL, such as `https://www.example.com/_api/_/realtime`. Only admins' [subscriber cookies](#the-subscriber-cookie) include that topic. The payload:

```json
{
  "@type": "CwaRealtimeEvent",
  "v": 1,
  "clientId": "0f3c2b9e-6a41-4d55-9b3e-2c7d8e1f4a60",
  "user": { "id": "/_/users/…", "name": "admin" },
  "event": "presence",
  "iri": "/_/components/1ec4…",
  "data": { "state": "editing" },
  "sentAt": "2026-10-21T18:30:00.123+00:00",
  "expiresAt": "2026-10-21T18:30:45.123+00:00"
}
```

- `user` is the sender: the user's IRI and username. It comes from the session, never from the body.
- `iri` and `data` are `null` when the sender left them out.
- `expiresAt` is 45 seconds after `sentAt`. Ignore an event that has expired.
- `v` is the payload's version. A change to its shape will change `v`.

Like every update, events stay in the hub's history, so a browser that reconnects with `last_event_id` can be sent old ones; `expiresAt` is how it tells. How much history the hub keeps is a setting of the hub's transport; see [Mercure's configuration](https://mercure.rocks/docs/hub/config){target="_blank"}.

### Rate limits

Each event counts against two limits, both token buckets:

| Limit | Burst | Then |
|-------|-------|------|
| Per user and `clientId` | 20 | 10 a second |
| Per user, across all their clients | 60 | 30 a second |

Past either, the endpoint answers `429` with `Retry-After`, the longer of the two waits in seconds.

The limits are kept in the cache pool `silverback.api_components.realtime.rate_limiter_cache`, which uses `cache.app` by default. That's local to each API pod, so with more than one pod (see [Scaled Mode](/deployment/scaled-mode)) each pod counts on its own. To count across pods, point the pool at a shared adapter:

```yaml [config/packages/cache.yaml]
framework:
    cache:
        pools:
            silverback.api_components.realtime.rate_limiter_cache:
                adapter: cache.adapter.redis
```

### Publishing is best effort

The event is published with a copy of the hub's HTTP client that waits at most 1 second and never retries, even when `framework.http_client` retries failed requests. A publish that fails or times out is logged at `error` (`The real-time event "<event>" could not be published on "<topic>": …`), and the sender still gets `202`. Saved changes don't use this client, so they keep the hub's usual behaviour.

### Turning it off

```yaml [config/packages/silverback_api_components.yaml]
silverback_api_components:
    realtime:
        enabled: false
```

The endpoint is then a `404`, and no subscriber cookie includes its topic. The setting is fixed when the container is compiled, so it must be `true` or `false`, never an environment variable: `'%env(bool:…)%'` fails with `realtime.enabled is fixed when the container is compiled, so it must be a literal boolean, not an environment variable.` To turn it off in one environment, set it in that environment's config file, such as `config/packages/prod/silverback_api_components.yaml`.

### Who saved a change: `X-CWA-Client-Id`

A write (`POST`, `PUT`, `PATCH` or `DELETE`) by a signed-in user that sends an `X-CWA-Client-Id` header holding a UUID gets `_metadata.lastWrite` on each resource it returns:

```json
"_metadata": {
  "lastWrite": {
    "clientId": "0f3c2b9e-6a41-4d55-9b3e-2c7d8e1f4a60",
    "userId": "/_/users/…",
    "at": "2026-10-21T18:30:00.123+00:00"
  }
}
```

It's in the writer's response and in the private `<iri>?draft=1` update (see [Public and Admin Updates](#public-and-admin-updates)), never in the public update. A browser can use it to spot its own saves coming back over Mercure. `at` is the server's time with milliseconds, the same for every resource in one request; to put drafts' updates in order, use `at`, not `modifiedAt`. A header that isn't a UUID is ignored.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**Allow the header in CORS.** When the front end is on another origin, its writes carry `X-CWA-Client-Id`, so the API's CORS config must allow it, or the browser blocks the write. With NelmioCorsBundle, add it to `allow_headers`. The template does from `main` after 2.0.0-alpha.45 ([`aca1900`](https://github.com/components-web-app/components-web-app/commit/aca1900b94f690afe267ce61cc42df3485ae8682)); in an older project:

```yaml [api/config/packages/nelmio_cors.yaml]
nelmio_cors:
    defaults:
        allow_headers: ['Content-Type', 'Authorization', 'Preload', 'Fields', 'Path', 'X-CWA-Client-Id'] # [!code focus]
```
::

## When Updates Don't Arrive

**If real-time updates stop but saves still work, check the API log for Mercure errors.** When a publish fails, for example because the hub can't be reached or rejects the token, the bundle logs it at `error` level and the save still returns its normal response. Other open pages miss that update until they next fetch. Monitor your error logs for messages containing `could not be published`. The log context includes `topics`, `resource` and `exception`.

A malformed publisher JWT is different: Mercure rejects it before sending anything, and that error still fails the request, so a misconfigured secret shows up straight away.

**A fixture load publishes nothing.** `doctrine:fixtures:load` doesn't publish the content it writes, so open pages don't update until they next fetch. *Since bundle 2.0.0-alpha.23 ([#465](https://github.com/components-web-app/api-components-bundle/pull/465)).* See [What a Load Leaves Until Later](/api/data-fixtures/getting-started#what-a-load-leaves-until-later).

The Symfony profiler's CWA panel lists what each request published, and which updates were made private; see [Debugging & Errors](/api/debugging#mercure-publications).
