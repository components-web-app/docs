When an API resource changes, the bundle publishes it to a [Mercure](https://mercure.rocks){target="_blank"} hub, and every open browser that shows it gets the new content. A resource is published when its `#[ApiResource]` has `mercure: true`. A draft of a `#[Silverback\Publishable]` resource is published as a private update, so only signed-in users who may see drafts receive it. How the Nuxt module applies updates is covered in [Real-Time Updates](/nuxt-module/component-helpers/real-time-updates).

## Requirements

The bundle requires Mercure and installs it with itself. It accepts `symfony/mercure` ^0.8 or ^0.9 and `symfony/mercure-bundle` ^0.5 or ^0.6, and speaks only the **Mercure 1.0** protocol. The Nuxt module subscribes with the 1.0 protocol too.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**The hub must be Mercure 1.0.** That means FrankenPHP 1.13 or later (the template's hub is the Mercure module inside FrankenPHP), or a standalone Mercure hub at 1.0 or later. A 0.x hub rejects the module's subscription and live updates stop. There is no setting in the bundle or the module that brings back the 0.x protocol.
::

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**Configure a default Mercure hub.** The bundle decorates the `mercure.hub.default` service, so `config/packages/mercure.yaml` must define a hub named `default`. Without it, the container fails to compile with `non-existent service "mercure.hub.default"`.
::

The hub's URLs and secrets come from the `MERCURE_*` variables in [Environment Variables](/api/configuration#environment-variables).

## `mercure.yaml`

Set `protocol_version: '1.0'` on the hub. `symfony/mercure-bundle` 0.5 defaults to the 0.x protocol, and 0.6 defaults to 1.0, so the setting is only required on 0.5. Set it on 0.6 too, so the config doesn't depend on the bundle's version. Mercure 1.0 tokens are OAuth access tokens, so add the `iss`, `sub` and `client_id` claims:

```yaml [config/packages/mercure.yaml]
mercure:
    hubs:
        default:
            url: '%env(MERCURE_URL)%'
            public_url: '%env(MERCURE_PUBLIC_URL)%'
            protocol_version: '1.0' # [!code focus]
            cookie_name: '__Secure-mercure_access_token'
            jwt:
                secret: '%env(MERCURE_JWT_SECRET)%'
                publish: '*'
                claims: # [!code focus]
                    iss: 'https://www.example.com' # [!code focus]
                    sub: 'api' # [!code focus]
                    client_id: 'api' # [!code focus]
```

- With `protocol_version: '1.0'` and any of the three claims missing, the container won't compile. On mercure-bundle 0.6, a `jwt.secret` hub needs the three claims even without `protocol_version`, because 1.0 is the default.
- On 0.5, a hub without `protocol_version: '1.0'` makes the bundle fail when it builds the Mercure cookie, at sign-in and on `/me`.
- `iss` can be any stable identifier, such as your site's URL, as long as the hub's `issuer` block uses the same value. `aud` is set for you: it defaults to `public_url`.
- On 0.6, `url` and `public_url` default to null, and an empty `url` publishes through FrankenPHP's built-in hub. Set both explicitly, as above.
- Pin `cookie_name` on 0.6. See [The Subscriber Cookie](#the-subscriber-cookie).
- Use `HubInterface`, `TraceableHub` and `StaticTokenProvider` (`mercure.hub.*.jwt.provider`). mercure-bundle 0.6 has no `Publisher`, `PublisherInterface`, `TraceablePublisher` or `StaticJwtProvider`.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**Decorating the hub yourself?** `HubInterface` has `getProtocolVersion()` and `getCookieName()`, and `getUrl()` is on `RemoteHubInterface`. A class that decorates `mercure.hub.default` without these methods breaks `cache:clear` with a fatal error. Implement `RemoteHubInterface` and forward the methods to the inner hub. The template's `api/src/Mercure/SkipAwareMercureHub.php` shows how, and so does the bundle's own `PublishableAwareHub`.
::

The bundle's own Mercure settings are `mercure.hub_name`, `mercure.cookie.samesite` and `mercure.secure_subscriptions`; see [Configuration](/api/configuration#full-configuration).

## Hub Caddyfile

A Mercure 1.0 hub verifies tokens per issuer. The keys go in an `issuer` block, whose name must equal the `iss` claim:

```caddyfile [api/frankenphp/Caddyfile]
mercure {
    name cwa
    transport bolt {$MERCURE_TRANSPORT_URL:bolt:///data/mercure.db}
    issuer https://www.example.com {
        publisher {
            jwt {env.MERCURE_PUBLISHER_JWT_KEY} {env.MERCURE_PUBLISHER_JWT_ALG}
        }
        subscriber {
            jwt {env.MERCURE_SUBSCRIBER_JWT_KEY} {env.MERCURE_SUBSCRIBER_JWT_ALG}
        }
    }
    resource_identifier {$MERCURE_PUBLIC_URL}
    anonymous
    subscriptions
    cors_origins {$MERCURE_CORS_ORIGIN:*}
}
```

`resource_identifier` is the audience the hub expects in a token's `aud`. The bundle's tokens carry the public hub URL. The API publishes through the internal `MERCURE_URL`, though, and without `resource_identifier` the hub expects the URL each request came in on. **Pin `resource_identifier` to the public hub URL, or every publish from the API gets a 401.**

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**Name the hub if Caddy runs more than one server.** A `SERVER_NAME` with several ports, such as the template compose stack's `localhost, php.local:80, php.local:443`, makes one server per port, each with its own copy of the `mercure` block. Mercure 1.0.3 and later refuse a second unnamed hub, so php doesn't start. Copies with the same `name` share one hub, so the API's publish on `php.local:80` still reaches browsers subscribed on `:443`. The template's Helm deploys use `SERVER_NAME=:80`, one server, so they don't need it.
::

Don't set `protocol_version_compatibility`. That directive keeps a 1.0 hub accepting 0.x clients, it only works in a binary built with the `deprecated_topic` and `deprecated_claim` tags, and it turns off the 1.0 token checks. In a modern-mode hub, the old top-level `publisher_jwt` and `subscriber_jwt` directives are a configuration error. Unknown directives are errors too, so a 0.x `demo` or `ui` in `MERCURE_EXTRA_DIRECTIVES` stops the php container from starting. Use `debugger`, and only in development.

## In the Template

The template runs Mercure 1.0 in modern mode, and both sides use the fixed issuer `cwa`:

```yaml [api/config/packages/mercure.yaml]
mercure:
    hubs:
        default:
            protocol_version: '1.0'
            cookie_name: '__Secure-mercure_access_token' # [!code focus]
            # url, public_url, jwt.secret, publish and algorithm as above
            jwt:
                claims:
                    iss: 'cwa' # must equal the Caddyfile's issuer # [!code focus]
                    sub: 'cwa-api'
                    client_id: 'cwa-api'
```

```caddyfile [api/frankenphp/Caddyfile]
issuer cwa { # [!code focus]
    publisher {
        jwt {env.MERCURE_PUBLISHER_JWT_KEY} {env.MERCURE_PUBLISHER_JWT_ALG}
    }
    subscriber {
        jwt {env.MERCURE_SUBSCRIBER_JWT_KEY} {env.MERCURE_SUBSCRIBER_JWT_ALG}
    }
}
resource_identifier {$MERCURE_PUBLIC_URL:https://localhost/.well-known/mercure} # [!code focus]
```

- `cookie_name` is pinned because the dev stack runs with `kernel.debug`, which would otherwise make the API set a prefix-less cookie that the hub doesn't read.
- `resource_identifier` follows `MERCURE_PUBLIC_URL`, the tokens' `aud`, because the API publishes through the internal `http://php.local/…` or in-cluster URL. Don't remove it: every publish would get a `401`.
- The issuer is fixed on both sides, because the hub trusts only its own API, so there is nothing to configure. If you change it, change `iss` in `mercure.yaml` and the Caddyfile's `issuer` together: if they differ, the hub rejects every token with a `401`.

Projects created from older templates may have a `MERCURE_JWT_ISSUER` variable or compatibility mode; see [Releases](/getting-started/releases).

### Where the hub runs

Mercure runs as a Caddy module inside the FrankenPHP `php` container. There is no separate hub service: the template's `compose.yaml` keeps the Flex recipe's `mercure-bundle` blocks empty, so the recipe doesn't add a standalone hub.

In compose, the two URLs default to:

```ini
MERCURE_URL=http://php.local/.well-known/mercure
MERCURE_PUBLIC_URL=https://${SERVER_NAME:-localhost}/.well-known/mercure
```

So in production the public URL follows `SERVER_NAME`, the site's domain plus `/.well-known/mercure`. Override them with `CADDY_MERCURE_URL` and `CADDY_MERCURE_PUBLIC_URL`. On Kubernetes, the chart's `mercure.publicUrl` sets the public URL (see [Kubernetes & Helm](/deployment/kubernetes)).

`CADDY_MERCURE_JWT_SECRET` feeds both `MERCURE_PUBLISHER_JWT_KEY` and `MERCURE_SUBSCRIBER_JWT_KEY`, and the API's `MERCURE_JWT_SECRET`. If the hub answers `401`, check that it's set, and the same, everywhere the `php` service is configured, `compose.prod.yaml` included.

::callout{icon="i-heroicons-information-circle"}
**Size the hub for every update.** The module subscribes with `match=*`, so every public update, and every private update the cookie allows, reaches every connected browser. Each browser then keeps only the updates for resources it shows.
::

## The Subscriber Cookie

The bundle sets a cookie that lists the topics a visitor may receive privately. It sets it at sign-in, on a JWT refresh and on `/me`, including the `401` a signed-out visitor gets there. The cookie name comes from the hub: with Mercure 1.0 it is **`__Secure-mercure_access_token`**. On `symfony/mercure-bundle` 0.6, a hub with no `cookie_name` uses `mercure_access_token` instead while `kernel.debug` is on (the `dev` environment), and a hub with the default `__Secure-mercure_access_token` name doesn't read it, so admins get no private updates in development. So on 0.6, pin the name:

```yaml [config/packages/mercure.yaml]
mercure:
    hubs:
        default:
            cookie_name: '__Secure-mercure_access_token'
```

Browsers only accept a `__Secure-` cookie over HTTPS. If your hub's `public_url` is plain `http://`, `symfony/mercure` throws when it builds the cookie. In that case, set the same prefix-less name on both sides, for local development only:

```yaml [config/packages/mercure.yaml]
mercure:
    hubs:
        default:
            cookie_name: 'mercure_access_token'
```

```caddyfile [api/frankenphp/Caddyfile]
mercure {
    cookie_name mercure_access_token
}
```

The template's development stack serves the hub at `https://localhost/.well-known/mercure`, so it keeps the `__Secure-` name.

The topics in the cookie are URL Patterns: `https://www.example.com/_api/_/component_groups/:id\?` for published resources, plus `…/:id\?draft=1` for users who may see drafts. They're also returned as `_metadata.mercureSubscribeTopics` on the user from `GET /me`. Each pattern ends in an explicit query part: a pattern without one would also match `?draft=1` and send draft updates to everyone with the cookie.

The cookie's `SameSite` attribute is `mercure.cookie.samesite` in the bundle config (default `strict`). The template reads it from `JWT_COOKIE_SAMESITE`.

## Secure Subscriptions

By default the subscriber cookie includes every resource topic — Mercure will push updates for any resource the front end subscribes to, regardless of the current user's access level. This is fine for public content but leaks real-time updates for resources that have server-side security expressions.

Set `mercure.secure_subscriptions: true` to scope it: the bundle evaluates each API resource's security expression when it issues the cookie and omits topics the current user cannot access:

```yaml
silverback_api_components:
    mercure:
        secure_subscriptions: true
```

**Caveats:**

- Security expressions that reference `object` (item-level security, e.g. `object.owner == user`) cannot be evaluated at that point, because there is no concrete entity instance. Those resource topics are always included — you cannot scope to specific items, only to the class/role level.
- The cookie is written at sign-in and re-issued whenever the JWT is refreshed. A role change mid-session therefore doesn't take effect immediately — the scope widens or narrows at the next refresh. Sign out and back in if you need it applied straight away.

Enable it in production for any application with role-gated resources. Leave `false` (the default) for fully public sites.

## When Updates Don't Arrive

**If real-time updates stop but saves still work, check the API log for Mercure errors.** When a publish fails, for example because the hub can't be reached or rejects the token, the bundle logs it at `error` level and the save still returns its normal response. Other open pages miss that update until they next fetch. Monitor your error logs for messages containing `could not be published`. The log context includes `topics`, `resource` and `exception`.

A malformed publisher JWT is different: Mercure rejects it before sending anything, and that error still fails the request, so a misconfigured secret shows up straight away.

**A fixture load publishes nothing.** `doctrine:fixtures:load` doesn't publish the content it writes, so open pages don't update until they next fetch. *Since bundle 2.0.0-alpha.23 ([#465](https://github.com/components-web-app/api-components-bundle/pull/465)).* See [What a Load Leaves Until Later](/api/data-fixtures/getting-started#what-a-load-leaves-until-later).

The Symfony profiler's CWA panel lists what each request published, and which updates were made private; see [Debugging & Errors](/api/debugging#mercure-publications).
