title: Admin Roles
description: The bundle's two narrow admin roles, ROLE_CMS_ADMIN for content and ROLE_USER_ADMIN for users, how ROLE_ADMIN and ROLE_SUPER_ADMIN reach them, and the rules for managing users.
---

The bundle splits admin access in two. **`ROLE_CMS_ADMIN`** edits the site's content. **`ROLE_USER_ADMIN`** manages user accounts. Your usual `ROLE_ADMIN` and `ROLE_SUPER_ADMIN` reach them through the role hierarchy, so you can give someone one job without the other.

## The Role Hierarchy

The bundle adds these roles to `security.role_hierarchy`:

```yaml
security:
    role_hierarchy:
        ROLE_SUPER_ADMIN: [ROLE_ADMIN, ROLE_USER_ADMIN, ROLE_ALLOWED_TO_SWITCH]
        ROLE_ADMIN: [ROLE_CMS_ADMIN]
        ROLE_CMS_ADMIN: [ROLE_USER]
        ROLE_USER_ADMIN: [ROLE_USER]
```

You don't write this yourself. The bundle merges it into your own `role_hierarchy`: a role you already list keeps its roles and gains the bundle's. The template's `ROLE_ADMIN: ROLE_USER` becomes `ROLE_ADMIN: [ROLE_USER, ROLE_CMS_ADMIN]`.

| Role | Edits content | Manages users |
|------|:-:|:-:|
| `ROLE_SUPER_ADMIN` | Yes | Yes |
| `ROLE_ADMIN` | Yes | No |
| `ROLE_CMS_ADMIN` | Yes | No |
| `ROLE_USER_ADMIN` | No | Yes |
| `ROLE_USER` | No | No |

To make someone a content editor who can't manage users, give them `ROLE_ADMIN`. `ROLE_CMS_ADMIN` and `ROLE_USER_ADMIN` on their own suit API clients of your own, such as an account manager that edits users but no pages.

::callout{icon="i-heroicons-information-circle"}
The Nuxt admin panel opens only for `ROLE_ADMIN` and `ROLE_SUPER_ADMIN`. A user with only `ROLE_CMS_ADMIN` or `ROLE_USER_ADMIN` can sign in but gets no admin bar or admin pages.
::

## What Needs `ROLE_CMS_ADMIN`

- **Content writes and drafts**, through `publishable.permission`, which defaults to `is_granted('ROLE_CMS_ADMIN')` (see [Sites with Non-Admin Users](/api/users/non-admin-users)).
- **Unrouted pages**, through `routable_security`, which defaults to the same expression (see [Access Control › `routable_security`](/api/users/access-control#routable_security)).
- A route's `liveAt` and `GET /_/routes/{id}/children` (see [Routes](/api/routes)).
- A page's `isReachableWithoutRoute` (see [Access Control › Public Pages Without a Route](/api/users/access-control#public-pages-without-a-route)).
- A component position's `pageDataProperty` and `pageDataClass` on read.
- Collaboration states (see [Versions & Conflicts](/api/versions-and-conflicts)) and the admin real-time channel (see [Real-Time › The Admin Real-Time Channel](/api/real-time#the-admin-real-time-channel)).
- A component's `/usage` (see [Component Groups › Where a Component Is Used](/api/components/component-groups#where-a-component-is-used)).
- The orphaned data reports and deletes (see [Orphaned Data](/api/orphaned-data)).
- `POST /_/http_cache/purge` and `POST /_/rendered_html/purge` (see [HTTP Caching](/api/http-caching)).

The two configuration values can be set to any expression. The other checks are fixed to `ROLE_CMS_ADMIN`.

::callout{icon="i-heroicons-information-circle"}
The template sets `publishable.permission` and `routable_security` to `is_granted('ROLE_ADMIN')`. A user with only `ROLE_CMS_ADMIN` fails those two, though they pass every fixed check. Set both to `is_granted('ROLE_CMS_ADMIN')`, or leave them out, if you hand out `ROLE_CMS_ADMIN` on its own.
::

## Managing Users

The bundle sets the `security` of every operation on your `User` class:

| Operation | Who can |
|-----------|---------|
| `GET` the collection, `POST` | `ROLE_USER_ADMIN` |
| `GET` one user | `ROLE_USER_ADMIN`, or the user themselves |
| `PATCH`, `PUT` | `ROLE_USER_ADMIN` and outranking the user, or the user themselves |
| `DELETE` | `ROLE_USER_ADMIN` and outranking the user |
| `GET /me` | Any signed-in user |

**Outranking** means the caller reaches every role the user reaches. A user admin can't edit or delete a super admin, for example: that's a `403`.

Only a user admin can write `username`, `emailAddress`, `roles` and `enabled`, and only a user admin reads `enabled`. A user editing themselves can change their password and start an email change (see [User Emails](/api/users/user-emails)).

### Assigning Roles

A caller can only **add** a role they reach themselves. Adding any other role is a `422` on `roles`:

```json
{
  "violations": [
    { "propertyPath": "roles", "message": "You may not assign the role(s) ROLE_SUPER_ADMIN." }
  ]
}
```

Removing a role isn't checked, and nor is a change made with no one signed in, such as [`user:create`](/api/console-commands#usercreate) or a fixture load.

`roles` in a response, including `/me`, lists every role the user reaches, not only the stored ones.

### Your Own `security` on a User Operation

An operation's own `security` is added to the bundle's: the caller must pass both. To use only your own expression, set the `user_admin_security` extra property to `false` (the constant `UserResourceMetadataCollectionFactory::OPT_OUT_EXTRA_PROPERTY`):

```php
// api/src/Entity/User.php
use ApiPlatform\Metadata\ApiResource;
use ApiPlatform\Metadata\Post;
use Silverback\ApiComponentsBundle\ApiPlatform\Metadata\Resource\UserResourceMetadataCollectionFactory;
use Silverback\ApiComponentsBundle\Entity\User\AbstractUser;

#[ApiResource(operations: [
    new Post(
        security: "is_granted('PUBLIC_ACCESS')", // [!code focus]
        extraProperties: [UserResourceMetadataCollectionFactory::OPT_OUT_EXTRA_PROPERTY => false], // [!code focus]
    ),
])]
class User extends AbstractUser
{
}
```

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
An opted-out operation with no `security` of its own is open to anyone your `access_control` lets through. Your `access_control` still runs first: the template's requires a signed-in user for every `POST`, so open registration also needs a `PUBLIC_ACCESS` rule for its path.
::
