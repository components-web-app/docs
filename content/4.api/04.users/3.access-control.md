This page covers who can read what through the API. Signing in is covered in [Authentication](/api/users/authentication).

## Public Access Follows Routes

One rule decides what anonymous visitors can read:

> **A resource is publicly readable if and only if it is reachable from a Route that exists and is live now.**

The one exception is a page or page data flagged `isReachableWithoutRoute`, which counts as though a live Route reached it. See [Public Pages Without a Route](#public-pages-without-a-route).

"Reachable" means following the page hierarchy down from that Route: its own Page or PageData, every ancestor above it (through `parentPage` / `parentPageData`), the template Page a PageData renders through, and the components placed in any of them. "Live" means its go-live date has passed, including any date inherited from an ancestor. See [Scheduling and Taking Routes Offline](/api/routes#scheduling-and-taking-routes-offline).

Two consequences are worth knowing:

- **Nested pages under an unrouted parent render for the public.** A child's live Route makes its whole ancestor chain readable, so a grouping parent with no URL of its own still renders at its depth.
- **A page that nothing routes to is private.** No Route on the page and none on any page below it means its Page, PageData and components are readable only by users who pass `routable_security`.

Routes themselves are always held to this rule. For pages, page data and components it is enforced when [`routable_security`](#routable_security) is set, as it is in the template app. Reachability is resolved per request by walking the page hierarchy; there is no join table to rebuild and no command to run.

### Public Pages Without a Route

Sometimes your application serves a CWA page from a route of its own, such as a Nuxt page that loads it by IRI to use as its template (see [Module Setup › Load a CWA Page by IRI](/nuxt-module/module-setup#load-a-cwa-page-by-iri)). That page has no Route, so with `routable_security` set, visitors get a `401` for it. Set **`isReachableWithoutRoute`** on the page or page data to make it public. It counts as though a live Route reached it: the page, its manifest, its components and its ancestors are readable, and its cache lifetime is capped at the next go-live date like a routed page's.

```http
PATCH /_/pages/{id}
Content-Type: application/merge-patch+json

{ "isReachableWithoutRoute": true }
```

- **It only applies to a page with no route.** A page with a Route ignores it, so its route's go-live date and `route_security` still decide.
- **A routed parent must be readable too.** If the page sits under a routed page, the nearest one must be live and pass `route_security`, or the flagged page stays private. You can set the flag before the parent goes live; it takes effect when the parent does.
- **Setting it on a template page doesn't make its page data public.** Set it on the page data itself. Page data's own flag does make its template readable.
- **Only admins can read or change it** (`ROLE_ADMIN`). Visitors don't see the property, and flagged pages aren't listed in `GET /_/pages`.

In the Nuxt admin, it's the **Public without a route** toggle in a page's or page data's settings (see [The Admin Panel › Visibility](/core-concepts/admin-panel#visibility)).

## `routable_security`

Controls who can read pages, page data and components that are **not** publicly reachable, and who can **create** new pages and page data:

```yaml
silverback_api_components:
    routable_security: "is_granted('ROLE_ADMIN')"
```

Without it, every `Page` and `PageData` record, and every component on them, is readable by anyone, whether or not a live Route reaches it. The template app sets it.

When `routable_security` is set:

**GET (read access)**
- Users who **pass** the expression see everything, including unrouted, scheduled and offline pages.
- Users who **fail** it can fetch any page or page data that is publicly reachable (see [Public Access Follows Routes](#public-access-follows-routes)), and any template Page that reachable page data renders through. Collections (`GET /_/pages`, page-data collections) list only records with their **own** live Route, so an unrouted parent is readable by IRI but not listed.
- Anything else is denied: 401 for an anonymous visitor, 403 for a signed-in user.

This stops anonymous users discovering templates, drafts and scheduled content through the API.

**POST (create access)**
Creating a new `Page` or `PageData` resource requires the `routable_security` expression to pass. This matches the existing restriction on edit operations — both creating and modifying CMS structure require admin access.

## Component Security

Components are secured by the same reachability rule, built into the bundle via `ComponentVoter`. The only configuration it needs is `routable_security`: without it, every check below ends in access being granted.

When a `GET` request is made for a specific component IRI, the bundle checks whether that component is accessible to the current user by:

1. **Page check** — is the component placed (directly, through a layout, or nested inside another component) on a page that is publicly reachable (see [Public Access Follows Routes](#public-access-follows-routes))? If yes, access is granted.
2. **PageData check** — is the component referenced as a property on a `PageData` resource that is reachable? If yes, access is granted. The property can be typed as the component's own class or any parent class, such as `AbstractComponent`. Editing a component held this way also purges the page data from the cache and publishes it to Mercure.
3. **Template check** — is the component placed on a template page (the page record that page data renders through) whose page data is reachable? If yes, access is granted.
4. If at least one check found a location but none of them is reachable, access falls back to `routable_security`: users who pass it can read the component, everyone else is denied (401 when anonymous).

This means components placed exclusively on admin, unrouted or not-yet-live pages are hidden from anonymous API clients.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
A component with **no** location at all — not in any component group, not referenced by page data, not on a template page — makes all three checks abstain, and the voter then **grants** access. An unplaced or orphaned component is readable by anyone who knows its IRI (the [orphaned resource report](/api/orphaned-data#orphaned-resource-report) lists them). Use `#[Silverback\Publishable]` or your own security expression if a component must stay private before it is placed.
::

## Route Security

Restrict which routes are visible in the API based on the current user's role:

```yaml
silverback_api_components:
    route_security:
        - { route: '/user-area*', security: "is_granted('ROLE_USER')" }
        - { route: '/admin*', security: "is_granted('ROLE_ADMIN')" }
```

`route_security` accepts any number of patterns. The `security` value is any Symfony expression-language security expression.

### How a pattern matches

A `route` pattern matches the route's **whole** path:

- `*` is the only wildcard. It matches any run of characters, including none and including `/`.
- Every other character matches only itself, byte for byte. Letters are case-sensitive and accent-sensitive, with no Unicode folding, and `.`, `%`, `_`, `?`, `[`, `!` and `\` mean themselves, not regex or SQL wildcards.

| Pattern | Matches | Doesn't match |
|---------|---------|---------------|
| `/user-area*` | `/user-area`, `/user-area/page`, `/user-areas` | `/other/user-area/x`, `/User-Area/page`, `/üser-area/x` |
| `/user-area/*` | `/user-area/page` | `/user-area`, `/user-areas` |
| `*/user-area*` | `/user-area`, `/other/user-area/x` | `/user` |
| `/user-area` | `/user-area` only | `/user-area/page` |

Generated route paths are lowercase ASCII slugs, so case only matters for a route created with an explicit path. To cover more than one spelling, add one rule per spelling.

Item access and collection filtering, below, apply the same rule.

::callout{icon="i-heroicons-circle-stack" color="info"}
The route list is filtered in the database, which is supported on **PostgreSQL, MySQL, MariaDB and SQLite**. On any other database, `GET /_/routes` fails with an error whenever a rule applies to the caller, rather than filter with the database's own collation, which could hide a route from the list that is still readable by IRI.
::

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**Upgrading:**

- **From 2.0.0-alpha.32:** letters are now case-sensitive. In alpha.32, ASCII letters matched in any case, so `/User-Area*` restricted `/user-area/x`; from alpha.33 it doesn't. Write patterns in the case your paths use, usually lowercase. Alpha.32's route list also compared through `LOWER()` and the column's collation, so on MySQL and MariaDB it could hide a route such as `/üser-area/x` that item access still served; the list and item access now agree on every path.
- **From before 2.0.0-alpha.32:** item access matched a pattern anywhere in the path, so `/admin*` also denied `/foo/admin/bar`, while the route list matched the whole path and read `%` and `_` as SQL wildcards. A pattern now matches only from the start of the path. To keep the old match-anywhere behaviour for item access, add a leading `*`: `*/admin*`.
::

*Since [bundle 2.0.0-alpha.33](https://github.com/components-web-app/api-components-bundle/releases/tag/2.0.0-alpha.33) ([#546](https://github.com/components-web-app/api-components-bundle/pull/546)); whole-path matching since [bundle 2.0.0-alpha.32](https://github.com/components-web-app/api-components-bundle/releases/tag/2.0.0-alpha.32) ([#538](https://github.com/components-web-app/api-components-bundle/pull/538)).*

Two things happen for each rule:

- **Collection filtering** — the `Route` collection endpoint (`GET /_/routes`) omits routes matching the pattern when the expression is not satisfied. Anonymous users won't see `/admin/*` routes at all.
- **Item access** — fetching a specific `Route` by IRI is denied if any matching rule's expression fails.

Independently of `route_security`, a route whose go-live date has not arrived is hidden in both places from anyone who fails `publishable.permission`. See [Scheduling and Taking Routes Offline](/api/routes#scheduling-and-taking-routes-offline).
