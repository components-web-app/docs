---
title: Sites with Non-Admin Users
description: Writing CWA content needs the publishable permission, so members, guests and registered users can sign in without being able to edit the site. How to open one operation to them.
---

Registration, guest accounts and member areas give people a signed-in account with `ROLE_USER`. None of them can change the site's content: every write to CWA content needs `publishable.permission`, whatever your app's own access rules allow. This page covers what that guards, what stays open, and how to open one operation to signed-in users on purpose.

## What Only Editors Can Write

Every `POST`, `PUT`, `PATCH` and `DELETE` operation on these resources needs `silverback_api_components.publishable.permission` (`is_granted('ROLE_ADMIN')` in the template):

- pages, layouts and routes, including route generation (`POST /_/routes/generate`)
- component groups, including the order `PATCH` (`PATCH {group IRI}/order`)
- component positions
- every component, including its `/move` and its file uploads
- every page data class

Your own components and page data classes are covered automatically, because the rule applies to every subclass of `AbstractComponent` and `AbstractPageData`. A new component is safe from the moment you create it.

A publishable class that sets [`#[Publishable(isGranted: …)]`](/api/components/annotations/publishable#configuring-who-can-publish) uses that expression instead of `publishable.permission`.

A caller who fails the permission gets a **403** when signed in and a **401** when anonymous.

Reads don't change. Who can read a page, page data or component is still decided by routes, `route_security`, `routable_security` and publishing (see [Access Control › Public Access Follows Routes](/api/users/access-control#public-access-follows-routes)).

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
**`ROLE_USER` must never imply editing.** Anyone who registers, signs in as a guest or joins a member area gets `ROLE_USER`. Editing rights belong to the role in `publishable.permission` alone, so never put that role under `ROLE_USER` in `role_hierarchy`. The template's `ROLE_ADMIN: ROLE_USER` is the right way round: an admin is also a user, a user is not an admin.
::

## What Stays Open

- **Form submissions.** The `POST` and the validating `PATCH` on `/component/forms/{id}/submit` don't need the permission, so a contact form works for visitors (see [Form Component › Submission Endpoint](/api/components/built-ins/form-component#submission-endpoint)). Creating, editing and deleting the form component itself needs it like any other component.
- The bundle's admin endpoints need `ROLE_ADMIN` themselves: the orphaned data reports and deletes, the cache purges, the admin real-time channel, collaboration states and a component's `/usage`.

## Your Access Rules Still Run First

Symfony's `access_control` runs before API Platform, so your app's rules are checked first. The template's `security.yaml` lets anyone submit a form and requires a signed-in user for every other write:

```yaml
access_control:
    - { path: ^/_api/component/forms/(.*)/submit, roles: PUBLIC_ACCESS, methods: [POST, PATCH] }
    - { path: ^/, roles: IS_AUTHENTICATED_FULLY, methods: [POST, PUT, PATCH, DELETE] }
```

Those rules are no longer the only guard: a signed-in user passes them and is then refused by the permission.

## An Operation's Own `security` Adds to the Permission

When an operation already has a `security` expression, the bundle combines the two: the caller must pass the permission **and** the operation's expression. Setting `security` on an operation doesn't open it to more people.

## Opening a Resource to Signed-In Users

To let people without the permission write a resource, opt the operation out with the `publishable_permission` extra property set to `false` (the constant `ContentWriteSecurityResourceMetadataCollectionFactory::OPT_OUT_EXTRA_PROPERTY`). The operation's own `security` then applies alone, so always give it one:

```php
// api/src/Entity/Comment.php
use ApiPlatform\Metadata\ApiResource;
use ApiPlatform\Metadata\Get;
use ApiPlatform\Metadata\Post;
use Silverback\ApiComponentsBundle\ApiPlatform\Metadata\Resource\ContentWriteSecurityResourceMetadataCollectionFactory;
use Silverback\ApiComponentsBundle\Entity\Core\AbstractComponent;

#[ApiResource(operations: [
    new Get(),
    new Post(
        security: "is_granted('ROLE_USER')", // [!code focus]
        extraProperties: [ContentWriteSecurityResourceMetadataCollectionFactory::OPT_OUT_EXTRA_PROPERTY => false], // [!code focus]
    ),
])]
class Comment extends AbstractComponent
{
    // ...
}
```

Only that `POST` is opened: editing or deleting a comment still needs the permission. Put the extra property on `#[ApiResource]` instead to opt out every operation of the resource.

::callout{icon="i-heroicons-exclamation-triangle" color="warning"}
An opted-out operation with no `security` of its own is open to anyone your `access_control` lets through. In the template, that's every signed-in user, and on a path your rules leave public, every visitor.
::

A publishable class that is opted out still treats a writer without the permission as described in [Publishable › Configuring Who Can Publish](/api/components/annotations/publishable#configuring-who-can-publish): their writes skip the draft stage and go live straight away.
